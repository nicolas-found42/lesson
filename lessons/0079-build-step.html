The build step: source becomes deployable files

Many projects are not published as-is. A program first turns your source files into a separate folder of finished files, and it is that folder — not your source — that goes online. Knowing which is which stops the classic "works on my machine, blank on the web" surprise.

Why this matters for shipping

Your mission is to get a real app onto a public URL. Some projects — a folder with an index.html, a stylesheet and a script — are already static sites: what you wrote is what gets served. Lesson 6.1 drew that line. But plenty of projects are written in a form browsers cannot run directly: a different flavor of JavaScript, several files joined into one, images that get renamed and compressed. Those projects need a build step in between, and if you and your agent publish the wrong folder, your visitors see nothing.

Source, build, output

Three words carry this whole lesson:

  • Source — the files you and the agent edit. Human-readable, full of structure.
  • Build step — a program that reads the source and writes a fresh set of files: joining, renaming, shrinking, rewriting.
  • Build output — the folder of finished files the build step wrote. This is what a host should serve.

Think of a print shop. Your source is the manuscript. The build step is the printing and binding. The output is the stack of finished books that actually gets shipped. You would never ship the manuscript, and you would never edit the printed book — edits go into the manuscript, and you print again.

GitHub's own description of Pages shows where the build step sits: Pages "takes HTML, CSS, and JavaScript files straight from a repository on GitHub, optionally runs the files through a build process, and publishes a website."[1] That word optionally is the fork in the road: simple projects skip it, built projects do not.

Where the output lives

Build tools write the output to a folder with a short conventional name. Vite, a common build tool, states its default plainly: "You are using the default build output location (dist)"[3] — and notes the location can be changed in the tool's settings. Other tools use names like build or out. You never memorize these: you look, or you ask the agent, "which folder does the build write, and where is it configured?"

The output folder is normally listed in .gitignore (lesson 3.3) — it can be regenerated at any time from the source, so nobody stores it in the repository. That is also why it can quietly go stale: the output on disk may be older than your latest source edits.

Recall before you read on

In your own words: what does a build step consume, what does it produce, and which of the two does a host serve?

It consumes source (the files being edited) and produces a fresh output folder of deployable files. The host serves the output, not the source. Editing source does not change the site until the build runs again.

Two settings that come with a build

Once a build joins the picture, two settings matter, and both are places beginners get burned.

The output folder choice. The host must be pointed at the output folder, not the project root. GitHub Pages offers exactly this choice when you publish: "You can publish your site when changes are pushed to a specific branch, or you can write a GitHub Actions workflow to publish your site"[2] — and either way you name which branch and folder is the publishing source. Lesson 6.5 walks through the Actions option; here you only need to recognize the decision.

The base path. A built page contains links to its own files. The build tool needs to know what address prefix those links should carry. Vite documents this setting as the "Base public path when served in development or production"[4] — by default it assumes your site sits at the top of a domain. If your site actually lives in a subfolder (as free project pages do — lesson 6.3 owns that topic), and the build assumed the top of a domain, every link inside the built page points to an address that does not exist. The page loads; everything it references is missing. You see a blank or unstyled page.

One consequence worth knowing now: because a build rewrites your files, the thing that runs on the host is not the thing you edited. Debugging a built site means changing the source, rebuilding, and republishing — never editing the output by hand.

A real pattern, anonymized

A real pattern, anonymized

A user asked an agent to turn a single public page into a small site holding several design drafts, one per folder, so colleagues could compare them. The agent built the site with a build tool and published it. Later, when asked to merge a change, the agent followed the repository's own rules and ran the site's checks first — and one check failed: the build step, newly added by the agent itself, was failing. The failure had been invisible because the live site still showed the old build. The agent fixed the build, waited for it to pass, and only then published. The lesson the user took away: after any change, run the build, then look at the fresh output — a green-looking site can be yesterday's output.

Build locally, deploy the output

For a static app the flow has three moves, and your agent does the middle one on request:

  1. Edit source (you and the agent, as always).
  2. Run the build — one command the project already defines. Ask the agent: "what is this project's build command? run it and show me the last few lines." A healthy build ends quietly, naming the files it wrote.
  3. Publish the output folder to the host, and open the real URL to confirm.
Prompt — find out how this project ships 
Look at this project and answer in plain words: does it need a build step? If yes, what is the build command, which folder does the build write, and what setting sets the base path? Then run the build and show me the last lines of its output. Do not change any files yet.

This is a safe ask: it only reads and builds, publishes nothing, and it leaves you knowing the project's shape — which matters the next time a deploy looks wrong.

Do it now — run a build and find its output

You should see the output folder in the listing, and its name in .gitignore. If the agent named a folder you cannot find, ask: "the build says it wrote to dist, but I don't see dist — where did the output go?" Asking beats guessing.

Check yourself

Question 1 of 3

What does a build step produce?

A build reads your source files and writes a fresh output folder of finished files — that folder is what a host should serve. Commits and backups are version control (unit 3), and hosting is the service that serves files (lesson 6.1).

Question 2 of 3

Your project uses a build tool. What goes to the host?

The host serves the built output, not the source. Shipping both wastes space and can confuse the host about which page is real; the output folder is normally gitignored precisely because it is regenerated by the build.

Question 3 of 3

After a build, the live page is blank. What is the most likely cause?

A blank page after a successful build usually means the build assumed the top of a domain while the site lives in a subfolder, so every internal link misses. "Never run the build" would leave the host with nothing to serve, which shows a 404 rather than a blank page. Lesson 6.3 covers the subpath case in detail.
