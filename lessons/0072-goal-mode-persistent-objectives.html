Goal mode and persistent objectives

Keeping a target active can help an agent finish a long task. It can also keep a bad task running long after you expected it to stop.

A reminder is not a finish line

To ship your app, you need completed work, not an agent that stays busy. A persistent objective can help keep a larger task in view. But making an instruction last longer does not make it clearer. Before you activate one, you need to know both what counts as success and what should happen when success is out of reach.

A persistent objective is a target kept active while work continues, rather than left only in an earlier message. Goal mode is a tool feature for managing that target. OpenAI describes the Codex feature as keeping the goal attached to the active session while work continues; omp describes setting or replacing a persistent objective.[1][2] The controls differ. Do not assume the same slash command has the same meaning everywhere.

This is different from the ordinary agent loop. Even without goal mode, an agent can read, act, and check repeatedly after one prompt. Anthropic names those phases “gather context, take action, and verify results.”[3] A persistent target helps manage continuing work; it is not what first gives an agent the ability to use tools.

What persistence does not settle

Consider “make the gallery reliable.” Reliable for whom? Which parts must work? Can the agent change the design? Should it publish changes? Persistence answers none of those questions. You still own the product decision and the definition of done: the observable result that counts as finished.

Your stop condition also needs a failure branch. “Stop when the page works” says nothing about the fifth unsuccessful repair. Add a limit and a useful report: “After two unsuccessful attempts, stop and show the evidence and remaining blocker.” That is not permission to claim success. It is permission to return an honest incomplete result instead of continuing without a boundary.

Keep approval prompts on, using lesson 0.6 if needed. Persistence is not a reason to grant broader permissions. An instruction to avoid paid services is also not a technical spending lock. For this lesson's practice, do not authorize paid calls at all.

Two runs with different boundaries

A real pattern, anonymized

A user approved an app redesign, made it a persistent objective, then asked for testing with no remaining problems. The feature work took a small part of the run. Most of the next half-day went into repeated checking and repair. Some failures came from the checker itself. More work kept appearing, a paid service ran out of credit, and the user eventually interrupted. The app had not reached the intended live acceptance result.

In another run, a user turned a specific list of unchecked behavior into an objective with a small spending cap and instructions for unavailable services. The agent found real defects and completed a finite set of changes. That run still had mistakes, including a test touching real saved data. A bounded target helped, but did not replace safe testing or review.

The difference to borrow is not “persistent goals are good” or “persistent goals are bad.” It is that a finite list can be completed, while an undefined search for perfection can always produce another task. Repeating a weak instruction more reliably can make its weakness more expensive.

Recognize the failure modes

The target keeps expanding. Fixing one button becomes redesigning the whole page. Ask whether each new change is necessary for the original observable result. Put unrelated discoveries in a report; do not silently add them to the objective.

Activity replaces progress. Another test run is not progress if it produces the same failure without new evidence. Require the agent to explain what changed and why the next attempt is different. A limit on attempts gives you a chance to decide rather than funding repetition.

The checker becomes the project. A failing check might reveal an app defect, a broken check, or an unavailable service. Do not authorize the agent to weaken the check until it passes. Ask it to distinguish those possibilities and show evidence. If it cannot, stopping with uncertainty is better than redefining success.

The objective becomes stale. You decide to leave publishing for later, but the active target still includes publishing. Revise or remove that target explicitly. A message about your new preference should not leave an older objective contradicting it.

Recall before revealing

A goal says “keep fixing until everything works.” Name two missing boundaries and explain why a persistent reminder cannot supply them.

It needs a finite definition of done and a stop condition for failure or exhausted attempts. It also needs allowed scope. Persistence keeps a target present; it does not decide what “everything” includes or when further work needs your decision.

Write the target before choosing the control

Use a bounded instruction that could stand alone. Start with a small result, not the whole app. Include the evidence you want back and the things the agent must not do.

Objective: repair the gallery's Next button so one click advances one image.
Keep the current layout and all other behavior unchanged.
Use only local checks and disposable test data. Keep approval prompts on.
Do not publish, use paid services, or touch real saved data.
Done when: a browser check shows one click advances one image, and the existing relevant checks pass.
Allow at most two repair attempts. Stop earlier if a required tool is unavailable or the scope must change.
At either stopping point, report evidence, changed files, remaining gaps, and whether the objective was met. Do not redefine success.

This prompt is a teaching example; adapt the button and result to your app. The attempt limit is a requested boundary, not a guarantee enforced by every tool. Stay present for the first run. If you need budgeting details, revisit lesson 4.4.

Manage the active target deliberately

For this exercise, use the ordinary prompt above rather than assuming a matching goal-mode command. Claude Code already works through its read, act, and check loop.[3] A prompt requesting boundaries is useful without a dedicated persistent-goal feature.

The documented controls are /goal <objective> to set a target and /goal to view it. Use /goal edit to revise, /goal pause to pause, /goal resume to resume, and /goal clear to remove it.[1] View the stored target before resuming; do not resume an obsolete objective.

omp (oh-my-pi) documents /goal set <objective>, /goal show, /goal pause, /goal resume, and /goal drop. Its slash-command page says goal mode requires goal.enabled and cannot start during plan or vibe mode.[2] These are single-vendor docs. Do not change settings to force activation for this exercise.

Pausing a persistent objective and interrupting a running operation are different concerns. Do not assume a goal-management command cancels work already in flight. Use the verified steering guidance in lesson 1.10 when you need to intervene.

Check yourself

Question 1 of 3

A persistent goal keeps producing new improvements. What should you inspect first?

A target without a finish line can keep generating work. More capacity does not define success or limit scope.

Question 2 of 3

You no longer want the publishing step in an active goal. What is safest?

Make the active target agree with your decision. Do not leave conflicting instructions for the agent to resolve by guessing.

Question 3 of 3

The attempt limit is reached without success. What report should you require?

Reaching a failure stop is not completing the objective. Report evidence and gaps so you can choose what happens next.
