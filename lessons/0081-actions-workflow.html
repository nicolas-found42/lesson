An Actions workflow: a recipe GitHub runs on every push

The checks on your pull request and the publishing of your site are not done by your laptop. They are done by a small recipe file in your repo that GitHub runs for you, on a fresh machine, every time you push.

About 15 minutesBuilds on: 3.7 The pull requestWin: you can add a workflow that runs on every push and read its result in the Actions tab

Why this matters for shipping your app

You have already met the effects of this lesson without seeing the machinery. In 3.7 your pull request showed a list of checks. In 6.3 your site appeared at a public URL. Both of those were done by GitHub Actions. GitHub's documentation describes it as a continuous integration and continuous delivery (CI/CD) platform that allows you to automate your build, test, and deployment pipeline.[1] Once you can read the recipe, you can make GitHub run your own steps on every push — and you can read a red check without guessing.

A recipe, not a robot

A workflow is a plain text file written in YAML that lives in your repository. GitHub's syntax page is blunt about the two rules that matter: A workflow is a configurable automated process made up of one or more jobs, and You must store workflow files in the .github/workflows directory of your repository.[3] The file must end in .yml or .yaml: Workflow files use YAML syntax, and must have either a .yml or .yaml file name extension.[3] The quickstart adds the discovery rule: For GitHub to discover any GitHub Actions workflows in your repository, you must save the workflow files in a directory called .github/workflows.[1]

Every workflow has four ingredients, and the documentation names them plainly:

  • Trigger — the on: line names the event that starts the run, such as a pull request being opened or an issue being created.[2] The most common for shipping is on: [push], which the quickstart confirms: Committing the workflow file to a branch in your repository triggers the push event and runs your workflow.[1]
  • Job — a set of steps that runs on one machine. A job will run inside its own virtual machine runner.[2]
  • Step — each step can run a script that you define or run an action, which is a reusable extension that can simplify your workflow.[2]
  • Runner — the machine itself. GitHub provides the machines, and each one is clean: Each workflow run executes in a fresh, newly-provisioned virtual machine.[2] Nothing you installed on your laptop travels with a push, which is exactly why 2.12 matters.

A minimal recipe you can read top to bottom

This is the smallest useful workflow, in the shape of GitHub's own quickstart example:

name: Say hello on every push
on: [push]

jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      - name: Check out the code
        uses: actions/checkout@v6
      - name: Print one line
        run: echo "This run was triggered by a push"

Read it as a recipe. on: [push] says "run this every time someone pushes." jobs: starts the work; runs-on: ubuntu-latest picks GitHub's Linux machine image. The first step, actions/checkout@v6, is a reusable action that copies your repo onto that machine; the second runs one shell command. When the push happens, GitHub starts the machine, runs the steps in order, and shows you the result.

A real pattern, anonymized

A user pushed a branch that changed one page of their small site. On the pull request, a check appeared and started running. That check was a workflow: on every push, GitHub started a fresh machine, checked out the code, ran the project's checks, and colored the check green or red. The user waited for green before merging — "merge" means "merge if the checks pass" — and a second workflow then rebuilt and published the site. After that, every push to the main branch updated the public page by itself. Nothing ran on the user's laptop.

The two workflows you will meet first

On your first projects, two recipes do almost all the work. The check workflow runs your project's checks on every pull request and every push — the checks you saw in 3.7, and the cloud-versus-laptop gap from 2.12. The Pages workflow builds and publishes your site; GitHub documents that Custom workflows allow GitHub Pages sites to be built via the use of GitHub Actions.[4] Its ready-made template is called static.yml — literally Simple workflow for deploying static content to GitHub Pages — and it Runs on pushes targeting the default branch and also offers workflow_dispatch, which Allows you to run this workflow manually from the Actions tab.[6] When you add a workflow through the web UI, GitHub offers these preconfigured templates: GitHub provides preconfigured workflow templates that you can use as-is or customize to create your own workflow.[1] You do not have to invent YAML from scratch.

Reading the result: the Actions tab

Every run is visible on your repository's Actions tab: Under your repository name, click Actions.[1] Click a run, then a job, and The log shows you how each of the steps was processed.[1] A green run means every step succeeded on GitHub's machine. A red run means a step failed there — read the log near the first error line before changing anything. If a failure was a one-off, GitHub lets you re-run a workflow run, all failed jobs in a workflow run, or specific jobs in a workflow run up to 30 days after its initial run,[5] and from the terminal the same page shows gh run rerun RUN_ID and gh run watch.[5] Re-running is for flakes; if the log names a real problem, fix the code or the recipe instead of re-running until green.

Recall before you read on

Without scrolling up: name the four ingredients of a workflow, say where the workflow file must live for GitHub to find it, and say what a red mark on the Actions tab actually means.

Trigger (on:), jobs, steps, and the runner machine. The file must be in .github/workflows with a .yml or .yaml name. A red mark means a job failed on GitHub's fresh runner machine — the log's first error line tells you what to fix.

Do this with your own project

You should see a run that turns green, whose job log contains the line This run was triggered by a push, and a second run that appears automatically after your next push. If the run is red instead, open the failing step's log and read the first error line — that reading is the skill.

Check yourself

Question 1 of 3

What is a GitHub Actions workflow, in one sentence?

It is a YAML file in the repo (stored in .github/workflows) that tells GitHub which jobs to run automatically when an event happens. Hosting, review, and support are different things.

Question 2 of 3

You saved your workflow as workflows/run.yml in the repo root. What happens?

GitHub only discovers workflows stored in the .github/workflows directory with a .yml or .yaml extension. A file elsewhere is just an ordinary file, so nothing triggers.

Question 3 of 3

A run on the Actions tab is marked red. What does that mean?

The runner is GitHub's own clean virtual machine, not your laptop. Red means one step exited with an error there; the job log's first error line says what to fix. Re-run only if it was a flake.
