What a test is

A test is a check a machine can repeat: set up an input, ask the app for a result, compare it with the result you expected. Three words come back with it — pass, fail, skipped — and only two of them tell you anything.

Why this matters for shipping your app

Every check you make by hand works once. A test is the same check written down in a file, so it works again tomorrow, after every change, and without you watching. That matters because your agent will make most of the changes: you need a check it can run by itself and read the answer from. Anthropic's guidance for coding agents states the trade plainly: If you give it something that comes back pass or fail, Claude can close that loop itself.[1]

You met the difference between a claim and its evidence in lesson 2.2. A test run is one of the cheapest kinds of evidence you can ask for, and also one of the easiest to misread. "All tests passed" and "2 passed, 1 skipped" sound similar and mean different things.

Three parts, in a file

The Python documentation gives the cleanest short definition I know: a test case checks for a specific response to a particular set of inputs.[2] Unpacked, every test you will meet has the same three parts.

  1. An input you control. Prices [2, 3, 5]. An empty list. A name with an accent in it.
  2. An action. Call the function, load the page, press the button.
  3. An expected result, written down. The total should be 10. Then a comparison, which is what makes it a test rather than a demonstration.

Here is a small one, from a practice folder holding two files: cart.js, which adds up prices, and cart.test.js, which checks it. The test file uses a runner that ships with Node, the same program that runs the app's JavaScript.

import test from 'node:test';
import assert from 'node:assert';
import { total } from './cart.js';

test('adds up three prices', () => {
  assert.strictEqual(total([2, 3, 5]), 10);
});

test('an empty cart costs nothing', () => {
  assert.strictEqual(total([]), 0);
});

test('applies a coupon', { skip: 'coupons not built yet' }, () => {
  assert.strictEqual(total([10], 'SAVE5'), 5);
});

Three tests. The first two compare a real answer with an expected one. The third is deliberately marked skip, with the reason written next to it.

Running it, and reading the three words

Run node --test in that folder and the runner prints one line per test, then a small summary. I ran exactly this in a scratch folder on 2026-11-02 and copied the output below.

✔ adds up three prices (0.30ms)
✔ an empty cart costs nothing (0.03ms)
﹣ applies a coupon (0.02ms) # coupons not built yet
ℹ tests 3
ℹ pass 2
ℹ fail 0
ℹ skipped 1

Now the three words, one at a time.

WordWhat happenedWhat it proves
passThe code ran and produced the expected result, for this input, right now.That one case works. Nothing about other cases.
failIt ran and the result differed — or it crashed before comparing.A real difference exists. The output usually shows both values.
skippedIt was not run at all. Someone marked it, or a condition was not met.Nothing. It is a note about the run, not a result.

The Node documentation for the built-in runner says the same in one line: Individual tests can be skipped by passing the skip option to the test.[3] Python's framework offers the same idea through a decorator or a call from inside the test.[2] The wording differs, the meaning does not: skipped means not executed.

When one of those checks breaks, the runner does not only say "fail". I changed one line in cart.js so it kept only the last price, then ran the same command. The summary became one pass, one fail, one skipped, and underneath it printed the actual comparison:

✖ adds up three prices
  AssertionError [ERR_ASSERTION]: Expected values to be strictly equal:

  5 !== 10

That 5 !== 10 is the whole value of a test. It names the input's real answer and the expected answer, side by side, with no opinion in between. I restored the file afterwards.

What the summary says

"All good, the checks ran."

Nothing here can be false in a way you could detect. It is a claim wearing a test's clothes.

What the output says

"tests 3 · pass 2 · fail 0 · skipped 1."

You can count it, rerun it, and see which test was left out and why.

Pass and fail are also a number

Under the human-readable lines there is one more signal, and it is the one your agent reads. A test command ends with an exit code. The Node documentation is explicit: If any tests fail, the process exit code is set to 1.[3] A clean run ends with 0. I checked both in the scratch folder: the passing run returned 0, the broken one returned 1.

This is why tests fit an agent so well. The agent does not have to interpret your mood or guess at quality; it runs a command, reads a number, and keeps working or stops. Lesson 5.9 goes further into exit codes and long-running commands.

Skipped is where the surprises hide

Beginners read "0 failed" and stop. The line that matters is often the skipped one, because a skipped test is a check that did not happen — and the reason is usually environmental, which means it may behave differently on another machine.

A real pattern, anonymized

A user asked their agent whether a project was in good shape. The agent ran the project's checks and reported 127 passed, 3 skipped, nothing failed. The three skipped checks needed a 3D tool that was not installed on that laptop, so the runner had quietly left them out and said so.

Days later the same checks ran on the hosting service, where that tool was present. Two of the three failed and pointed at real bugs in files the laptop had never examined. The first report was not a lie. It was a true statement about a smaller set of checks than the user assumed, and the word "skipped" was the only clue.

So when you read a run, count all three numbers. Passed tells you what held. Failed tells you what broke. Skipped tells you what nobody looked at, and that is usually the list you want next. Lesson 2.12 takes up the local-versus-cloud version of this, and lesson 2.11 covers the harder case where a passing test is itself unreliable.

Recall before you read on

Without scrolling up: name the three parts of a test, and say what a skipped test proves. Then say which number tells your agent that the run went badly.

An input you control, an action, and an expected result that gets compared with the real one. A skipped test was never run, so it proves nothing — it is a gap. The exit code tells the agent how the run went: 0 for success, a non-zero value such as 1 when a test failed.

What a test does not do

A green run is evidence about the cases somebody wrote down. It is not evidence that the page looks right, that the flow makes sense, or that the app works for a stranger. Anthropic's own guidance pairs the two checks rather than replacing one with the other: after the tests, it suggests having the agent build and run the app and look at the result, because that catches the kind of problem that tests and typechecks miss.[1]

That is why lesson 2.1 came before this one, and why lesson 2.7 comes after it. Tests narrow the space where you have to look. They do not look for you.

One more caution, because it shapes how much a green tick is worth. Google's testing blog defines a flaky result as a test that exhibits both a passing and a failing result with the same code, and reports that about 1.5% of their test runs were flaky.[4] A pass is always a statement about one run of one check. Repeating the run costs little, and it is the honest way to find out whether the result sticks.

Do it in your own agent 
Do not change any files. Look at this project folder and answer four things, quoting the exact commands and output.
1. Does this project have any automated tests? Which folder are they in?
2. What command runs them here? If the project documents it, quote the line that says so.
3. Run that command once and paste the full summary: how many tests, passed, failed, skipped.
4. For every skipped test, quote the reason the runner printed. If there is no reason, say so plainly.

If there are no tests at all, say that instead of inventing a command, and list the three things you would test first in this app.

You should see a real command, a real summary with the three counts, and at least one sentence that begins with a number rather than an adjective. If the agent answers "all tests pass" with no command, ask again: "Paste the command you ran and its raw output." A project with no tests is a normal answer at this stage; the useful part is the list of what should be tested first, which lesson 2.4 builds on.

Check yourself

Question 1 of 3

A run reports "3 tests, 2 passed, 0 failed, 1 skipped". What do you know?

Skipped means not executed. Two checks produced a result and one produced none, so one area of the app is untested by this run.

Question 2 of 3

Which of these is a test rather than a description of one?

The comparison against an expected result is what makes it a test. Installing libraries and changing settings are setup, and a bug list is a report about the past.

Question 3 of 3

The test command returns exit code 1. What does that mean?

Node's documentation states that a failure sets the exit code to 1, and 0 means success. Skipped tests do not fail a run on their own.
