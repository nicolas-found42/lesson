Docker: run tests in a throwaway box, not on your real data

Once your app has a backend, every test can write to a database. Docker lets you start a private, disposable copy of that backend so tests never touch what is real. Four words cover it: image, container, volume, port.

About 15 minutesNeeds: 5.9 Background processes, exit codes, waiting vs pollingWin: you can ask for an isolated test run that cannot touch your real data

Why this matters for shipping

So far your app was a static page, and running it was harmless. In this unit your app may gain a backend with a database (lesson 8.9). From that moment, every test that starts the app can also write to that database. If the test uses the same database as your real app, a test can add fake entries, overwrite settings, or delete rows you care about. Docker is the standard way to say: start a separate copy, used only for this test, and throw it away afterwards. You still check the result yourself; Docker makes the playground safe.

The four words

You only need four words. Docker's own documentation defines the first two plainly.

WordWhat it isOne-liner command
imageAn image is a read-only template with instructions for creating a Docker container.[1] Think of it as a recipe plus a frozen snapshot of the software.docker build makes one from a Dockerfile; docker pull downloads one
containerA container is a runnable instance of an image.[1] A running copy. By default, a container is relatively well isolated from other containers and its host machine.[1]docker run = create and run a new container from an image[3]
volumeVolumes are persistent data stores for containers, created and managed by Docker.[2] Data in a volume survives even when its container is removed.docker run -v my-data:/app/data … = bind mount a volume[3]
portA door number. A container has its own private network; publishing a port opens a door from your computer to inside the container.docker run -p 8080:80 … = publish a container's port(s) to the host[3]

One property makes containers worth the trouble for tests. Docker says they are lightweight and hold everything the application needs to run. So a container does not rely on what happens to be installed on your machine. A check that passes inside it is passing against the same setup every time, not against a lucky local install.

Why a container is not enough on its own

A container alone is disposable in the wrong way: Docker warns that when a container is removed, any changes to its state that aren't stored in persistent storage disappear.[1] That is exactly what you want for a test — the fake data vanishes with the container. But your app's real data must live in a volume, which exist[s] outside the lifecycle of a given container and is persisted even if the container using it is removed.[2] So the rule is simple: real data gets a named volume; tests get a throwaway volume or none at all.

Ports work the same way. The real app might listen on port 5432 on your machine; the test copy should use a different published port, like -p 15432:5432, so the two never collide.

Named volumes and anonymous ones

Docker's volume page draws a distinction you will use often. A volume can be named, with a name you choose, or anonymous, with a random name Docker picks. Both outlive the container that used them. There is one exception: the --rm flag destroys the anonymous volume attached to that container when the container exits.

That exception is why --rm belongs in test commands. A test container with an anonymous volume leaves nothing behind, so the fake rows vanish with the container. A named volume stays even when no container is running, which is what real data needs.

Unused volumes are not cleaned up on their own either. Docker keeps them until you run docker volume prune. That is a cleanup command, not a test command. Run it only when you are sure which volumes are disposable, and never when a real data volume happens to be sitting unattached.

A real pattern, anonymized

A real pattern, anonymized

A user asked their agent to check whether their project worked. The agent ran the project's checks, including a start-the-app smoke test. That test started the app in a container pointed at the user's real saved-data volume, and it wrote fake entries into it. A second reviewer agent noticed, the agent disclosed it, cleaned up the fake entries, and re-ran the test against a throwaway volume on a different port. Afterwards the user made it a standing rule: never touch my real data or real ports in a test.

Without isolation

Test starts the app against the real volume and the real port. Fake rows land next to real ones. If the test crashes midway, real data is already changed. You find out later, or never.

With a throwaway container

Test starts a fresh container with its own temporary volume and a spare port (--rm deletes it when done). Nothing real is reachable. The test can fail as badly as it wants — nothing to clean up.

Run in the background, then check once

Lesson 5.9 covered waiting vs polling for commands your agent runs. Containers follow the same idea: start one in the background with -d (run container in background and print container ID[3]), then check its state once with docker ps (list containers[3]) instead of staring at the output. Add --rm and Docker will automatically remove the container and its associated anonymous volumes when it exits.[3]

Recall before you read on

Without scrolling up: name the four Docker words, and say in one sentence why a test container should not share a volume with the real app.

Image (read-only template), container (runnable instance of an image), volume (persistent data store), port (published door to the container's network). A test container must not share the real volume, because anything the test writes there becomes real data.

Say it once, in a prompt

You can paste this to any agent whenever a test might touch data:

Run the tests against a throwaway Docker container with its own temporary volume and a spare published port. Never use my real data volume or my real ports. Use --rm so the container deletes itself. Report exactly which container, volume and port you used, and paste the test output.

Check yourself

Question 1 of 4

What is a Docker image?

Docker's docs: an image is a read-only template with instructions for creating a container. A container is the running instance of that template.

Question 2 of 4

A container is removed. What happened to the data it wrote?

Changes to a container's state disappear when it is removed, unless they were stored in persistent storage such as a volume.

Question 3 of 4

Why publish a port with -p when running a container?

-p publishes a container's port to the host, so your browser can reach a server running inside the container. It does not change memory, logs, or the image.

Question 4 of 4

Your tests must not touch real user data. What is the best move?

A throwaway container with a temporary volume and spare port (plus --rm) makes the test disposable. Skipping tests or running them against the live site both risk real data or real users.
