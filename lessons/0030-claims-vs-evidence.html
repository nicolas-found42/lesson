Claims versus evidence

"Done" is a sentence about what the agent believes. Evidence is something that would have come out differently if the work were wrong. Only the second one lets you ship.

About 15 minutesBuilds on: 2.1 Run it yourselfWin: you can ask for proof, and name what is still unproven

Why this matters for shipping your app

Soon you will send a link to people who do not know you and cannot fix anything themselves. At that moment, the only question that matters is not "did the agent say it was done?" but "what is actually true about this app?" The gap between those two questions is where beginners get hurt: they publish on a cheerful summary, and a stranger finds the broken part first.

This lesson gives you one habit and one question. The habit is to ask for evidence rather than accept a claim. The question is "what did you not verify?" It is short, and it finds the part of the job that is still guesswork.

Two kinds of sentence

A claim is a statement with no support behind it. "The page works on phones" is a claim. It may be true, and it is still a claim, because nothing in it would change if it were false.

Evidence is different in kind. It is an artifact that had to be produced by the work itself: a command and its output, a file diff, a screenshot, a URL that opens. The test is simple. If this thing had gone wrong, would the artifact look different? If yes, it can serve as evidence. If no, it is decoration.

What you hearWhat would actually settle it
"It works."You open it and look, or a screenshot you can see.
"All tests pass."The command, its full output, and how many tests ran.
"The link is live."The URL opening in your own browser.
"I fixed the search."The exact search that failed before, run again.

Anthropic's best-practices page says it directly: ask Claude for evidence: the command it ran and its output, or the screenshot. It adds that a summary on its own is nearly worthless: “All tests pass” on its own tells you very little.[1]

The evidence does not have to be long. One command line and twenty lines of output are usually enough to change "I hope so" into "I know so".

Why the report drifts from reality

An agent's turn ends when it believes the task is finished. Anthropic describes the same loop you met in lesson 0.1 as gathering context, taking action and verifying results.[2] But the last phase only happens if the agent has something to run and chooses to run it. Its guide states the consequence plainly: Claude stops when the work looks done.[1] Earlier documentation admits the failure from the other side: Claude said it was done and it wasn't quite, usually because it had no way to check its own work.[1]

This is usually not dishonesty. The agent sees a partial picture. It read the file it changed and not the one that calls it. It ran the check before the last edit. It has no account to log in with, so it skipped the screen that needs one. Each gap is invisible from inside the run, and each one turns a true sentence into an overclaim.

A vendor page for another agent lands on the same point from the interface side. A green tool card, it warns, only means that the action finished: A successful card means that action completed, not that the whole task is correct.[3] Everything can look calm while the app is wrong.

What a good report sounds like

The useful signal is not confidence. It is specificity: which commands ran, which files changed, which checks passed with what counts, and what was left untried. Anthropic's research note makes the general version of the point: agents need “ground truth” from the environment at each step, and human review remains crucial for whether a solution fits what people actually need.[5]

A real pattern, anonymized

A user typed one line into their agent: "does the project work?" The agent read the project's documented checks, ran them, and answered yes, with a table of what had passed. Then came the part worth keeping. Under a heading like "not exercised", it listed the things it had not tried: real credentials, a live outside service, and about two dozen tests the project marks as skipped. The yes was true and narrow, and the report said where the edge was.

The user's next message took that list and made it the job: do those too, but spend no more than a set amount and do not invent credentials. The gap the agent named became the next task instead of a surprise in production.

Compare that with a report that ends at "everything works". Both may be honest. Only one gives you something to act on.

Ask for the hole, not the whole

Here is the question this lesson is built around:

Keep this one in your pocket

"What did you not verify, and what would it take to verify it?"

It works for three reasons. It is answerable: the agent knows which tools it did not call and which files it only read. It is finite: instead of "is it finished?", which can always be argued, you get a list you can count. And it is checkable: every item on the list names a thing you or the agent could do next.

The answer is still a claim, so treat it as a lead rather than a certificate. But a specific gap is far more useful than a broad assurance, and an answer of "nothing" to that question is a warning sign, not a comfort. In one session where an agent was asked to explain how an existing app worked, the final answer ended with a line saying that no walkthrough in the running app had been done. That single line was the most valuable sentence in the report, because it told the reader exactly how far the findings could be trusted.

Before you tell me it is done, give me the evidence:
1. The exact commands you ran, with their full output, not a summary.
2. Which files you changed, and how I can see the change myself.
3. What you did NOT verify, and why you could not.
4. For each item in 3, the smallest check that would settle it.

Do not describe a check you did not run. If you are unsure whether something works, say so plainly.

Question 3 is the one beginners skip. Question 4 turns the answer into a plan. When you have that list, you can hand part of it back as a bounded task, with a spending cap and a stopping point (lessons 4.4 and 4.3).

Recall before you read on

Without scrolling up: what makes a piece of output count as evidence rather than a claim? And why is "what did you not verify?" a better question than "are you sure?"

Evidence is something that would have come out differently if the work were wrong: a command and its output, a diff, a screenshot, a URL that opens. "Are you sure?" only asks for another opinion. "What did you not verify?" asks for the specific gaps in the run, which you can then check or turn into the next task.

Evidence goes stale

One more trap, because it catches careful people. Evidence has to match the final state of the work. A test run from before the last edit proves something about an older version. A screenshot of a tab you loaded ten minutes ago may show a page that has since changed. A command run in the wrong folder can pass beautifully while saying nothing about your app.

So when you look at evidence, ask two questions, not one: what did this check? and when, and where, did it run? If the answer is "before the change", the evidence is history, not proof. Lesson 5.8 goes deeper into stale and invented claims; lesson 2.11 covers the case where the check itself is unreliable.

Where to look in each agent

The three agents show evidence in different places, but all of them let you see the raw material rather than only the summary.

Tool activity appears in the session as it runs, so you can read the commands rather than the summary. The best-practices page also documents a command for the end of a task: once the agent says it is done you can run /verify, which makes it build and run the app and look at the result.[1]

Two commands in the CLI reference are useful here. /diff will Show the Git diff, including files Git isn’t tracking yet. And /review asks for a fresh review of your working tree; the reference suggests it after Codex completes work.[4]

Each read, command or change appears as a card in the transcript; the docs tell you to Expand tool cards and diffs and to Check the changed paths, command exit status, test result, and final explanation. Press Ctrl+O to expand or collapse tool output.[3]

Do it in your own agent

You should see a report that separates what ran from what did not, and at least one command you can repeat yourself. If the answer is all reassurance and no commands, send one more line: "Which commands did you actually run? Paste their output." If the "did not verify" list is empty, ask again: "Name at least one thing you assumed rather than checked."

Check yourself

Question 1 of 3

Which of these is evidence rather than a claim?

Only the command and its output could have come out differently if the work were wrong. The others are sentences of belief, however confident.

Question 2 of 3

After "done", which question teaches you most?

It asks for the specific gaps in the run, which you can check or turn into the next task. The others are about style, time or preference, not about what is true.

Question 3 of 3

A report says "0 failed, 3 skipped". What do you know?

Skipped means not run. Nothing failed, and nothing was proven either. Treat skipped checks as items for the "not verified" list.
