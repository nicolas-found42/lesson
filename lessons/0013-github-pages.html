GitHub Pages: what your URL will be

Why the address matters

Lesson 6.1 established that a static site is a folder of files, and that hosting means putting those files somewhere a browser can ask for them. This lesson is about the somewhere: GitHub Pages, the free host that comes with a GitHub account. It reads the files straight out of your repository and serves them as a website.[1]

You care because your finished app is a link you send to a friend. If that link opens a page with no styling, or a menu whose items go nowhere, the app looks broken even though every file is present. Almost always the cause is a mismatch between the address you expected and the address the host actually gave you.

Two kinds of Pages site

GitHub documents exactly two shapes. A user site lives in a repository named after your account, YOUR_USERNAME.github.io, and appears at http(s)://YOUR_USERNAME.github.io. A project site lives in any other repository and appears at http(s)://YOUR_USERNAME.github.io/REPOSITORY.[1]

File names on a Pages site are matched exactly: GitHub's troubleshooting page warns that Index.html will not be found, and that the file should be index.html, not index.HTML.[3]
Shapes quoted from GitHub's "What is GitHub Pages?" page.[1]
Kind of siteRepository namePublic address
User siteYOUR_USERNAME.github.iohttps://YOUR_USERNAME.github.io/
Project sitemy-apphttps://YOUR_USERNAME.github.io/my-app/

Most first projects are project sites, because you already have a repository called something like my-app and you do not want to rename it. That single fact — the repository name sits in the middle of the address — is the source of nearly every broken link beginners hit. The extra piece is called a subpath: your site is not at the root of the domain, it is one level down.

The folder becomes the path

Inside the site, nothing is renamed or flattened. GitHub says that each file will be available on your site in the same directory structure as your publishing source.[2] The docs give a worked case: a file at /about/contact-us.md in the published branch appears at https://<user>.github.io/<repository>/about/contact-us.html.[2]

There is one required starting file. Pages looks for an entry file and the docs name index.html, index.md, or README.md, which must sit at the top level of the source folder.[2] That file answers a request for the folder itself, which is why https://YOUR_USERNAME.github.io/my-app/ can show a page without you typing a filename.

Recall before you read on

Without scrolling up: your project is a project site in a repository called my-app. Write the public address of the file pages/contact.html. Then say, in one sentence, what part of that address would disappear if the site were a user site instead.

https://YOUR_USERNAME.github.io/my-app/pages/contact.html. On a user site the repository segment my-app is gone, so the same file sits at https://YOUR_USERNAME.github.io/pages/contact.html — the domain root is the site root.

Why /style.css breaks

A link's meaning depends on the page it sits in. MDN explains the rule: because the browser already has the document's own URL, it can use this information to fill in the missing parts of any URL available inside that document.[4] A link that omits the domain is resolved against the page you are on. A link that starts with a slash keeps the domain but throws away the rest of the path — MDN calls it a domain-relative URL.[4]

Put those two facts together. GitHub places a project site under /my-app/; a leading slash sends the browser to the domain root instead. The repository name, and with it your whole site, is skipped.

A real pattern, anonymized

A user asked an agent to publish a small interactive gallery so non-technical friends could open it, and to put the link where visitors would look first. The site worked perfectly on the user's own machine, where it was opened at the root of a local server. Before publishing, the agent served the finished folder under the same /my-app/ subpath the public host would use, opened it in a browser, and found the stylesheet and two navigation links pointing at the domain root. It changed them to relative links, checked again under the subpath, and only then published. The friend who received the link saw the intended page on the first try.

Here is that difference as a table. The page is https://YOUR_USERNAME.github.io/my-app/pages/contact.html and each row is a link written inside it. The right column is what a browser actually requests; I produced it with Python's standard urljoin, which implements the same resolution rule.

/style.css…/style.css — repo name lost

The habit: relative inside, absolute outside

A relative link is written without the domain, so the browser completes it from the current page. An absolute URL contains every part, including https:// and the host name. MDN's example of going up one level, ../Web/CSS/Reference, is relative in exactly this sense.[4]

The rule that keeps you out of trouble is short. Links between pages of your own site: relative. Links to somebody else's site: absolute. When a link must point into your own site from a page at an unknown depth, a relative path that climbs with ../ still works, because it is measured from wherever the page happens to be.

Two free repairs

Relative links survive a repository rename, a switch between a project site and a user site, and a later custom domain — all of which change the part of the address before your files. GitHub also notes that switching a repository between public and private will change the URL of your GitHub Pages site, which will result in broken links until the site is rebuilt.[3] Relative links are the version that does not need repairing.

Do it now

The second audit lists no domain-relative or absolute links that point inside your own site, and the predicted addresses match the ones in the browser's address bar after publishing. If a page is missing, check that its file name matches the link exactly, including capital letters, and that index.html sits at the top of the publishing folder.[3]

One detail worth knowing before you publish

Pages does not serve your page the instant you push. GitHub's quickstart warns that it can take up to 10 minutes for changes to your site to publish after you push the changes to GitHub.[2] So a link that returns "not found" right after a push is not automatically a broken link; give it time and reload. Whether the site is genuinely live is the subject of lesson 6.6, and the build step that usually sits in front of Pages is lesson 6.2.

Start it with claude inside your project folder, then paste the request from step 3 as a normal message.[5] Claude Code's starting permission mode differs by version, so before you rely on seeing each edit, check which mode your session is in. Lesson 0.6 shows how to move to a mode that asks.

Start it with codex inside your project folder. It can inspect code, make changes, run commands, and automate repeatable work without leaving your terminal, which covers both the search and the rewrite.[6] Keep the approval prompts as they are; lesson 0.6 covers them.

Start it with omp inside your project folder. Its documentation comes only from its own authors, so treat anything surprising there as worth double-checking; the prompts in this lesson work the same way in all three agents.[7]

Check yourself

Question 1 of 3

Your project site is published at https://YOUR_USERNAME.github.io/my-app/. Which address serves the file about/contact.html?

Pages keeps the folder structure and adds the repository name once, after the domain. The other three either drop the subpath or reorder the folders.

Question 2 of 3

A page at …/my-app/pages/contact.html contains <link href="style.css">. Where is style.css looked for?

A relative link with no leading slash is completed from the page's own address, so it resolves next to contact.html. A leading slash would jump to the domain root and lose the repository name.

Question 3 of 3

Which link keeps working after the same site is served from a different subpath or a custom domain?

Relative paths are measured from the page that contains them, so the moving prefix in front of your files does not matter. The other three bake in a location that changes.
