Prove the bug before you fix it

A test written after a fix can only agree with the fix. A test that fails first is evidence that the bug was real, that the test exercises it, and that the repair changed something.

Why this matters for shipping your app

Every change to a working app is a chance to break something that already worked. When you ship, people keep using the parts you are not touching. A fix you cannot prove is a guess that happens to look right today, and the same bug can come back next month unnoticed. This lesson turns each bug into a small, permanent guard, and it stops the agent from "fixing" a problem it never reproduced.

What a regression is

A regression is a thing that used to work and now does not, because of a change. The name is the plain English sense: the software went backwards. Wikipedia defines the testing that catches it as re-running functional and non-functional tests to ensure that previously developed and tested software still performs as expected after a change.[1]

A regression test is one test added when you learn about a bug. It must fail on the broken version, pass on the fixed one, and keep passing from then on. It is a guard placed exactly where the fence was missing.

The one-sentence version

You do not have a fix until you have a test that failed before it and passes after it.

The trap: a test written after the fix

Agents are quick to write a test that passes. If the code has already changed, a test that goes green on its first run teaches you little. It may check the behaviour you wanted, or it may merely describe what the code now does, bug included. You cannot tell those apart from a green tick.

Here is the trap in miniature. A cart total should take ten percent off a forty-unit order, but the code subtracts ten units instead of ten percent, so it returns thirty instead of thirty-six.

youadd a test for the discount bug
agentwrites: expect the total to be 30, and it passes
noteThe test agrees with the broken code. It has locked the bug in, and it will now fight anyone who fixes it.

The agent was not dishonest. It added a test and the suite went green. The instruction was wrong, not the agent. Ask for the failing run and the ambiguity disappears.

Failing first, on purpose

The failure is the part that carries information, but only if it fails for the right reason. A test that cannot even start, because a file name is misspelled, also reports red. It has proved nothing about the bug. Read the message that comes with the failure.

Fails for the wrong reason

Error: Cannot find module './pricing.js'. The test never reached the code under test. Fix the setup and run again; do not touch the app.

Fails for the right reason

Expected values to be strictly equal: 30 !== 36. The test ran, called the real function, and got the number the bug produces.

The second message does three jobs: it shows the bug exists, shows the test can see it, and names the number you expect after the repair. "Fixed" stops being an opinion.

Claude Code's own best-practices page recommends exactly this shape for a bug report: write a failing test that reproduces it, then fix it.[3] Its guidance for unattended runs asks whether the agent has a failing test it has to turn green.[3] Codex's guidance is less specific about order but names the same goal: ask it to create tests when needed, run the relevant checks, confirm the result before you accept the work.[4]

A worked example, run for real

A small shop-cart file was run in a throwaway folder with Node's built-in test runner, which needs no install. The runner starts with node --test and, in the documentation's words, If any tests fail, the process exit code is set to 1.[2] The transcript below is one pass of that cycle; the numbers are the ones the runner printed.

youthe cart takes 10 percent off a 40.00 order, but it charges 30.00. Write a test that fails first.
agenttest: ten percent off a 40.00 cart leaves 36.00
younode --test
redfail 1   30 !== 36   (exit code 1)
younow fix the cause, then run it again
agentsubtracts a percentage instead of a flat amount
younode --test
greenpass 1   fail 0   (exit code 0)

Two runs, two results, one changed line. That pair, kept in the session or your notes, is the evidence. A single green run is not.

What a good regression test looks like

  • One behaviour. The test name reads like a sentence about the app: "ten percent off a 40.00 cart leaves 36.00". Not "test discount 2".
  • The bug's own numbers. Use the value the user actually saw and the value they expected. Those two numbers are the whole test.
  • No network, no clock, no shared folder. Keep it repeatable on any machine. A test that depends on the time of day will pass today and lie tomorrow.
  • Left behind. The test stays in the suite after the fix. That is what makes it a guard rather than a one-off check.
A real pattern, anonymized

An app's own suite was green: dozens of tests, all passing. An outside review then found three real bugs the suite could not see. For each, the agent was asked to reproduce before repairing. It wrote a test that called the app's own lookup, watched it fail with the wrong value in the message, and only then changed the code. Without that failing run, nobody could say whether the change fixed the bug or moved it.

Green tests are not proof the app is correct, only that the behaviours you thought to check still hold. Each bug tells you about a check you were missing; the regression test buys that check once and keeps it.

Ask for the failing run

You do not need to write the test yourself. You need the order to be non-negotiable. This prompt works in all three agents:

Users report [the symptom, with the numbers you saw].
Before changing any code, write ONE test that reproduces it.
Run it and show me the failing output, including the expected and actual values.
If it fails because of a setup mistake rather than the bug, fix the setup and run it again.
Only after I have seen it fail on the real bug, fix the cause.
Then run that test, then the whole suite, and show me both results.

The order matters more than the wording. "Write a test and fix it" lets the agent choose, and the cheap order is fix first. "Show me the failing output" removes the choice.

You can also run the test yourself without leaving the session. All three tools accept a leading ! for a shell command:

A ! at the start of the line puts the input box in shell mode: Run a command directly, add its output to the session, and have Claude respond to it.[5] So ! node --test runs the suite and the agent sees the same red you do.

The CLI documents the same prefix: Prefix a line with ! to run a local shell command under the current approval and sandbox settings.[6] Approval prompts stay on; you are only saving a window switch.

omp uses ! to Run the command in your user shell, stream the result in the TUI, and include it in conversation context.[7] A double !! runs the command but keeps the output out of the model's context.[7]

Recall before you read on

Without scrolling up: why is a test that passes on its first run weak evidence, and what should you look at in a failing run before you accept that the bug is real?

A test written after the fix may only describe the code as it now stands, bug included, so its first green run proves nothing about the bug. In a failing run, read the message: it should name the behaviour and show the expected and actual values, not a setup error such as a missing file. Only a failure on the real bug, followed by a pass after the repair, is evidence.

Practise the cycle

Put the four steps in order before you try them on your own app.

Put the steps in order

Do it in your own agent

You should see two runs of the same test: one red with the expected and actual values from your bug, then one green. The suite total should go up by one, and the new test should stay in the folder. If the first run was already green, stop and say so: either the bug is not reproduced or the test is checking something else. Do not accept the fix until you have seen red.

When a test passes on one run and fails on the next with unchanged code, it is flaky rather than proof of a bug. That is its own problem, covered in lesson 2.11 The checker can be wrong.

Check yourself

Question 1 of 3

Which test deserves to be called a regression test?

A regression test is defined by its history: it failed on the broken version and passes on the fixed one, and it stays behind as a guard.

Question 2 of 3

Which step gives you the strongest evidence that the bug was real?

A failure on the bug itself shows the bug exists and that the test can see it. A green suite afterwards then means the fix changed the behaviour, not the test.

Question 3 of 3

The new test fails with "Cannot find module". What is the right reading?

That message means the test never reached the code under test, so it says nothing about the bug. Fix the import or path and get a failure that names the real behaviour.

Ask your teacher

Stuck on reading a failure? Paste the whole output, not the last line, and ask: "Which line tells me the test reached the real bug?" If the agent's test looks like it is describing the bug rather than catching it, say so and ask for the failing run.
