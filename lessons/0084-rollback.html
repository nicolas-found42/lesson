Rollback: main is not the live site

A friend reports your app is broken. The fastest way back is not "undo everything" — it is knowing which of two separate records you need to fix: the branch called main, or the copy your host is serving.

About 15 minutesBuilds on: 6.6 Merged is not liveWin: you can say whether main or the live site is ahead, and pick the matching way back

Why rolling back matters for shipping

Your mission is a public app. A public app can break in public: a bad change merges, the site misbehaves, and the people you built it for are looking at the mess. The skill that turns that from a crisis into a chore is rollback — returning the site to a version that worked. Doing it badly costs time; doing it while confused about which thing you are rolling back can cost work you thought was safe.

Lesson 6.6 showed that merged, deployed and live are three separate states. Rollback is the same three states travelled in reverse, and the reverse trip has the same rule: each step is separate, and each can fail on its own.

Two ledgers, kept by different clerks

Main is a record of commits inside your repository. It changes when you merge or push. It has no connection to the internet; a repository nobody deploys can have a thousand commits and no site at all.

The live site is a record kept by your host. It changes only when a deployment finishes, and it shows whatever was in the last successful deployment — which is not necessarily the newest thing on main.

The one-line habit

Before any rollback, ask: which ledger is ahead — main or the live site? Answer it with evidence, not memory: the log tells you about main, the URL tells you about live.

Two ways back, and what each one changes

Way 1: roll the code back. In Git, you do not rewind history. The revert command moves you forward by adding an opposite: it will revert the changes that the related patches introduce, and record some new commits that record them.[1] On a shared branch like main, that reversal goes through review like any other change: Reverting a merged pull request creates a new pull request that reverts the original merge commit.[2] You merge that pull request, a fresh deployment runs, and a few minutes later the site is back. Slow-ish — but at the end, main and live agree again, and the history honestly records both the mistake and the fix.

Way 2: roll the host back. Some hosts keep earlier deployments on hand and can repoint your address at one without touching your repository. Cloudflare Pages, for example, documents: Rollbacks allow you to instantly revert your project to a previous production deployment.[3] That is seconds instead of minutes — but notice what it does not do. Main still contains the broken change. The moment another deployment runs from main, the bug returns.

Neither way is wrong. They answer different questions. Way 1 fixes the code. Way 2 buys you time. Confusing them is how people "roll back" a site and then watch the bug come back with the next push.

Which way applies to your Pages site?

With the workflow you set up in lesson 6.5, publishing is a workflow run: Your GitHub Pages site will always be deployed with a GitHub Actions workflow run.[4] Each run builds and publishes whatever main has. So the dependable path back on this setup is Way 1: revert the bad merge, merge the revert pull request, and let a new run publish the corrected copy. Expect the usual publish lag — it can take up to 10 minutes for changes to your site to publish after you push the changes to GitHub[5] — and verify the URL as lesson 6.6 taught, in a private window, looking for text only the old version has.

If you later move to a host with a rollback button (lesson 6.8 surveys some), you gain Way 2 as well — with the agreement above: after a host-side rollback, main and live disagree until you also fix the code.

A pattern from real sessions

From the author's own agent sessions (anonymized)

A user ran a small web app that teammates relied on. Late in a long session, something went wrong with a deployment, and the user asked how to get back to a good state. The agent answered confidently that main was "the rollback point." It was wrong. The live site had never received the last eleven commits — the deploys had not succeeded — so "going back to main" would actually have moved forward, onto the newer code. Only when the agent fetched the real URLs, saw them answering with 404s, and compared that against the commit log did it notice the direction was backwards. It retracted its own advice out loud and started over from evidence.

The lesson is not that the agent was careless. It is that "main is the safe state" is an assumption, and rollback decisions are exactly the wrong place for assumptions.

Ask which is ahead, then choose

Confused

"Roll back the app to main." Assumes main is older than the site, contains only good work, and is what a visitor needs. Any of the three can be false.

Evidence first

"Show me the last five commits on main, then fetch the live URL and tell me what it serves. Which one is behind? Propose the shortest way to a working site and wait for my go."

Compare your two ledgers in about a minute

Do it now — on your own project

You should end with two checked facts (a commit message and a page heading) and one decision sentence. You have not changed anything — that is correct. Knowing which ledger is ahead is the whole prerequisite for a safe rollback; the reversal itself is one revert away.

One prompt that works in any agent

The live site is broken. Do not edit any files yet.

First, report:
1. the last five commits on main;
2. what the public URL serves right now — fetch it and give
   the status code and one line of text from the page;
3. which is ahead: main, or the live site.

Then propose the shortest way to a working site — revert PR,
host rollback, or something else — and wait for my go.
Keep approval prompts on. Make no unrelated edits.

The last line does real work. A panicked "fix the site" prompt invites an agent to start editing files in every direction at once. Asking for a proposal and a wait keeps you the decision-maker; lesson 1.7 calls this the confirmation gate, and lesson 4.3 explains why "stop before acting" needs to be said out loud.

Do not rewind main by force

A tempting shortcut is to move main itself backwards — erase the bad commits from history with a forced push. On a shared branch this is the destructive move lesson 3.11 warns about: Git's manual says pushing with force can cause the remote repository to lose commits; use it with care.[6] A revert commit reaches the same result by moving forward, which is why it is the default on main.

Recall before you read on

Without scrolling up: what two facts must you gather before deciding how to roll back, and which tool or window gives you each one? Write it in your own words.

Fact one: what main contains right now — from git log --oneline -5 or your agent reading the repository. Fact two: what the live URL actually serves — from opening it in a private window or having the agent fetch it and quote a status and a line of text. Comparing the two tells you which ledger is ahead, and that decides whether a revert (roll the code forward to good) or a host rollback (point the address at an earlier deployment) is the right move.

Check yourself

Question 1 of 3

A broken change is merged on main and the live site shows the bug. What does a host's rollback button change?

A host rollback changes only what the address serves; your repository keeps the bad commits, so the bug returns with the next deployment unless you also revert the code.

Question 2 of 3

You merge a revert on a Pages site set up as in lesson 6.5. What brings the old content back?

Publishing is always a fresh workflow run, and it can take up to ten minutes. The revert changes what main contains; the new run is what changes the site.

Question 3 of 3

The live site looks fine, but main is eleven commits ahead with a broken feature merged. What must you decide first?

The counts and the blame are interesting but not decisive. The decision is direction: the site is behind, so rolling it "back" to main would actually move it forward onto untested code.
