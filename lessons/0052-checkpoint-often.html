Checkpoint often

A coding agent can work for an hour and change a hundred lines across a dozen files. If none of that is committed, the folder holds one undivided lump of work. A checkpoint cuts the lump into pieces you can keep, compare and drop.

Why this matters for shipping your app

Your mission needs a working app at a public address. The way you get there is a series of changes, most of them made by an agent while you read a paragraph or two of its report. If every change lands on top of the last with no commit in between, then the only state you can return to is the one from this morning — or none at all. You would be building on a pile with no floors.

This lesson is the habit that keeps floors under the pile. Lesson 3.1 explained what a commit stores. Here you decide when to take one.

"Saved" is not the same as "committed"

Your agent writes to files on disk. Those writes are saved in the ordinary sense: close the laptop and the text is still there. So the sentence "my work is saved" is true and useless at the same time. What matters is whether the state is committed — copied into the project's history as a snapshot with a name.

Anthropic's documentation for Claude Code draws the line: its built-in checkpoints work alongside git rather than replacing it.[4] The omp documentation says the same thing from the other side: File changes are applied to your working tree as omp works. They are not committed unless you ask for a commit.[5] Nothing in the folder records a state unless someone takes that step.

So a checkpoint is a commit you take on purpose, at a boundary you chose. The next section shows what accumulates when you skip it.

What one long run can pile up

Here is a small project before a run. One file, one commit, nothing else.

$ git status --short
$ git log --oneline
4d2ccea Add a first page

The agent is then asked to lay out a grid of recipe cards and make them respond to clicks. It works for a while and reports success. Before anyone commits, the folder looks like this:

$ git status --short
 M index.html
?? css/
?? js/
$ git diff --stat
 index.html | 19 ++++++++++++++++++-
 1 file changed, 18 insertions(+), 1 deletion(-)

Notice the gap: git diff reports 18 added lines, but the folder also gained two new files containing 108 lines. Untracked files are outside this comparison.[1] These outputs came from a throwaway project prepared for this lesson.

Nothing is lost yet. But if a later edit breaks the layout while improving the click handler, separating the two will require more investigation. A checkpoint between those steps would give you a clear comparison.

A real pattern, anonymized

In one session, a small visual fix expanded into nearly a day of work, with no commit for about nineteen hours. The resulting change was too large for an automated reviewer, which skipped it. In another session, about fifty minutes of autonomous work left source edits and new tooling uncommitted. These were risks, not reports of lost files: the useful work had no recent recorded boundary.

A run can keep finding more work. Choose the checkpoint boundaries yourself rather than waiting for the agent to declare the whole project finished.

Four things a checkpoint buys you

The point of committing often is not tidiness. It changes what you are able to do next.

Without a checkpointWith one
A later edit may overwrite work you liked.You have a recorded version to compare against.
Stopping leaves an unfinished pile to understand later.A checkpoint identifies what was working at the break.
Several steps may have introduced a failure.You can check earlier commits to narrow the cause.
A large mixed change is harder to review.Small, focused changes are easier to inspect.

Small commits do not remove the need to investigate. They give that investigation useful boundaries instead of one tangled before-and-after comparison.

A rhythm you can follow

Codex's documentation gives the instruction in one line: Create Git checkpoints before and after a task so you can revert changes.[2] Before and after. That is the whole rhythm, and the "before" half is the part people skip. A checkpoint taken after the damage is a record of the damage.

Four moments cover almost everything in a beginner project:

  • Before a risky instruction. "Rewrite the home page", "change the colour scheme everywhere", "try a different layout". If the result is worse, the previous state exists.
  • After something works. You opened the page and the gallery loaded. That state is now worth keeping, even if the code is not pretty.
  • Before you stop for the day. Record the verified work so tomorrow's starting point has a name.
  • Before an unattended run. If you are going to leave the agent working while you do something else, the last known-good state should already be committed.

OpenAI's security guidance puts the reason plainly: Commit frequently so you can roll back in small increments.[3] Small increments are the unit of rollback. One enormous commit gives you one enormous increment.

Checkpoint is not stop

A commit does not end the session. You can record a working step and continue. You can also stop an agent before committing: stopping does not itself discard files. If the agent is making unwanted changes, stop it first, inspect what remains, and then decide what is safe to record.

Built-in undo is not a checkpoint

Claude Code has its own checkpoints, but they are separate from git.[6] Its documentation warns that a file changed only by a shell command is not restored by that rewind feature.[4] Do not assume a tool's undo covers every action it performed.

A Git commit can include changes regardless of which tool made them, provided you select them for that commit. It does not automatically include every file. Check the list, leave unrelated work alone, and never sweep in passwords or API keys. 3.4 Commit messages and staging covers that selection.

Git's reference log records when the tips of branches and other references were updated, not a history of every file edit.[7] Do not count on it to rescue overwritten uncommitted work.

Recall before you read on

Without scrolling up: when does Codex recommend checkpoints, and why does Claude Code's rewind not replace Git commits?

Before and after a task. Claude Code's rewind has limits, including files changed only by shell commands. A Git commit records the content you deliberately select, regardless of which tool changed it. Neither mechanism excuses skipping inspection.

Asking for a checkpoint

Keep approval prompts on, as described in 0.6 Approvals and permissions. Adapt the named task in this prompt to your own project.

Pause before starting more edits. Help me checkpoint the recipe-card layout.

Show git status --short, summarize the changes, and identify untracked
files. Tell me what was checked and what remains unchecked.
Propose the exact files to include and a clear commit message.
Exclude unrelated work, secrets and generated clutter.
Wait for my approval before staging or committing.

After I approve, create the commit and show its identifier and the
remaining status. Do not push, deploy or begin another task.

Claude Code's checkpoints cannot reverse actions affecting remote systems.[6] A Git commit cannot undo a sent message or a database change either. Keep approvals on; recording files is not permission to perform irreversible actions.

OpenAI recommends a feature branch and a clean git status before delegating.[3] If other work is already present, ask Codex to identify and preserve it rather than silently including it in your checkpoint.

omp says changes are not committed unless you ask for a commit.[5] Use the same approval-first prompt above. A finished turn is not evidence that the work entered Git history. This is single-vendor documentation.

A session transcript records a conversation; a commit records selected project content. Keep the distinction clear.

Try it in your own project

Do this now (about 6 minutes)

Your log should have your new identifier and message at the top. Here is the prepared example; your history and identifiers will differ:

$ git log --oneline
43b91b3 Lay out recipe cards and wire the click handler
4d2ccea Add a first page

$ git status --short
(no output means nothing is waiting)

Status should be empty if you committed all intended work and nothing else was pending. If unrelated changes remain, that is fine: the agent should explain them rather than delete them. The win is knowing exactly what your checkpoint includes.

When a checkpoint is not enough

A local commit is not an off-machine backup. See 3.6 Remote, origin, push for copying committed work to a remote. Do not mistake “committed” for “published.”

The aim is to make the next step recoverable. Continue with 3.11 Undo for recovery choices, or 4.9 Long unsupervised runs for supervising work between checkpoints.

Check yourself

Question 1 of 3

An agent has edited for an hour with no commit. What is actually at risk?

Committed history and the remote copy are separate from this hour's edits. The hour of uncommitted work is the exposed part: one bad rewrite and there is no earlier state to return to.

Question 2 of 3

Which request makes the safest checkpoint in the middle of a task?

A commit records the folder and can be compared or restored later. A folder copy is unversioned and easy to confuse with the original; asking the agent to remember depends on the agent, not on the project.

Question 3 of 3

Which statement about Claude Code's built-in checkpoints is accurate?

The documentation says checkpoints are separate from git and work alongside it, and that they only cover file changes. A file changed by a shell command is not restored, so they are not a substitute for a commit.

Ask your teacher

Unsure whether something is worth a commit? Ask the agent: "I am about to ask you to change the layout. Is everything that currently works committed? Show me the output." Questions are the point.
