Outcome-sized prompts, not micro-managing

One prompt should buy one result you can look at. Smaller than that and you are doing the agent's job of choosing steps. Larger than that and nobody can tell when it is finished.

About 15 minutesBuilds on: 1.1 Goal and audience, not methodWin: you can size a request to one checkable outcome

Why this matters for shipping your app

Lesson 1.1 taught you to state a goal and an audience instead of a method. That leaves an open question: how much work should one message ask for? Too little and you spend the evening typing the steps yourself, one file at a time. Too much and the agent wanders for an hour and hands back something you cannot judge. Both feel like work. Neither ships your app.

The useful size is one outcome: a result you could describe in a sentence and check by looking at it. This lesson is about finding that size, on purpose, every time you press enter.

You are the project manager, not the typist

Think of the job you actually hold. A project manager does not stand behind a colleague naming each keystroke. They agree on the deliverable, the deadline, the boundary, and how the result will be judged, then get out of the way and review the result. That is the job you have with a coding agent. The agent owns how: which files to open, what to try first, what to redo. You own what, why, and how much is enough.

Both official guides point at the same imbalance. Anthropic's prompt engineering guide says to Prefer general instructions over prescriptive steps.[1] Anthropic's own agent guide notes that current models usually carry on through an agreed task without being told, and lines like that are more likely to cause over-work than fix a stall.[2] In other words: they do not need you to push them step by step, and pushing can make things worse. omp's guide puts the positive version in one line: State the outcome and boundaries.[3]

Two ways to get the size wrong

Micro-managed

"Create index.html. Now add a nav bar. Now create style.css. Now set the body font to 18 pixels. Now add a footer. Now center the heading. Now open it."

Outcome-sized

"Make the one-page menu for my café readable on a phone, with the dish names and prices large enough to read without zooming. Show me the page when it is done. Do not add online ordering yet."

The first version is not wrong work. It is work you did, in six messages, with the agent reduced to a pair of hands. You chose every step, so you own every step that turns out to be the wrong one. The second names a result, a reader and one boundary, then stops. Codex's best-practices page calls the opening line of that shape Goal: What are you trying to change or build? and says it helps Codex stay scoped, make fewer assumptions, and produce work that’s easier to review.[4]

What "outcome-sized" means in practice

An outcome-sized prompt passes two tests at once.

  • One sentence of result. You can say what should exist without naming a single step. If your description is a list of instructions, it is too small.
  • One look to check. When the agent says it is finished, you know how to confirm it in under a minute: open the page, click the button, run the check. If you cannot name that check, it is too big.

Size by result, never by file. "Rewrite style.css" is small but pointless; the file is a means, not a deliverable. "Make the menu readable on a phone" is a result, and the agent may touch three files to reach it. That is its business.

A useful phrase: one sitting, one screen. If you would want to sit and watch the whole thing, it is small enough to be safe. If you would want to leave and come back later, it needs a written definition of done first (lesson 4.1).

The same job, two transcripts

youAdd an index.html file with the café menu.
agentCreated index.html with the menu.
youNow make a style.css and link it.
agentLinked style.css.
youNow make the text bigger on phones.
agentWhat size would you like?
you18 pixels. And center the heading.
Four turns, one decision each. You supplied the plan and the agent supplied typing. Nothing here checks the result on a real phone.
youMake the café menu readable on a phone, then show me how to look at it on a narrow window. Done means I can read every price without zooming. No online ordering yet.
toolread index.html · edit index.html · edit style.css · run local preview
agentDone. Prices are 20px on narrow screens; here is the preview address. I did not test on a real phone.
One turn, one outcome, one check you can perform, and a clear statement of what was not verified.

Notice what the second version did not contain: no file names, no pixel values, no order of operations. The agent found the stylesheet because it had to. You kept the two things only you knew, the reader and the boundary.

Why bigger is not automatically better

Under-asking wastes your evening. Over-asking wastes the agent's hour and your trust. When a request covers several unrelated results, the agent has to guess an order and invent a definition of done, and you get a long report you cannot check. Claude Code's own guidance for unattended runs lists the five things such a run must know: what done looks like, how to check itself, what it may touch, what stops it, and where the result goes.[2] If you cannot answer all five for your request, it is too big for one message.

That does not mean every prompt needs five paragraphs. It means the outcome must be small enough that the five answers are obvious. "Make the menu readable on a phone" passes easily. "Finish the whole restaurant site" does not, because done has no single image.

A real pattern, anonymized

A user handed an agent a roadmap of more than eighty small items, written in one line: implement the roadmap. The same message added a stop condition, "stop when items 10, 11 and 88 are merged." Because the work was sliced and the finish line was named, several helpers could work at once without the scope growing. Later the user asked the agent to critique their own prompting. The answer was blunt: they were acting as project manager between every step, and would do better handing over a bigger outcome, such as "deliver a review-ready pull request, own the sequencing and cleanup, stop before merging" rather than a series of instructions.

Read that carefully. The fix was not "ask for less". It was "ask for one coherent deliverable, and hand over the sequencing". The line between the two is the outcome, not the number of words: a large deliverable with a written finish line and a stop condition is manageable; a small errand without one is not.

Recall before you read on

Without scrolling up: what are the two tests that tell you a prompt is outcome-sized? And which parts of the job stay with you?

One sentence of result, and one look to check it. You keep what, why, and how much is enough; the agent keeps the steps, the file choices, and the order of work.

A prompt you can size with

Fill this in for any task. The first two lines carry the outcome; the rest keep it sized.

Outcome: when you are done, [one result I can look at].
It is for [who], who will [how they use it].
Done means: [the one check I can perform myself].
Do not [one boundary], and do not start [the next obvious thing] yet.
Work out the steps yourself. If you hit a choice that changes what I see, ask me once instead of guessing twice.
When you finish, tell me what you checked and what you did not check.

If you find yourself unable to fill the "Done means" line, stop. That is the signal to cut the request, not to write a longer prompt. If the outcome line reads like a to-do list, stop as well: you have slipped back into being the planner.

Do it in your own agent

You should see the second run need one turn instead of four, and should be able to perform the check you named without asking the agent what to look at. Expect the agent to choose some details differently from what you had in mind; that is the trade. If the second run instead asks you several questions, your outcome line was too broad. Narrow it to one screen or one flow and retry.

Check yourself

Question 1 of 3

Which request is sized to one outcome?

Only the second names a result a person can look at. The others name steps or an errand, which means you keep the plan.

Question 2 of 3

You have sent nine messages, each naming the next file to change. What is the cost?

Micro-managing moves the planning onto you. The agent still types, but you own the sequence and every wrong step in it.

Question 3 of 3

Which is a sign that a request is too big for one turn?

Without a one-sentence finish line there is nothing to check, so the agent invents one. The other three are exactly what a well-sized prompt contains.

Best practices for Claude Code (Anthropic). Read "Write a specific prompt" and "Let Claude run without you". Together they show both ends of the size question: give the agent what it cannot see, then say what done looks like and what stops it. The advice is tool-specific but the shape works in any agent.

Ask your teacher

Unsure whether your request is one outcome or three? Ask the agent that gave you this course. Try: "Here is my prompt. Tell me which parts are steps I chose, and rewrite it as one outcome with a check." or "Split this request at its natural seams and tell me which piece to send first."
