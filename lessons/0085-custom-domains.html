Your own address for the site (optional)

Your app already has a working address like YOUR_USERNAME.github.io/my-app. A custom domain — yourname.com — is a nice extra, not a requirement. This lesson shows what it involves so you can decide whether it is worth it.

About 15 minutesBuilds on: 6.8 Other hostsWin: you can decide whether a custom domain is worth it, and if so, point one at your live site yourself

The address you already have is real

Every site on the internet is found through a domain. The one GitHub Pages gave you — YOUR_USERNAME.github.io/my-app/ — is a real address; it belongs to GitHub, and it is long to say. A custom domain is an address you own, such as my-app.com, that forwards to the same site. Nothing about your app changes. Visitors typing either address see the same pages. The trade is this. The github.io address already works and needs no renewal. A custom domain is rented by the year and must be renewed.

So treat this lesson as optional polish. Ship first, share the link from lesson 6.7, and come back here only if a short, memorable address would genuinely help your audience.

How a domain finds your site: DNS in one paragraph

When someone types a domain into a browser, the browser asks the DNS — think of it as a phone book — where that name lives. You control the phone book entry through your registrar (the company where you bought the domain). The entry you write is a DNS record. Vercel's own explanation: DNS maps human-readable domain names to computer-friendly IP addresses.[4] Changing the record is what "points" your domain at your hosted site. Concretely, one line with the name www, the type CNAME and the value YOUR_USERNAME.github.io says one thing. Anyone asking for www.my-app.com should be sent to the GitHub Pages site. Three fields, one line, and that is the whole edit.

Step 1 (you do this): buy a domain

Search any registrar for the name you want and buy it. You pay the registrar a yearly registration fee; current prices vary by company and by ending (.com, .io, your country's ending), so check the registrar's own pricing page rather than trusting any number quoted here. Some registrars also sell hosting — you do not need it; your site is already hosted (lesson 6.8). Keep the login for that registrar account; you will need it in step 3. This purchase is a human-only step: no agent can or should buy a domain for you, and you should never type that registrar password into a chat.

Step 2 (you do this): tell your host about the domain

On GitHub Pages, open your site's repository, then Settings → Pages → Custom domain, type your domain, and click Save. GitHub's docs note that saving will create a commit that adds a CNAME file directly to the root of your source branch — a small file that tells GitHub "this site answers to this address".[1] On Cloudflare Pages, Vercel, or Netlify the same idea lives in the project's Custom domains settings page: pick the project, add the domain, continue.[3]

GitHub warns you to do this step before touching DNS: Make sure you add your custom domain to your GitHub Pages site before configuring your custom domain with your DNS provider.[1] Skipping ahead can let someone else host content on one of your subdomains.

Step 3 (you do this): write the DNS record at your registrar

Two shapes exist, and GitHub spells out both:

  • Apex domain (example.com): create an A record (or ALIAS/ANAME if your registrar offers it) pointing to GitHub Pages' addresses — 185.199.108.153, 185.199.109.153, 185.199.110.153, 185.199.111.153.[1]
  • Subdomain (www.example.com, blog.example.com): create a CNAME record pointing the subdomain to YOUR_USERNAME.github.io — without the repository name.[1] On Cloudflare Pages a subdomain is a CNAME pointing at <YOUR_SITE>.pages.dev.[3]

A subdomain (often www) is the easier, safer choice for beginners; GitHub recommends setting up both apex and www so it can redirect one to the other automatically.[1]

Do not create wildcard records like *.example.com. GitHub's warning is direct: wildcard records put you at an immediate risk of domain takeovers, even if you verify the domain.[1] GitHub also recommends verifying your domain (a TXT record in your DNS) before adding it, to improve security and avoid takeover attacks.[2]

Step 4: wait, then check

DNS edits are not instant: GitHub notes DNS changes can take up to 24 hours to propagate. Resolvers hold on to answers for a while, so the old value can linger even after your registrar has saved the new one.[1] You can watch the change yourself from a terminal with dig YOURDOMAIN.com +noall +answer — a read-only lookup, no risk. The answer line names the record you asked for, its type, and the value it resolved to; if that value is your host's address, the edit is live from that resolver's point of view. Once the record resolves, open https://yourdomain.com in a private window and confirm it loads your app, not a parking page. On GitHub Pages, tick Enforce HTTPS once it appears (it can take up to 24 hours before this option is available[1]) so the padlock shows for visitors. Cloudflare, Vercel, and Netlify issue the HTTPS certificate for custom domains automatically from their dashboards.[3][5]

A pattern from real sessions

A real pattern, anonymized

A user shipped a small portfolio site on GitHub Pages and wanted it at a domain they owned. They asked the agent to "set up my custom domain." The agent could not — buying the domain and editing DNS records require logins only the user has. What the agent could do was useful: it wrote out the exact steps and the exact DNS values for their host, so the user did the three human steps in about ten minutes, then asked the agent to run dig and confirm the record had propagated before sharing the new address.

The lesson: hand the agent the parts it can do (the checklist, the dig check), and keep the account logins for yourself.

Do it (only if you already own a domain)

Do it now — optional, needs a domain you own

dig eventually shows your GitHub Pages address, and the private window loads your app at the custom domain with a padlock after Enforce HTTPS. If it still shows the registrar's parking page after several hours, the record is not saved yet — re-check the CNAME value; do not recreate records repeatedly. If you do not own a domain, skip this entirely: the github.io address is a complete, shareable result.

Recall before you read on

Without scrolling up: in what order do the three steps go — buying, telling the host, editing DNS — and which one must come first for safety, and why?

Tell the host first (Settings → Pages → Custom domain), then write the DNS record at your registrar; buying can happen before or in between. GitHub warns that configuring DNS before adding the domain to GitHub can let someone else host content on your subdomain — so host first, DNS second.

Check yourself

Question 1 of 3

You bought example.com. Where do you first tell GitHub Pages about it?

GitHub's own instructions say to add the custom domain in Settings → Pages → Custom domain (Save creates the CNAME commit) before configuring DNS at the registrar, to avoid subdomain takeovers.

Question 2 of 3

Which DNS record do you create for an apex domain like example.com on GitHub Pages?

Apex domains use A records (GitHub lists four IPs, e.g. 185.199.108.153) or an ALIAS/ANAME pointing at YOUR_USERNAME.github.io. CNAME records are for subdomains like www, and an MX record is for email, not websites.

Question 3 of 3

You saved the DNS record but yourdomain.com still shows a parking page. What is the sensible next move?

GitHub states DNS changes can take up to 24 hours to propagate. Recreating records or switching browsers does not speed that up; run dig to see whether your record is live yet.

Ask your teacher

Deciding whether the domain is worth it? Ask your agent: "My site is live at https://YOUR_USERNAME.github.io/my-app/. I'm thinking of buying a custom domain — list exactly what I'd have to do for GitHub Pages and what could go wrong." Then do the account-logged-in steps yourself.
