Undo: revert, reset, and the copy of the remote you cannot see

There are two ways to take a change back, and they make opposite promises. Choosing the wrong one is the fastest way for a beginner to lose work that other people can no longer recover.

Why this matters for shipping your app

You can already commit, push, and merge (lessons 3.1, 3.6 and 3.7). Sooner or later you will want one of those changes gone: the agent's work looked right and was not, or a commit swept in files you never asked for. That is a normal, fixable moment. It becomes an unfixable moment only when the undo is chosen by guesswork.

Two undos, two different promises

Git gives you two families of undo, and the difference is not cosmetic. git revert leaves history alone and adds to it. The reference says it will revert the changes that the related patches introduce, and record some new commits that record them.[1] The faulty commit stays in the log, and a new commit on top cancels its effect.

git reset moves the branch itself. The reference says the command changes which commit HEAD points to.[2] Everything after that point leaves your branch. Those commits usually still exist somewhere on your disk, but the branch you ship from no longer contains them.

Revert: add a correction

History grows by one commit whose message begins "Revert …". The original commit remains visible and can be read, blamed and discussed.

Safe on a branch other people already have, because nothing they hold is replaced.

Reset: move the branch back

The branch label moves to an older commit. Later commits drop off the branch and the log no longer shows them.

Fine on work that has never left your machine. Destructive once other people have the commits.

Here is a real run in a throwaway project with three commits: a home page, a banner, a footer. I asked git to undo the footer commit without erasing it.

$ git log --oneline
31ed074 Add footer
75650c2 Add banner
454ec2c Add home page

$ git revert --no-edit HEAD
[main 207e2a9] Revert "Add footer"
 1 file changed, 1 deletion(-)

$ git log --oneline
207e2a9 Revert "Add footer"
31ed074 Add footer
75650c2 Add banner
454ec2c Add home page

Four commits where there were three, and the page is back to two lines. Nobody reading the project later has to guess why the footer disappeared: the reason is a commit in the history.

The sentence to remember

Revert answers "what changed?" with a new entry. Reset answers it by pretending the entry never happened. Only the first answer survives being shared with other people.

What reset can destroy

git reset has three strengths. The gentle two, --soft and the default --mixed, move the branch label and leave your files in place. --hard is the one to slow down for. Its documentation says it will Overwrite all files and directories with the version from <commit>.[2] Pro Git is blunter: --hard is the only way to make the reset command dangerous, and one of the very few cases where Git will actually destroy data.[3]

In the same project I typed one uncommitted line into the page, then reset back two commits:

$ git status --short
 M index.html

$ git reset --hard HEAD~2
HEAD is now at 1e5c266 Add home page

$ cat index.html
<h1>My Recipe Box</h1>

The banner, the footer and the half-written line are all gone from the folder. Two of them are recoverable. The half-written line is not, because it was never a commit, so nothing recorded it.

Committed work usually survives a reset, and this is where a beginner's luck comes from. Git keeps a log of where your branches used to point: reflogs record when the tips of branches and other references were updated in the local repository.[4] In the same project, git reflog still listed the dropped commits, and git reset --hard HEAD@{1} put them back.

The reflog is not a backup

It lives in the same folder as the repository, it is local, and git prunes old entries from it.[4] It cannot return an edit you never committed, and it cannot save a project you deleted. Checkpoint often is lesson 3.13 for that reason.

Recall before you read on

Without scrolling up: which undo adds a commit, which one moves the branch, and which of the two can throw away an edit that was never committed?

Revert adds a new commit that cancels an earlier one, and history keeps both. Reset moves the branch pointer back, and --hard also overwrites the files in your folder, so uncommitted edits are destroyed for good.

The question that decides: has anyone else got it?

Before choosing, ask one question: have these commits left my machine, or could someone else have pulled them? If yes, revert. If the work has never been pushed, reset is available and private.

Force pushing is what lets a reset travel to a shared branch. Git's push reference describes the flag plainly: It can cause the remote repository to lose commits; use it with care.[5] I rewrote a commit message, then tried an ordinary push from a clone whose history no longer matched the server:

$ git push
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs
hint: Updates were rejected because the tip of your current branch is behind

The refusal is the safety net working. The server is telling you that replacing its history would discard commits it has and you do not.

If you truly must replace published history, --force-with-lease is the narrower option. Its documentation warns that blindly pushing with --force will lose their work, and explains that the lease checks the remote is still where you last saw it.[5] In a second clone I amended a commit while a teammate pushed, left my copy stale, and the lease refused the push with rejected … (stale info). Plain --force accepted it and the teammate's commit vanished from the branch.

Hosted repositories often refuse the situation entirely. GitHub says a protected branch can block force pushes or deletion.[6] The "PRs only" convention in lesson 3.15 exists partly for this.

On a shared branch, the version that keeps everyone's work is a revert, and it can be done from the site: Reverting a merged pull request creates a new pull request that reverts the original merge commit.[7] It requires permission to write to the repository, so ask before promising it.[7]

Your picture of the remote is a memory

Names like origin/main are not the server. They are notes your repository keeps about where the server was the last time you fetched. Git's reference for --prune says it will remove any remote-tracking references that no longer exist on the remote,[8] which only makes sense because git otherwise keeps them: Git has a default disposition of keeping data unless it's explicitly thrown away.[8]

So a list of branches can be confidently wrong. In a throwaway pair of repositories I deleted a branch on the server side and looked again from the clone:

$ git branch -r
  origin/add-search
  origin/main

$ git fetch --prune
 - [deleted]         (none)     -> origin/add-search

$ git branch -r
  origin/main

Nothing about your own commits changed. What changed was the memory. This is why "that branch still exists" is a claim to check rather than repeat, whether it comes from you, an agent, or a second reviewer.

A real pattern, anonymized

A user finished a tidy-up and asked an agent to delete the branches that were already merged. The agent answered from its local list of remote branches and said one of them still existed on the server, so it left that branch alone. A second reviewer disagreed. The agent then fetched from the server, saw the branch had been gone for a day, and corrected its answer. No work was lost, because nothing had been forced. The user's takeaway was smaller than the story: "still exists" is a statement about a memory until someone fetches.

Asking your agent for the safe undo

An agent will run whichever undo you name, and it may name one for you if you leave the choice open. Give it the decision rule instead of the command.

Something I merged is wrong. Before changing anything:

1. Show me `git log --oneline -10` and `git status`.
2. Tell me which commit introduced the problem, and whether it has been pushed.
3. If it has been pushed or merged, undo it with `git revert` and explain the new commit.
   If it has never left this machine, tell me that too, and wait for my approval before any reset.
4. Do not use `git reset --hard`, `git push --force`, or `--force-with-lease` without asking me first.

Then show me the file and the log again, and stop there. Do not push.
Do it in your own project

A new commit whose message starts with Revert, the original commit still visible below it, and the page back to how it looked before the change. If the log is shorter than before, a reset happened: stop and ask why before anything is pushed.

Check yourself

Question 1 of 4

A change you merged last week is already live and it broke the page. What is the safe undo?

The commits are already shared, so replacing history would erase work other people hold. A revert adds a correction that everyone can pull normally.

Question 2 of 4

You have uncommitted edits in a file and run git reset --hard HEAD~1. What happens?

--hard rewrites the working files to match the older commit. Nothing recorded those edits, so the reflog cannot bring them back.

Question 3 of 4

A push fails with "non-fast-forward". What is the server telling you?

The server refuses updates that are not a fast-forward, because replacing its tip would lose commits you have not seen. Pulling or reverting resolves it; forcing over it hides it.

Question 4 of 4

Someone says a branch "still exists on the remote". What makes that a check rather than a claim?

Your remote-tracking names are a memory of the last fetch. git fetch --prune updates that memory and deletes names for branches the server no longer has.
