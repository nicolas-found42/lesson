CORS: why tests pass and the real click fails

Your app's page and the service it calls live at different addresses. Browsers only allow that when the service explicitly says so — and only a real browser enforces the rule, which is why every test can be green while the first real click fails.

Two addresses are two countries

Every address on the web has an origin: the scheme, the host name, and the port. MDN states the rule plainly: Two URLs have the same origin if the protocol, port (if specified), and host are the same.[2] So http://localhost:5173, http://localhost:8080, and https://you.github.io/my-app are three different origins, even though they are all "your app".

Browsers enforce the same-origin policy: a critical security mechanism that restricts how a document or script loaded by one origin can interact with a resource from another origin.[2] And for security reasons, browsers restrict cross-origin HTTP requests initiated from scripts.[1] The key word is browsers. The rule lives in the browser, not in your code and not in the API.

What CORS actually is

CORS (Cross-Origin Resource Sharing) is the escape hatch. MDN defines it as an HTTP-header based mechanism that allows a server to indicate any origins (domain, scheme, or port) other than its own from which a browser should permit loading resources.[1] In plain words: the API answers with a header such as Access-Control-Allow-Origin: https://you.github.io, which means "the page at this address is allowed to read my responses." If the header is missing or names the wrong origin, the browser throws the response away before your JavaScript ever sees it.

Some requests get an extra check first. If your page sends an Authorization header (which OAuth access tokens do), the browser first sends a preflight request — MDN: browsers make a preflight request to the server hosting the cross-origin resource, in order to check that the server will permit the actual request.[1] The server must answer that too, or the real request is never sent.

One sharp edge: if the request carries credentials (like an OAuth token), the server must name an explicit origin. MDN: the server must not specify the * wildcard for the Access-Control-Allow-Origin response-header value, but must instead specify an explicit origin.[1]

One call, two origins

Take a page at http://localhost:5173 and an API at https://api.example.com. Compare two calls from that page. Nothing in your script changes. Only the address changes.

Same origin. The page calls http://localhost:5173/api/notes. The scheme, host, and port all match. The browser sends the request, reads the reply, and hands the data to your script. No CORS header is involved. This is the ordinary case, and it is why a local app can work with no extra setup.

Different origin. The page calls https://api.example.com/notes. The scheme differs. The host differs. The port is implied rather than written, and it still counts. The browser sends the request. The server answers it. What changes is the step after that answer. Before your code may read the reply, the browser looks for Access-Control-Allow-Origin.

That detail explains most of the confusion. The block is not a network failure. The bytes did travel. Open the Network tab and you may see the full reply, with the status you expected, followed by an error from your own call. The reply arrived, and the browser held it back.

A preflight puts one round trip in front of the last two rows. The browser asks first, with an OPTIONS request, whether the real call will be allowed. The server replies with the same headers. Only then does your call go out. A server that handles the real call but not the preflight fails at the earlier step, and from the page the two failures look alike.

Why the tests passed anyway

A test that calls the API from a script runs outside any browser, so no same-origin policy is watching. An emulator or a same-origin setup never triggers the check either. Only a real page in a real browser enforces it — the same lesson as 2.7: a green test suite proves the API works, not that a browser may talk to it. And when the block happens, the page gets nothing: CORS failures result in errors but for security reasons, specifics about the error are not available to JavaScript.[1] The error text appears in the browser's developer-tools console, not on the page.

A real pattern, anonymized

A user's dashboard let each teammate connect an outside account with per-user sign-in. Every automated test and the local emulator run was green, so the agent reported the feature done. The first real click on the connect button in a signed-in browser failed silently in the page — the popup could not reach the service. The cause was on the server: it had never been configured to allow the dashboard's origin, and the missing header only surfaced as a console error in a real browser. The fix was a server setting, not a line of page code.

Recall before you read on

Without scrolling up: your page calls an API at a different origin and the call fails. Who enforces the rule, where do you see the error message, and which side — page or API — usually needs the fix?

The browser enforces the same-origin policy. The error appears in the developer-tools console, not in the page's own text. The fix almost always belongs on the API server: it must send CORS headers naming the page's origin.

See it yourself, then fix the right side

The reliable loop is: reproduce in a real browser, read the console, fix the server, re-click. Do this in your own app:

What you should see: the console shows a CORS error before the fix, the API's response is missing Access-Control-Allow-Origin, and after the server change the same click completes with no CORS error.

My page at http://localhost:5173 calls my API at https://api.example.com. A real browser click fails with a CORS error in the devtools console, but all tests pass. Inspect the API server's CORS configuration and tell me exactly which response header is missing or wrong, and what origin value it must send for my page. Do not change the page's code.

Note the placeholder addresses: use your page's real address (including its port) and your API's real address. With OAuth from lesson 8.7, the token travels in an Authorization header, so expect a preflight — the server must allow your origin on that too, and * will not do.

The habit

"Tests pass" means the API works. "It works in a real browser" means the browser was allowed to talk to it. When a feature involves another origin, the real-browser click is the test that counts.

Check yourself

Question 1 of 4

Your page calls an API at a different origin. Tests pass, but a real browser click fails. What is the most likely cause?

The browser blocked the response because the API never sent CORS headers naming the page's origin. Tests pass because scripts are not browsers and no same-origin policy applies.

Question 2 of 4

Why do automated tests often stay green while the real click fails?

Test scripts and emulators do not enforce the same-origin policy; only a real page in a real browser does. That gap is exactly what lesson 2.7 warns about.

Question 3 of 4

When do two addresses count as the same origin?

Origin = scheme + host + port. That is why localhost:5173 and your live https://you.github.io address are different origins even though both are "your app".

Question 4 of 4

Your API replies with Access-Control-Allow-Origin: * but the browser still blocks a call that carries an OAuth token. Why?

Credentialed requests (like ones with an Authorization header) require an explicit origin, never *. The server must name your page's exact origin.
