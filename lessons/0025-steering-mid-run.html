Steering an agent that is already running

A run that takes twenty minutes is not a black box. You can add a condition, stop a wrong turn, ask where things stand, and send it on again, all without losing the work it already did.

About 15 minutesBuilds on: 0.1 What a coding agent isWin: you can redirect a running agent without restarting it

Why this matters for shipping your app

The first lesson showed that one message can become fifty tool calls. That is useful right up to the moment the agent is fifty calls into the wrong idea. Beginners then face a false choice: sit and watch, or stop everything and start over. Both waste the time you need to get your app finished.

There is a third way. A turn can be steered while it runs: add a condition, halt one bad action, ask what it thinks it is doing, then let it continue. Steering is how a fifteen-minute wait becomes a result instead of a lesson.

Three moves, in order of force

Everything in this lesson is one of three moves. Learn the difference and you will stop reaching for the biggest one first.

MoveWhat it doesReach for it when
QueueAdds a message the agent reads after the work in flight finishes.The current step is still useful; you have one more condition.
InterruptStops the action in progress and hands control back to you.The next action would be wrong, or expensive to undo.
ContinueSends the agent on with the intent it already had.You stopped at a good point and want the same task to go on.

There is also a move that is not a move: asking. "What is the task and its state?" costs one message and often saves an interruption.

Queue: say it now, act later

You are watching a run and notice something the agent should also honour. You do not have to wait for it to finish, and you do not have to stop it. In Claude Code, Type a message and press Enter while Claude is working. Claude Code queues the message instead of interrupting the turn[1] and passes it on as soon as the running tool call finishes, still inside the same turn.

youRename the “Submit” button to “Send” everywhere it appears, then run the checks.
agentsearching 14 files for “Submit”…
youAlso keep the wording “Send feedback” unchanged; that one is a different button.
agentMessage queued. It will be read when the search finishes.
agentfound 9 matches in 6 files…
agentYour line is read before the first edit is made.

That is the trick to practise first. A queued message is cheap: the agent has not been derailed and you have not lost your place. But it lands after the current action, not before it, so do not queue a contradiction and expect it to be read instantly.

One caution: a queued message is not a pause. If the action already running is the wrong one, queueing does not save you. That is what the next section is for.

Interrupt: Esc stops the action, not the work

When the agent is about to do something you do not want, stop it. In Claude Code, the running tool call is canceled and Claude waits for your next instruction[2], and the key table adds that Claude keeps the work done so far.[1] The same page puts it plainly: Esc stops Claude mid-action and keeps everything up to that point, so you can redirect without losing work.[3]

A real pattern, anonymized

A user set an agent to test a small desktop app by launching it and driving its menus with scripted keystrokes. Each run took twenty minutes, and the first screenshot was only taken at minute fourteen. Two minutes into a run, the user stopped it, looked at the frames that existed, and said in effect: stop now, check what you have, then start again. The restart had frames every twenty seconds, so a bad run showed up in the first minute instead of the fourteenth. The interruption cost two minutes. Watching the full run would have cost twenty.

Notice what the interrupt did not do: it did not undo the morning's work or end the session. It ended one action, and everything already written to disk stayed written. That is what makes interrupting safe enough to use early, which is when it is cheapest.

The state question

Before deciding whether to interrupt, find out what is actually happening. Do not guess from the last line on screen. Ask, in words:

What is the task, and what is its state?

Answer in four parts:
1. The task in one sentence, as you understand it now.
2. Done: what is finished, and where.
3. In progress: what you are doing right now.
4. Not done or blocked: what remains, and anything you could not check.

This works in any agent because it asks for a summary, not a feature. Memorise it: it is the cheapest way out of the common bad feeling that the run has been going for a while and you no longer know what it is for.

A real pattern, anonymized

A user came back to a long automated run, found the app had been closed underneath it, and typed: what is the current task and what is the state of it? The answer separated what was finished from what was not, and the user then chose to accept a partial result and finish the rest later. One question replaced a re-run that would have taken another twenty minutes.

A word of warning about shortcuts. Each tool has a status command, but they report the session, not the task. Codex's /status is documented as showing session configuration and token usage[4], and omp's status line shows model, path and context use[5]. Neither will tell you that three of five steps are finished. Ask in a sentence instead.

Continue: the shortest useful message

Sometimes you interrupt at exactly the right moment: the agent has finished a coherent piece and is about to start something you would rather sequence yourself. You do not want to restate the task. You want it to carry on.

The instruction is one word. Claude Code's guidance is direct: If a run does stop short, say continue[3]. omp gives it a key as well, listing Continue the prior intent against Send . or c[5]. In every tool, the important part is what you do not say. Do not re-describe the goal, do not paste the original prompt again, and do not add "start over". Those turn a resume into a restart, and a restart is how a fifteen-minute run becomes two runs.

The habit

Interrupt to change direction. Continue to resume the direction. Restating the whole task is for when you actually want a fresh start, and that is a different decision.

Restart versus steer

Side by side, with an agent halfway through adding a contact form and about to install a package you did not ask for:

Restart

"Stop. Forget all that. Here is the whole task again, and this time do not install anything." The agent starts from zero, re-reads every file, and you wait again.

Steer

Press Esc. Then: "Do not add any packages. Use a plain HTML form that posts to the address I gave you. Then continue." The files it already wrote are still there, and it picks up from them.

The second version is shorter and keeps the work. That is the economy of steering: your correction is about the next step, not the last twenty.

What each agent calls it

Queue: type and press Enter while it works. Interrupt: Esc cancels the running call and keeps earlier work. Send queued messages now: Ctrl+Enter or Ctrl+X Ctrl+S.[1] Continue: say continue.[3]

Steer: Press Enter while Codex is working to inject new instructions into the current turn. Queue: Tab queues a follow-up for the next turn.[4] From another terminal, codex queue --thread <id> --message "…" does the same by name.

OpenAI's CLI page does not document an Esc-to-interrupt key, so do not count on one; it lists Ctrl+C as closing the session.[4] Check your version's shortcut list before relying on a key.

Steer: Enter sends a steering message to the active turn. Queue: Ctrl+Q or Ctrl+Enter. Interrupt: Escape. Continue: . or c.[5]

Escape is focus-sensitive: if a picker or autocomplete is open, the first press closes that instead.[6] Press it again for the run itself.

Claude Code and omp document a one-word resume; the Codex CLI reference does not mention one. If yours does not, name the next step in a sentence instead.
Recall before you read on

Without scrolling up: what are the three moves, and which one keeps the work already done when it is used? Write your answer, then check.

Queue a message for after the current action, interrupt to stop the action in progress, and continue to resume the same intent. All three keep the work; an interrupt cancels one action rather than deleting files or ending the session. Asking for the task's state is the move to make before choosing.

Try it, in your own project

What you should see: the second message listed as pending or greyed out until the current step ends, then answered. Esc leaves a cancelled or interrupted marker, keeps the files untouched (the task was read-only), and does not close the session. The state answer names the task and separates finished work from what remains. continue picks the task back up instead of re-reading everything.

Check yourself

Question 1 of 3

An agent is 40 seconds into a slow run. You realise it must keep the current colours. What is the smallest move?

Queueing adds your condition without cancelling useful work in flight. Interrupting is for when the next action is wrong, not when you have one more requirement.

Question 2 of 3

You press Esc in the middle of a tool call. What has just happened?

Esc cancels the running action and returns control to you. Files already written and messages already exchanged stay where they are, which is why interrupting early is cheap.

Question 3 of 3

You come back after a break and cannot tell where the run stands. What should you do first?

A status command reports session settings, not the state of your task. Asking in words gets you the four things you need before you decide whether to interrupt.
