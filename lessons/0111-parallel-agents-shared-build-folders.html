Parallel agents and the shared build folder

Two agents working at once can finish in half the time — or quietly overwrite each other's work. The difference is usually one folder: where the build writes its output.

Why this matters for shipping your app

Once your app grows past a few files, every change takes longer to build and check, and you will be tempted to work on two things at once: fix the bug users hit today while building tomorrow's feature. Agents make parallel work easy to start and hard to notice when it goes wrong. This lesson is about the one specific trap that bites beginners: several agents building into the same output folder at the same time.

Running agents in parallel

Lesson 3.10 gave you worktrees: a second folder holding another branch of the same repository. Git's own reference says it plainly: A git repository can support multiple working trees, allowing you to check out more than one branch at a time.[1] That is what makes parallel agents safe to start. Codex's documentation recommends exactly this: Worktrees let Codex run multiple independent chats in the same project without interfering with each other, and each worktree has its own copy of every file in your repo.[2] Claude Code's own guide says the same thing from the session side: you can run parallel Claude sessions by using git worktrees, which create separate directories for individual branches.[3]

A single agent can also split one task into parallel helpers, called subagents, that each report back a summary. omp's documentation describes it as delegate independent parts of a task to subagents, such as auditing several packages at once.[4] Whether you start a second agent yourself or let one agent spawn helpers, the rule is identical: each worker gets its own folder.

Where a build writes its output

A build takes your source files and produces finished files: the dist/ folder for a typical web app, the target/ folder for a Rust app. These output folders are one per project folder, and they are not where the race starts — the race starts when two workers share one. Vite's configuration reference states the default outright: build.outDir has Default: dist,[5] so two agents building the same checkout both write into the same dist/. I confirmed the same shape for Rust locally: after cargo build in a fresh throwaway project, the compiled program appeared at target/debug/<name>.[6] And these folders should never be saved in git anyway: Pro Git lists automatically generated files such as log files or files produced by your build system among the files you ignore, because they can be rebuilt.[7]

The race, concretely

A real pattern, anonymized

A user asked an agent to implement several independent pieces of a larger plan at once. The agent started two helpers in parallel, each in its own worktree — but both builds were configured to write their compiled program into one shared output folder. One helper's binary overwrote the other's while a check was running. The check refused the mismatched result, the capture was rejected, and the fix was to give each helper its own build folder. Roughly ten minutes lost to a race that produced no error message at all — only a finished file that belonged to the other task.

Notice the shape: nothing crashed, no tool call failed. Two processes wrote to the same path, the last writer won, and the result looked complete. Git cannot protect you here, because the output folder is gitignored — git deliberately never watches it.

This is where worktrees help, and where they stop helping. A worktree gives a worker its own source tree. It does not give that worker a private build folder unless the build is told to write inside that tree. Many build tools let you point the output somewhere else. If that somewhere else is one path shared by both workers, their source is separate and their output is not.

The report still sounds fine for a simple reason. Each agent judges its build by the exit code of its own command. The command exits zero, so the report says success. That answer is true for the process. It says nothing about the file on disk a minute later. A check that reads one path can only describe that path at the moment it ran.

Recall before you read on

Without scrolling up: if two agents build the same project at the same time, which folder do both builds write into by default, and what goes wrong when they do? Answer in your own words.

Both builds write into the same output folder of the shared checkout (for example dist/ or target/). The writes overwrite each other with no error, so the finished files can be a mix of both builds or belong to only one of them.

The rule: one worker, one build folder

The fix is boring and reliable. Every agent that builds gets its own checkout (a worktree) and therefore its own output folder, or you tell it explicitly which output folder to use. The prompt below is copy-paste and works in any agent; give one copy per parallel worker, each in its own folder.

Run `pwd` and show me the output before doing anything else.

Build the project, but write ALL build output into a folder named
build-output-<YOUR_BRANCH_NAME> inside this checkout. Do not write
into dist/, target/, or any shared output folder.

Then show me `git status --short` and the path of the finished files.

Two habits make this stick. First, build output stays gitignored, so a race never becomes a false commit — only a false file. Second, after any parallel run, verify per worker: the finished files exist in each worker's own folder, and a change you expected from worker A is not missing because worker B overwrote it.

The check that catches it

If two agents ever did share one output folder, do not trust either result. Rebuild once, alone, in a clean checkout, and compare. A mixed build looks finished but is not evidence — the same "done is a claim" habit from lesson 2.2 applies to files, not only to messages.

Try it yourself

Skills practice

git worktree list shows two paths on two branches. The agent's build output lands in build-output-parallel-test/ inside the new folder only, and git status --short in the original folder prints nothing. If output appeared in a shared dist/ or target/, the agent ignored the instruction — stop and re-ask before running a second worker.

Check yourself

Question 1 of 3

Two agents build the same project at the same time, sharing one checkout. What is the main risk?

Both builds write into the same output folder of the shared checkout. The writes overwrite each other silently — no error, only wrong or mixed output files.

Question 2 of 3

Why should each parallel worker build into its own output folder?

Two processes writing one folder means last-writer-wins with no warning. Separate folders per worker remove the shared path entirely, so each build's output stays whole.

Question 3 of 3

After a parallel run, one agent claims its build succeeded but you suspect the shared output folder was used. What is the best next move?

A shared-folder race leaves no error, so the claim is not proof. Rebuilding alone in a clean folder gives a trustworthy reference to compare against.
