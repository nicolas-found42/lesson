People open the repo before they open your link

Shipping your app means giving people an address. But when someone hears about your app, searches for it, or sees it in a profile, they usually land on the repository page — not on your site. GitHub itself says a README is often the first item a visitor will see when visiting your repository.[1] If the link to your live app is only in a chat message, the repository page sends visitors nowhere.

This lesson is about the two spots on that page where a link earns its keep: the README and the About box. You set both in about two minutes, and lesson 6.6's rule still applies — only put in a link you have verified is actually live.

The two places people look

GitHub renders a file named README.md in the root (or .github or docs) folder below the file list: GitHub will recognize and automatically surface your README to repository visitors.[1] On the right of the same page sits the About box: a one-line description, a Website link, and topics. Topics appear on the main page of a repository and help people find your project.[3]

Place on the repo pageWhat it isWhat belongs there
README, topThe rendered file shown below the file list.The live link as the first line, then what the app does and how to open it.
About: descriptionOne short line under the repo name.One sentence saying what the app is, in plain words.
About: WebsiteA clickable link shown in the sidebar.The exact live URL, including the /repository-name/ part.
About: topicsSmall labels under the Website field.Two or three words about the subject, like static-site.

What goes in the README, top to bottom

A README for a small static app does not need chapters. Four short blocks are enough, and the order matters: a visitor reads from the top and stops as soon as they have what they need.

BlockContentWhy it sits there
1. The linkLive site: https://YOUR_USERNAME.github.io/my-app/It is the one thing most visitors came for.
2. What it isOne or two sentences about what the app does and who it is for.Confirms the visitor is in the right place.
3. How to open itThe same URL as a clickable link, plus anything needed to use the app.Some readers copy an address; others click a link.
4. How it is madeOne line naming the files, such as "Plain HTML, CSS and JavaScript in index.html."Helps the next person who edits it.

Here is that README for the example app used through this unit, in full:

Live site: https://YOUR_USERNAME.github.io/my-app/

A small static app that runs in the browser.
Open the live site and use the first button you see.

Files: index.html, style.css, app.js.

Six lines, counting the blank ones. Nothing in it needs a framework, and nothing in it goes stale the moment you change a colour. The link comes first because a visitor who reads only one line should still get the thing you built.

Length is not the risk here. GitHub truncates a rendered README past 500 KiB, and a useful one is a few hundred bytes. If your README keeps growing, the extra text probably belongs in a separate file that the README links to.

The About box in one minute

The About box is the sidebar beside the file list: a description, a Website field, and topics. You edit it from the repository's main page, and the same three fields are what gh repo edit changes from a terminal. The description is the sentence a visitor reads while deciding whether to click. Keep it to one line and say what the app is: "Coffee shop notes, rated by visitors" does that job; "A journey into modern web development" does not.

Topics are discovery labels, not sentences. Use two or three lowercase words joined by hyphens, such as static-site, coffee, or github-pages. GitHub accepts up to 20 topics of 50 characters each, so the limit you reach first is a reader's patience. Three precise topics beat ten vague ones.

The command-line way to set the same fields is gh repo edit, whose own help lists -d, --description as Description of the repository and --homepage as Repository home page URL.[2] The web form and the command change the same fields; use whichever you are comfortable with.

A pattern from real sessions

A real pattern, anonymized

A user asked an agent to put a small showcase online for friends who are not technical and would not know how to use a repository — and in the same message asked for the link to be written into the README and the repo description. Naming the audience is what made the agent choose the right deliverable: a link in the places non-technical visitors actually look, not instructions about branches.

The agent deployed, verified the live URL in a real browser, and only then edited the README and set the description and Website fields. Bundling the follow-up into the same prompt mattered: the agent knew from the start that done included the link in both places, so nothing was left half-finished.

Do it on your own repo

Do it now — on your own live site

In a private window, the repository page shows your description and a clickable Website link in the About box, the README's first line is the live link, and clicking that link opens the page you verified in lesson 6.6. If the Website link 404s, the address is missing the /repository-name/ part — fix the field, not the app.

Or hand it to your agent as one small task

The same edit is a good one-message job for your agent. This prompt works in any of the three agents; it names the audience, the two places, and what not to touch.

My live site is https://YOUR_USERNAME.github.io/my-app/ and I have already verified that URL opens it.

Update the repository so people find the app from the repo page:
1. Put "Live site: https://YOUR_USERNAME.github.io/my-app/" as the very first line of README.md.
2. Set the repository description to one plain sentence about what the app does.
3. Set the Website (homepage) field to the live URL — you can use `gh repo edit` with --description, --homepage and --add-topic.

Do not change any app files. When done, show me the top of the README and the About box as they now appear. Keep approval prompts on.
The agent may use the gh command, which needs your GitHub sign-in — approve the prompt when it appears, and never share a password with the agent.
Recall before you read on

Without scrolling up: name the two places on a repository page where the live link belongs, and say what goes in each. Write it in your own words.

The README (rendered below the file list) gets the live link as its first line plus a sentence about the app; the About box gets a one-line description, the live URL in the Website field, and a few topics. Both are on the repository page — the place many visitors see before ever clicking your link.

Check yourself

Question 1 of 3

A friend opens your repository page on GitHub. What appears below the file list?

GitHub surfaces a README from the root, .github or docs folder below the file list. With no README, that area stays empty; commits and stars live elsewhere on the page.

Question 2 of 3

What belongs in the About box's description and Website fields?

The description is one plain sentence; the Website field is the exact live URL, shown as a clickable link. Pasting the whole README or build logs there defeats the purpose.

Question 3 of 3

The agent says it updated the README and the repo description. What should you do before sharing the repo with friends?

"Done" is a claim. Open the repository page yourself, see the link in the README and the About box, and click the Website link to confirm it reaches the live site.
