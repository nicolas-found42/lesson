Vague prompts are safe only when the repo defines "works"

A short request like "does the project work?" can be the cheapest message you ever send — or the start of a twelve-hour run with no finish line. The difference is not in the wording. It is in what your repository already says about the word "works".

Why this matters for shipping your app

You are not going to write a careful paragraph every time you talk to the agent. Some days you want to type four words and read the answer. That is a reasonable way to work, because earlier lessons gave you the two pieces that make it reasonable: a rules file carrying your standing instructions, and one command that returns pass or fail. This lesson is about the bargain between those pieces and the prompt.

The bargain is simple to state. A vague prompt is safe when the repository, not the agent, decides what "works" means. When the repository is silent, the agent fills the silence with its own idea of done — and you see that idea only after the work is already done.

The four-word prompt that worked

A real pattern, anonymized

A user opened a long-running project and typed only: "does the project work?" That was the entire message. The agent ran the project's documented checks — formatting, type checking, linting, the test suite — then started the app, then started it again in a container to confirm the data survived a restart. Eight minutes, a few dozen tool calls, and an answer of yes, delivered with a table of what passed. The answer also listed what had not been exercised: real credentials, live providers, slower tests.

Nothing in those four words named a test, a command, or a definition. The definition was already in the project: a rules file that told the agent which command decides, and a gate that answered pass or fail. The prompt was vague; the repository was not.

Where the missing words live

Compare the same prompt sent into two projects. The words are identical. The work is not.

Vague prompt, silent repository

"does the project work?" The agent decides for itself what working means. It may open a file, read a little, start the app, see a page appear, and report success. That is not a lie; it is the best available reading of a request with no bar attached.

Vague prompt, repository defines it

"does the project work?" The rules file names one command. The command runs the checks and ends in an exit code. The agent runs it, reads the number, and reports the number plus the checks it could not run. You can rerun the same command and get the same verdict.

This is why the lesson sits in this order. Lesson 2.6 built the gate: one command, pass or fail. Lesson 1.12 put the gate's name where every session reads it. Without those two, "does it work?" is a question for the agent's taste. With them, it is a question for the repository.

The prompt is a pointer, not a specification

Anthropic's guide describes the mechanism from the agent's side: Claude stops when the work looks done. With nothing to run, "looks done" is all it has to go on.[1] A vague prompt works only when it points at something that can tell the agent it is wrong.

OpenAI's guide says the same of its own agent: Codex can do this loop for you, but only if it knows what "good" looks like, and that knowledge may live in either the prompt or AGENTS.md.[2] Both guides treat a vague prompt as a normal thing to send, provided the standard is written down somewhere the agent reads.

Claude's guide even names the exception: a loose request is fine when you're exploring rather than fixing something specific, and You'll correct a bit more as you go.[1] Exploring is the exception that proves the rule. You accept the extra corrections because there is no bar to meet yet. The moment the output has to be accepted — committed, merged, shipped — the bar has to exist.

The test to apply before you press send

Ask yourself: if the agent answered "done" to this, what would I check, and could the agent have checked it too? If the answer is "run the gate", you may be as vague as you like. If the answer is "I would have to look and judge", the definition is still in your head, not in the repo.

What the repository has to contain

Three things, all from earlier lessons. Together they turn a four-word prompt into a bounded task.

  1. A command that returns pass or fail. The gate from lesson 2.6. Node's test runner, for example, reports failure through the exit code: If any tests fail, the process exit code is set to 1, so the shell — and the agent — can read the result without opinion.[3]
  2. A rules file that names it. Claude Code treats these files as persistent instructions for a project, though as context, not enforced configuration.[4] Codex reads AGENTS.md files before doing any work.[5] omp loads it automatically and applies it throughout the session.[6]
  3. A written sentence about when the work counts as finished. Codex's prompting guidance calls this element "Done when" — what should be true before the task is complete, such as tests passing or a bug no longer reproducing.[2] The idea is older than coding agents; the Scrum Guide says a definition of done creates transparency by providing everyone a shared understanding of what work was completed.[7]

The rules file can hold the second and third together: it names the gate, and states in plain words what passing it means. "Green gate, and the home page lists every product with a price" is a definition. "Good quality" is not.

The other kind of vague: "until it is good"

Not every vague request delegates to a check. Some delegate the judgement itself. That is where the bargain breaks, and it breaks quietly, because the sentence sounds like a standard.

A real pattern, anonymized

A user asked an agent to improve a research app, then added: "run several tests until no issues remain." The thing grading each run was itself a model, and each fix exposed a new class of complaint — output too long, a quote that did not match, a fact gone stale. The agent kept finding issues because the bar kept moving. Twelve hours and roughly fourteen hundred shell commands later, the user returned and interrupted a branch that had never been merged.

That request had no exit condition, and no file could have supplied one, because "no issues remain" means "until the judge is satisfied" — and the judge was a second model with its own opinions. Notice the contrast with the first vignette. There, "does it work?" was answered by a command that cannot change its mind. Here, "is it good?" was answered by a critic that could.

The fix is not a longer prompt but the same three pieces as before: a named check, a named judge, a stopping point — plus a budget. Lesson 4.3 covers stop conditions and lesson 4.4 covers caps. A one-dollar cap was in fact enough to bound the follow-up work in the first case; the second case had neither cap nor exit.

Watch for these wordings

"Until no issues remain", "make it polished", "improve it", "fix whatever is broken". Each one hands the definition to the agent and then asks it to keep going until it is satisfied with its own work. If you want that exploration, say so and set a limit. If you want a result, point at the gate instead.

The same request, rewritten as a pointer

You do not have to become precise to be safe. You have to be precise about where the standard lives:

vague, repo carries the bar
  you    "does the project work?"
  agent  runs `npm run check`, reads the exit code,
         reports the number and the gaps

vague, nothing carries the bar
  you    "make it feel finished"
  agent  picks its own idea of finished, works until
         that idea is satisfied, and tells you it is done

The second message is not wrong because it is short. It is wrong because no sentence in the project can contradict the agent's idea of "finished". Add one sentence to the rules file — what must be true, and which command shows it — and the same short message becomes checkable.

Recall before you read on

Without scrolling up: a short prompt is safe in one situation and unsafe in another. Name the situation, and name the two things in the repository that create it.

Safe when the repository, not the agent, decides what "works" means. That takes a gate — one command returning pass or fail — and a rules file that names the command and states in plain words what passing it means. Without them, the agent supplies its own definition, and you only discover it after the work is done.

Try it on your own project

This exercise is a probe, not a build. You are testing whether your repository can answer a question you did not spell out.

Do it in your own project

In a project whose repository defines "works", the agent answers step 2 in one or two lines — the command, and what it covers — then runs it. In step 4 it quotes your rules file. If instead it explains what "working" ought to mean, or lists criteria you never wrote, that is the signal: the definition lives in the agent's head, and every short prompt will inherit it.

Check yourself

Question 1 of 3

Which condition makes a vague request like "does the project work?" safe to send?

The repository supplies the bar, and a gate turns it into a number the agent can act on. Confidence is a claim, a file list is not a standard, and your glance is exactly the manual checking a gate replaces.

Question 2 of 3

Which request most needs the repository to define the word "works"?

"Polished" is a judgement no command can settle, so the agent must invent the bar. The other three name an observable result: a button that responds, a page carrying an address, a command whose output you read.

Question 3 of 3

The agent answers "does this project work?" with yes, then lists what it did not test. What is the best next move?

The gap list is the valuable part, so turn it into a bounded task with a cap. Repeating the question adds nothing, merging on a yes trusts a claim, and "until issues vanish" removes the finish line entirely.
