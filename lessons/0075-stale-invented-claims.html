Stale or invented claims: check the source of truth

An earlier answer is not proof of the current state. Learn to trace a claim to the right source, check its freshness, and mark what remains unverified.

About 15 minutesBuilds on: 2.2 Claims vs evidenceWin: you can make any agent prove a claim against the real thing

Why this matters for your app

Your mission is to ship a real app, not a convincing report about one. An agent's statement that a branch is gone or a page is live is a claim to check. Earlier output may describe an earlier state; a plausible explanation may have no supporting observation at all. Before you act on either, ask where the answer came from and whether that source still answers your question.

Two kinds of wrong

A stale claim relies on information that no longer describes the current situation. An invented claim presents a false statement as fact without supporting evidence. An unsupported claim is not necessarily false: it is unverified until you check it. These distinctions matter. You do not need to accuse the agent of inventing something to ask for evidence. A confident tone settles none of them.

What counts as the source of truth depends on the claim. For a file, it is the file on disk right now. For a server or a live website, it is the server's answer right now. For a command, it is running the command again. Git gives a good example: your local copy keeps remote-tracking references, which are only local notes about the server, and git's own manual warns that these stale references accumulate if you never refresh them — the fix is git fetch --prune, which deletes local notes for things the server no longer has.[1] I confirmed this on a throwaway copy: after deleting a branch on the server, git branch -a still listed it until a pruning fetch removed it.

A table makes the choice concrete. Each row is a claim you might hear, and the one place that can settle it.

A claim aboutWhere to check it
A file's contentsThe file on disk, read now
A command's resultThe command, run again read-only
A branch on the serverA fresh fetch, then the branch list
A live page's textThe public address, opened now

A real pattern, anonymized

A real pattern, anonymized

A user asked an agent to clean up old branches. The agent insisted one branch still existed on the server, because an earlier command in the same session had listed it. A second opinion disagreed. Instead of arguing from memory, the agent ran a fresh command against the server, found the branch was already gone, and corrected itself in front of the user. In another session, an agent read a documentation page that had quietly become a "page not found" and confidently wrote a false rule into the project notes. It was caught only when someone re-opened the real page and noticed the address was dead.

Both mistakes had the same shape: the agent trusted a cached or second-hand picture instead of the live one. The fix in both cases was identical and cheap — re-check at the source.

The habit: check the source of truth

Anthropic describes the agent loop this way: Each tool use returns information that feeds back into the loop, informing Claude's next decision.[2] That gives you a useful question: which observation supports this answer? Its best-practices page describes a familiar failure: Claude said it was done and it wasn't quite, usually because it had no way to check its own work.[3] Testing is one remedy; Anthropic's engineering guidance recommends extensive testing in sandboxed environments with appropriate safeguards.[4]

So make "prove it" your default prompt. This block works in any agent:

Copy-paste prompt 
Check this claim against the current source of truth. Use read-only checks;
do not change files, deploy, or repeat an action that changes anything.
Show the relevant evidence, its source, and when you checked it.
Redact secrets. Separate what you observed from what you infer.
If you cannot access the source, mark the claim unverified.

Keep approval prompts on; lesson 0.6 explains the settings. Do not blindly re-run a command that changes something. Checking whether a deploy succeeded means inspecting its result, not deploying again. Ask for the smallest read-only check that answers the question, without printing passwords or private data.

Recall before you read on

Without scrolling up: what is the difference between a stale claim and an invented claim, and what single habit catches both?

A stale claim relies on an outdated picture. An invented claim states something false without support. A claim without evidence should be marked unverified, not automatically called false. Check the relevant current source before deciding what to trust.

Practice: make your agent prove one claim

Do it in your own project

What you should see: a read-only tool call running git --version, followed by the installed version or an error explaining why it could not be checked. Your version may differ from the author's git version 2.56.0. The summary should agree with the actual output.

Match the evidence to the question

Fresh does not automatically mean relevant. A current file in the wrong project folder cannot prove what is in your project. A current local page cannot prove what your friends see at the public address. Ask the agent to identify the folder, page, or service it inspected. If those do not match your question, you still do not have the evidence you need.

Use three parts in a useful report: claim, observation, limit. For example: "The public page shows the new heading; I opened the public address now; I did not check the contact form." This is stronger than "everything is live." It tells you exactly how far the evidence reaches, and where another check would be needed.

A cached result is a saved copy, not automatically a bad copy. Earlier output can help you find where to look. The mistake is treating it as proof of a changing fact without checking freshness. Nor does a source link alone prove a claim: open the page and confirm it actually contains the information. A page-not-found message gives you no basis for inventing a replacement rule.

If the source is inaccessible, stop at that boundary: "I cannot verify it from here." Ask for the missing access or check it yourself. Repeating the question, requesting more confidence, or collecting another summary does not turn missing evidence into a verified fact.

Write the result where the work lives: the claim, the check you ran, and the date. That line is what a teammate or a later session reads instead of repeating your search. It also ages honestly. A dated check of a live page is easy to spot as old, while an undated "it works" quietly becomes a stale claim of its own.

Check yourself

Question 1 of 3

An agent says a branch still exists on the server, based on output from earlier in the session. What is the best move?

The earlier output is a cached picture. Only a fresh command against the server is the source of truth, so the claim needs re-checking, not trusting or guessing.

Question 2 of 3

Which of these is the source of truth for a claim about a live website?

Memory, comments, and search caches are all second-hand. The live page's current response is the only first-hand source.

Question 3 of 3

Your agent reports "deploy shipped", but you doubt it. What is the best next step?

Confidence is not evidence. Checking what the live site actually shows, against what the deploy claimed, is a real verification step (lesson 2.2).
