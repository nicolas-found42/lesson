LLM calls as a dependency: limits, timeouts, retries, JSON

When your app calls an AI model at runtime, that model is a dependency like any other service — it can be slow, capped, overloaded, and it does not guarantee well-formed output. Learn the four ways those calls fail and the rules that make them safe.

About 15 minutesBuilds on: 8.4 Third-party API keysWin: you can write retry, timeout, and output-shape rules your agent will actually follow

Why this matters for shipping your app

Until now, your agent was the only thing that called an AI. That changes when your app calls a model at runtime. Maybe it summarizes a page, sorts a support ticket, or writes a draft reply for a user. From that moment, the model is a dependency. A dependency is something your app needs but does not control.

Dependencies fail. A payment API goes down. A database times out. An AI provider gets busy, runs out of your credits, caps its answer, or replies in prose when you asked for JSON. If your app treats every answer as guaranteed, one bad call can take the whole feature down.

Four ways an LLM call fails

Think of an LLM call as having four failure shapes, each with a different fix:

FailureWhat it looks likeRight response
TimeoutThe request hangs, then failsSet a time limit; stream long requests
Output limitAnswer cut off mid-sentenceRaise the cap; check for truncation
Overload / rate limit429 or 529 error codesBack off, honor Retry-After, retry a few times
Bad shapeProse, or broken JSONAsk for JSON only; validate before using

Timeouts: the call can hang

A model call is not instant. A long one can hang until the connection gives up. Anthropic's API error reference lists 504 timeout_error: The request timed out while processing. Consider using the streaming Messages API for long-running requests.[1] The same page warns about requests especially those over 10 minutes.[1]

The rule is short. Give every call in your app its own time limit. Long answers should stream. Streaming means the reply arrives in chunks as the model writes it. A streamed answer shows progress, so a slow model does not look like a dead one.

Output limits: the answer can be cut off

Each provider caps how much a model may write in one reply. That cap is set by the max_tokens parameter.[2] When the cap is hit, the answer stops. It can stop mid-sentence, mid-word, or inside a JSON object. Anthropic's own guidance says to give the model enough tokens to "think" before it writes itself into a corner.[3] So set the cap high for your task. Then check every reply for truncation. A cut-off sentence can still look finished, so read for a missing ending.

A cut-off JSON answer is the most common way "the model replied" turns into "the app crashed". Treat a short reply as a question, not an answer. Ask whether the reply ended where your format says it should.

Retries: overload is temporary, but back off

Providers get busy. Anthropic's error reference lists 529 overloaded_error: The API is temporarily overloaded, and 500 api_error with the advice retry the request with exponential backoff.[1] Rate limits (429) act the same way. MDN notes that a 429 may carry a Retry-After header. That header says how long a client should wait before making the request again.[4]

Anthropic's SDKs make this concrete. They retry short-lived failures with exponential backoff, twice by default, honoring the retry-after header when present.[1] Exponential backoff means each wait gets longer: 1 second, then 2, then 4. The growing gap stops you from hammering a busy service. It also gives the provider time to recover.

Not every error deserves a retry. A 400 invalid_request_error means your request is wrong.[1] Sending the same request again changes nothing. Fix the request instead.

A real pattern, anonymized

A user had an agent run a long check loop. The loop called a live AI service to grade its own output. Three things went wrong. The loop hit a model timeout of about three minutes. An output cap cut answers short. The grader sent back malformed JSON. The run ground through fix cycles for hours, because each failure looked like a new bug. In fact, these were four known failure shapes of an outside dependency. The run needed a timeout, a retry budget, a truncation check, and JSON validation from the start. The same user later ran out of credits mid-run. The agent stopped and asked a human. That was the right move.

JSON shape: the model does not promise a format

If your app needs structured data, you must ask for it and then check it. Anthropic's agent-design essay is blunt about formats: you can return code inside markdown or inside JSON, and writing JSON requires extra escaping of newlines and quotes. That escaping is where models slip under pressure.[3]

The safe pattern has three steps. Ask for JSON only in the prompt. Parse the reply in code. A parse error tells you the shape was wrong; it does not mean the app should crash. Then keep a fallback for the case where parsing fails. A fallback is a plain default, such as a short apology or a queued retry. Never pass model output straight into your app. Validate it first.

Recall before you reveal

Without scrolling up: name the four ways an LLM call can fail, and the correct response to each.

Timeout → set a time limit and stream long requests. Output limit → raise the cap and check for truncation. Overload/rate limit (429, 529, 5xx) → back off exponentially, honor Retry-After, retry only a few times. Bad shape → ask for JSON only, parse and validate, keep a fallback. Errors like 400 are not retryable.

Write the rules once, in your rules file

These four habits belong in your project's rules file (lesson 1.12). Put them there once. Then the agent applies them to every feature, instead of relying on memory.

Rules for every feature that calls an AI model at runtime:
1. Every model call gets an explicit timeout, and long generations stream.
2. Retry transient failures (429, 529, 5xx, timeouts) at most 3 times with
   exponential backoff, honoring any Retry-After header. Never retry 4xx
   errors like 400 — fix the request instead.
3. Ask the model for JSON only when the app needs structured output, then
   parse and validate it before use; on invalid JSON, use the fallback, do not crash.
4. After each call, check the reply was not truncated by the output limit.
5. Set a spend cap with the provider before any long run (lesson 8.4).

Try it with your agent

What you should see: the rules file now contains the five rules; the agent points to a concrete call site (or adds one) with a timeout, a small retry-with-backoff helper, and a parse-and-validate step with a fallback.

Check yourself

Your app calls an AI provider and gets HTTP 529. What does that mean?

529 means "temporarily overloaded" — the provider is busy right now. A token cap, an invalid key, and an oversized body are different errors (output truncation, 401, and 413), each with its own fix.

The model was asked for JSON but returned prose around it. What is the right fix?

Models do not guarantee a format, so the app must parse and validate every reply, and the prompt should request JSON only. A longer timeout does not fix prose, and a tight retry loop hammers the provider.

Which failure should your app NOT fix by retrying?

429, 504, and 529 are transient — back off and retry. A 400 means the request itself is malformed; retrying the identical request changes nothing, so fix the request instead.
