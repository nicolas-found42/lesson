Triage first: diagnose before you act

When a project has grown several branches and open questions, the expensive mistake is acting on a guess. A read-only triage pass turns "something is off" into a ranked list you approve before anything changes.

Why this matters for shipping

By now your project folder is a repository with branches (lesson 3.5): parallel lines of work that you merge, or abandon, one at a time. Late in a project you can easily end up with several branches, some already merged, some stale, and a vague feeling that "something needs cleaning up". If you ask the agent to "fix it" in one sentence, it will pick a branch, pick a fix, and start editing — and you will own a change you did not choose, in a place you cannot yet name. The triage habit separates understanding the mess from changing the mess, so the second step happens only after you have seen the first.

The mess you are triaging

A typical late-project state: a main branch, a few feature branches, one of which was merged days ago and is now only a name, one with uncommitted work, and maybe an open pull request nobody remembers. None of this is visible from the folder alone; it lives in git's state. That is exactly what an agent is good at reading. Anthropic's own best-practices page puts the underlying habit in one line for side-effecting work: Make sure you're on main with a clean tree. If not, stop and ask.[1]

The two-step ask

The pattern has two messages, and keeping them separate is the whole point.

Step one — triage, read-only. You send a saved prompt that forbids changes and asks for a report. The agent reads branches, status, logs, and files, and answers with a diagnosis and recommendations. Nothing on disk changes.

Step two — approve, then act. You read the report, adjust anything that looks wrong, and send one short message: "carry out your recommendations". Only now does the agent edit, commit, or merge.

Why keep the two messages apart? A diagnosis written before any change can be checked against reality: you can run git branch and confirm the branch list yourself. A diagnosis that shows up only inside an edit cannot be checked, because the edit has already happened. The split also keeps the agent's context small: the report is the summary, and your second message points at it instead of re-describing the mess.

A real pattern, anonymized

A user with several live branches and open tickets sent one saved "triage" prompt. The agent inspected the branches read-only and reported that three could not be merged as they stood, which one should go first, and which were already contained in main. The user then replied "complete all of your recommendations" and approved the result in a single sentence — the diagnosis stayed a diagnosis until a human had seen it.

The triage prompt

Copy this into a text file you can reuse; it works in any of the three agents because it relies only on reading and reporting:

Triage this project. Do not create, edit, delete, commit, push, merge, or close anything — read only.
Report four things:
1. State: which branches exist, which are already merged into main, which are stale, and what is uncommitted right now.
2. Diagnosis: each problem you find, with the evidence you used (command output, file and line).
3. Recommendations: ranked safest first, each with the exact command or prompt I should run next.
4. Stop there. Wait for my approval before doing anything from step 3.

The last line is not politeness. Lesson 1.2 shows why "do not edit" must be said out loud, and how each agent enforces a read-only turn; lesson 1.7 turns the report into an approved plan.

What a good triage report looks like

PartLooks likeRed flag
State"main is clean; branch A is merged; branch B has 2 unpushed commits."Vague words like "some branches look old" with no evidence.
Diagnosis"Branch B cannot merge because it conflicts with the login change in main (file X, line Y)."A fix proposed before the cause is named.
RecommendationsRanked list, safest first, each with an exact command or prompt."You should probably clean things up" with no order and no command.
StopThe turn ends with a report, zero edits.Files changed during a "read-only" triage.

Read the ranking as a budget, not a schedule. The first item should remove the most uncertainty for the least risk — usually committing work you forgot was uncommitted, or deleting a branch already merged into main. Merges come last, because they are the hardest step to undo.

If the triage edited something

The promise was broken, not merely bent. Check git status yourself, and if the working tree changed, undo it (lesson 3.11) before trusting anything else in that session. Keep approval prompts on (lesson 0.6) so a stray edit asks first.

The second message: approve in one sentence

When the report is good, your reply can be very short: "Carry out recommendations 1 and 2, then stop." Naming a subset keeps you in charge of scope. Two habits from real sessions are worth copying: ask for the exact command or prompt for each step (so step two is copy-paste, not interpretation), and keep the merge decision yourself — lesson 9.4 shows what happens when "merge" is left to automation. The report itself is still a claim: spot-check one piece of its evidence, as lesson 2.2 teaches.

Recall before you read on

Without scrolling up: what are the two messages of a triage pass, what must the first one forbid, and what should its report contain?

Message one is a read-only triage prompt that forbids creating, editing, committing, pushing, or merging, and reports state, evidence-backed diagnosis, and ranked recommendations with exact commands. Message two is a one-sentence approval, possibly naming only some recommendations, after which the agent acts.

When to skip the triage

Triage is a tool, not a ritual. Skip it when the mess is one file you can name, or the change is a single word you wrote this morning — asking for a full report there is over-asking (lesson 4.11). Use it when the state is genuinely unknown: many branches, unclear what is merged, or a bug you have not diagnosed. A good middle size is "triage only the branches" rather than "triage everything".

Do it in your own agent

Practice on your own repo

You should see a report listing your real branches, which are merged or stale, plus ranked recommendations with exact commands — and no edits during step 3. After step 5, exactly one recommended action has been performed and the agent stops and waits.

Check yourself

Question 1 of 4

You have several branches and do not know which are stale. What is the best first message?

Acting on a guess (delete, merge, rename) can destroy work. The triage message only reads, so it cannot break anything, and its report makes your next message exact.

Question 2 of 4

Which of these does NOT belong in a triage report?

State, ranking, and exact commands are the report. Editing during triage breaks the read-only boundary and is the failure this lesson exists to prevent.

Question 3 of 4

After a good triage report arrives, your second message is...

The second message approves action — ideally naming a subset, as in "carry out the first recommendation only" — so the agent acts on a diagnosis you have already reviewed.

Question 4 of 4

When is a full triage pass a waste of a turn?

Many branches, fresh comments, and an unclear live branch are exactly when triage pays. If you already know the one file to edit, a full report is over-asking.
