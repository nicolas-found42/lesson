From one big spec to a frontier of tickets

When your app grows past what fits in one prompt, you stop asking for "the app" and start asking for one ticket at a time. The pipeline is: spec, then tickets, then the dependency graph — and the frontier tells you what is safe to build next.

Why one big prompt breaks down

Your mission is to ship a real app, and a real app is never one prompt. Your first page was small, but the next version of your app will have a gallery, a form, a second page — each a change you want to see, check, and undo on its own. One giant prompt produces one giant change you cannot review piece by piece, and a single "done" you have to trust whole (lesson 4.1 covered why that is risky).

A real pattern, anonymized

A user had written a roadmap of about eighty items across several earlier sessions, then sent the agent a single line: "implement the spec." The sentence that saved the week was the second one: "stop when items 10, 11 and 88 are merged and closed." The agent worked through the items one at a time, several in parallel where that was safe, and stopped exactly where the user said. The roadmap was the spec, the sentence was the stop condition, and together they replaced a multi-day sprawl with one bounded run.

Spec, then tickets

A spec is the whole picture: what the app does, for whom, and what must be true at the end. It is too big to hand over as one job. A ticket is one small piece of the spec that a single run can finish: a title, a one-sentence goal, a "depends on" list, and "done when" checks you can verify by looking (the acceptance criteria from lesson 4.1).

Tickets do not need a special tool. A plain file in your project works, and the agent can read and update it. If you already use GitHub, issues are the natural home — GitHub's documentation describes issues as a way to track ideas, feedback, tasks, or bugs.[3] Either way, keep each ticket small enough to read in one screen:

Ticket fieldExample
Title"Photo grid on the home page"
Goal"Visitors see all six photos without scrolling sideways."
Depends on"Shared page layout"
Done when"At phone width all six photos show in one column, and the project's check command passes."

The dependency graph and the frontier

Tickets point at each other. When ticket B lists ticket A under "depends on", B is blocked until A is done — starting B earlier means guessing at code that does not exist yet. Drawn with arrows, the tickets form a dependency graph. The frontier is the set of unfinished tickets whose dependencies are all finished: the only tickets that are safe to start right now.

GitHub has the same idea built in. Its documentation on issue dependencies says you can see which issues are blocked by, or blocking, other work, with a "Mark as blocked by" option in the sidebar.[4] Whether your tickets live in GitHub issues or in a plain file, the graph and the frontier are the same.

A useful habit is to ask the agent for the graph out loud: "Which tickets are on the frontier, which are blocked and by what, and what is the shortest path to the next shippable piece?" The answer is a short list, not a wall of text — and it tells you what to say "go" to.

A small example shows how the frontier moves. Five tickets, each listing what it depends on:

TicketDepends onState
A — Shared page layoutnothingdone
B — Photo gridAdone
C — Contact formAready
D — Photo captionsBready
E — Gallery searchC, Dblocked

At the start, only A was on the frontier, so A was the only safe first move. Once A and B were done, C and D became ready at the same time. E stays blocked until both C and D finish. The frontier is not the whole of the remaining work; it is the moving edge of work that is unblocked right now.

Expect the graph to change as you learn. A ticket that looked independent may turn out to need a shared piece, and that piece becomes a new ticket with its own dependencies. When that happens, add the ticket, re-run the pipeline, and read the frontier again. Redrawing the graph is a normal step, not a failure of planning.

Dependencies are not only between tickets. In one real session, two helpers built at the same time wrote their compiled output into the same shared build folder, and each overwrote the other; the project's own checks caught the mismatch and refused the result. The fix was giving each helper its own build folder. Shared files and folders are dependencies too — lesson 9.3 covers this.

Run it as a pipeline

You do not have to invent this structure yourself — the agent can build it from your spec. This prompt works in any of the three agents:

Read my spec in SPEC.md. Split it into tickets, each small enough to finish in one run.
For every ticket write four lines: Title; Goal (one sentence); Depends on (titles of other tickets); Done when (checks I can verify by looking).
Then draw the dependency graph and list the frontier: the unfinished tickets whose dependencies are all done.
Do not start any ticket yet. If two tickets would write to the same file or folder at the same time, say so explicitly.

Once you have the frontier, hand the agent one ticket — with the stop condition from lesson 4.3 attached:

Work on the frontier ticket "<ticket title>" and on nothing else.
Stop when its "done when" checks pass and the changes are committed — and stop there.
Report one line per check: what you ran or looked at, and what you saw.

The two prompts keep the scales separate: the first is planning, the second is one bounded run. Planning every ticket up front is not required — you can also split off the next slice of the spec and re-run the pipeline when the frontier empties.

Recall before you read on

Without scrolling up: what is the frontier of a dependency graph, and why must a blocked ticket wait?

The frontier is the set of unfinished tickets whose dependencies are all finished — the only tickets safe to start now. A blocked ticket waits because its "depends on" tickets are not done yet; starting it would mean building on something that may still change.

Do it on your own app

Run the pipeline once on your real project. It takes one session and gives you a list you can reuse.

Your turn — about 10 minutes

You should get a numbered or bulleted list of small tickets, then a short frontier list — often one to three tickets. The agent works on exactly one ticket and stops. Its final report has one line per check. If a check says "failed" or "not verified", that is the system working, not failing.

Check yourself

Question 1 of 3

Your spec has ten tickets. Three have no unfinished dependencies. Which tickets form the frontier?

The frontier is defined by the graph, not by approval, file order, or taste: it is exactly the unfinished tickets whose dependencies are all done. Here that is the three.

Question 2 of 3

Ticket B lists ticket A under "depends on", and A is not finished. What should you do?

B is blocked until A is done, so the safe move is to start a ticket on the frontier instead. Starting B anyway builds on something that may change; deleting A just hides the dependency.

Question 3 of 3

Why does every ticket carry its own "done when" checks?

Small checks keep every ticket independently verifiable, so one big "done" never has to be trusted whole. The other options describe the opposite of what checks are for.
