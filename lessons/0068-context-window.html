The context window: what your agent remembers

An agent does not remember your project the way you remember a room you are standing in. It holds a working memory that fills up, gets summarized, and can lose early instructions. Knowing that explains a lot of strange behaviour on long builds.

Why this matters for shipping your app

Your mission is to take an idea to a live app by directing a coding agent. The longest part of that journey is one long working relationship: hours of building, fixing, and checking. When the agent suddenly "forgets" a rule you gave it an hour ago, or acts like a stranger to its own work, the cause is not laziness or a broken tool. It is the size of its working memory. Once you can picture that memory, the fix for each strange behaviour is small and boring, and you will stop losing hours to it.

The window

Everything the agent can currently pay attention to fits in one limited space, called the context window. Anthropic describes what it holds: Claude's context window holds your conversation history, file contents, command outputs, CLAUDE.md, auto memory, loaded skills, and system instructions.[1] Codex and omp work the same way; the three tools differ in what they show you about it, not in the idea.

So the window is not a diary. It is a desk. Your messages sit on it, and so does every file the agent read, every command result, and the tool's own instructions. As the loop from lesson 0.1 turns — gather, act, verify — each turn drops more paper on that desk. A long session is a desk filling up.

The window is measured in tokens, the small word-pieces models read. Lesson 5.2 covers tokens, cost, and caching.

Two consequences follow, and both are verifiable in the tools' own documentation. First, a brand-new session starts empty: Sessions are independent. Each new session starts with a fresh context window, so it has no memory of what you discussed yesterday.[1] Second, the window has a hard size, so something has to give when it fills.

Compaction: the summary swap

When the desk is nearly full, the agent does not stop. It compacts: it replaces older back-and-forth with a shorter summary and keeps working from that summary. Anthropic's best-practices page describes it plainly: To keep a long session going without you managing it, your conversation is compacted automatically before the context window fills.[2]

Compaction is genuinely useful and genuinely lossy. The same documentation warns: Claude compacts automatically, but instructions from early in the conversation can get lost.[1] The summary keeps the shape of the work — what was asked, what changed — but a detail you stated once, in passing, in the first ten minutes may not survive the rewrite.

A real pattern, anonymized

A user ran one session for about five hours, driving an agent through dozens of long test runs. Partway through, the tool quietly compacted the conversation. Shortly afterwards the agent drifted from a rule the user had set at the start of the session. The user did not argue with the agent about it; they restated the rule in one line, and the rest of the session followed it. The lesson they drew: a rule that matters gets repeated, or written somewhere that survives compaction.

Three defences, in increasing order of strength:

  • Watch the space. Claude Code has a command that shows what is using room: run /context to see what's using space.[1] omp shows context use right in its status bar.[5]
  • Compact on purpose, with a focus. Claude Code accepts a focus, for example /compact focus on the API changes, so the summary keeps what you name.[1] Codex documents the same idea: its /compact command will Summarize the visible chat to free tokens.[3]
  • Put rules where compaction cannot reach. Persistent instructions live in the project rules file (CLAUDE.md / AGENTS.md), which reloads regardless of what the summary kept. Anthropic says it directly: Put persistent rules in CLAUDE.md rather than relying on conversation history.[1] Lesson 1.12 teaches writing one.
Recall before you read on

Without scrolling up: what happens when the context window fills, and what is the one thing that gets lost first? Write it in your own words.

The conversation is compacted: older turns are replaced with a summary and the agent continues. What gets lost first is early detail — instructions stated once, early, that the summary did not keep. Persistent rules belong in the rules file, which survives.

Resume: yesterday's session comes back

Because each session is saved, quitting does not throw work away. Resuming reopens a saved session and continues it, history included. This matters for real builds: you will stop mid-task, sleep, and come back.

Anthropic documents both doors: Resuming a session with claude --continue or claude --resume reopens it under the same session ID and appends new messages to the existing conversation.[1] Inside a session, /resume opens a picker of saved sessions.

Codex ships a resume command: Continue a previous interactive session by ID or resume the most recent chat.[3] Inside the CLI, /resume picks a saved session.

omp records sessions as you work — its docs note There is no Save command — and omp -c continues the most recent session in that project, while omp -r opens a picker.[4] omp is documented only by its own authors, so treat surprises as questions for your teacher.

One caution pairs with this convenience. A resumed session returns with its full history, so it is also close to full. If the session ended because it was drifting, resuming reopens the drift along with the work. Lesson 5.8 covers why an agent should re-check facts against the files rather than trust its own memory of them.

Fork: two tries from the same past

Sometimes you stand at a decision point: the app could go two ways, and you want to try one without losing the other. A fork copies the conversation so far into a new session, and the original stays as it was.

From the same documentation: Forking with --fork-session or /branch copies the history into a new session ID, leaving the original unchanged.[1]

Codex documents codex fork as a way to Fork a previous interactive session into a new chat, preserving the original transcript.[3]

omp offers /fork, which Selects an earlier message and creates a separate session file from it, plus /branch for a second line inside the same session file.[6]

Beginners rarely need a fork in week one, but the idea is worth having: a fork is to a session what a branch is to a repository (lesson 3.5) — a safe parallel try. If a fork's experiment fails, the original is still there, untouched.

Handoff: moving to a clean desk

There is a third move. Instead of continuing a crowded session, you can ask the agent to write down the state of the work and start fresh from that note. This is a handoff.

omp has this built in: its /handoff command Generates a handoff document and commits it as a compaction entry in the same session.[6] But you do not need a built-in command. The behaviour works in any agent, as a prompt:

Before we continue, write a handoff note for a fresh session of this project.
Include: the goal in one line, what is done and checked, what is in progress,
decisions we made and why, any standing rules, and the next three steps.
Save it as HANDOFF.md in the project folder. Then stop and wait for me.

Then open a new session and start it with Read HANDOFF.md, then continue from the next step. The fresh session has a small, tidy desk with the important paper on it — often better than a crowded one, and it links to what you already know: the note lives in the project folder, next to the code, where the next agent (or a human teammate) will find it. Unit 9's lesson on handoff docs for long sessions builds on this pattern; git save points from Unit 3 are what make a mid-task restart safe in the first place.

Common trap

Do not treat the summary or the handoff note as the finished truth. Both are the agent's account of the work, not the work. The files on disk — checked with your own eyes and saved with git — remain the source of truth. Lesson 5.8 is about exactly this habit.

Weak: trust the long session

Give every rule in the chat's first message, run for hours, never commit, never repeat a rule. When behaviour drifts after an automatic summary, argue with the agent about what it was told.

Strong: work with the window

Keep standing rules in the rules file, commit at each finished step, glance at context use, compact with a focus before a big new phase, and hand off to a fresh session when the work changes shape.

Try it in your own agent

This works best in a practice project folder — anything small you made in Unit 0. Keep approval prompts on, as always.

Do it now
  1. In your project folder, start your agent and ask: "Read the main files in this project and summarize what it does."

    The agent reads a few files and answers. Those file contents now sit in the context window.

  2. Check how much of the window is used.

    Claude Code: type /context. omp: read the context-use part of the status bar. Codex: type /status for session information. Exact numbers vary; the point is seeing that the window is finite and measured.

  3. Compact on purpose, with a focus: /compact keep the project's purpose and its file layout.

    The agent replaces earlier turns with a short summary and confirms it. Nothing in your project folder changed — compaction rewrites the conversation, not your files.

  4. Test what survived: ask, "What is this project for, and which files matter most?"

    The answer should match your focused summary. Anything you did not name in the focus may be gone — that is the lossiness, demonstrated safely.

Tick each step as you finish it.

Check yourself

Question 1 of 3

Your agent has been building for an hour and its context window is nearly full. What happens?

Compaction replaces older turns with a summary and the work continues. The cost is detail: instructions stated early can be lost, which is why standing rules belong in the rules file.

Question 2 of 3

You want to try a second approach without losing the first. What does forking a session do?

A fork copies the history into a new session and leaves the original unchanged — like a git branch for a conversation. The original path stays available if the experiment fails.

Question 3 of 3

A long session ends mid-task. Tomorrow you want to continue that same work. Your best first move?

Every tool here saves sessions and can reopen them, history included. Resuming is the designed path; a handoff note is the alternative when the old session was too crowded or drifting.
