Screenshots as evidence

A picture is the closest you get to "I looked at it". But a file that ends in .png proves only that some program wrote a file. Here is how to tell a useful capture from a useless one, and why so many of them come back black.

About 15 minutesBuilds on: 2.7 Real versus simulatedWin: you can judge a screenshot before trusting it, and name why a capture failed

Why this matters for shipping your app

Lesson 2.7 ended with a rule: check the real thing in a real browser, not a simulation of it. When the agent does the checking, what it hands back is usually a picture — one standing in for your eyes. If it is black, stale, the wrong width, or the wrong window and nobody notices, the check was decoration.

You do not need image analysis. You need one habit: open the file and ask what it would look like if the work had gone wrong.

What makes a capture count as evidence

Lesson 2.2 gave the test for any artifact: would this look different if the work were wrong? A screenshot passes only when the answer is yes and you can see why.

Three things have to be settled before the picture means anything: which state it shows, which view it is, and whether it is fresh. A capture taken before the click describes a page that already worked. A full-page image of a long page says nothing about the first screen a visitor sees. A file with yesterday's timestamp says nothing about today's edit.

What the capture showsWhat it actually settles
The page after you click "Save"That this click produced this view, at that moment
The whole page, top to bottomLayout of a very tall screen; not what fits on a laptop
One panel, cropped tightThat panel only; nothing about what surrounds it
Your desktop, with other windowsNothing about the app, and a privacy problem

Automated browser tools make the difference explicit. Playwright's screenshot page offers a full-page image, as if you had a very tall screen and the page could fit it entirely, and separately notes that Sometimes it is useful to take a screenshot of a single element.[1] Those are two different claims. Say which one you want, or you get whichever the agent picked.

A real pattern, anonymized

A user left a long automated test of a desktop app running and came back to a report of forty screenshots captured across the run. Every one was a solid black rectangle. The machine had locked itself mid-run, and the capture tool had faithfully recorded an empty screen. The agent had not looked at a frame; it had counted files.

After the machine was unlocked, the same run produced normal frames, so the app had been fine. The agent added a guard: if a frame is one flat colour, stop and say so instead of collecting more. In a second project, the user kept typing in another window during a run; that run died twelve minutes in, with exit code zero and no frames. The likely cause was stray keys reaching the frontmost app — the report could not prove it.

Notice what failed: not the app, but the evidence pipeline — and the report described its output as if it described the app.

Recall before you read on

Without scrolling up: name the three things a screenshot must settle before it can count as evidence, and one reason a black frame is not proof that the app is broken.

It must settle which state is shown, which view (full page, one panel, which window width), and whether it is fresh. A black frame can come from the capture failing — a locked screen, a missing screen-recording permission, the wrong window — so it says nothing yet about the app's code.

Why a frame comes back black

Black has two opposite meanings, and the picture cannot tell you which.

The capture failed. The machine was locked, the screen slept, the tool lacked screen-recording permission, or it grabbed the wrong display. Anything an agent sees through your desktop needs that desktop visible and unlocked. Claude Code's computer-use page states the permission plainly: Screen Recording: lets Claude see what’s on your screen, granted once in macOS settings, sometimes needing a restart of the tool afterwards.[2] No permission, no picture — and a program that does not check will happily save the nothing it got.

The app really drew nothing. A blank window, a canvas that failed to initialise, text in the same colour as its background. That is a genuine bug, and a black frame is weak evidence of it: you cannot see whether the window or the capture is empty.

Separate them with a negative control: one capture of something you know works — the tool's own browser on a page you can see, or the desktop with a clock on it. If the control is also black, the pipeline is broken and the app is untested. If the control is fine and your page is black, you have a real bug. Lesson 2.11 takes this further.

Locked screens and focus stealing

When an agent drives your actual desktop, it needs your screen to itself. Claude Code hides other visible apps while it works, keeps only the terminal visible and excluded from screenshots, and lets you press Esc anywhere to abort.[2] It allows one session at a time on the computer, so a second session fails with an error naming the first.[2]

Two side effects matter for evidence. A locked screen stops everything: the session may keep running, and its captures turn black. And the app under test becomes the frontmost window, which receives your keystrokes. Type a message to a friend during a GUI run, and those characters can land in the app being tested, changing its state mid-run. That is what happened in the vignette.

The cheap rules

Before a GUI run: keep the machine unlocked and awake, and agree not to type until it ends. If you must keep working, ask for a capture path that never touches your desktop — a browser the agent drives itself. Claude Code's Chrome integration is one; its page shows the request Take a screenshot of the checkout page and save it to disk and notes that Claude reports the file path.[3] Codex's built-in browser can likewise open pages, click, type, inspect rendered state, take screenshots, and verify the result of its work in the page, but that browser lives in the ChatGPT desktop app, not the CLI.[4]

Ask for a capture you can check

A request that ends at "take a screenshot" gives you a file with no claim attached: ask for the file, the path, and one line saying what should be visible, then open it yourself.

Weak request

"Take a screenshot so I can see it worked."

Request with a check

"Save one frame of the results panel after the search runs, at 1280 px wide, to shots/after.png. Tell me the path and one line naming what should be visible. If the frame is blank or one flat colour, stop and say so."

The second version can fail visibly. That is the point. It also lets the agent catch its own bad capture before reporting success — the same move as lesson 2.2's "ask what you did not verify".

Run the flow once more and save three screenshots:
1. the page before the click,
2. the page after the click,
3. the same view at 1280 px wide.
Save them as shots/before.png, shots/after.png, shots/narrow.png.
Tell me each file path and one line saying what should be visible.
If any frame is blank, one flat colour, or identical to the previous one,
stop and tell me instead of continuing.
Keep approval prompts on.

Where each tool takes the picture

The mechanics differ, and so does the answer to "whose screen is being captured".

Two paths. For web pages, the Chrome integration captures inside the browser and can save files to disk.[3] For native apps, computer use drives your real desktop; it is a macOS research preview, off by default, needs a paid plan and the two macOS permissions, and downscales every capture: a Retina capture of 3456×2234 becomes roughly 1372×887.[2] Small on-screen text can therefore be unreadable even when the app is fine. Ask for a larger font, not a bigger monitor.

In the CLI, the agent does not drive your desktop; screenshots reach it as attachments you add, with codex -i shot.png "…" for one file.[5] Its own browser work happens in the ChatGPT desktop app, where Computer Use can capture the page it is driving.[4] The documentation is explicit that Browser isn't available in Codex CLI or the Codex IDE extension.[4]

Attach an image with Ctrl+V, by dragging it in, or by mentioning @path/to/image.png; a chip confirms the attachment.[6] Input is normalized and resized by default, and if the active model cannot read images, omp may ask a vision-capable model for a description instead — which means the picture you sent is no longer the thing being judged.[6] The pages read for this course describe attaching images, not controlling your desktop; if your build gains that, the same checks apply.

Two details apply everywhere. Saving a screenshot as a file beats pasting it into chat: a file has a path you can reopen tomorrow and compare. On macOS the manual shortcut is Shift+Command+4 for a region, saved as .png named "Screenshot" plus the date and time.[7] That name is weak evidence of freshness; check the date before you trust it.

Do it now, in your own project

You should end up with three files you can open, at least one of which looks different from the others. It is normal for a first attempt to produce a blank frame, a duplicate, or a capture at the wrong size; say which and ask again. If the agent answers that it cannot capture a screen at all, that is an honest answer — attach your own screenshot instead. Keep approval prompts on throughout.

Check yourself

Question 1 of 3

A report says twelve screenshots were captured. What should you check first?

Counting files proves only that files exist. A run can produce twelve black frames. Open one and see whether it shows the state you asked about.

Question 2 of 3

Every frame from an overnight run is solid black. What is the best first move?

A black frame has two causes: capture failed, or the app drew nothing. A control capture separates them before you change any code. In the vignette the screen had locked.

Question 3 of 3

An app the agent drives jumps to the front while you type elsewhere. Why does this matter?

The frontmost window receives keystrokes. Text meant for another window can change the tested app mid-run, which is why a run can end with no usable frames and no error.

Ask your teacher

A frame you cannot interpret is a good question. Try: "This screenshot is grey in the middle — is that an empty list or a failed capture?" or "How do I take a screenshot without including my other windows?"
