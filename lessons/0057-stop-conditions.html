Stop conditions: decide where the run ends

A definition of done says what finished looks like. A stop condition says where the work ends — and what the agent must not start next.

About 15 minutesBuilds on: 4.1 Definition of doneWin: you can close a run with one sentence the agent can check

Why this matters for shipping your app

Your app reaches the public through runs you can end. The failures that cost a beginner an evening are rarely wrong code in the feature they asked for. They are runs that kept going: the ticket was finished, and then the agent tidied a page nobody mentioned, renamed folders, and "improved" the part you already liked. Every extra step is another change to review and another chance to break what worked.

You are not trying to keep the agent busy. You are trying to reach a public URL with a small amount of work that you can check. That means the run needs an end, stated in advance, in words the agent can compare against what it sees.

The loop stops when the agent thinks it is done

No agent has a built-in sense of "this is enough". Anthropic's guidance for Claude Code says it plainly: Claude stops when the work looks done.[1] And when there is no check to run: If it has nothing to run that tells it whether the work actually is done, “looks done” is all it has to go on.[1]

Lesson 4.1 gave you acceptance criteria: a list of things that must be true before you call the result good. That list sharpens the agent's judgement, but it does not tell the agent to put the tools down. A result can meet every criterion and still be followed by ten minutes of unrequested polishing. Anthropic's essay on building agents notes that a task often terminates upon completion, but it’s also common to include stopping conditions (such as a maximum number of iterations) to maintain control.[3]

Two questions, not one

A stop condition answers a different question from acceptance criteria. Keep them apart and both get easier to write.

A stop condition has two halves, and beginners usually write only the first. The finish line names the state that ends the run. The boundary names the neighbouring work that is out of bounds. In one sentence: "Stop when the pull request is merged, and do not start the next ticket."

Codex's prompting guide builds the same idea into its four-part prompt, asking for a line called Done when: What should be true before the task is complete, such as tests passing, behavior changing, or a bug no longer reproducing?[2] That is the finish line. The boundary is the sentence you add after it.

Prefer an event to an adjective

"Merged" is a fact on a pull request page. "Polished" is an opinion, and the agent's opinion of its own work is the least reliable part of the run. The more your finish line names something a second person could look up, the less room the agent has to decide it has done enough.

Good finish lines are events you can already see in your project: a pull request showing as merged, the live URL returning the new page, a check command exiting successfully, a screenshot at phone width with no overlap. Each one has a yes or no answer that does not depend on the agent's mood. "Stop when the deploy is live" is a real boundary. "Stop when it feels finished" is an invitation to keep going.

The test for a stop condition

Could a stranger read it, look at the project, and say "yes, that happened" or "no, not yet"? If not, it is a wish, not a stop condition.

"And stop there" is doing real work

The second half is short and easy to skip, which is why it is the half that saves the most time. An agent that has only now finished a task is still in its loop. The next obvious improvement is right there, and helpfulness pushes it to take one more step. Naming that step as forbidden costs five words and prevents a second review.

A real pattern, anonymized

A user handed an agent a roadmap of roughly eighty small tasks with a one-line prompt, plus the sentence "stop work when items 10, 11 and 88 are merged and closed". Three helpers worked in parallel; the run ended when those three pull requests were merged, and not after. Later, asking for cleanup, the same user wrote: preserve the evidence, archive it, delete the merged branches, "and stop there". The agent produced a checksum-verified archive before deleting anything, then stopped instead of continuing into the next piece of work.

Notice what the sentence did not do. It did not explain the whole plan, and it did not name every file. It named the last useful action and drew a line immediately after it. That is enough, because the agent can compare its next intended step against a sentence it was given.

Same task, two endings

No finish line, no boundary

"Make the gallery page nicer and keep improving it until it feels right."

Every word is a judgement call. There is no state to reach and no neighbouring work to avoid, so "one more improvement" is always permitted.

One event, one fence

"Change only the caption layout. Stop when the live URL shows the new captions with no overlap at phone width. Do not resize the images or touch the data files."

The finish line is visible in a browser. The fence names the two things most likely to get "improved" along the way. You can check both in under a minute.

Where to put it

Put the stop condition at the end of the prompt, after the request, so it is the last instruction the agent reads before it starts. If you are already mid-run, the same sentence works as a steering message; lesson 1.10 covers how each agent accepts one while it works. What you should not do is bury it in the middle of a long paragraph of context, where it reads as background rather than as a rule.

There is a second, blunter version for the moment the agent sails past the line: "You have reached the stop condition. Stop now and report what is done." It is not a punishment and it is not a new task. It is the boundary being repeated in the present tense, which is often all a run needs.

Task: [the one change you want, in one or two sentences].

Done when: [the observable state — page live at the URL, check
command passing, screenshot at phone width with no overlap].

Stop when that is true. Then stop: do not start the next task,
do not refactor neighbouring files, and do not "improve" anything
I did not ask about.

If you cannot reach the done state, stop anyway and tell me what
blocked it, what you tried, and what you would need from me.

The last paragraph matters as much as the fence. Without it, "stop when X" can turn into "try anything until X", which is how a small change becomes a rewrite. Lesson 4.4 adds caps on time and attempts for the runs where even a clear finish line is not enough.

Recall before you read on

Without scrolling up: what are the two halves of a stop condition, and why is an event like "merged" stronger than a word like "polished"? Write it in your own words.

A finish line (the state that ends the run) and a boundary (the neighbouring work that must not start). An event can be checked by someone else against the project; "polished" is a judgement, and the agent is judging its own work.

Making the condition stick

A sentence in the prompt is enough for most short runs. When a run is long, or you will not be watching, each agent offers a way to hold a condition beyond the current turn. These are optional; the plain sentence works everywhere, including versions released after this course.

Inside a session, /goal sets a condition that a separate model checks against the conversation after every turn, and Claude keeps going until the condition is met.[1] A separate check means the agent is not the only judge of whether it has arrived. For unattended runs, the same page lists a Stop hook, which sends the agent back to work while a check command keeps failing.[1]

/goal <objective> gives Codex a persistent target to track while a larger task runs; /goal alone shows it, and /goal pause, /goal resume, /goal clear manage it.[4] The objective is text, so write it as the same event you would put in the prompt, not as a mood.

omp's documentation names Goal mode as one of its specialised workflows and warns that Goal, Vibe, Prewalk, Loop, Fast, and related controls are specialized workflows — start with ordinary messages and choose them deliberately.[5] omp has only single-vendor documentation, so treat anything surprising there as something to check with your teacher rather than a promise.

Lesson 5.5 covers persistent goals and their failure modes in detail. This lesson only needs the sentence you write before the run.
Do it now: close one small run

You should see the agent restate the condition in its own words, then stop at the named event rather than drifting into a second task. The report should name the evidence for the finish line — the URL you can open, the command and its output, the screenshot. If it repeats the condition but still continues, your finish line was probably an adjective in disguise; replace it with an event and run the same prompt again.

Check yourself

Question 1 of 3

Which line is a stop condition rather than an acceptance criterion?

Only this line names a state that ends the run. The others describe what must be true of the result, which is the job of acceptance criteria.

Question 2 of 3

The agent finished the ticket, then began restyling a page you never mentioned. What was missing?

The run had a job but no boundary. A finish line plus "do not start the next task" is what keeps a completed ticket from turning into extra work.

Question 3 of 3

Which finish line can a stranger check against your project?

Merge status is visible on the pull request page to anyone. The other lines depend on taste, consensus, or the agent's own opinion of its work.

Ask your teacher

Not sure whether your sentence is an event or an adjective? Ask the agent that gave you this course: "Here is my stop condition. Could a stranger check it, and what would they look at?" Then ask it to rewrite the sentence as an event if the answer is no.
