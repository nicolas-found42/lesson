Anatomy of a web page

Every page you ship is a small set of text files. One holds the words, one holds the look, one holds the behaviour. Learn to tell them apart and you can point your agent at the right one.

About 15 minutesBuilds on: 0.3 Your project is a folderWin: you can name which file does which job

Why this matters for shipping your app

Sooner or later a page will look wrong: a heading in the wrong colour, a button that does nothing, a picture that refuses to appear. If you cannot tell which file owns which job, the only thing you can say is "the page is broken". That sends your agent hunting through the whole folder. If you can say "the words are right but the colours are wrong", you have already halved the search, and you can check the result yourself.

Three languages, three jobs

A web page is built from three kinds of text file. They are usually described as three languages, though only one of them is a programming language in the usual sense.

  • HTML carries the structure and the content: headings, paragraphs, lists, pictures, links, buttons. MDN's glossary calls it a descriptive language that specifies webpage structure.[1] "Descriptive" is the key word. You are labelling what each piece of text is, not telling the browser to compute anything.
  • CSS carries the look: colours, fonts, spacing, size, position. MDN defines it as a declarative language that controls how webpages look in the browser.[2] The same HTML can look like a newspaper, a shop or a game menu, purely by changing CSS.
  • JavaScript carries the behaviour: what happens when someone clicks, types or waits. MDN describes it as a programming language used most often for dynamic client-side scripts on webpages.[3] It can also change the page while you look at it.
MDN calls HTML, CSS and JavaScript the three core web technologies, and notes that CSS usually styles HTML.[2] That is the relationship to hold on to: HTML first, the other two attached to it.

A useful picture: HTML is the skeleton and the words, CSS is the skin and clothing, JavaScript is the muscles that move things. A page can exist with only HTML. It can look finished with HTML and CSS. It only reacts to you once JavaScript is there.

Inside an HTML file, content sits between tags. MDN states the pattern: Elements are surrounded by matching opening and closing tags.[1] A paragraph opens with <p> and closes with </p>. Some tags also carry settings called attributes — You can extend HTML tags with attributes — the way a link's href carries the address it points to.[1] When your agent edits a page, it is moving these tags around.

A CSS file works in rules. Each rule pairs a selector, which picks elements, with the properties that say how those elements should look. MDN calls a rule a set of properties associated with a selector.[2] Because a selector can match many elements at once, one edit in this file can restyle every page that links to it.

The browser assembles the page from named files

The page file also has two halves. MDN's tutorial describes the head as a container for all the stuff you want to include on the HTML page that isn't the content you are showing to your page's viewers, and the body as the part that contains all the content that you want to show to web users when they visit your page.[4] That split explains why the links to CSS and JavaScript belong in the head: they describe the page rather than display anything in it.

You do not paste the CSS and JavaScript into every page by hand. The HTML file names them, and the browser fetches each one and applies it. MDN's beginner tutorial puts the CSS link inside the page's head, the part of the file that describes the page rather than displaying it.[5] For JavaScript, MDN explains that the script element applies the JavaScript to the page so it can affect the HTML.[6]

Those names are paths, and paths are where beginners get hurt. MDN's file-structure guide gives the rule plainly: To link to a target file in the same folder as the invoking HTML file, just use the filename.[7] If your page asks for style.css and the file is really called styles/style.css, the browser does not stop and complain loudly. It draws the page without that styling.

A real pattern, anonymized

A user published a small gallery. On their own machine it had a dark background, tidy cards and working buttons. At the public address, the same page appeared as plain black text on white, and the buttons did nothing. The HTML was fine. It asked for its stylesheet and its script by paths that only worked on that person's computer, so at the public address those paths pointed nowhere. The files had travelled; the directions to them had not. The agent repointed both links relative to the page, and the gallery came back.

This is the most common "it worked yesterday" surprise on the way to a live site, and it has nothing to do with the quality of the design. A page is a bundle of files that must find each other.

A worked example: one invitation, three files

Here is a complete little page in a folder called invite. The front page holds the words, a heading and a button.

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Saturday lunch</title>
  <link rel="stylesheet" href="style.css">
</head>
<body>
  <h1>Saturday lunch</h1>
  <p id="count">Bringing: 0</p>
  <button id="add">Count me in</button>
  <script src="script.js"></script>
</body>
</html>

The head names style.css. That file decides how the heading and button look:

h1 { color: darkred; }
button { font-size: 1.2rem; padding: 0.6rem 1rem; }

The script at the end of the body names script.js. That file makes the button count:

let n = 0;
const label = document.getElementById("count");
document.getElementById("add").addEventListener("click", () => {
  n = n + 1;
  label.textContent = "Bringing: " + n;
});
What you seeWhich file to open
Wrong words, missing heading, a link going nowhereindex.html
Right words, ugly colours, cramped spacing, tiny textstyle.css
A button that does nothing, a counter stuck at zeroscript.js

Notice what is not in the table: taste. All three files can be correct and the page still unattractive. That is a design decision, not a bug, and it is yours to make.

Recall before you read on

Close your eyes. Name the three languages, one job each, and say which file the browser reads first. Then say what happens if style.css is missing.

HTML gives structure and content, CSS gives appearance, JavaScript gives behaviour. The browser reads the HTML file first, then fetches the files it names. If the stylesheet cannot be found, the page still appears, but unstyled.

Do it in your own agent

You should get a short file list naming the HTML page and any stylesheet or script it uses, not a tour of the whole folder. The colour change should be reported as an edit to the CSS file (or to a style block inside the HTML), with a line number. If the agent instead rewrote the whole page, ask it to restore the file and make the one-line change. That answer tells you whether it understands the anatomy too.

Check yourself

Question 1 of 3

The words on your page are correct, but every colour is wrong. Which file most likely needs the edit?

Colours and spacing belong to CSS. Changing HTML would change the words or structure, and JavaScript would change behaviour.

Question 2 of 3

Which sentence best describes what the HTML file does for a page?

HTML labels content: this is a heading, this is a paragraph, this is a button. CSS handles appearance and JavaScript handles behaviour.

Question 3 of 3

A button appears correctly but nothing happens when you click it. Where do you look first?

The button is on screen, so HTML and CSS did their jobs. Reacting to a click is behaviour, which is JavaScript's job, though a broken script path can also be the cause.
