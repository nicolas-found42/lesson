Never print, never commit

A secret key that appears on your screen or in your project's history is a key a stranger can use. This lesson gives you two habits — never print a secret, never commit one — and one repair move: rotate a leaked key immediately.

Why this matters for shipping your app

By now your app may talk to a paid service: a map provider, an image generator, a database. Each of those hands you a secret — a long password that proves to the service that the requests come from your account. Lesson 8.1 taught you what secrets are and why they do not belong in code. This lesson is about the two ways secrets escape anyway, both of which happen quietly while an agent works: the secret gets printed into output you and the agent can see, or it gets committed into your project's git history. A stranger who finds a leaked key does not hack anything; they log in as you, on your account, on your credit card. Rotating — replacing the key with a new one so the old one stops working — is the only real fix.

Rule one: never print a secret

"Printing" means making text appear: in your terminal, in a log file, or in your agent's transcript. The danger is that these are not fleeting. Agent sessions are saved. When you resume yesterday's session — Claude Code with claude -c, which its quickstart describes as Continue most recent conversation in current directory[3], or omp with omp -c[4] — everything the session printed is still there. omp's own documentation is blunt about the storage: The local database is not encrypted at rest.[5] Anything printed once has been written to disk.

This matters extra with an agent, because the agent reads everything in the session to decide what to do next. A secret printed in step 3 is sitting in the agent's attention in step 40, and may be copied into a summary, a commit message, or a report later without anyone noticing.

A real pattern, anonymized

A user was setting up a sign-in service for their app, with the agent driving the setup commands. One command printed the new key's value straight into the output. Later in the same day, a screenshot the agent took of a setup page caught another secret in plain view. The user treated both as leaked: every exposed key was replaced with a fresh one, and the setup steps were redone so that key values moved through files and the clipboard instead of ever appearing as text. Nothing bad happened — because the response was fast and the keys were rotated.

The fix in that story was not clever. It was: assume anything printed is public, and swap the key.

Rule two: never commit a secret

Git remembers every committed version of every file, forever. The Pro Git book explains the model: Git thinks of its data more like a series of snapshots of a miniature filesystem.[6] Each commit is one full snapshot. Deleting the file in a later commit does not reach back and edit the earlier snapshot; it only changes the newest one.

You can prove this to yourself in one minute (you will, below). The short version: put a file with a fake key in a git repository and commit it. Delete the file and commit again. Ask git to show the file from the older commit — and there it is, intact. The delete never touched it.

Once a secret is committed and pushed to a remote like GitHub, it is no longer only on your machine. Anyone who cloned or forks the repository has the whole history, secrets included. GitHub tries to help at the front door: its push protection feature is designed to prevent hardcoded credentials, such as secrets or tokens, from ever being pushed to your repository[2] — but it only recognizes common secret formats, and it does not exist everywhere you might push. The habit has to be yours.

If a key leaks, rotate first

So the file slipped through: it was printed, or committed, or both. Here is the order of operations, and the order matters.

  1. Rotate the key at the provider. Sign in to the service that issued the key, revoke the old one, and create a new one. GitHub's own guidance puts this first: as a first step you need to revoke and/or rotate that secret[1] — because once that is done, it can no longer be used for access, and that may be sufficient to solve your problem.[1]
  2. Only then clean up the project. Remove the secret from the current files (lesson 8.2's .env pattern), check .gitignore covers it (lesson 3.3), and tell your agent what happened so it can check for other copies.

Why rotate first? Because scrubbing a secret out of git history is genuinely hard — GitHub describes it as something you can do if you can carefully coordinate with everyone who has cloned it and you are willing to manage the side effects[1] — while rotation takes two minutes and works even if copies already exist somewhere you will never find. A key that no longer opens anything is harmless, wherever it sits.

Telling your agent, without leaking again

When you ask the agent to help with a leak, do not paste the secret into the prompt — that prints it again, into a brand-new transcript. Name the file instead:

The file keys.txt contains a leaked API key. Do not display, print,
or echo its contents. Steps:
1. Confirm the file exists and note only its size and date.
2. Remove the file from the working tree.
3. Remind me which provider console I need to visit to revoke the key.
4. Check .gitignore covers it, and tell me whether it was ever committed.

Notice what the agent is and is not asked to do. It inspects and cleans up; the revocation itself happens in the provider's web console, which is a step you do as the human (lesson 5.10 covers human-only steps like this).

Recall before you read on

You committed a key by mistake, deleted the file, and committed the deletion. A teammate says "it's fine now." What two things are wrong with that, and what is the correct first action?

Wrong, twice: the key still exists in the earlier commit's snapshot (git history keeps every version), and if it was pushed, copies exist beyond your machine. The first action is to rotate the key at the provider, so the leaked value stops working. Cleaning the files comes second.

See the history trap yourself

Do it: prove a deleted file survives in history

You will build a tiny throwaway git repository, leak a fake key into it, delete the file, and then watch git hand the "deleted" secret right back. Nothing here touches your real project or any remote.

In your terminal, one line at a time:

mkdir history-demo && cd history-demo
git init
echo "API_KEY=PASTE_YOUR_KEY_HERE" > .env
git add .env
git commit -m "add config"
rm .env
git commit -am "remove key"
git show HEAD~1:.env

The last command prints API_KEY=PASTE_YOUR_KEY_HERE — the file you deleted one commit ago, served straight out of history. Run git log --oneline and you will see both commits listed. The deletion changed the newest snapshot only.

When you are done, cd out and delete the history-demo folder. Then check your real project: if your keys live in a .env file, ask your agent "is .env covered by .gitignore, and has it ever been committed in this repo?" — a safe question, because it asks for a yes/no, not for the contents.

Check yourself

Question 1 of 3

A teammate committed and pushed a real API key by accident. What should happen first?

Rotation comes first because a revoked key is useless to an attacker even while copies still exist. History rewriting is slow, needs coordination with everyone who cloned the repo, and GitHub's guidance says revoking may be sufficient on its own.

Question 2 of 3

You delete a key file and commit the deletion. Where can the key still be found?

Git stores every commit as a full snapshot. The deletion created a new snapshot without the file; the older snapshot is untouched and still contains the key — you proved this with git show HEAD~1:.env.

Question 3 of 3

Why is "never print a secret" a rule even on your own machine?

Agent sessions are saved and resumable, and their storage is not necessarily encrypted. Once a secret is printed it lives on disk and can resurface in summaries, reports, or commits later.
