When two changes collide

Sooner or later two branches change the same line, and Git stops and asks you to choose. That stop is not a failure. It is the moment the tool refuses to guess about your app.

Why this matters for shipping your app

Your app is built from main. Your work happens on a branch, and main keeps moving while you work, because you or your agent merged something else. When the two lines of work touch the same part of the same file, Git cannot combine them on its own, and the pull request that would ship your change is blocked.

GitHub says it plainly: If your pull request has a merge conflict between the compare branch and base branch, the Merge pull request button is deactivated until the conflicts are resolved.[1] Nothing is broken and nothing is lost. But the merge button is now a locked door, and only a decision you make opens it.

What a conflict actually is

Most of the time Git merges by itself: different files, or different lines of one file, combine without help. A conflict is the remaining case. GitHub's reference names the usual causes: Merge conflicts often happen when people make different changes to the same line of the same file, or when one person edits a file and another person deletes the same file.[1]

When that happens, Git stops halfway and writes both versions into the file, fenced by markers. The git manual describes the layout: The part before the ======= is typically your side, and the part afterwards is typically their side.[2] "Your side" means the branch you are on right now. The other label names whatever you are bringing in.

<<<<<<< HEAD
<p>Contact: support@example.com</p>
=======
<p>Contact: cook@example.com</p>
>>>>>>> new-contact

Three markers, two blocks. Between <<<<<<< HEAD and ======= is what your current branch has; between ======= and >>>>>>> new-contact is what the other branch has. The names are labels for humans. Git does not care what you leave between the markers, only that they are gone when you finish.

Recall before you read on

Without scrolling up: in a conflict block, which side is HEAD, and what does the word after the last marker name?

HEAD is the branch you have checked out — your side. The word after >>>>>>> labels the other side, usually the branch or commit you are merging, rebasing or cherry-picking into your branch.

Resolving: a decision, then two commands

Resolving means choosing the final text: your side, their side, or a blend neither branch contained. The git manual gives the procedure: Edit the files into shape and git add them to the index. Use git commit or git merge --continue to seal the deal.[2] Delete the three marker lines as part of the edit. A file with markers still in it is not resolved; it is a file with stray arrows that will reach your live site.

Staging is how you tell Git "this file is settled". That is the same git add you met in 3.4, doing a different job here. If you change your mind entirely, there is a clean exit: git merge --abort will Abort the current conflict resolution process, and try to reconstruct the pre-merge state.[2] Backing out is allowed and cheap. Starting over with a clearer head beats forcing a resolution you do not believe.

tool$ git merge new-contact
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.
tool$ git status
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)
Unmerged paths:
  both modified:   index.html
youKeep the support address; it is the one customers already write to.
tool$ git add index.html
$ git commit -m "Merge new-contact, keep support address"
Run in a throwaway repository on this machine. The status output is the real text from git 2.56.0.

The status output names the file, its state, and the two ways forward. If you read one block of Git output, read this one. GitHub's walkthrough adds the consequence a beginner feels first: You cannot push the merged result until you resolve the conflict and commit the resolution.[6]

Rebase: replaying your commits somewhere else

Merging ties two histories together and adds a merge commit. Rebase does something different, and Pro Git describes it exactly: you can take all the changes that were committed on one branch and replay them on a different branch.[3] Your own git agrees: Transplant a series of commits onto a different starting point.[4]

The end result can be identical. Pro Git is careful: There is no difference in the end product of the integration, but rebasing makes for a cleaner history.[3] Only the shape changes: instead of a fork that rejoins, you get one line where your work appears to have happened after everything on main.

That rewriting has a price, and Pro Git states the rule in one line: Do not rebase commits that exist outside your repository and that people may have based work on.[3] Rebase is abandoning existing commits and creating new ones that are similar but different[3], so anyone holding the old ones holds something that no longer exists upstream. The practical rule: rebase your own branch when you are its only user, and never a branch a teammate works from.

A rebase can hit conflicts too, one commit at a time. The loop is the merge loop with different verbs: fix the file, git add it, then git rebase --continue. Your own help page lists the other two exits: --skip drops the commit that would not apply, and --abort puts the branch back where it started[4].

The rebase trap for beginners

If the branch was already pushed, rebasing means the pushed copy no longer matches, and updating it requires a force push that overwrites history. Ask your agent, before it starts, "will this need a force push?" If the answer is yes and you do not understand why, ask for the merge instead. Lesson 3.11 covers recovering from a rewrite that went wrong.

Cherry-pick: one commit, copied elsewhere

Cherry-pick is the narrow tool. The manual defines it as: Given one or more existing commits, apply the change each one introduces, recording a new commit for each.[5] You point at one commit and say "that change, here".

The everyday beginner case is a fix that landed on the wrong branch. Your agent fixed a broken link on a feature branch, and you need that fix on main now, without the rest of the feature. Cherry-pick copies the change and leaves the original commit where it was. It is not a move and it does not clean up the branch you took it from; if the fix should not stay there, that is a separate decision.

The copy is a new commit with a new identity, so doing the same change twice leaves both copies in the history. Use it for one deliberate commit, not to move a whole branch; merge and rebase are for that. Conflicts work as before, with --continue, --skip and --abort.

A real pattern, anonymized

A user had a pull request that could no longer merge, because main had moved underneath it. Their instruction was one sentence: rebase the branch onto main, resolve the conflicts, run the full check suite quietly, and push it ready for review. The agent hit four conflicts and resolved every one by keeping both sides. The checks passed, the pull request went green, and the agent reported which commit it had dropped along the way. That last sentence is what made the run trustworthy. "Keep both" is a guess about intent, and it is right only when both changes were meant to coexist.

What to ask your agent

An agent will resolve a conflict for you, often correctly. The risk is that it resolves by pattern — keep both, take the newer one — when the right answer depends on what your app is supposed to do. So ask for the decision, not only the result.

Hands off the wheel

"Fix the conflicts and merge it."

You will learn what happened only if something breaks later.

Keeps the decision

"Show me each conflicted block, say what each side was trying to do, and recommend a resolution. Wait for my answer before you stage anything."

The agent does the reading; you keep the intent.

Make two questions routine. "Did you check that the app still runs after resolving?" catches a resolution that is syntactically fine and behaviourally wrong. "Did anything get dropped?" catches a --skip or a lost commit, the quiet loss that shows up as a missing feature a week later. The habit from 2.2 applies: "resolved" is a claim until the file and the running app agree.

Do it: make a conflict on purpose, then back out

Practice somewhere harmless: a throwaway repository, a forced conflict, and an undo, with the agent's approval prompts left on.

In a new folder called conflict-practice, create a tiny git repository with one HTML file that has a contact line.
Make two branches that each change that same line differently, then merge them so the merge stops with a conflict.
Do not resolve it and do not touch any other folder.
Show me the file with the conflict markers and explain which side is which.
Your turn

The first merge exits with a conflict message naming one file. The file holds a <<<<<<< block, a ======= line and a >>>>>>> line with a branch name. After resolving, git add plus git commit (or git merge --continue) creates a commit with two parents, visible in the graph as a fork that rejoins. After git merge --abort, status reports a clean tree and the log is back to what it was before the merge.

Check yourself

Question 1 of 3

Inside a conflicted file, what does the block under <<<<<<< HEAD contain?

HEAD is the branch you are on, so the first block is your side. The block after ======= is the side being brought in, labelled after the final marker.

Question 2 of 3

A branch you already pushed is shared with a teammate. What is the safe way to bring new main changes into it?

Rebasing rewrites commits, so a shared branch would need a force push that discards the copy your teammate may be building on. Merging adds commits and is safe to push.

Question 3 of 3

A fix landed on the wrong branch. What does git cherry-pick do?

Cherry-pick applies the change that one commit introduced and records a new commit on your branch. The original stays where it was, so nothing is moved or cleaned up.

Ask your teacher

Confused by a conflict in your own project? Ask the agent: "Read this conflicted file and tell me what each side was trying to do, without changing anything." Then decide. If you cannot explain the resolution in one sentence, you are not ready to stage it.
