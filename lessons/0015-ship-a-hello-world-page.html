Ship a hello world page

A file in a folder and a page a stranger can open are separated by five named states. This milestone walks all five once, with a page too small to distract you.

About 20 minutes of reading, plus the ship itselfBuilds on: 0.7 First prompt to a page · 3.1 Why save points exist · 3.6 Remote, origin, push · 6.3 GitHub Pages · 6.6 Deploy, merge, liveWin: a public link to a page that is yours

Why this milestone exists

Everything after this point assumes you have felt the whole path once: a file you can see, a commit you can name, a push that reached GitHub, a publish that finished, and a public address that answered. Read about those steps and they blur together. Do them once with a page that says almost nothing, and they stop blurring.

The page is deliberately trivial. A heading and one sentence are enough. Its job is to be a vehicle, not a portfolio. Keep the ambition for the capstone; here you are learning the road.

This is also your first taste of the habit the rest of the course is built on. The agent will say it is done. You will open the link yourself, in a window that has never seen your project, and check.

Five states, five names

You have met each of these words in an earlier lesson. The milestone adds no new machinery. What it adds is the ability to say which state you are in, which is what tells you what to do next.

StateWhat is trueHow you know
1. On your screenA local server serves the file to your own browser. Nobody else can reach it.localhost plus a port number appears in the address bar.
2. CommittedA snapshot exists in the project's history on your machine.git log --oneline -1 shows one line with your message.
3. PushedThat snapshot also exists on GitHub, the remote.The repository page shows your commit; git status says the branch is up to date.
4. PublishedGitHub Pages has taken the files from the repository and built the site it will serve.The repository's Pages settings show a finished build, not "queued" or "building".
5. LiveA stranger's browser at the public address receives your page.You opened the address yourself, logged out or in a private window.

The vocabulary is not decoration. Pro Git describes a commit as a snapshot of your project that you can revert to or compare to later.[6] A push is the step that puts that snapshot on a server: The command for this is simple: git push <remote> <branch>.[5] Publishing is separate again. GitHub Pages takes HTML, CSS, and JavaScript files straight from a repository on GitHub and serves them, and GitHub's own description says whenever changes are pushed to the source branch, the changes in the source folder will be published.[1][2]

A static site is the only kind GitHub Pages hosts. Lesson 6.1 explains why that is enough for most first projects.

Notice what the fifth state adds. The first four are all things that exist somewhere in a system. The fifth is an observation. Nothing in your repository can prove it. Only a request to the public address can.

A run, end to end

Here is the shape of a real session, rewritten without names or project details. The person had a folder, a working local page, and a GitHub account. They had never published anything.

youI want to ship a one-page hello world site to a public address. A friend will open the link on a phone and will not sign up for anything. Set it up, publish it, and give me the URL. Do not change my approval settings.
toolread the project folder; write index.html with a heading and one sentence
toolstart a local server; open localhost in a browser; confirm the heading renders
toolgit init, add, commit — "add hello world page"
toolcreate a public repository, add it as the remote, push
toolturn on Pages for the main branch; wait for the build
toolopen the public URL → 404; the entry file was not at the top of the publishing source
toolmove the page to the top level; commit; push; wait; open the URL again
toolpage loads; write the link at the top of the README; commit; push
agentLive at the URL below. The first attempt returned a 404 because the page was one folder too deep. I checked the address in a browser before writing it down.
Anonymized from a real first-publish session. The 404 is the common one, and it is a naming or placement problem, not a broken site.

Three things in that run are the whole milestone. The commit happened before the push. The push happened before the publish. And the publish was not believed until an address answered. Everything else was typing.

The prompt that gets you there

You have written goal-first prompts before. This one adds the states as the definition of done, so the agent knows the job is not finished at "file created".

I want to ship a one-page hello world site to a public web address.

The page should show a heading with my name and one sentence about
what I am learning.

The audience is a friend I will send the link to. They will open it
on a phone and will not sign up for anything.

Please:
1. Create the page and check it on localhost.
2. Commit it with a clear message.
3. Create a public GitHub repository for this folder and push.
4. Turn on GitHub Pages for the main branch.
5. Give me the public URL, and put the same link at the top of the
   README.

Do not change my approval settings. Ask me before creating anything
on GitHub.

Done when: I can open the URL in a private window and see the page.

If your agent asks which host to use, or whether the repository should be public, answer in one line and let it proceed. Those are method questions, and method is its side of the table.

Recall before you read on

Without scrolling up: name the five states in order, and say which one you have not reached yet. Be honest about the fifth.

On your screen (localhost), committed (a snapshot on your machine), pushed (the snapshot is on GitHub), published (Pages has built the site), live (you opened the public address and saw it). Most beginners stop at the first or second and assume the rest.

Do it

Use your own folder and your own agent. Keep approval prompts on: every step below either edits files or creates something on GitHub, and you want to see each one before it happens.

Ship the page

A page at https://YOUR_USERNAME.github.io/my-app/ showing your heading. A clean git status. A README whose first line is the link. The build can take a few minutes; GitHub's quickstart warns of up to 10 minutes after a push.[3] If the URL answers with a 404, read the next section before changing anything.

What goes wrong, and which state it means

Almost every first-publish problem is one of four, and each one tells you where you are. The table is worth keeping beside you for the rest of the course.

What you seeState you are probably inWhat to check
A 404 at the public address4, attemptedPages will look for an index.html file as the entry file for your site, and it must sit at the top of the publishing source. The name is case-sensitive.[4]
The old text after a push4, in progressThe build has not finished, or your browser cached the old page. Reload in a private window.
The repository page has your file, the URL does not3Pages is off, or pointed at another branch or folder.
Everything "worked", a friend sees nothing5, unverifiedYou checked a local address, not the public one, or your repository is private on a free plan: Pages is available in public repositories with GitHub Free.[1]
One rule for this milestone

Do not accept "it should be live" as the answer. The only evidence is the public address opening in a window that is not logged in to your account. Ask the agent for the URL, then use it.

Put the states in order

Click them in the order they happen. A wrong click tells you which step you placed too early.

Order the five states

Starting and resuming the same job

The five states are the same in all three agents, because the agent runs the same git and gh commands in your terminal. What differs is how you get back into the session if you close the window halfway through.

Start with claude in the folder. To pick the session back up, claude -c will Continue most recent conversation in current directory.[7] Recent versions start in auto mode, which does not ask before every action; lesson 0.6 covers how to move to a mode that asks, and why a beginner should.

Start with codex in the folder. codex resume will Continue a previous interactive session by ID or resume the most recent chat.[8] Keep the approval setting where lesson 0.6 left it; the publishing steps should stop and ask you.

Start with omp in the folder. omp -c continues this terminal's last session in the current directory.[9] omp's built-in default approval mode is yolo, which prompts for nothing; lesson 0.6 explains how to move to a mode that asks before you run this milestone.

If you get stuck between states, the useful question is not "is it done?" but "which state am I in, and what is the next one?" That question also works on the agent: "Tell me which of these five states we are in: local, committed, pushed, published, live."

Check yourself

Question 1 of 3

Your page opens at localhost:8000. Which state is that?

localhost means this machine. A local server proves the file renders, not that anyone else can reach it. The next four states are about the copy that leaves your laptop.

Question 2 of 3

The agent writes "the site is live". What is the best evidence?

Only the public address answering is evidence of the fifth state. A green build or a confident sentence can both be true while the URL still serves a 404 or an older page.

Question 3 of 3

You pushed a fix ten seconds ago and the site is unchanged. Most likely?

Publishing lags the push; GitHub's quickstart warns of up to ten minutes. Wait, reload in a private window, and only then look for a real fault such as the entry file's name or location.
