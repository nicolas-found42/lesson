Ask what a word means

Half of a beginner's trouble with an agent is vocabulary. One question, asked at the moment the word appears, turns a paragraph you skim into a decision you can check.

Why this matters for shipping your app

You will judge the agent's work mostly by reading what it says. Every word you do not know is a place where your only option is to nod and hope. The app may still ship, but you stop being able to say why it works, what to change when a friend reports a problem, or whether the next step is safe. Asking costs one turn. Not asking costs your ability to direct the work.

The habit: ask at the word, not after the task

All three agents in this course explain themselves gladly. Anthropic's guide for people new to the terminal says plainly that Claude can explain things, help you learn, or plan out a project[2], and its own documentation is blunt about it: Claude Code can teach you how to use it.[1] Codex's CLI page makes the same offer in its first-task instructions: ask Codex to explain the project, make a focused change, or help debug an issue.[3] Nothing about asking is unusual, and nothing is broken by it.

What matters is when. The word shows up in the middle of a reply, while the agent still holds the task in mind. That is the best moment to ask: the agent can point at the exact line it wrote, and the answer arrives before ten more decisions are built on top of it. Ask at the end of the session and you will get a tidy definition that has lost its connection to your app.

A real pattern, anonymized

A user was partway through tightening a project's automatic code checks when the agent mentioned a data structure by name. The user typed a four-word question about it. The agent answered in three lines, then carried on with the same task where it had left off. Later in the same session the user hit a numbered question they did not follow, typed "explain 14", and got the same treatment: a short answer, then the work resumed.

Notice what did not happen. No new session, no lost work, no restart, no change of plan. Two questions, two short answers, one task that kept moving.

Ask so the answer is usable

A vague "what does that mean?" leaves the agent guessing which word you mean, and how much you already know. Three details fix both problems: name the exact word, say what you are not, and ask for one example from your own project.

I don't know the word "TERM" from your last message.

Explain it in two sentences, in plain words, as if I were not a programmer.
Then give one example of where it appears in my project, and what would
change if it were wrong.

The quotation marks are doing real work. Without them the agent may explain a neighbouring word it thinks you must mean. The phrase as if I were not a programmer is not an apology; it is the context that tells the agent which of its several vocabularies to use. Anthropic's prompting guide makes the general point: explaining to Claude why such behavior is important, can give Claude more information about your goals[5]. Saying why you are asking is part of the question.

When the answer still doesn't land: re-pitch it

The first explanation is a draft, not a verdict. Sometimes it arrives in words that are themselves unfamiliar, or at a level of detail that answers a different question. Do not reply "I still don't get it": that tells the agent nothing about what to change, so it produces a near-copy of the answer you already rejected.

Asks for a repeat

"I still don't understand. Explain again."

The agent has no signal about the form, the depth, or the setting. Expect the same answer, slightly reworded.

Asks for a re-pitch

"Re-pitch that with an example from my app. Which file would break if this were wrong?"

The second request names the form (an example), the setting (my app) and the test you will use to judge the answer (which file would break).

That still doesn't land. Re-pitch it with an example, the way you would
explain it to a friend over coffee.

Use something from my project rather than a generic example, and keep it
under four sentences. If there is a simpler word for it, use that word.

Two or three re-pitches is normal for a genuinely new idea. Ten means the idea is not the problem: the agent is answering a different question than the one you are asking, and you should say what you already understand so far. "I follow the first half, up to the part about caching" is a far more useful message than "still confused".

Say it back

The last move is the one beginners skip. Write the idea in your own words and send it as a question:

So it means: <your sentence in your own words>.

Is that right? If it is wrong, correct the part that is wrong and leave
the rest alone.

A correction is the fastest proof that you now hold the idea, in the form you will actually use it. This checks your understanding, not the agent's honesty; a confident answer is still a claim, which is a separate habit (lesson 2.2).

Recall before you read on

Without scrolling up: name the three details that make a question about a word easy to answer, and say what you should ask for when the first answer still doesn't land.

Name the exact word in quotes, say you are not a programmer, and ask for one example from your own project. If it still doesn't land, ask for a re-pitch with an example — the same idea in a different form — then say it back in your own words and ask whether you got it right.

Explain as you go, without asking every time

If you want the reasoning attached to every change for a whole session, one of the three agents has a built-in setting for it. Claude Code calls it an output style: a session-wide instruction that sets the agent's role, tone and response format, so you do not repeat the request in each prompt[4]. Its Explanatory style adds short Insight blocks that explain the choices behind the code it writes, and those notes aren't written into your files as comments[4]. Turn it on for a session where you want to learn, and turn it off when you only want the work.

Run /output-style explanatory, or run /config and choose Output style. With no argument, /output-style lists the styles and marks the current one. Switch back with /output-style default; the change applies from your next message.[4]

You can still ask about a single word at any time. The style only changes what you get without asking.

I found no documented equivalent style in Codex's docs, so use a standing instruction in your prompt instead: "After each change, add one sentence in plain words explaining what changed and why."

To ask while it is still working, Press Enter while Codex is working to inject new instructions into the current turn.[6]

omp's docs describe no equivalent style. Its guidance is that A steering message is for now; a follow-up is for after the agent yields.[7] Pressing Enter while it works steers the current turn; one documented example of a queued follow-up is After that, explain the migration risk.[7]

omp's documentation comes only from its own authors, so check anything surprising against your installed version.

An output style makes every reply longer, because it explains work you may not care about. Switch it off once the vocabulary stops being the obstacle. Permissions are a different setting entirely; see lesson 0.6.

Keep the words you learn

A glossary turns one conversation into a lasting gain. Keep a notes file in the project folder with one line per word, written in your own words, and add to it after each session. The act of writing the line is the check: if you cannot write it, you have not understood it yet. Later, the agent can read that file and match its language to yours, and you stop paying for the same explanation twice. Our course glossary is a starting point, not a substitute for your own lines.

Two rules of thumb

Ask about words, not about whole tasks. One word, one question, then back to work. And keep the answer to a length you will actually read: two sentences and one example beats a lecture you skim.

youI don't know the word "build step". Explain in two sentences, not as a programmer, then one example from my project.
agentA build step is a small job that runs before your site is published, such as copying your files into a folder the host can serve. It matters because the published site comes from that folder, not from your source files.
agentIn your project, the step copies everything in src/ into dist/. If it were wrong, the page you open online would show old text even though your file on disk is correct.
youSo it means: the published site is built from a copy, so editing my file is not enough until the copy runs again. Right?
agentRight, with one addition: the copy runs when you publish, so a local edit that was never published has no effect on the live page.
noteThree short turns. No files changed, and the next instruction can be written in words the user owns.
Do it now, in your own agent

You should get a two- or three-sentence answer, then a second answer that uses something from your own folder, then a short "right" or a correction. Nothing in your project should change, and no approval prompt should appear, because you asked a question rather than requested an edit.

Check yourself

Question 1 of 3

The agent writes "I moved the build step into CI." You do not know "build step". What is the best move?

Ask at the word, while the agent still has the task in view, and ask for one example from your project. Restarting or approving blind both cost more than the question.

Question 2 of 3

What makes a re-pitch different from asking the same question again?

A re-pitch changes the form — a concrete example, a familiar setting, a shorter length — so the agent has something new to work with. A repeat produces a reworded copy.

Question 3 of 3

You have asked twice and still cannot follow the answer. What is the most useful next message?

Change the form and anchor it in something you already know: your own app. Repeating or demanding the final answer skips the step you are stuck on.

Ask your teacher

Anything unclear? Ask the agent that gave you this course. Try: "Here are three words from my last session I nodded past: … Explain each in two sentences with an example from my project." or "Quiz me on the vocabulary in this lesson, one word at a time."
