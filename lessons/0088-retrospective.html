Retrospective: which failure modes did you hit?

You built and shipped an app. Before the memory fades, name the ways the run went wrong — because the failure modes you hit once are the ones you will hit again, unless you write them down.

Why this matters for shipping your app

Your first app is live. The tempting next move is to start the next idea. Resist it for fifteen minutes. A run that ends without a review teaches you only what you happened to notice; a run that ends with a review teaches you the pattern underneath. That pattern is what keeps your second app from costing what your first one cost.

This course has names for the ways agent runs go wrong — the failure-mode field guide collects them. Unit 4 walked through the common ones: work that grew past what you asked (4.2), runs with no end (4.3), fixes that hid the problem (4.5), agents that pleased you instead of the goal (4.7), and runs you left alone too long (4.9). A retrospective is the step where your own run gets matched against that list.

Your session record is the raw material, and it is still there. Scroll back through the run and look for the moments you typed a correction. Those moments are the expensive ones, and they fade within a week. A named pattern is easier to spot the second time, because you have a word for it.

What a retrospective is

A retrospective answers three questions in order: what actually happened, which known failure mode each problem matches, and what one sentence would have prevented it. Not "what went well" first — with a coding agent, the expensive lessons are almost all in the failures.

One entry looks like this: "the agent said the page was done; opening it showed an error — an unverified claim — so I now open the page before I accept done." A name, a fact, and a rule you can follow tomorrow. Vague entries such as "be more careful" cannot be checked, so they do not survive the next run.

Anthropic's best-practices guide describes the classic shape of the mistake: Claude said it was done and it wasn't quite, usually because it had no way to check its own work.[1] If that happened to you during the capstone, the retrospective is where "it wasn't quite" turns into a rule, such as "no run ends until I have opened the page myself."

Keep each entry small. One problem, one matching name, one rule. A retrospective that lists twenty observations changes nothing; three rules you will actually apply change everything.

A worked retrospective

A real pattern, anonymized

A user built a small gallery site with an agent and shipped it to a public host. Reviewing the session afterwards, they found three things. First, the agent had restyled two pages nobody asked about — work that grew past the request. Second, it had reported "done and tested" on a page that errored when opened; nobody had verified it. Third, most of that drift happened during one long stretch when the user had stopped watching. Matching each to the field guide: scope creep, an unverified claim, and an unsupervised run. Three rules came out: a stop line in every prompt, one personal check of the live page before any "done", and a check-in at least every ten minutes on long runs.

Notice the shape. The user did not blame the agent or themselves. They matched each surprise to a named pattern, and each pattern produced a single sentence they could paste into the next run. The prompt patterns reference and the four-part prompt from Codex's guide — Goal: What are you trying to change or build? plus context, constraints, and a "Done when" line[2] — are where those sentences live.

Let the agent help, but you decide

Your agent kept a record of the whole session, so it can help you find what you missed. Copy this prompt, fill in the blank, and send it in the same project folder:

Look back over this session with me. List, in order:
1. Every time I had to correct, interrupt, or redo your work.
2. Every claim of "done" that I later found wrong or incomplete.
3. Any work you did that I never asked for.
Keep each item to one line. Do not fix anything now.

The list you get back is evidence for the review, not the review itself. Expect it to be long on detail and short on judgement.

Then do the part the agent cannot do honestly: for each item, name the failure mode yourself and write the rule. An agent grading its own homework will soften the findings — the pattern behind 4.7 applies to reviews too. You match the names; the agent supplies the evidence.

Recall before you read on

Without scrolling up: what are the three questions of a retrospective, in order? Write them in your own words.

What happened (the corrections, the wrong "done" claims, the unrequested work), which named failure mode each problem matches, and what one sentence would have prevented it. One problem, one name, one rule.

Keep the rules where the next run reads them

A rule that lives only in your memory protects one project. Put it where every future session starts from it: the rules file, the plain text file each agent reads at the start of a session. Anthropic's guide treats it as a core habit: Think of AGENTS.md as an open-format README for agents.[2] The name differs by tool:

Claude Code reads a rules file named CLAUDE.md in your project folder.[3] Add one line per retrospective rule, in plain words.

Codex reads a rules file named AGENTS.md in your project folder.[2] Add one line per retrospective rule, in plain words.

omp reads project rules from AGENTS.md in your project folder, and can also read the Claude-style .claude/CLAUDE.md.[4] omp has only single-vendor documentation, so if the file seems ignored, check the omp context-files page before assuming.

Rules age. Read the file at the start of your next project and drop any line that no longer matches how you work. A short file you trust beats a long one you skim past.

Keep rules short and checkable: "Stop when the pull request is merged; do not start the next task" beats "be careful with scope". A rule the agent can compare against what it sees is a rule it can follow.
Do it now: run your capstone retrospective

You should see the agent list real moments from the session — corrections you had forgotten, a "done" you had to undo — and stop without fixing anything. Your rules file should now contain two or three sentences you can read in five seconds. If the list comes back empty but you remember friction, re-ask: "You listed nothing. Check again for times I rephrased the same request twice."

Check yourself

Question 1 of 3

Your agent said a page was done and tested; it errored when you opened it. Which failure mode is this?

The claim of "done and tested" was never checked against reality. That is an unverified claim — the reason a retrospective always asks which "done" statements turned out wrong.

Question 2 of 3

Why should you name the failure modes yourself instead of asking the agent to grade its own session?

An agent judging its own work tends toward the answer that looks best — the same pressure behind reward hacking. It supplies the evidence; you supply the judgement and the names.

Question 3 of 3

Where should a rule from your retrospective live so the next session starts from it?

The rules file is read at the start of each session in that project, so every future run inherits the lesson. A chat transcript ends; a commit message describes one change.
