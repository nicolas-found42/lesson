The pull request: a proposal, not a merge

A branch keeps your work separate. A pull request is how that work gets looked at, checked, and only then allowed into main.

About 15 minutesBuilds on: 3.6 Remote, origin and pushWin: you can open a pull request and read its checks before anything merges

Why this matters for shipping your app

Your app goes public from the main branch of your repository. Every change that reaches main is a change the world can see, and on a site that deploys automatically, a broken merge is a broken link within minutes.

A pull request is the door between "I made this on a branch" and "this is part of the app". It is also the one place where a machine tells you, in plain sight, whether the change passes its checks. Learn to read that page and you can merge without taking anyone's word for it.

A proposal, not a merge

GitHub's own reference is blunt about the word: Pull requests are proposals to merge code changes into a project.[1] Nothing about opening one changes the app. It creates a page where the change sits in the open until someone — you — decides.

A pull request always compares two branches. GitHub notes that Pull requests can only be opened between two different branches[2]. In plain words: the head branch holds your new commits, and the base branch is where they would land. In your project the base is almost always main. If you have not made a branch yet, lesson 3.5 covers that, and lesson 3.6 covers getting the branch onto GitHub, which must happen first.

That separation is the whole safety property. Commits on a branch cannot break the live site, because the live site is built from main. A pull request is a proposal to change that, with the evidence attached.

What the page actually holds

The pull request page is a set of tabs, and each answers one question a person would ask before merging.

Tab or areaThe question it answers
ConversationWhat is being proposed, and what have people said about it?
CommitsWhich saved snapshots does this proposal carry?
Files changedWhich lines would actually change in main?
ChecksDid the automated tests, builds and linters pass?
Merge boxIs anything still blocking the merge?

GitHub describes the last two of those directly: The Checks tab shows automated tests, builds, and other validations. and The Files changed tab shows the diff that reviewers use to understand the proposed changes.[1] Near the merge button, a merge status line highlights blockers, missing approvals, and other requirements before merging[1]. When it says the branch is behind, or a review is missing, that is not a defect: it is the page refusing to let you skip a step.

Opening a pull request also does not require the branch to be finished. GitHub offers a draft: Draft pull requests cannot be merged, and you mark one ready when you want real feedback[1]. A draft is a good place to park work in progress, because the checks still run while nobody can merge it by accident.

The description is the argument

Reviewers — including you, next week — arrive without your context. The description is where you supply it. Three short paragraphs are enough, and each has a job.

Weak description

"Fixed the gallery stuff. Should be working now."

A reader cannot tell what changed, why, or what "working" would look like. Nothing here can be checked.

Usable description

"The gallery page showed every photo at full size, so it took eleven seconds to load on a phone. This adds thumbnails and loads the big file only when a photo is tapped. I checked it in a browser at phone width; the first screen now draws in under a second."

What changed, why it mattered, and the check that was run. All three can be argued with.

Your agent can draft this from the branch's commits, and you should still read it. A description that claims a check the agent did not run is worse than no description, because it invites you to trust the wrong thing. The habit from lesson 2.2 applies to the page itself: the sentence "tested in a browser" is a claim until the Checks tab or your own eyes back it up.

Recall before you read on

Without scrolling up: opening a pull request changes which branch, and which two branches does it compare?

It changes nothing on main; it only creates a page. It compares a head branch (your new commits) with a base branch (where they would land, normally main). GitHub requires the two to be different branches.

Checks: the page's own opinion

A check is a result reported by a machine about a specific commit. GitHub's definition is precise: Status checks show whether commits meet the conditions set for a repository.[3] They normally come from continuous integration: the tests, builds and linters that a server runs after every push.

Three states matter to you. A check is pending while it runs, and the merge button waits. It passes when the work succeeded, or fails when something did not. GitHub adds one consequence worth knowing: If status checks are required for a protected branch, they must pass before the pull request can be merged.[3] Protection is a repository setting; lesson 3.15 takes it up.

A green check can be a skipped check

GitHub's checks page says a job that is skipped will report its status as "Success"[3]. A test suite that quietly did not run can therefore look like a passing one. Read what ran, not only the colour. Lesson 2.12 is about the gap between checks on your laptop and checks in the cloud.

You do not need to memorise where the buttons are to know the state. The gh command line tool on your machine has gh pr checks, documented in its own help as Show CI status for a single pull request.[4] Two details from that help page are useful to a beginner: run without an argument, the pull request that belongs to the current branch is selected, and the command exits with code 8 while checks are still pending[4]. A non-zero exit there means "not finished", not "broken".

What merging means, and when not to

Merging is a separate act with its own button. GitHub's instructions put the condition first: Merge a pull request when the proposed changes are ready and any repository requirements are satisfied.[5] The word "ready" is doing the work. Ready means you read the description, you looked at the changed files, and the checks you care about finished and passed.

There is a real cost to pressing the button early. Once a branch is merged, it cannot take more commits, so a review comment that arrives afterwards needs a brand-new pull request. That is not a catastrophe; it is rework you can avoid by waiting a few minutes. Lesson 3.8 covers the merge methods themselves.

A real pattern, anonymized

A user had three pull requests open and typed "merge" while the checks on one were still running. The agent could not wait for them, so it asked: merge now on the local test run, or leave the request open? The user chose now. Hours later a review comment arrived on the merged change and found a genuine bug; the fix had to go through a new pull request on a new branch. Nothing was lost, and the second attempt went through green checks. The lesson the user drew was simple: the merge box was already telling them what to wait for.

Do it: open one, then read it

You need a repository on GitHub with a branch you have pushed, and the agent's approval prompts left on. Ask for the pull request and the evidence, not only the link. If the agent opens it with gh pr create, its help page notes that Upon success, the URL of the created pull request will be printed.[4]

Open a pull request from the branch I am on into main.
Do not merge it.
Write the description as three short parts: what changed, why, and exactly how you checked it.
Then run gh pr checks and tell me the state of every check, including any that were skipped.
Your turn

A page with a title, a description you can read without asking questions, a list of commits, and a number of changed files. The checks area lists named jobs with a state; the merge box either offers a merge button or names what blocks it. If the description is vague or claims a check that is not listed, that is the finding — send it back before merging.

Check yourself

Question 1 of 3

You open a pull request from a branch into main. What has changed on main?

A pull request is a proposal. The base branch changes only when someone merges, which is a separate action.

Question 2 of 3

A check on your pull request reports a failure. What does that mean?

A failed check says a condition set for the repository did not hold. Read the details, fix the branch, and the new commits re-run the checks.

Question 3 of 3

The checks are still running. What is the honest next step?

Pending means the evidence is not in yet. Merging first turns a check into a report about code that is already in main.

Stuck on a check you do not recognise? Ask the agent: "Explain this check in plain words, and tell me what failure would look like." Then ask whether it ran or was skipped.
