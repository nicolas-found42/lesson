The checker can be wrong

A green check is a claim too. Tests can pass without testing anything, the same test can give two answers for one unchanged file, and an AI asked to judge your work has good days and bad days. The skill is telling a real pass from a quiet one.

Why this matters for shipping your app

The evidence that your app works comes from checks: your tests, your agent's review command, a browser run, a model grading the result. Lesson 2.2 taught you to ask for evidence instead of a claim. This lesson is the uncomfortable next step: evidence can be wrong too. A check that always says yes is worse than none, because it removes your reason to look. The fix is not to distrust every check, but to learn the three ways a check goes quiet and to run one small experiment that exposes each.

Three ways a check lies to you

The checkWhat you seeWhat actually happened
Vacuous"pass", every time, in greenIt never compared anything, so it could not fail
FlakyFail now, pass on the next runSomething outside the code differed between runs
Noisy judgeA score, a verdict, a findingA model's opinion, with real variance and bias

First: can this check fail at all?

The cheapest question about a check is whether you have ever seen it go red. If the answer is "not yet", you do not know whether it guards anything. Scientists have a name for the deliberate version: a negative control is an input you know should produce a failure; in one reference's words, Negative controls are one type of falsification tests.[1] Software has a heavier version, mutation testing: Mutation testing involves making small changes to the program being tested, and In this way, the tests are tested.[2] You need the habit, once per check, not the tool.

Here is a two-line function that adds prices, with one test, run by Node's built-in runner.

export function total(prices) {
  let sum = 0;
  for (const p of prices) sum += p;
  return sum;
}

test('adds up three prices', () => {
  assert.strictEqual(total([2, 3, 5]), 10);
});

The run is green: pass 1, exit code 0. Now the control. I changed one character so the function starts from 1, and ran the same command:

✖ adds up three prices
  AssertionError [ERR_ASSERTION]: Expected values to be strictly equal:

  11 !== 10

It exited with status 1 and named both numbers, so it compared something real. I restored the file, then removed the comparison but kept the call:

test('adds up three prices', () => {
  total([2, 3, 5]);
});

This test cannot fail: it calls the function and throws the answer away, which is what a vacuous check does. It still printed ✔ and exited 0, with the broken function on disk. The green tick measured only that no exception was thrown. A third version costs an afternoon: a filter that matches nothing still exits 0, because Tests that are not executed are omitted from the test runner output.[3] Read the counts, not the colour of the last line.

The one-sentence habit

Before you trust a green check, break something on purpose and watch it turn red. If it stays green, the problem is the check, not your app.

Recall before you read on

Without scrolling up: what is a negative control, and what does a green run prove if you have never seen the check fail? Answer in your own words, then compare.

A negative control is a deliberately broken input that the check should reject. If it goes red, the check is connected to the thing it measures. If you have never seen it fail, green only proves the check ran — a test with no comparison, or a filter that matched nothing, passes while checking nothing.

Second: one file, two answers

A flaky test changes its result without the code changing. Google, which runs a very large number of tests, keeps a working definition: We define a "flaky" test result as a test that exhibits both a passing and a failing result with the same code.[4]

Flakiness is not a beginner's problem. Google measured about 1.5% of all test runs reporting a "flaky" result, said Almost 16% of our tests have some level of flakiness associated with them![4] The same post names the human cost: It is human nature to ignore alarms when there is a history of false signals coming from a system.[4]

Common causes are timing, a network call, a file another program is also writing, test order, or a value that changes every run, such as the current date. None of them mean the app is wrong. So the response to a single red run is not to edit the app. Rerun the same check on unchanged code and see whether the answer moves.

What a flaky check tempts you to do

"It failed, so change the code until it passes."

You are now editing working code to satisfy a coin flip.

What to do instead

"Rerun it unchanged, note both results, then look for the cause."

Two answers from one file is a fact about the environment.

There is a quieter version. Node lets you mark a test todo: TODO tests are executed, but are not treated as test failures, and therefore do not affect the process exit code.[3] I ran one with a false comparison on purpose. It printed ⚠ and exited 0. That is honest when temporary and labelled, and a hiding place when the reason is "this one is annoying". A suspended check still counts in the total, so write why it is off and what would switch it back on.

Third: the judge is a model too

Lesson 2.10 added a second agent that reads your work with fresh eyes. That helps, and it is still not an oracle. When a model grades anything, its answer is a sample, not a measurement.

Research on models as judges names the failure modes: position, verbosity, and self-enhancement biases, plus limited reasoning.[5] A separate study flipped the ranking of two answers without changing either one's content: the quality ranking of candidate responses can be easily hacked by simply altering their order of appearance in the context.[6] Longer answers score higher; so do answers placed first. The same answer graded twice can score differently.

The vendors say this themselves. omp's review docs warn about their verdict: Correct means no correctness bugs or blockers were established under this review contract[7], and Findings: none is not a substitute for your own domain-specific checks.[7] Anthropic's guidance names the reviewer's incentive: A reviewer that's asked to find problems will always find something.[8] Ignoring reviewers is not the answer; repeating the measurement is.

Telling the three apart in your own agent

You need two runs, or a swap. The agents differ in how you ask for a repeat and what the report says about its certainty.

/code-review takes an effort level. At low it reports the findings it's most confident in, so you see fewer false positives; from medium up it broadens coverage.[9] Run it twice at one level and keep only findings that appear both times.

/review summarizes issues it finds in your working tree, focusing on behavior changes and missing tests, and it uses the current session model unless you set review_model.[10] The reviewer's quality is a setting you control, not a constant.

/review returns correct or incorrect with a confidence, and its docs say plainly: Confidence is not severity.[7] Read the cited lines before acting on any finding.

All three reviews are read-only, so a wrong verdict costs reading time rather than a broken file.
Two real patterns, anonymized

An agent building a slide generator wrote its own layout checker. It compared every pair of boxes and reported no overlaps, run after run. Then the agent overlapped a heading with a paragraph and ran it again. Still no overlaps. The checker skipped element types added later, so it approved the pages it could not see.

In another project the acceptance check was a model with a rubric. A page description scored 0.82, then 0.79, then 0.81 with nothing changed. Larger text scored lower; a reworded description scored higher. The agent measured the spread across repeated grades and reported a plateau: the remaining movement was noise.

What this looks like as a habit

  1. Have I seen this check fail? If not, break something on purpose and look — in a scratch copy, never in the files you are about to ship.
  2. Does it give the same answer twice? Rerun on unchanged code. Two answers means the check is measuring the environment as much as the app.
  3. How much does the judge move? Grade the same thing twice, and swap the order if you compare two versions. Only a difference larger than that movement is worth acting on.

None of these steps requires reading code. Each produces a sentence for another person: "the test fails when I break the total", or "the grader moved with no edits". That turns a check from a ritual into evidence.

Do it in your own project

You should see a red run with a real comparison in it, such as two numbers that differ, and exit code 1. That is your negative control working. On the three reruns, three identical summaries mean the check is steady; a disagreement means you have found a flaky check, and the next step is to name what differed. From the double review, expect some findings to appear once and vanish. If your agent says it broke the code and everything still passed, do not accept "the tests are fine" — ask which test it ran and paste the command.

Check yourself

Question 1 of 3

Your tests all pass. How do you find out whether the suite can fail?

That is a negative control: a break you know should be caught. Two identical green runs only show the check is stable, deleting the file shows nothing, and the agent's opinion is another claim to test.

Question 2 of 3

A test failed, then passed on an identical rerun. What is the right next step?

Two results from one unchanged file is a fact about the environment, not yet a bug in the app. Repeat before you edit; deleting or skipping hides the signal instead of explaining it.

Question 3 of 3

An AI grader scored your page 6, then 8, with no edits. What now?

A model judge has real variance and known order and length biases. Repeating, and swapping which version comes first, shows how much of the difference is noise. Neither chasing the score nor abandoning measurement follows from two numbers.
