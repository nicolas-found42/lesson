Orient first

Before you ask for a change, ask for a map. One question that only reads costs almost nothing. One change built on a wrong guess has to be found and undone.

About 15 minutesBuilds on: 0.7 First prompt to a pageWin: you can open any folder with a question that changes nothing

Why this matters for shipping your app

You have a page on your screen from lesson 0.7. The next thing you want is a change: different words, a photo, a button that does something. The tempting move is to describe it immediately, because you can already picture the result. The agent cannot. It has never seen your folder, so it guesses where things live, what the page already does, and which file matters, then acts on those guesses. Guesses made while editing turn into edits, and edits have to be found and undone later.

A question asked first becomes knowledge you keep for the rest of the project. That is the whole habit this lesson teaches: orient first.

The cheapest question is one that only reads

To orient is to find out what exists before you decide anything. A cheap question asks the agent to read and report, so nothing is written down and nothing can break. Four that fit almost any folder:

  • "What files are in this folder, and what is each one for?"
  • "How does this page get the text in its header today?"
  • "If I wanted a second page, where would it go and what would link to it?"
  • "What else uses the file I named? What would break if it changed?"

Cheap here means low risk, not zero effort. The agent still reads and thinks. But reading cannot damage anything, and the answer makes your next request sharper: a minute of looking against an afternoon of undoing.

The opposite move is expensive. "Make the header dark green" sounds small until you learn there are three pages, each with its own header, and you meant the first. The agent edits all three because nobody told it there were three.

The same request, two openings

Straight to the change

"Add a dark mode to my site."

One question first

"Before changing anything: how are colours set on this site, which files control them, and what would a dark mode touch? Answer only, no edits."

The first opening asks the agent to invent a plan in the dark: it picks a file, invents a mechanism, builds it. Sometimes that works. When it does not, you own a change you did not ask for in a place you cannot name. The second costs one turn and produces a map, so your next message can be short and exact: "Good. Change the one colour rule in the styles file, nowhere else."

A map, then a change

What orienting looks like in a session, in a project the user had never opened:

youBefore you change anything: how are the pictures on this page made? Which files decide that? Answer only, no edits.
toolread index.html, read render.js
agentNothing is stored as an image file. Each picture is drawn by one function in render.js from a list of shapes and numbers. index.html only reserves a space for it. Changing the look means editing that list, not swapping a file.
Nothing on disk changed. The answer is the map.

Only after that answer did the user describe the work they wanted. Because they now knew there was no image file to replace, they asked for the shapes to be adjusted instead of asking for "a new picture", which would have sent the agent hunting for something that did not exist.

A real pattern, anonymized

A user opened an unfamiliar project and typed one plain question about how it worked before asking for any change. The agent read the code, named the two files involved, and explained the mechanism in a short paragraph. No file was touched. The answer also exposed a limit in the existing design, so the user scoped the real task around it instead of hitting the limit later.

Ask for three things

A useful map has three parts: the files involved, how the thing works now, and the one surprise worth knowing. Ask for all three in one message. The third is where the value hides, because the agent has read the code and you have not.

Before changing anything, read the project and answer three things.
1. Which files would I touch to change [the thing I care about]?
2. How does that work today, in two or three sentences?
3. What would surprise me, or what would break if I changed it?
Do not edit any files yet. Report only.

That last line is not politeness. It is an instruction the agent will follow, and it protects you while you are still deciding. Lesson 1.7 builds on this when the answer becomes a full plan you approve.

The agent is built for this

Asking first is not a trick to slow the agent down. Reading is what it does best. Anthropic's guidance says it plainly: Claude starts every task by reading your code, and current models are very good at this.[1] OpenAI's Codex CLI page offers the same first move, suggesting you ask Codex to explain the project.[2] Asking for a map uses the strongest part of the tool before spending its weakest part: guessing what you meant.

Reading is not free in every sense: what the agent reads fills its context window (lesson 5.1). It costs no edits and no undo, which is the kind of cost that matters here.

Say "do not edit" out loud

An agent told to "look into" a problem may decide the fastest way to help is to fix it. Each tool offers a way to keep the read-only promise. Learn yours, and keep approval prompts on (lesson 0.6).

Plan mode is the built-in version of this habit: Plan mode tells Claude to research and propose changes without making them.[3] Anthropic lists it for Exploring a codebase before changing it.[3] You enter it by pressing `Shift+Tab` or prefixing a single prompt with `/plan`.[3] The status bar shows when it is on.

The CLI quickstart's example first message is a single line: Tell me about this project.[2] If you want a hard boundary rather than a polite request, start with the read-only sandbox: read-only: The agent can inspect files, but it can't edit files or run commands without approval.[4] The flag is --sandbox read-only.

The omp docs give the exact sentence to use: If you only want an explanation, say “investigate, but do not edit.”[5] For anything larger, /plan gives you a separate planning turn before execution.[5] omp documents only itself, so treat these pages as single-vendor sources.

These features differ in name and strength. The habit does not: one message that asks for understanding, and no edits, before the message that asks for work.

Recall before you read on

Without scrolling up: what makes a question cheap, which three things should its answer contain, and what do you say so the agent does not start editing?

A cheap question only reads; it cannot break the project. Its answer should name the files involved, explain how the thing works today, and flag the surprise or risk. Say "do not edit any files yet", or use your agent's read-only or plan mode.

Check the map before you build on it

A map is also a claim, and it can be wrong in a large or unusual project. Check one thing yourself: open the file it named, or look at the page and see whether the description matches. If that check fails, treat the rest as unproven. Lesson 2.2 makes this routine.

When not to bother

Orienting is a tool, not a ritual. Skip it when you already hold the map: a file you wrote ten minutes ago, a change of a single word you can point at. A questionnaire about a three-line file wastes the attention you meant to save. Lesson 4.11 covers where that turns into over-asking.

Do it in your own agent

You should see a short list of real files that you can find in your folder, a one- or two-sentence explanation, and no edits at all in the agent's report. Your second message should now name a file instead of describing the whole page. If the agent edited something during step 2, its read-only setting is off: check lesson 0.6 before going further.

Check yourself

Question 1 of 3

What makes a question cheap to ask before a change?

A question is cheap because it cannot damage anything and it improves your next request. Reading is the work; writing is what you are postponing.

Question 2 of 3

You want a change to a page you did not build. What comes first?

The first message buys a map: the files, the current behaviour, the risk. Every other option asks the agent to act on guesses about a page it has never read.

Question 3 of 3

Which instruction keeps the agent reading instead of editing?

"But edit nothing" sets the boundary in the same sentence as the request. Guessing, rewriting and deleting all break the read-only promise before the answer exists.
