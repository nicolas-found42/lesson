Long runs you don't watch: checkpoints and progress logs

Some tasks take twenty minutes or two hours, and you cannot stare at the chat the whole time. Two habits make a long run safe: demand the first piece of evidence early, and make the run write down what it is doing as it goes.

About 15 minutesBuilds on: 3.13 Checkpoint oftenWin: you can start a long task and still learn within minutes whether it is going wrong

Why this matters for shipping your app

Most of the time your agent spends on your app is not spent chatting. It is spent in long runs: a big build, a refactor across many files, a migration, a test suite. During those runs you are usually not watching. If the run fails at minute forty of forty, you have lost forty minutes and learned nothing about why. Anthropic's own best-practices page describes exactly this trap: in a run you leave unattended, nobody tells it, and you find out the next morning that it spent the whole night building on the wrong assumption.[1]

This lesson gives you two tools for that situation. An evidence checkpoint is the first real result you get to look at, on purpose, early. A progress log is the run's diary, written as it goes instead of at the end.

The failure shape

Picture a run that takes twenty minutes and produces one screenshot at the very end. If the screenshot is wrong, the whole run was wasted, and you cannot tell whether the mistake happened in minute one or minute nineteen.

A real pattern, anonymized

A user asked an agent to drive their app through a long automated check that took about twenty minutes. The first screenshot only appeared at minute fourteen, so when the user interrupted the run at minute two to ask what was happening, there was nothing to show. The fix was simple: the agent restarted the run so that a frame was captured every twenty seconds starting at the one-minute mark. After that, a bad run showed up in the first minute instead of the fourteenth.

The lesson: when evidence arrives matters as much as whether it arrives. Anthropic's advice for any session is to watch the first minute and step in the moment the agent drifts.[1] For a run you plan to leave alone, you cannot watch it yourself, so you move that first look into the task: you tell the agent to produce a checkable artifact early and to keep going only if it looks right.

Checkpoint one: early evidence

An evidence checkpoint is a small, concrete thing you can inspect: a file that exists, a line of output, a test result, a screenshot, a diff. It is not a feeling and not a summary sentence. Anthropic's guidance on verification says to ask the agent for the command it ran and its output, or the screenshot, because for a session you were not watching, it's also the only evidence you have.[1]

So when you hand over a long task, put the checkpoint in the prompt: "Within the first few minutes, show me one concrete result — the file, the output line, or the screenshot — before continuing." If that first artifact is wrong, you have spent minutes, not hours.

Recall before you read on

Without scrolling up: what are the two protections this lesson gives you for a long unattended run, and what is the difference between them?

An evidence checkpoint is the first concrete, inspectable result, demanded early, so a wrong run is caught in minutes. A progress log is a file the run appends to as it goes, so that even if the run dies or you stop it, you can read exactly where it stopped and why.

Checkpoint two: the progress log

The agent's chat transcript is a summary written at the end. If the run crashes, is stopped, or your session is closed, that summary may never exist. A progress log is different: it is a plain file on disk that the run appends to, one line per step, as it happens. When something goes wrong, the last line of the log tells you where the run actually was.

Here is what that looks like in practice. A five-step script was started and then stopped partway through; because each step appended its own line immediately, the log survived (run in a throwaway folder on this machine):

19:55:13 step 1/5 start  collect files
19:55:15 step 1/5 done   collect files
19:55:17 step 2/5 start  build page
19:55:17 step 2/5 done   build page
19:55:19 step 3/5 start  run tests
19:55:19 step 3/5 done   run tests
19:55:19 step 4/5 start  copy output
[process stopped here — no "done" line, no final summary]

Read that log and you know immediately: step 4 started and never finished. Contrast that with a run that prints everything only at the end — when it is stopped, you have nothing at all. The rules that make a log useful are simple: write each line as the step happens, not in a batch at the end; include a final ALL DONE line so that its absence means something; and write failures into the log too, not only successes.

Ask for both, in the prompt

You do not need any special tool for this. It is a behaviour you request in plain words, and it works in any agent:

Run this task, but unsupervised-proof it:
1. Within the first 5 minutes, produce one concrete checkpoint I can
   inspect (a file, an output line, a test result, a screenshot).
   Show it to me, then continue only if it looks right.
2. Keep a progress log at progress.log in the project folder.
   Append one line per step as you go: timestamp, step name, status.
   Also log failures. End with a final line "ALL DONE".
3. If you get stuck twice on the same step, stop and report instead
   of retrying forever.

Item 3 is a stop condition, which lesson 4.3 covers in depth; here it makes the run end honestly instead of silently grinding.

Where each tool shows you the running work

While a long command runs, each agent has its own place to peek at it without interrupting:

Press Ctrl+B to move a running command to the background; its output is written to a file and Claude can retrieve it using the Read tool, and /tasks lists running shells and subagents.[2] An interrupted command keeps the work done so far.[3]

Type /ps to show background terminals and their recent output — each terminal shows its command plus up to three recent, non-empty output lines so you can gauge progress at a glance — and /stop to stop them.[4] While Codex works, Tab queues a follow-up message for the next turn.[5]

Type /jobs, which shows running and recently settled background jobs,[6] and press Escape to interrupt the active turn; a steering message sent while it works reaches the next step.[7] (omp's docs come only from its own authors, so treat details as single-vendor.)

Your choice of tab is remembered, so later lessons show your agent first.

What these checkpoints are not

Three things this lesson does not replace

A progress log is not a commit. It records what a run did, not a save point you can return to — lesson 3.13 covers committing often during long work. An evidence checkpoint is not a budget; until no issues remain never ends, as lesson 4.4 explains. And neither one lets you turn off approval prompts — keep them on (lesson 0.6).

Try it in your own project

You should see progress.log growing while the run is still going, with one line per finished step, and a concrete checkpoint artifact (file, output, or screenshot) that appeared early. The agent's spoken answer should match the log. If the log is empty until the end, the run is not logging as it goes — tell the agent to append per step.

Check yourself

Question 1 of 3

A long run produces its first checkable output only at the very end. What is the main risk?

With evidence only at the end, a mistake made in minute one costs the whole run, and you cannot tell where it went wrong. An early checkpoint exposes the problem while it is still cheap to fix.

Question 2 of 3

Which of these belongs in a progress log for a long run?

The point of the log is that it exists while the run is happening and survives a stop or crash. A summary written only at the end disappears with the run if it never finishes.

Question 3 of 3

You start a long run and step away. A few minutes later you come back. What is the best first move?

The log and the early checkpoint exist precisely so you can see the state mid-run and steer. Waiting until "done" forfeits the whole advantage of having them.
