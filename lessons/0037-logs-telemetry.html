Logs and telemetry: enough to diagnose?

When something goes wrong, a screenshot shows you the symptom. A log shows you what the app was doing at that moment. Without one, every fix is a guess.

Why this matters for shipping your app

You will not be sitting in front of every visitor. When a friend writes "it broke after I clicked Pay", you get a sentence and maybe a photo. The app itself has to have written down what happened, or nobody can reconstruct it. That written record is what this lesson is about, and asking whether it exists is a skill you can use before you spend an hour on a fix.

A log is a record with a time on it

A log is a message the program writes while it runs. OpenTelemetry, the open standard for this kind of data, defines one as a timestamped text record, either structured (recommended) or unstructured, with optional metadata.[1] Python's documentation puts the purpose in one line: Logging is a means of tracking events that happen when some software runs.[2]

Telemetry is the wider word for that kind of self-report. OpenTelemetry says Telemetry refers to data emitted from a system and its behavior.[3] A professional setup also collects counts and timings (metrics) and the path of a single request (traces). You do not need those yet. You need logs, and you need to know when they are missing.

What makes a log line usable

Three things have to be in a line before it can help you: when it happened, what happened, and which values were involved. A line that says only "error" is nearly useless an hour later, because every error in the session looks identical.

Not diagnosable

console.log("error")

No time, no run, no values. If this appears twelve times, you cannot tell which click produced which line, or what the numbers were.

Diagnosable

console.log("checkout", {run: 42, step: "pay", items: 2, total: 14.5})

A label, a run number, the step, and the values. Anyone reading it later can tell what the app believed at that moment.

Separating the values into named fields is what people mean by structured logging. OpenTelemetry's guidance is that OpenTelemetry accepts any log format, but not all formats are equally useful for analysis.[1] For a beginner app, structured means little more than: put the numbers in the line, and give each one a name.

A log without a time is a note. A log with a time, a label and the values is evidence you can sort, count and compare between runs.
Recall before you read on

Without scrolling up: name the three things a usable log line should contain, and say what is wrong with a line that only says "error".

When it happened, what happened, and which values were involved. "error" on its own has no time, no label and no numbers, so two occurrences cannot be told apart and nothing can be compared between runs.

The question to ask before you fix anything

Here is the move this lesson is built around. When something misbehaves, before asking for a fix, ask the agent:

Do you have enough logs or state history to diagnose this?
Answer first, before changing any code:
1. What does the app currently record, and where does that output go?
2. At the moment the bug appears, what would you need to see?
3. Which of those things is missing today?
4. What is the smallest temporary log line or export that would fill the gap?

Do not guess at a cause yet. If the answer is "not enough", say so plainly.

Notice that this asks for honesty about the instrumentation, not for a theory. An agent that has no logs will still produce a confident-sounding cause; that cause is a guess wearing a lab coat. Asking the question first turns a guess into a short, bounded job: add the missing line, reproduce, read it.

A real pattern, anonymized

A user was building a small simulation: dots that learn to move around a screen, scored by how far they get. After a long run the dots froze at the same point and then behaved strangely. The user did not ask for a fix. They asked whether the agent had enough logs and state history to diagnose it. The agent said no: nothing was being recorded, so the only evidence was the user's description.

So the next task was not "fix the freeze" but "add diagnostics": a counter panel, an export of the run, and a replay of the last few seconds. The following run exported real data, and the cause was visible in it: a number that had been healthy for a hundred rounds collapsed at a specific point. The agent reproduced that collapse first, then fixed it. The fix took one pass, because the evidence had already narrowed the search.

The order matters. Instrument, reproduce, read, then fix. Skipping the first step does not save time; it moves the cost into a series of guesses, and each guess needs its own test.

Too little, and too much

Logs carry a level, and the level decides what actually gets printed. Python's documentation gives the plain meanings: debug is Detailed information, typically of interest only when diagnosing problems, while info is Confirmation that things are working as expected.[2] The same page notes that the default level is WARNING, so debug and info lines silently disappear unless someone turns them on.[2]

That default explains the most common surprise in this lesson: a programmer adds a careful diagnostic line, runs the app, and sees nothing. The line is not broken. The level is filtering it out. Before you conclude "the code never runs", check which level is being shown.

The opposite failure is noise: a line inside a loop that repeats thousands of times, burying the one line you need. The habit that keeps both problems small is to log at the few points where the app makes a decision, not on every step it takes.

Never log secrets

Logs get copied into chat windows, issue trackers and screenshots. Never ask for passwords, API keys or personal details to be written into a log line. Lesson 8.1 covers what counts as a secret; lesson 8.3 covers what happens after one leaks.

Where the logs actually are

There are three places to look, and beginners often look in the wrong one.

  • The browser console is where a web page's own messages and errors appear. MDN describes it as the place that reports the errors encountered as the browser tries to execute your code.[4] On a Mac, open the developer tools with ⌘+⌥+I, then choose the Console tab.[4] The console object itself provides access to the debugging console, with methods for plain messages, warnings and errors.[5]
  • The terminal is where a program that runs on your machine prints its output, including crashes. If you started a local server, its messages land in the window that is running it.
  • The host's build log is where a deployed site reports what happened while it was being published. On GitHub, Logs include the status for each job and step in a workflow, under the Actions tab.[6]

One more distinction, because it causes real confusion. Your agent's session transcript, the list of tool calls it made, is not your app's log. It records what the agent did while building; it says nothing about what your app did when a visitor clicked. When a bug appears at runtime, the evidence has to come from the running app.

Do it in your own agent

You should end with either a console line that describes the failing click, or a clear statement from the agent that no such line exists. A good line names the action and shows the numbers involved, for example a label plus the item count and the total. If the console stays empty after the click, check that you are looking at the same tab that shows your page, and that the message is not being filtered out by its level.

Check yourself

Question 1 of 3

Your app freezes on one button and nothing has been printed anywhere. What should you ask first?

Before any cause can be tested, you need to know whether the app recorded anything about the failing moment. If it did not, the first task is to add that record, not to guess.

Question 2 of 3

A log line contains only the single word "error". Which addition helps most?

Time, a run identifier and the values are what let you match a line to a moment and compare runs. Presentation and tone change nothing about what can be diagnosed.

Question 3 of 3

You ask about a bug. The agent says it has no logs. What comes next?

Instrument, reproduce, read, then fix. Guessing produces a change you cannot check, and a rewrite throws away the very behaviour you are trying to observe.
