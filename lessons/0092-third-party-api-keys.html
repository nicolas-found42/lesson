Third-party API keys, rate limits, and spend caps

Your app will call services you don't run — maps, weather, AI. Their keys work like yours: they identify you, meter you, and can run out or hit a ceiling. Learn the two error numbers that mean "slow down" and "pay up".

About 15 minutesBuilds on: 8.2 Env varsWin: you can recognize 429 and 402, and put a real spending cap in the provider's console

Why this matters for shipping your app

Your mission is a public app that does something useful. Useful usually means calling a service someone else runs: a map, a translation, an AI model, a payment check. Those services are not free and not unlimited. They recognize your app by a third-party API key — a secret string you store exactly like the agent's own key: in an environment variable, never in code (lessons 8.1 and 8.2). This lesson is about what happens when that key meets the provider's limits: rate limits, credits, and spend caps.

A key is a meter, not merely a password

A provider hands you a key so it can do three things: know who is calling (so a leaked key is your problem — rotate it, lesson 8.3), count how often you call, and charge what you use. The counting and charging are not punishments; they are how the service stays up for everyone. Your job is to expect them, not be surprised by them.

Rate limits: the 429 "slow down"

Every provider caps how many requests you may send in a given window. Cross the cap and the call fails with HTTP 429 Too Many Requests. MDN's reference puts it plainly: 429 indicates the client has sent too many requests in a given amount of time. The practice of asking the client to slow down the rate of requests is commonly called rate limiting.[1] The response may carry a Retry-After header telling you how many seconds to wait.[1]

So a 429 is not a bug in your app and not a ban. It is the provider asking you to pause. The right behavior is to wait the stated time and try once more — and to cache results so you ask less often in the first place. The wrong behavior is an instant retry loop: every retry is another request, and it can keep you over the limit.

A real pattern, anonymized

A user let an agent run a long verification loop that called several live services. Partway through, news and AI endpoints started returning 429s while the loop kept hammering them. The fix was not more retries; it was fewer, spaced-out calls with the wait time respected. The lesson: when a run hits 429, the agent should back off and report, not retry in a tight loop.

Credits: the 402 "pay up"

Many paid services run on credits — a prepaid balance that shrinks with every call. When the balance is gone, some providers answer with HTTP 402 Payment Required. MDN is careful here: 402 is a nonstandard status reserved for future use and no standard use convention exists and different systems use it in different contexts — but in practice providers use it for billing and credit problems.[2] Anthropic's own error reference maps it exactly: 402 - billing_error: There's an issue with your billing or payment information.[3]

A real pattern, anonymized

In another session, a paid judgment service returned 402 out of credits in the middle of a long unattended run. The agent did the right thing: it stopped and asked the human, who topped up the balance about an hour later. Lesson: a 402 means a human decision is needed — top up, switch plan, or stop — not "try again".

Contrast the two numbers: 429 = wait and retry later; 402 = stop and ask a human. Write that distinction into your prompts (below).

Spend caps: enforcement lives in the provider's console

Lesson 4.4 taught that a dollar figure in a prompt is an instruction, not enforcement. The enforced version of a cap is a spend limit set in the provider's own dashboard. OpenAI's documentation distinguishes the two controls. A spend alert sends a notification; API traffic continues, while a hard spend limit means affected API requests return a 429 error — an enforced monthly cap on the organization or project.[4] Anthropic similarly documents spend limits as a maximum monthly cost an organization can incur for API usage. While usage is paused for crossing one, API requests return HTTP 429.[5]

A real pattern, anonymized

Two users each set a small dollar ceiling before letting an agent make paid calls. One agreed to a five-dollar cap for experiments, another set a one-dollar limit and the agent later reported spending about half of it. Both are the right habit: name the ceiling before the run, and check the provider's usage page afterward. The report is evidence of spend, not proof the cap was watched the whole time.

Instruct the agent to stop, not hammer

Weak — retries everything blindly

Call the weather API for every city and keep trying until it works. Don't stop for errors.

Strong — named errors, named actions

Call the weather API once per city and cache the result. On 429, wait the Retry-After time and try once; on a second 429, stop and report. On 402, stop immediately and report — a human must decide. Spend at most $1; report usage from the provider dashboard.

Recall before you read on

Without scrolling up: what does 429 tell you to do, what does 402 tell you to do, and where does a real spending cap have to be set to count?

429 means too many requests: wait (honor Retry-After), retry once, then stop and report. 402 means a billing or credits problem: stop and ask a human. A spending cap only counts if it is a spend limit set in the provider's own console — a number in a prompt is only an instruction.

Do it in your own project

Do it in your own project 
Add a feature that calls the third-party service using the key stored in .env as THIRD_PARTY_API_KEY. Read it from the environment only; never print, log, or commit it.

If a call returns HTTP 429, wait the Retry-After seconds (or 60) and try once more; on a second 429, stop and report. Do not retry in a loop.
If a call returns HTTP 402, stop immediately and report that credits or billing need a human decision. Do not retry.

Budget: spend at most $1 on third-party calls for this task. When done, tell me the usage shown in the provider dashboard, and what you did NOT verify.

You should see code that reads the key from the environment, the key nowhere in your files or git history, a spend limit visible in the provider console, and — if you trigger an error — a stop-and-report message instead of a retry storm.

The trap to avoid

Do not answer a 429 or 402 by raising the cap or adding retries without reading the report first. A 429 wants time, not money; a 402 wants a human decision, not more attempts. And keep the key out of the prompt itself — pass it through .env, or it ends up in session logs and git history.

Check yourself

Question 1 of 3

Your app's calls to a weather service start failing with HTTP 429. What does that mean?

429 means too many requests in a given time window. MDN calls this rate limiting; the response may include Retry-After. Wait, retry once, then stop if it repeats.

Question 2 of 3

A paid service answers one of your calls with HTTP 402. What is the most accurate reading?

402 is nonstandard and conventions vary, but providers use it for payment, billing, or credits problems. Anthropic maps it to billing_error. Stop and involve a human; do not retry.

Question 3 of 3

You want a real guarantee that a provider never bills you above $10. Where does that guarantee come from?

A number in a prompt is an instruction the agent may forget; enforcement is a spend limit in the provider's dashboard. A hard limit makes affected requests fail (often with 429) instead of silently billing you.

The habit

Every third-party key gets three things before a run: a home in .env (never in code or prompts), a hard spend cap in the provider console, and a prompt rule — 429 means wait and retry once, 402 means stop and ask you.
