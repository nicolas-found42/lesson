Why this matters for shipping your app

Your mission ends with a page that other people open. Those people will never see your files, your terminal, or the agent's explanation. They will see a screen. So the skill that decides whether your app ships well is not reading code. It is putting the app in front of your own eyes, often, and noticing what is there.

In practice this is the step beginners skip. They read the agent's summary, agree that it sounds right, and ask for the next change. Then they publish, and a friend opens the page on a phone and finds the menu off the edge of the screen. Nobody lied. Nobody checked either.

This lesson covers the physical half of verification: your eyes on the running app. The next lesson, 2.2 Claims vs evidence, takes up the other half — what the agent's words are worth.

The loop: change, start and open, look

After every change you make one round of the same three steps. It takes about a minute, and it is the same round whether the app is one page or fifty. Only the first round of the day also starts the server; every round after that refreshes a page that is still being served.

The agent takes part in all three steps. You type the request; it edits files; it may start the server and open a tab. Step three is the one that cannot be delegated, because the thing judged is whether the result matches what you meant. A report can describe a screen. Only you can say it is wrong for your reader.

Recall before you read on

Close your eyes for a second. What are the three steps of the loop, and which one belongs to you alone? Write it down before revealing.

Change, start and open, look. The agent helps with all three, but look is yours. The question is whether the screen matches what you meant, and only you hold what you meant.

Start once, refresh after every change

Lesson 0.7 used the phrase start and open, and explained the address and the port. Here is what comes after the first time. The server keeps running, answers the same address all afternoon, and reads whatever is in the folder at that moment. So after a change you start nothing. You refresh the page: one key press.

Keep the two verbs apart. Start brings the server into existence and happens once. Refresh asks the server that already exists for the page, and happens after every change. Open is the first time you point a browser at the address; after that the tab is already there, and you refresh it.

change  →  (server still running)  →  refresh the address  →  look
Restart every time

Stop the server, run the start command again, hope the port is free, open a new tab, find the page again. Four steps, one new way to fail.

Start once, refresh

Leave the server in its own terminal window. Change, refresh, look. The terminal prints a line for each visit, which is your proof the page came from there.

Two facts make this safe. The page is read from disk on each request, so an edit shows on the next refresh with no rebuild; I checked by editing a file and asking for the same address again. And the server keeps running until you stop it, so a second copy on the same port fails — MDN's advice for a busy port is to choose another number and use it in the address.[1]

If the change is not on screen

Refresh first. Still nothing? Check that the address matches the one the agent printed, port included. Then look at the terminal window: if you closed it, the server stopped and the browser will say it cannot connect. Restart the server and reload. If a recent edit still will not appear, the browser may be reusing a stored copy of the page; browsers keep responses and reuse them.[2] A new tab usually settles it.

Do not skip the server by double-clicking the file. The address then starts with file://, and browsers can block a local page's requests for its own stylesheet, pictures or script, so it looks broken for no reason you can see.[1]

Then look — five questions, five seconds

Looking is a skill with a checklist. Run these in order, and answer to yourself.

  1. Is the thing I asked for there? Repeat your request in your own words, then find each part on the screen. "Bigger heading" means you can point at a bigger heading, not remember that the agent said it made one.
  2. Is anything else different? Look at the change's neighbours. A heading that grew may have pushed a button off the bottom. Most surprises live here.
  3. Does it survive a narrow window? Drag the window narrow, or use the browser's phone-sized view. Many readers arrive on a phone.
  4. Are there holes? A blank box where a picture should be, text sitting on top of other text, a doubled line, an empty space that looks like a mistake.
  5. Am I looking at the right page? Same address as the agent gave you? The page you edited, not an older copy of it?

One change per round. Ask for five things and get three, and you cannot tell which misbehaved; if something unrelated breaks, you cannot say which change did it. Five small rounds cost five minutes and leave you able to describe what happened.

And if you cannot find your change, it is not done, whatever the report says.

A real pattern, anonymized

A user ran a small app after every change; their whole ritual was two words, "start and open". One round, they asked for the controls to live inside the running app. The agent built a separate launcher window instead. The user saw it on the first look, about two minutes in, and said the controls were in the wrong window. The agent restated what it had misunderstood and fixed it in one turn. Nothing was broken; the request had been read one way and meant another, and the screen was the only place that difference showed.

Say what you saw, not what you think

After looking, you send the report. The useful version describes the screen in order and compares it with what you expected. "The button is broken" sends the agent hunting. "The button is there but sits under the last paragraph; I expected it above" tells it where to look and leaves the cause to the party that can read the file.

youI looked at localhost:8000. The heading is bigger. On a narrow window the menu runs off the right edge, no scrollbar. I expected it to wrap onto two lines.
agentChecking the menu styles. The row is fixed to one line with no wrapping allowed.
youYes — make it wrap. Then I'll look again.
Note what the user did not do: guess at CSS, or accept "it should be fine". One observation, one fix, one more look.

Two sentences are enough when they are about the screen. Naming the file is the agent's job; naming the symptom is yours.

Asking each agent to start and open

The request is the same everywhere, and it is worth adding one clause: ask for the start command. That is what makes you independent next time.

Start the app and open it in my browser. Give me the address and the exact command you used to start it, so I can start it myself next time. Do not change any code until I have looked.

Claude Code ships two skills for this loop. /run will Launch and drive your app to see a change working; /verify will Build and run your app to confirm a code change does what it should.[3] Its best-practices page says running the app and looking catches the kind of problem that tests and typechecks miss.[4] Plain words work too; the skills are a shortcut.

In the Codex CLI, browser control is not built in: Browser isn't available in Codex CLI or the Codex IDE extension.[5] So ask Codex to start the server and print the address and command, then open the address yourself. In the ChatGPT desktop app, a built-in browser gives you and the agent a shared view of websites and local web apps inside a chat, to preview a page.[5]

omp has its own browser tool. /browser visible shows the browser it controls; the bare command toggles the browser between headless and visible and restarts it.[6] If the tab does not appear, ask omp what it did and open the address it printed. The plain request above works either way.

Do it in your own agent

The change should appear within a second of a refresh, and the terminal should print a line each time your browser asks for something. Close that terminal and reload: the address stops answering, which shows that the server, not the agent, is what puts the page on your screen.

Check yourself

Question 1 of 3

The agent says your heading change is in the files. What comes next?

The change is a claim until you have seen the screen. Refreshing the address costs a second, and your eyes settle it. Asking again collects another claim; reading files tells you the code changed, not what appears.

Question 2 of 3

You opened the page by double-clicking the file. What can follow?

A file:// address makes the browser treat your own pictures, styles and scripts as cross-origin requests, so they can be blocked. Serving the same folder over http://localhost avoids that and matches how the live site will load.

Question 3 of 3

You refreshed and your change is not on the page. Best next move?

Say what you see and let the agent find out why: wrong address, a stopped server, a stale copy, or an edit in another file. Making a second change before the first is explained leaves you unable to tell which one mattered.
