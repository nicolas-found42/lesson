Commit messages, and what a commit includes

A commit is a labelled save point. The label is the only part you will read six weeks from now, and the label can lie about what the commit holds. This lesson fixes both halves.

About 15 minutesBuilds on: 3.2 Repository, working tree, uncommitted changeWin: you can choose what goes into a commit and name it honestly

Why this matters for shipping your app

When your app breaks after an agent's long run, the commit history is the list of doors you can step back through. A message like update gives you twenty identical doors and no way to choose. A message like Move the gallery filter into its own file tells you where the change you want to undo began.

There is a second problem, quieter than a bad label. A commit can contain more than the work you asked for. If you say "commit all", the save point may also hold half-finished experiments, a scratch file, or a change from a different task. Then undoing your mistake undoes someone else's work too.

The message: a title, then a reason

Git's own manual gives the shape. It is a good idea to begin the commit message with a single short (no more than 50 characters) line summarizing the change, followed by a blank line and then a more thorough description.[1] Everything before the first blank line is the title, and git uses it wherever it shows a commit in a list.[1]

GitHub's beginner guide says what the message is for: it is a description explaining why a particular change was made, so other people can understand what you've done and why.[2] That "why" is the part beginners skip. The diff already shows what lines moved. Only you can say what you were trying to achieve.

Message you will regret

update

fix

changes from agent

Write the title as the outcome, not the mechanics. "Rename util.js to helpers.js" tells you what happened but not why; "Move shared helpers out of the page script" tells a reader the intent. Both are honest. The second is more useful when you are deciding which commit to undo.

Keep the body for the things a reader cannot see: what was broken, what you ruled out, what is still not handled. Two or three sentences is plenty for a small app. If the body would need a page, the commit is probably doing too much — which is the next section.

Staging: choosing what the commit contains

The staging area is git's waiting room. Git's manual for git add describes it as what you use to prepare the contents of the next commit.[3] A plain git commit records only what is in that waiting room. That is the whole mechanism, and it is why a commit can be smaller than your working tree.

Pro Git suggests a better way to read the command than its name: think of git add more as "add precisely this content to the next commit" rather than "add this file to the project".[4] It stages the file as it is at the moment you run it. Edit the file afterwards and the newer edit is not staged; you would run git add again.[4]

So the safe habit is three moves, in order: look, pick, check.

$ git status --short
 M index.html
 M style.css
?? ideas.txt

$ git add index.html

$ git diff --staged
diff --git a/index.html b/index.html
--- a/index.html
+++ b/index.html
@@ -1 +1 @@
-<h1>Hello again</h1>
+<h1>Hello, friends</h1>

git diff --staged shows exactly what is waiting to be committed, which is what git commit will record.[5] Read those + and - lines before you commit. If something is in there that you did not mean to include, git restore --staged <file> takes it back out without touching your file on disk.

A real pattern, anonymized

A user finished a long task and typed "commit all" into their agent. The agent staged everything in the folder, wrote a short message, and made one commit. The commit held roughly thirty-five files: the finished work, but also the user's own unfinished edits from earlier in the day and a folder of experiments. Nothing was lost. But when a problem appeared two days later, that single save point could not be undone without also undoing work the user still wanted.

"Commit all" and the two commands behind it

People say "commit all" to mean at least two different things, and the tools behave differently for each.

git commit -a stages every tracked file that was modified or deleted, then commits. The manual is precise about the gap: new files you have not told Git about are not affected.[1] That sentence is the trap. You add a new page, ask for a commit with -a, and the commit is missing the page. The save point looks complete and is not.

git add -A stages everything in the working tree, including files git has never seen.[3] Now the opposite problem: scratch notes, a downloaded sample, and a config file with a key in it can enter the history alongside your fix.

Pro Git warns about the first form in plain words: This is convenient, but be careful; sometimes this flag will cause you to include unwanted changes.[4] The same caution applies with more force to git add -A, because it reaches files that were never part of the project.

The rule of thumb

One commit, one intention. If you cannot describe the commit in one title line without using "and", split it. Two small commits are easier to read, easier to undo, and easier to review than one large one.

Asking your agent for a commit

All three agents will run these commands for you. That makes the wording of your request matter more, not less: "commit" is not a precise instruction. Say which work you mean, and ask to see the list first.

Show me `git status --short` before you stage anything.

Then stage only the files changed for the empty-list message.
Show me `git diff --staged`, and propose a one-line commit message
plus a two-sentence body. Do not commit until I say go.

The last sentence keeps the decision with you, which is the same approval habit the earlier lessons asked for. When the list appears, look for files you do not recognise. A name you cannot explain is a reason to ask, not a reason to continue.

Recall before you read on

Without scrolling up: what does git commit -a include, and what does it leave out? Then say what git add -A adds that -a does not.

-a stages tracked files that were modified or deleted. It leaves out every new file git has not been told about. git add -A also picks up those new, untracked files — which is why it can sweep in notes, downloads and stray experiments.

Try it in your own project

Do this now (about 5 minutes)

Your last step should look like this, with your own file name and message:

$ git log -1 --stat
commit 3f0ceaa...
Author: You <you@example.com>

    Change the greeting to mention friends

 index.html | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

One file, one line changed, one clear title. The other modified files are still in your working tree, untouched — and git status will say so.

How the three agents handle it

Anthropic's overview says it works directly with git. It stages changes, writes commit messages, creates branches, and opens pull requests.[6] Because it writes the message itself, read the message before you accept it. A vague title from an agent is still a vague title in your history.

Codex has a review command for exactly this moment: codex review --uncommitted gives a non-interactive review of uncommitted changes, and its options say it covers staged, unstaged, and untracked changes.[7] Run it before committing if you want a second read of what is about to go in.

omp's docs are clear that committing is your decision: changes are not committed unless you ask for a commit.[8] Its documentation comes only from its own authors, so check anything surprising with your teacher.

The commands are the same in all three. Only the wording you use to request them differs.

Check yourself

Question 1 of 3

Why keep one commit focused on one change?

A focused commit has one honest title and one reason. When something breaks, you can step back over exactly that change without dragging unrelated work with it.

Question 2 of 3

What does git commit -a include?

The manual says new files git has not been told about are not affected. That is how a commit can look complete while a freshly created page is missing from it.

Question 3 of 3

What belongs in the title line of a commit message?

Git recommends a single short line summarizing the change, then a blank line and a fuller description. File names and timestamps are already stored by git; the title should say what changed for a person.
