Static or dynamic, and what hosting means

Some apps are a pile of files that a host hands over untouched. Others need a program running all the time. Which one you are building decides whether free hosting is enough.

Why this matters for shipping your app

You have made a page appear on your own screen. To let a friend open it, the files have to live on a machine that stays awake and answers requests. That arrangement is called hosting. Before you choose a host, you need one fact about your app: is it static or dynamic? That single fact decides whether a free host is enough, whether you need a database, and whether your agent can finish the job in one sitting.

A page is a set of files

Lesson 0.8 gave you the three languages: HTML describes the content, CSS styles it, JavaScript makes it respond. Add images, fonts and video, and that is the whole site. Each of those is a separate file with its own address. When someone opens your page, this is what happens:

Put one page view in order

Every image and stylesheet repeats that middle exchange. A host, then, is mostly a machine that answers "here is that file". The word covers both the machine and the software on it. MDN's summary says exactly that: The term web server can refer to hardware or software, or both of them working together.[1]

Static: the host hands over files as they are

A static site is one where the host makes no decisions. It looks up the requested file and sends its bytes unchanged. MDN puts the name's origin plainly: We call it "static" because the server sends its hosted files as-is to your browser.[1]

GitHub Pages is a static host, and its own description is a good definition: GitHub Pages is a static site hosting service that takes HTML, CSS, and JavaScript files straight from a repository and publishes them.[2] Pages is available in public repositories with GitHub Free, which is why Unit 6 uses it.[2]

Static does not mean plain or old-fashioned. It means "no decisions are made on the host". The look of the page is a separate question.

The practical consequence is large. Any machine that can store files and answer requests can serve a static site. There is no program of yours to keep running, no database to keep alive, and nothing to crash at three in the morning.

Buttons are not the dividing line

Here is the mistake almost every beginner makes. Your page has a filter, a dark-mode switch, a dropdown that opens with animation. Surely that is dynamic? No. All of that JavaScript runs in the visitor's browser, on the visitor's own machine. MDN names it: Code running in the browser is known as client-side code.[3] The host still did nothing but hand over files.

Feels alive, still static

A filter that sorts a list already contained in the page. A light and dark theme. An image gallery that opens a larger picture on click. Every visitor receives the same files, and their own browser does the rest.

Actually dynamic

Comments that every visitor can read. A score that another player sees. A page assembled from rows in a database. Here the answer depends on who is asking, and on what happened before.

Ask the question this way: does one visitor's action change what the next visitor receives? If the answer is no, you can probably ship static files.

Dynamic: code runs for each request

A dynamic site adds software between the request and the reply. In MDN's words: A dynamic web server consists of a static web server plus extra software, most commonly an application server and a database.[1] The application server updates the hosted files before sending content to your browser, for example by filling a template with rows from a database.[1]

That is more power and more obligations: the program must be running whenever a visitor arrives, it may hold secrets such as a password for the database, and someone must keep it patched. Free tiers exist, but the shape of the work changes. Unit 8 covers backends properly; for now, the point is only that this is a different kind of project.

Recall before you read on

Without scrolling up: what does "static" mean here, and why does a page with buttons and animations still count as static?

Static means the host sends stored files exactly as they are, making no decision per visitor. Buttons and animations are produced by JavaScript running in the visitor's browser (client-side code), so the host still only handed over files.

What hosting actually is

Hosting is somebody else's computer, kept on and connected, with software that answers requests for your files at a public address. MDN lists why people rent one instead of using their own machine, starting with the plainest reason: A dedicated web server is typically more available (up and running).[1] Your laptop sleeps, closes its lid, and joins a different network when you take it to a café.

The address and the machine are two different things. The address is what a person types or clicks; the files still have to live somewhere that answers. When you later read about custom domain names (lesson 6.10), that is the address changing, not the host.

The trap: a folder that is too big to publish

Static hosting is simple, but it is not unlimited. GitHub states the ceiling in one short line: Published GitHub Pages sites may be no larger than 1 GB.[4] A beginner rarely knows this number, and an agent working alone will not raise it unless it measures first.

A real pattern, anonymized

A user asked an agent to put a gallery of 3D models online so friends could browse it from a link. The project folder held about 3.6 GB, mostly model files; the free host allows 1 GB. The agent measured the folder before choosing a plan. It published only the small app and its index, and made the page load the large model files from the code-hosting site at a fixed version, so the links would never change. Then it opened the real public address and checked that a model loaded. The user's one message had said nothing about size, because the user did not know the limit existed.

Two lessons sit in that story. First, the limit is real and worth measuring before you promise a link to anyone. Second, the fix was a design decision, not a compression trick: keep the published site small and let big files live elsewhere. Lesson 6.4 goes into that trade-off; lesson 6.2 covers the step that turns source files into the published set.

Three questions that decide

You do not need to understand servers to classify your own idea. Ask:

  • Does one visitor's action change what another visitor sees? Comments, shared scores, bookings, a leaderboard.
  • Does anything need a secret? A password or an API key that must not be visible to visitors.
  • Must data survive after the visitor closes the browser, on your side? Orders, accounts, messages sent to you.

If all three answers are no, start static. You can ship this week, for free, with a public link. If one answer is yes, you are building a dynamic app, and the honest move is to say so before the agent starts rather than discover it during deployment.

Do not add a server as a precaution

A server adds a second thing to run and keep secure, often with a secret to protect and a bill once free limits are passed. Add one when a real user needs something static files cannot do. Lesson 8.9 covers the choice between hosting, functions and a database.

Do it: have your agent classify your folder

Your agent can read the folder and tell you which side you are on. This works the same in all three tools; the only rule is to keep approval prompts on (lesson 0.6).

Read the files in this project folder and answer in plain words.
1. Which files would a browser need in order to show the site?
2. Does anything here have to run on a server, or can every file be sent exactly as it is?
3. What is the total size of the files that would be published?
Then tell me: could this go on a free static host with a 1 GB limit? If not, say what you would leave out and where the rest would live.
Do it in your own agent

You should get a short list of files, a verdict (static or needs a server) with a reason, and a size in megabytes. The follow-up should name something like shared data, a login, or a secret key. If the agent only describes static sites in general and never opens your files, ask it to list the folder first.

Check yourself

Question 1 of 4

Which of these needs a server, rather than static files?

A guestbook stores what one visitor wrote so the next visitor can read it. The other three are files plus JavaScript running in each visitor's own browser.

Question 2 of 4

What does "static" describe about a site?

"Static" is about what the host does, not what the page looks like. The host looks up a file and returns it unchanged, every time, to everyone.

Question 3 of 4

Your folder is 3.6 GB and the free host allows 1 GB. What is the sound move?

Keep the published site under the limit and let large assets live somewhere built for large files. Deleting content or ignoring the quota both fail at the moment you share the link.

Question 4 of 4

Which sentence best describes hosting?

Hosting is a machine kept on and reachable, with software that answers requests. Your laptop can do it in principle, but it sleeps and changes networks, which is why people rent one.
