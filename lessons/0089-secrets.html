Secrets: what they are and why they never live in your code

The moment your app talks to a paid service, you hold a password-like value that must never end up in a file that git tracks. Knowing what counts as a secret — and why code is the wrong home for one — is the foundation for everything else in this unit.

About 15 minutesNeeds: 3.3 .gitignoreWin: you can name what a secret is, and audit a project so no real secret is tracked

Why this matters for shipping your app

So far your apps have been static: pages that anyone can open, with nothing to protect. Real apps usually do more — send a message through a delivery service, look up data in a paid catalogue, call an AI model. Almost every service like that hands you a secret: a password-like value that proves the request came from you, and bills your account. Put one in the wrong place and anyone who sees your code can spend your money or read your data. This lesson teaches you to spot secrets and keep them out of your project's saved history; the next lessons (8.2 env vars, 8.3 never print or commit) teach where they do live and what to do after a leak.

What counts as a secret

A secret is any value that lets someone act as you. The common kinds:

  • API keys. Long strings a service gives you so it knows which account to charge. An API is a way for programs to talk to a service; the key is your membership card.
  • Passwords and login tokens. A token is a temporary password a service hands out after you sign in.
  • Connection strings. One string that names a database and includes the password to open it.
  • Private key files. Files (often ending in .pem or .json) that let a program sign in to a cloud service without a human typing a password.

Notice what these share: possession is enough. There is no second question, no "are you really you?". Whoever holds the value is you, as far as the service is concerned. That is why the bar for handling them is higher than for ordinary files.

Why code is the wrong home

The tempting move is to paste the key straight into the code next to the line that uses it. It works — once. Then the file gets committed, and three things happen that are hard to undo.

First, a commit is a snapshot that never fully goes away. Git, the version control tool you have been using since Unit 3, thinks of its data more like a series of snapshots of a miniature filesystem.[1] Deleting the line tomorrow changes future snapshots; the old one still contains the key, in the same repo, forever unless you rewrite history — which GitHub documents as carrying a high risk of recontamination, because old copies keep resurfacing from forks and caches.[4]

Second, a public repo is a place scanners watch. GitHub runs a service that looks for accidentally committed credentials: When credentials like API keys and passwords are committed to repositories as hardcoded secrets, they become targets for unauthorized access.[2] The scanners exist because automated programs crawl public commits looking for key patterns the moment they appear. Some protection exists — GitHub's push protection blocks pushes that contain secrets before they reach your repository[3] — but it covers known key formats only, and not every host offers it. Treat it as a net under the tightrope, not the tightrope.

Third, a committed secret leaks to everyone who can see the repo. For a public repository that is the whole internet. For a private one it is every collaborator, every agent session with repo access, and every integration you ever connect. The safe assumption is: once it is in a commit, assume it is public, and act accordingly.

This is the same rule that keeps secrets out of the repo in the first place: lesson 3.3 listed .env (the conventional name for a local file of such values) among the things .gitignore should exclude. Unit 8 is where that one-line habit becomes a full practice.

Secrets and your agent

Your agent reads files and runs commands, so it will inevitably be near your secrets. Two habits keep that safe.

Do not paste secrets into the conversation. A session is saved on your machine, and what the agent prints can end up in logs, screenshots, or a window a friend glances at. One agent even documents the risk about its own storage: The local database is not encrypted at rest.[5] If a value must reach the agent, point it at the file that holds it rather than typing the value.

A real pattern, anonymized

A user asked an agent to add sign-in to a small web app. The setup succeeded, but along the way the agent ran a command that printed a key's value into the session, and a screenshot taken later caught part of a second key on screen. The agent noticed both exposures and said so; the user replaced both keys in the service's console. The lasting fix was procedural: from then on the pair moved values through a file the agent reads directly, never through text pasted or printed into the conversation.

Let the agent check you. Because the agent is good at searching text, it is also good at finding secrets that should not be there. The practice section below has you ask for exactly that audit — with one guard: ask for file names only, so the check does not print the values it finds.

Recall before you read on

Name the four kinds of secret from this lesson, and the one sentence that explains why a committed secret is considered leaked even if you delete it later.

API keys, passwords and login tokens, connection strings, and private key files. A commit is a snapshot: deleting the value later changes only future snapshots, so every old snapshot — in the repo, its clones, and its forks — still contains the secret.

Practice: audit a project for secrets

Do it now (read-only, nothing is changed)

Step 2 should produce a short list of file names with no values shown — if the agent prints an actual key, stop reading and treat that key as exposed (lesson 8.3 covers what to do). Step 4 printing nothing is the goal: it proves the file has never been part of a snapshot. If a commit is listed, do not delete anything yet; bringing that file to your next session, or to lesson 8.3, is the correct next move.

Check yourself

Question 1 of 4

Which of these is a secret?

A secret is any value that lets someone act as you. A password qualifies; page titles, images and links are ordinary content that is fine to commit.

Question 2 of 4

Why is a commit the wrong home for a secret?

Git stores snapshots, so removing the line later leaves the secret in every earlier snapshot — in the repo, its clones, and any forks. Nothing about speed, size, or agent willingness is the issue.

Question 3 of 4

You find a real API key in an old commit. What comes first?

GitHub's own guidance: as a first step you need to revoke and/or rotate that secret. Cleaning history is harder, slower, and never undoes the exposure — a dead key cannot be abused.

Question 4 of 4

What does GitHub's push protection do?

Push protection checks a push for known secret patterns and blocks it before the commit reaches the repository. It is a safety net for recognized formats, not a substitute for keeping secrets out of code.
