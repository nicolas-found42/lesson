One command gate: put the checks in the repo

When all your checks live behind one short command, the agent can grade its own work before it tells you it is finished. You type the same command, and you get the same verdict.

About 15 minutesBuilds on: 2.3 What a test is · 1.12 The project rules fileWin: you can run one command and know whether the project is acceptable

Why this matters for shipping your app

You are going to put an app in front of other people. Before that, something has to answer a plain question: does this project still work? You can answer it by clicking around for ten minutes, but you will get tired and skip steps. The agent has the opposite problem. It stops when the work looks done. Anthropic's own best-practices page names the failure: Claude said it was done and it wasn't quite, usually because it had no way to check its own work.[1]

A gate fixes both problems at once. A gate is one command, stored in your project, that runs every check you care about and ends with a pass or a fail. The agent runs it. You run it. A robot can run it later. Nobody has to remember the list.

Pass or fail is the whole contract

Every command on your computer finishes with an exit code: a small number the shell keeps after the command ends. Zero means success. Anything else means something went wrong. Most tools you will use follow this, and their documentation says so. Node's test runner states: If any tests fail, the process exit code is set to 1.[2] Deno's type checker exits with a non-zero status code if there are type errors.[3]

That little number is why a gate works. The agent does not need to judge your code. It needs one thing that comes back pass or fail, and then it can loop: make a change, run the gate, read the failure, fix it, run again. Claude Code's guide puts it exactly this way: Give Claude something it can run that comes back pass or fail.[1]

Two ordinary homes for the gate

The gate must live in the repository, as a file that is committed along with the app. If it lives in your head, in a chat message, or in your terminal history, it disappears the moment someone else — or a fresh agent session — arrives.

There are two common places to put it, and neither is more correct than the other.

A package script

A JavaScript project usually has a package.json file with a scripts section. npm run check runs an arbitrary command from a package's "scripts" object, and npm runs it from the root of the package folder.[4] The command is short and the tool is already installed with Node.

A Makefile

A Makefile holds named rules. A rule has a target, a colon, and a recipe — the commands to run.[5] Recipe lines must start with a tab character, a detail the manual warns catches the unwary.[5] Declaring the target .PHONY means "this is an action, not a file", so it runs every time.[6]

The same gate, written both ways, for a small project with one source file and one test file:

# Makefile
.PHONY: check
check:
	node --check price.js
	node --test

# package.json
"scripts": { "check": "node --check price.js && node --test" }

The && matters. It means "run the next command only if this one succeeded", so the gate stops at the first failure instead of burying it under later noise. With several checks, the order should be cheapest first: a syntax check takes a second, the tests take longer.

A real run, failing then passing

I ran this in a throwaway folder with a small discount function and one test that says ten percent off 50 is 45. First, the function was wrong.

youmake check
tool✖ 10 percent off 50 is 45
AssertionError: Expected values to be strictly equal:
40 !== 45
make: *** [check] Error 1
The gate failed, and it said why: 40 is not 45. Exit code 2.
you(fix the function)
youmake check
tool✔ 10 percent off 50 is 45
ℹ pass 1
ℹ fail 0
Exit code 0. That is a verdict, not an opinion.

Notice what the agent gains here. It does not have to reason about whether the discount looks right. It runs a command, reads a number, and either continues or fixes something. You gain the same thing, plus one line to ask for when you want proof.

A real pattern, anonymized

In one session a user typed only "does the project work?" The agent ran the project's documented checks — formatting, type checking, linting, the test suite — plus a real start-up and a quick smoke test, and answered yes. It also listed what it had not tried: real credentials, live providers, some slower tests. That honest gap list became the user's next request, with a spending cap attached. In another session, the whole build phase rested on a single command: the user wrote a three-word instruction to implement a reorganization, and the agent knew it was finished only because that command came back green.

Recall before you read on

Without scrolling up: what does an exit code of zero mean, and why is that number more useful to an agent than a paragraph of explanation?

Zero means the command succeeded; any other number means it failed. The number is a verdict the agent can act on without judging the code itself, so it can keep fixing and re-running until the gate passes.

Name the gate in the rules file

Lesson 1.12 taught the rules file: a small text file at the top of the project that the agent reads at the start of every session. It is the natural place to record the gate, because the gate is a procedure you do not want to repeat in every prompt. Claude Code's guide calls this the single most useful line in your CLAUDE.md when the repo already has checks.[1]

Put the line in CLAUDE.md, which Claude Code loads as persistent instructions for a project.[7] The page is careful about what that buys you: Claude treats these files as context, not enforced configuration.[7] So the line tells Claude what to run; it does not force it to run.

Put the line in AGENTS.md. Codex reads AGENTS.md files before doing any work.[8] The same caveat applies: this is guidance the model reads, not a lock on its behaviour.

Put the line in AGENTS.md at the repository root, which omp loads and applies throughout the session.[9] Keep it to the command and one sentence about when to run it.

Exact filenames and load rules differ slightly between tools; lesson 1.12 has the table. The sentence you write inside the file is the same. 
## Checks
Before you report a task as done, run `make check` from the repository root.
It must exit with code 0. If it fails, read the output, fix the cause, and run it again.
Paste the last ten lines of its output in your final message, including any counts.

The last line is the part beginners skip. A gate produces evidence, and evidence is what turns "done" into something you can check without redoing the work. Lesson 2.2 covers that habit; here you are just arranging for the evidence to exist.

Where a gate stops short

A gate is only as honest as the checks inside it, and it can only see what it runs.

  • It says nothing about a check you left out. A project with no browser test can pass its gate while the page is blank on a phone. Lesson 2.7 takes that case.
  • A skipped test is not a passing test. Node's runner reports skipped tests separately and they do not affect the process exit code.[2] Read the counts, not only the final line.
  • Green on your laptop is not green in the cloud. A command can pass locally because a file or a setting happens to exist there. Lesson 2.12 is about that gap.
  • The gate itself can be wrong. A test with a mistaken expectation fails a correct app, and then "fixing" the code makes things worse. Lesson 2.11 covers this.
Do it in your own project

First run: every check passes and the command exits 0. Second run, after your deliberate break: it fails, names the broken check, and exits with a non-zero code. If the second run still passes, the gate is not really checking that part of the project — fix that before you trust it.

Check yourself

Question 1 of 3

What is a one-command gate?

A gate gathers your checks behind one name and returns pass or fail. Printing changes, opening the app and listing errors are separate jobs that a gate may call, but none of them is the gate itself.

Question 2 of 3

The agent reports "all tests pass". What should you ask for?

The claim is only as good as the command behind it. A named command, plus its output and counts, is evidence you can check in seconds. The other questions do not test the claim at all.

Question 3 of 3

Where should the gate live so everyone uses the same one?

A message is forgotten and terminal history is local to you. A file in the repository travels with the project, so every session, every helper and later the cloud runner use the same command.
