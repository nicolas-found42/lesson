Remote, origin and push

A commit saves your work on your own machine. A push copies those commits to a server, where a lost laptop cannot take them and where Unit 6 can publish them.

Why this matters for shipping your app

Your app becomes public in Unit 6, and what gets published is not a folder on your desk but a repository on GitHub holding a copy of your commits. Until you push, every commit is one dropped laptop away from gone, and no link can point at it.

You need not memorise commands, but you must know what a push does, because the agent will report one and you must judge whether it happened. Lesson 0.1's habit applies: a success message is a claim until you look at the server.

What a remote is

A remote is a named address of another copy of the same repository. GitHub explains it plainly: a remote URL is Git's fancy way of saying the place where your code is stored.[1] That place may be your repository, a copy someone else made, or a server at a company.

Git stores the name and URL and tries when you ask; it does not check reachability or permission. A remote can therefore be configured correctly and a push still fail: configuration and permission are two different facts.

GitHub puts the pairing plainly: Git associates a remote URL with a name, and your default remote is usually called origin.[1]

origin is a nickname, not a place

Origin is the conventional name for the remote you treat as the main copy. It is not a website and not special to GitHub. Pro Git: if you cloned, origin — that is the default name Git gives to the server you cloned from[2]. You could call it backup; almost nobody does.

To see what your project actually has, list the names and addresses:

$ git remote -v
origin  https://github.com/YOUR_USERNAME/my-app.git (fetch)
origin  https://github.com/YOUR_USERNAME/my-app.git (push)

Two lines appear because Git keeps one address for reading (fetch) and one for writing (push); normally they match. A project with no remote configured prints nothing at all. That is a normal starting state, not an error.

Recall before you read on

Without scrolling up: what two things does a remote store, and what does an empty result from git remote -v tell you?

A remote stores a name (usually origin) and a URL pointing at another copy of the repository. An empty list means no remote is configured, so there is nowhere for a push to go until you add one.

Push sends commits, not files

This is the distinction that trips up most beginners. A push copies commits, not the current contents of your folder. An edit you never committed sits inside no commit, so it has nothing to travel with.

Git's reference states the simplest form and its meaning in two lines: The simplest way to push is git push <remote> <branch>. and git push origin main will push the local main branch to the main branch on the remote named origin.[3]

I ran this in a throwaway project. After pushing three commits, then editing one file without committing it:

$ git status -sb
## main...origin/main
 M index.html

$ git push
Everything up-to-date

The modified file shows as M index.html, yet the push had nothing to send: that edit was never committed. The line ## main...origin/main, with no ahead or behind, means your branch and its remote counterpart are level. After committing another change without pushing, the same command printed [ahead 1]: one commit exists only locally. That status line is your cheapest check that a push is pending.

A real pattern, anonymized

A user asked their agent to commit and push everything. The agent pushed to one copy of the repository they owned, then paused before a second, shared copy: the user had said not to touch it. When the user answered "push all", the push was refused for lack of permission. Nothing in the code was wrong; the account had no write access there. The user granted access in the browser, said "I gave access", and the agent retried the same push successfully. It could not have fixed this itself, and did not pretend it had.

A push is an act on someone else's machine, and permission belongs to your account, not the agent's cleverness. A refusal is information, not a bug to route around; lesson 3.12 covers the messages.

The first push: naming the branch once

On GitHub, create an empty repository and copy its URL. GitHub's instructions for an existing local project are this pair of commands: git remote add origin REMOTE-URL, then git push -u origin main[4]. The same page says: To avoid errors, do not initialize the new repository with README, license, or gitignore files.

The -u is the part worth understanding. Git's documentation says it adds an upstream (tracking) reference, used by argument-less git-pull[3]. In plain words, it records that your local main belongs with origin/main, so later git push needs no arguments. Pro Git calls these tracking branches and defines them as local branches that have a direct relationship to a remote branch[5].

That relationship lets git status say ahead 1 or behind 2. Without it, Git notes, git push may fail if you haven’t set an upstream for the current branch[3] — the confusing first-push failure -u prevents.

agentPushed. Your branch tracks origin/main. I did not check the page renders; that is Unit 6.

Your GitHub account is the permission

GitHub requires a personal account and a verified email address before you can create a repository[6]. Signing up is a browser task and it is yours: the agent never needs your password. Over an HTTPS address Git asks for credentials, and GitHub says Password-based authentication for Git has been removed, so you enter a personal access token instead[1]. A credential helper can remember it.

Before your first push

Never commit or push passwords or API keys. GitHub's import guide warns plainly: Never git add, commit, or push sensitive information, for example passwords or API keys[4]. A pushed secret is harder to remove than an unpushed one, because the server now has a copy. Lesson 3.3 keeps such files out of commits; Unit 8 covers what to do after a leak.

What a push does not do

You did thisWhat is on the server afterwards
Edited a file, did not commitNothing new. The edit stays local.
Committed on a branch you never pushedNothing new. A branch is a named line of commits; only pushed lines appear.
Committed and pushed mainThose commits, on the remote's main.
Pushed, but your site still looks oldThe commits are there; publishing is a separate step (lesson 6.6).

A push is also refused, not merged, when someone else pushed first: Pro Git says your push will rightly be rejected and you must incorporate their work first[2].

Checking it yourself

Not evidence

"Pushed successfully." One sentence in a chat window. It may be true, and it may describe a push to a different remote than the one you meant.

Evidence

## main...origin/main with no ahead, plus the commit listed on the repository page in your browser. Two independent views agree.

Do it in your own project 
This project has commits on main and no remote yet.

Do this one step at a time, and show me each command before running it:
1. Add my GitHub repository as the remote named origin. The URL is:
   PASTE_YOUR_REPO_URL_HERE
2. Push main and set it to track origin/main.
3. Show me the output of `git remote -v` and `git status -sb`.

Do not rewrite history, do not force push, and do not commit any file I have not reviewed.
If the push is refused, stop and tell me the exact message instead of trying another approach.

Two origin lines pointing at your repository; a push reporting the new branch or the commits sent; a status line reading ## main...origin/main with no ahead; and the same commit message listed on the repository page. If the status still says ahead, the push did not happen, whatever the summary said.

If your agent asks for approval

A push leaves your machine, so all three agents can be set to ask first. Keep the asking mode on while you learn; lesson 0.6 owns the details.

Do not assume you will be asked. Anthropic's docs say that from v2.1.283, auto mode is the built-in starting permission mode, and that page lists what each mode allows without asking.[7] Switch to a mode that asks before a push, as lesson 0.6 describes.

Codex separates the sandbox from approvals; its docs say For most work, start with Ask for approval, and /permissions opens the same settings in the CLI.[8] Its security docs also note that By default, the agent runs with network access turned off, and a push needs the network.[10]

omp's docs say The built-in default is yolo, which prompts for nothing, and recommend tools.approvalMode: write for interactive use.[9] If you have not changed that setting, ask before letting an agent push.

Check yourself

Question 1 of 4

What does a remote in Git actually point at?

A remote is a name plus a URL for another copy of the same repository. It is not a folder on your disk and not a branch.

Question 2 of 4

You edit a file but do not commit it. What does push send?

Push copies commits. An edit inside no commit stays on your machine until you commit it and push again.

Question 3 of 4

What does git push -u origin main do the first time?

-u sets the upstream reference, so later git push and git status know which remote branch belongs with your local one. Nothing is downloaded and nothing is protected.

Question 4 of 4

A friend opens your link and sees an old page. Why?

The published site is built from the repository on GitHub, so a commit that stayed on your laptop cannot appear there. Check git status -sb for ahead before blaming the host; lesson 6.6 separates deploying from pushing.
