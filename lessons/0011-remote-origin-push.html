Remote, origin and push

A commit saves your work on your own machine. A push copies those commits to a server, where they can survive a lost laptop and where the rest of this course can publish them.

About 15 minutesBuilds on: 3.1 Why save points existWin: your commits exist somewhere other than your laptop

Why this matters for shipping your app

Your app becomes public in Unit 6, and what gets published is not a folder on your desk. It is a repository on GitHub: a server holding a copy of your commits. Until you push, every commit is one dropped laptop away from gone, and no link can point at it. This lesson moves your work from "mine, here" to "ours, online".

You need not memorise the commands, but you must know what a push does, because the agent will report one and you will have to judge whether it happened. The habit from lesson 0.1 applies: a success message is a claim until you look at the server.

What a remote is

A remote is a named address of another copy of the same repository. GitHub's own explanation is plain: A remote URL is Git's fancy way of saying "the place where your code is stored."[1] That place can be your own repository on GitHub, a copy someone else made, or a server inside a company.

Git never assumes the address is reachable or that you are allowed in. It only stores the name and the URL, and tries when you ask it to. This is why a remote can be configured correctly and a push can still fail: configuration and permission are two different facts.

GitHub says the name and the address travel together: Git associates a remote URL with a name, and your default remote is usually called origin.[1] That single sentence explains most of the confusing vocabulary in this lesson.

origin is a nickname, not a place

Origin is the conventional name for the remote you treat as the main copy. It is not a website, and it is not special to GitHub. Pro Git describes the same convention: if you cloned a repository, origin — that is the default name Git gives to the server you cloned from[2]. You could call it home or backup; almost nobody does, and every tutorial you read will say origin.

To see what your project actually has, ask Git to list the names and addresses:

$ git remote -v
origin  https://github.com/YOUR_USERNAME/my-app.git (fetch)
origin  https://github.com/YOUR_USERNAME/my-app.git (push)

Two lines appear because Git stores one address for reading (fetch) and one for writing (push); for a normal setup they are the same. On a project you have only kept on your laptop, this command prints nothing at all. That is the normal starting state, not an error.

Recall before you read on

Without scrolling up: what are the two things a remote stores, and what does an empty result from git remote -v tell you?

A remote stores a name (usually origin) and a URL pointing at another copy of the repository. An empty list means this project has no remote configured yet, so there is nowhere for a push to go until you add one.

Push sends commits, not files

This is the distinction beginners get wrong most often. A push copies commits to the remote. It does not copy the current contents of your folder. Anything you edited but never committed is not part of a commit, so it has nothing to travel with.

Git's reference for the command states the simplest form directly: The simplest way to push is git push <remote> <branch>. It then spells out the meaning: git push origin main will push the local main branch to the main branch on the remote named origin.[3]

I ran that sequence in a throwaway project to see what the terminal reports. After one commit, a second commit, and one uncommitted edit, the state was:

$ git status -sb
## main...origin/main
 M index.html

$ git push
Everything up-to-date

Two things are worth noticing. The modified file is visible as M index.html, yet the push had nothing to send, because that edit was never committed. And the line ## main...origin/main says your branch and its remote counterpart are level: no arrow, no ahead or behind. After one more commit the same command printed ## main...origin/main [ahead 1], meaning one commit exists only locally. That status line is the cheapest check you have that a push is pending.

A real pattern, anonymized

A user asked their agent to commit and push everything. The agent pushed to one copy of the repository owned by the user, then paused before a second, shared copy: the user had earlier said not to touch it. When the user answered "push all", the push was refused for lack of permission. Nothing in the code was wrong; the user's account simply had no write access to that shared copy. The user granted access in the browser, said "I gave access", and the agent retried the same push successfully. The agent could not have fixed this itself, and it did not pretend it had.

The lesson in that pattern: a push is an act on someone else's machine, and permission belongs to your account, not to the agent's cleverness. A refusal is information, not a bug to route around. Lesson 3.12 covers the refusal messages; this lesson only asks you to recognise one when it appears.

The first push: naming the branch once

On GitHub, create an empty repository, copy its URL, and attach it to your local project. GitHub's own instructions for an existing local project are exactly this pair: git remote add origin REMOTE-URL, then git push -u origin main[4]. The page also says: To avoid errors, do not initialize the new repository with README, license, or gitignore files. Those files would exist on both sides before the first push.

The -u is the part worth understanding. Git's documentation says it adds an upstream (tracking) reference, used by argument-less git-pull[3]. In plain words: it records that your local main belongs with origin/main, so later you can type git push with no arguments and Git knows where to go. Pro Git calls these tracking branches and explains that they are local branches that have a direct relationship to a remote branch[5].

That relationship is also what lets git status tell you ahead 1 or behind 2, and Git's push reference notes that git push may fail if you haven't set an upstream for the current branch[3] — the confusing first-push failure that -u prevents.

Your GitHub account is the permission

GitHub requires a personal account and a verified email address before you can create a repository[6]. Signing up is a browser task, and it is yours: the agent never needs your password, and you should not paste one into a chat. When you push over an HTTPS address, Git asks for credentials; GitHub notes that its Password-based authentication for Git has been removed and that when prompted for a password you enter a personal access token instead[1]. A credential helper can remember it for you, which is why your second push may not ask at all.

Before your first push

Never commit or push passwords or API keys. GitHub's import guide opens with that warning: Never git add, commit, or push sensitive information, for example passwords or API keys[4]. A pushed secret is harder to remove than an unpushed one, because the server now has a copy. Lesson 3.3 covers keeping such files out of commits, and Unit 8 covers what to do after a leak.

What a push does not do

You did thisWhat is on the server afterwards
Edited a file, did not commitNothing new. The edit stays local.
Committed on a branch you never pushedNothing new. Only pushed branches appear.
Committed and pushed mainThose commits, on the remote's main.
Pushed, but your site still looks oldThe commits are there; publishing is a separate step (lesson 6.6).

Two more limits belong here because they surprise people. A push is refused, not merged, when someone else pushed first: Pro Git says your push will rightly be rejected and you must incorporate their work first[2]. And a push only updates the server; it does not change your own working files, so a file you see locally is not proof that the server has it.

Checking it yourself

The agent will usually offer a summary. Replace that with two observations you can make in ten seconds.

Not evidence

"Pushed successfully." A sentence in a chat window. It may be true, and it may describe a push to a different remote than the one you meant.

Evidence

## main...origin/main with no ahead, plus the commit visible on the repository page in your browser. Two independent views agree.

Do it in your own project 
This project already has commits on the main branch and no remote yet.

Do this, one step at a time, and show me each command before running it:
1. Add my GitHub repository as the remote named origin. The URL is:
   PASTE_YOUR_REPO_URL_HERE
2. Push main and set it to track origin/main.
3. Show me the output of `git remote -v` and `git status -sb`.

Do not rewrite history, do not force push, and do not commit any file I have not reviewed.
If the push is refused, stop and tell me the exact message instead of trying another approach.

You should see two origin lines pointing at your repository, a push that reports the new branch or the commits sent, and a status line reading ## main...origin/main with no ahead. The repository page in your browser should list the same commit message. If the status line still says ahead, the push did not happen, whatever the summary said.

If your agent asks for approval

A push leaves your machine, so every one of the three agents can be configured to ask first. Keep the asking mode on while you learn; lesson 0.6 owns the details.

The prompt should appear before the command runs, and you can read the whole command in it. If you are unsure which mode you are in, the documentation's page on permission modes lists each one and what it allows without asking.[7]

Codex separates the sandbox from approvals; its documentation recommends starting with "Ask for approval" for most work, and the CLI opens the same settings with /permissions.[8] A push needs network access, so expect a prompt that names the command.

omp's documentation says its built-in default is yolo, which prompts for nothing, and recommends setting tools.approvalMode to write for interactive use.[9] If you have not changed that setting, ask before you let an agent push.

Check yourself

Question 1 of 4

What does a remote in Git actually point at?

A remote is a name plus a URL for another copy of the same repository. It is not a folder on your disk and not a branch.

Question 2 of 4

You edit a file but do not commit it. What does push send?

Push copies commits. An edit that was never committed is not inside any commit, so it stays on your machine until you commit it and push again.

Question 3 of 4

What does git push -u origin main do the first time?

-u sets the upstream reference, so later git push and git status know which remote branch belongs with your local one. Nothing is downloaded and nothing is protected.

Question 4 of 4

A friend opens your link and sees an old page. Why?

The published site is built from the repository on GitHub. A commit that stayed on your laptop cannot appear there. Check git status -sb for ahead before blaming the host; lesson 6.6 separates deploying from pushing.
