Worktrees: two checkouts, one repository

A worktree gives you a second folder showing a different branch of the same project at the same time. It removes the need to keep switching, and it creates a new way to lose track of where the agent is typing.

About 15 minutesBuilds on: 3.5 BranchWin: you can keep two checkouts straight and tell your agent which one to edit

Why this matters for shipping your app

Once your app is live, you often want two things at once: fix a bug in the version people are using, and build a feature that is not ready. Lesson 3.5 gave you branches for that, but a branch only helps while you are standing on it. One folder holds one branch at a time, so every switch rearranges the files under the agent that is working in them.

A worktree removes that shuffling. You get a second folder on disk, checked out to another branch, sharing the same history. The benefit is real and the hazard is specific: two folders that look almost identical, and an agent that will edit whichever one it was pointed at. This lesson is about the second half.

One repository, more than one folder

Git's reference defines it in two sentences: Manage multiple working trees attached to the same repository. and A git repository can support multiple working trees, allowing you to check out more than one branch at a time.[1] You keep your original folder, called the main worktree, and add others. Each extra one is a linked worktree.

I ran this in a throwaway project with one page and one commit:

$ git worktree add ../my-app-dark -b dark-mode
Preparing worktree (new branch 'dark-mode')
HEAD is now at af5932e Add home page

$ git worktree list
/…/my-app       af5932e [main]
/…/my-app-dark  af5932e [dark-mode]

There are now two folders, my-app on main and my-app-dark on dark-mode, both holding the same one page. Nothing was duplicated except the files themselves, which are small. The history, the branches, and the remote live once, in the main repository.

The mental picture

A branch is a label on a commit. A worktree is a folder that has one of those labels checked out. You can have many labels and many folders, and the folders are what an editor or an agent actually touches.

The files really are separate

Editing in one folder leaves the other alone. I added a line in the second checkout and asked both folders what changed:

$ cd ../my-app-dark && git status --short
 M index.html

$ cd ../my-app && git status --short
(no output)

$ cat index.html
<h1>My Recipe Box</h1>
<ul><li>Soup</li></ul>

The edit exists in one folder and not the other, and the second folder is not "behind": it is a different branch. That is the whole point, and it is also where beginners lose time. A change you can see in one window is invisible in the other, so a screenshot taken from the wrong folder proves something about the wrong app.

Two rules git enforces

The first rule is that a branch can be checked out in only one place. OpenAI's Codex documentation spells out why: Git only allows a branch to be checked out in one place at a time.[2] Git's reference says the add command refuses to create a new worktree when <commit-ish> is a branch name and is already checked out by another worktree.[1] I tried it:

$ git worktree add ../another main
Preparing worktree (checking out 'main')
fatal: 'main' is already used by worktree at '/…/my-app'

That refusal is a gift. It means two folders can never quietly write to the same branch, so the worst case is a change in the wrong folder, not two agents overwriting each other's commits.

The second rule concerns removal. A linked worktree can be removed with git worktree remove, and Git's reference restricts it: Only clean worktrees (no untracked files and no modification in tracked files) can be removed.[1] Uncommitted work is protected unless you force it. Removing the folder does not delete the branch; in my run dark-mode survived with its commit, ready to be checked out again in a new folder.

Recall before you read on

Without scrolling up: what does a worktree add to a project, and what does git refuse to do with a branch that is already checked out somewhere? Answer in your own words.

A worktree adds a second folder, checked out to a different branch, sharing the same repository history. Git refuses to check the same branch out in two worktrees at once, so no two folders can commit to one branch.

The failure this creates

An agent does not have a map of your disk. It has a working directory: the folder it was started in, which it treats as the project. Every relative path it edits is resolved against that one folder. Two checkouts of the same repository are, to the agent, two unrelated places, and only one of them is "here".

A real pattern, anonymized

A user's repository had a rule: do the work in a worktree, never in the main checkout. An agent ignored it, edited the main checkout directly, and reported the change as committed. A reviewer caught it, and moving those commits into the worktree took extra steps. In a different session the same class of mistake repeated more than five times: the agent's file tools resolved paths against the session's working folder rather than the checkout being prepared for release. Each edit looked successful and changed the other copy. The only signals were a diff that did not match the summary and a reviewer asking why a file was unchanged.

Notice the shape of the failure. Nothing errors. The edit lands, the tool call succeeds, the agent's summary is confident, and the file you care about did not change. This is why the habit in lesson 2.2 matters more here than anywhere else in this unit: a claim about a file is not a reading of that file.

Tell the agent where work happens

You do not need the agent to understand your folder layout. You need to remove the ambiguity before it starts, and check it after. Four sentences do most of the work:

  1. Name the folder, not the project. "Work in /…/my-app-dark" beats "work on the dark mode branch". The first is a place; the second is a label the agent must resolve.
  2. Ask it to prove where it is. "Run pwd and git worktree list before editing." Both are read-only and take a second.
  3. Ask for the diff, not the summary. "Show git status --short in that folder after the edit" turns an invisible success into evidence you can read.
  4. Say which copy must not change. "Do not edit the main checkout at /…/my-app" gives a reviewer something concrete to check against.

For larger work, the same rule can live in the project rules file from lesson 1.12, so it applies to every session rather than the one where you remembered.

Do it in your own project 
Before changing anything, run `pwd`, `git status --short`, and `git branch --show-current`, and show me the output.

Create a second checkout with:

    git worktree add ../my-app-experiment -b experiment

Then work ONLY in the new folder ../my-app-experiment. Do not edit any file in the folder you started in.

In the new folder, change the main heading in index.html to "My Recipe Box (experiment)" and commit it with a one-line message.

Afterwards, show me `pwd`, `git status --short`, and the first line of index.html in the new folder, then run `git worktree list`.

Stop there. Do not merge, do not push, and do not remove the worktree.

git worktree list shows two paths, the original on main and the new one on experiment. The heading is changed in the new folder only. In the original folder, git status --short prints nothing and index.html still has the old heading. If the original changed instead, the agent edited the wrong checkout even though its message said otherwise.

How the three agents create one

Each tool can make the second checkout for you, and each names it differently. None of them changes the underlying rule: the agent edits the folder it is running in.

Starting with --worktree or -w creates an isolated checkout and runs the session there. The docs say it is created under .claude/worktrees/<name>/ at your repository root, on a new branch named worktree-<name>.[3] A fresh checkout is not a complete copy of your setup: gitignored files like .env aren't there and dependencies aren't installed.[4]

Codex has a --worktree option that will Start in a new managed Git worktree.[5] Its worktree page describes the second copy plainly: A worktree allows you to create a second copy ("checkout") of your repository.[2] In the desktop app the same choice appears as Worktree in the new chat view.[2]

omp ships a command for this. omp worktree --help on the installed 18.16.0 reports omp worktree add ../feature and omp worktree list, and the parent help calls it Add, list, or clear git worktrees.[6] omp's documentation comes only from its authors, so treat the flags as observed behaviour of the version you installed.

A missing .env is not a bug

Because a worktree is a fresh checkout, files git is told to ignore are absent. A key file or local settings file will not be there, and an app that needs one may fail for that reason alone. Say so in the prompt, and let the agent tell you what is missing instead of pasting secrets into a new folder.

When a worktree is worth it

For a one-page site, switching branches is fine and cheaper to reason about. A worktree earns its keep when you want both versions present at once: a bug fix against the live app while a redesign continues; a second agent reviewing a change without touching the first agent's files; a long build or test run in one folder while you keep editing in the other. The cost is one more path to keep straight, and one more place an agent can put an edit.

Check yourself

Question 1 of 3

What does adding a worktree give you?

A worktree is a second checkout of the same repository, on its own branch. The history is shared; the files are separate.

Question 2 of 3

Your agent reports a committed fix, but your main folder is unchanged. What is the likely cause?

With two checkouts, an agent works in whichever folder it was started in. The edit succeeds somewhere real, just not in the folder you were looking at.

Question 3 of 3

You ask git to check out main in a second worktree. What happens?

One branch, one checkout. Git's add command refuses a branch that another worktree already holds, which keeps two folders from committing to the same line.
