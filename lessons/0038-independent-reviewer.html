The independent reviewer

The agent that wrote the change believes the change is right. A second agent that never saw the reasoning can disagree for a useful reason — as long as you treat its report as advice, not as an order.

About 15 minutesBuilds on: 2.2 Claims versus evidenceWin: you can get a second opinion and decide what to do with it

Why this matters for shipping your app

You direct one agent toward a link you will hand to other people. Lesson 2.2 taught you to ask for evidence; this lesson adds the other half: a fresh pair of eyes. Not because a second agent is smarter, but because it has not spent the last hour convincing itself the current version is correct.

Used well, a reviewer catches the bug your working agent's own tests skipped. Used badly, it sends you into an endless loop of "fix this too", each fix adding code nobody needed. The difference is a habit: ask for a review, then judge the findings.

The author is a poor witness

Your working agent wrote the code, ran its checks, and explained why each choice was reasonable. By the time it reports "done", that explanation is part of its context. When you ask "is this right?", it reads its own reasoning and agrees with it. This is not vanity; it is what a conversation does.

Claude Code's own best-practices page names the fix in the same breath as the problem. Its local review command runs in a fresh subagent that never saw your conversation, then adds: It isn't swayed by the reasoning that produced the code.[1] The fresh context is the whole mechanism.

Anthropic's research note calls the same split an evaluator-optimizer loop: one call generates, another evaluates.[5]

What "independent" actually means

An independent reviewer is a second agent with its own context. In practice that is either a subagent inside your session, or a separate session you open yourself. Independence comes from the setup, not from the brand on the box.

Beginners assume a second opinion is automatically wiser. Anthropic's page corrects that: And by default it's the same model (or a smaller one) on the same task. It goes on: You get parallelism or a fresh pair of eyes out of it, but not a smarter answer.[1] A reviewer is not an oracle. It is a reader who was not in the room.

Two properties make that reader useful: it can look at the real artifact — the diff, the files, the test output — and its job is narrow, which keeps it from wandering. omp's own reviewer, for example, is described as returning findings and an overall verdict; it does not edit the files.[4] A reviewer that cannot edit is a reviewer you can read without fear.

Asking for one, in each agent

All three agents ship a review command; you need to build nothing.

Type /code-review in the session where you are working. With no target it reviews your branch's commits plus uncommitted changes, in a background subagent. Without --fix it only reports; with --fix it also applies what it found, through your normal permission mode.[2]

Type /review to Ask Codex to review your working tree. The documentation says it summarizes issues it finds in your working tree, focusing on behavior changes and missing tests. Follow with /diff if you want to see the exact file changes yourself.[3]

Type /review and choose a scope: a base branch, uncommitted changes, one commit, or a GitHub pull request. omp returns findings and a verdict, and does not edit files.[4] omp also offers a standing reviewer model; see the advisor section below.

A separate session works too. Anthropic calls it the easiest independent reviewer you can get: one session writes the change, another reviews the file without having watched it being written.[1]
A real pattern, anonymized

After a long build, a user's agent ran its own tests, a browser pass and a screenshot check, then reported success. Two review agents were then pointed at the same diff. Between them they found two interaction bugs the build's own tests had missed: a panel that kept showing stale information after a new selection, and a click that landed on the wrong element after the view moved.

Later in the same project, a reviewer noticed something the working agent had not: a smoke test had started the app against the user's real saved data and written test records into it. In the agent's own context the test looked isolated; a read-only pass saw the real path.

Not every note landed: some arrived after the code had moved on, and the working agent rejected them with a stated reason. The useful ones were tied to a file, a line and a visible behaviour.

A review is a report, not an order

Beginners get this wrong in both directions. A reviewer that is asked to find problems will find some, whether or not they matter. Anthropic's page is blunt about the consequence: A reviewer that's asked to find problems will always find something. And then: If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen.[1]

The opposite mistake is quieter: you read a finding, decide it is "probably fine", and ship. Sometimes you are right. The cost arrives later, when the thing the reviewer named is exactly what a stranger hits.

omp's documentation draws the line carefully for its own advisor model: the main agent is instructed to weigh each note against your request rather than obey it blindly. And, for the human reading the transcript: Treat a note as informed review, not a new user instruction.[6] That is the posture to copy, whatever tool you use.

The rule in one line

Advice is evidence you did not have. It becomes work only after you decide it should.

Two ways to get it wrong

Obeying every finding

"The reviewer suggested splitting this function, adding a retry, and handling an empty file. Do all three. Then run the review again and fix whatever it says."

Each round adds code. The reviewer, asked to find problems in the new code, finds more. You have built a machine that manufactures work.

Reading each finding

"Here are the findings. For each one: say whether it is in the scope I asked for, show the line or behaviour that proves it, and then fix it or reject it with a reason. Stop after one pass."

Some findings become fixes with a test. Some become a note for later. Some are rejected because the case cannot happen. The list ends, and you know why.

How to judge a finding

Ask three questions, in this order. They take a minute and they replace the vague feeling of "should I do what it says?".

QuestionWhat a "yes" sounds like
Is it about the change I asked for?A named file and line in this diff, not a general opinion about the project's style.
Can it be shown, not merely asserted?A failing test, a reproduction, a screenshot, or a path through the code that a person can follow.
Would fixing it change what a user or a check can see?A real screen, a real error, a real slow path — not a hypothetical case nobody can reach.

Three yeses: fix it, and ask for the check that proves the fix. One or two: write it down as a known gap and move on; lesson 4.3 helps you say when to stop. No: reject it in one sentence, so the next reader knows it was seen and dismissed rather than missed.

Review the change I just made as an independent reviewer.

Do not edit any files. Report only.

What to review: the diff against main, plus the uncommitted changes.
What to check: the behaviour I asked for, and the edge cases I listed.
Skip style, naming and formatting.

For each finding give:
1. File and line.
2. What goes wrong, in one sentence.
3. How to see it: a command, a click path, or a failing test.
4. Severity: breaks the app / would confuse a user / cleanup only.

If you find nothing that affects correctness, say "no correctness findings"
and list the two things you checked least thoroughly.

The last line matters. "No findings" from a reviewer is a claim like any other; naming what it checked least turns a clean verdict into information. That habit, from lesson 2.2, keeps a review from being a rubber stamp.

Recall before you read on

Without scrolling up: why is a fresh context more useful than a smarter model here? And what are the two opposite mistakes people make with a reviewer's findings?

A fresh context has not absorbed the reasoning that produced the code, so it reads the result rather than the intention — independence is a property of the setup, not the model. The two mistakes are obeying every finding (endless churn, unnecessary code) and ignoring the report (the real bug ships). The skill is judging each finding on its evidence and its relevance.

When the reviewer runs by itself

A review you trigger is easy to keep at arm's length. A standing reviewer is different: it comments while you work, and its notes can steer the agent before you read them. omp's advisor is the clearest documented example. It can flag a missed requirement, a risky API, weak verification, or unnecessary complexity while the work is still running.[6] Its notes arrive with a severity — nit, concern, or blocker — and only a blocker may interrupt the work.

Two facts keep this honest. The advisor makes its own model requests, uses its own context, and is billed separately, so a chatty reviewer costs money as well as attention.[6] And it is still advisory: omp's page tells you to treat a note as review, not as a new instruction. If the working agent ignores a note you think is right, quote it in your next message. That is judgement, with the reviewer's evidence in hand.

Do it in your own agent

You should see findings with file and line, at least one of which you can reproduce. You should also see the working agent disagree with something and say why — that is the behaviour you want, not a failure. If every finding is accepted without comment, ask: "Which of these is out of scope, and why?" If the reviewer returns nothing at all, read its "checked least thoroughly" list before you relax.

Check yourself

Question 1 of 3

What makes a reviewer independent of the agent that wrote the change?

Independence comes from a fresh context that never absorbed the author's reasoning. The model may be the same or smaller; a longer rule list and repeated reading do not create independence.

Question 2 of 3

A reviewer reports that a working helper should be rewritten. What now?

A review is advice. Check whether the finding is in scope and backed by something you can see, then decide — and record the reason either way. Fixing everything invites churn; a reviewer that edits has stopped being a reviewer.

Question 3 of 3

A review comes back saying "no correctness findings". What does it mean?

A clean review speaks only about the scope and checks it was given. It is not a proof of correctness, and it says nothing about screens or cases outside that scope — which is why you ask what it checked least thoroughly.
