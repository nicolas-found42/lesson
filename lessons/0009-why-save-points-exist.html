Why save points exist

An agent can rewrite twenty files while you watch one paragraph of text scroll by. A commit is how you decide that this state of the folder is worth keeping, and give it a name you can come back to.

About 15 minutesBuilds on: 0.3 Your project is a folderWin: you can say what a commit stores and when to take one

Why this matters for shipping your app

You will hand your project folder to an agent many times. Each time it may add files, delete a section, or move text between files. If the result is worse, you want a way back that does not depend on the agent remembering what it did, or on you remembering which paragraph looked right an hour ago. That way back is version control — a record of past states kept inside the folder itself — and its unit is the commit.

This lesson is about the idea, not the commands; the next lesson (3.2 Repository, working tree, uncommitted change) puts names on the parts and shows you how to inspect them.

Your files change with no record

When you save a file in a text editor, the old text is gone. The editor replaces the contents and nothing keeps the previous version. Coding agents edit the same files on disk, so a run can leave your folder better, worse, or merely different, and the folder keeps no memory of how it got there.

The fallback most beginners use is asking the agent to undo. That depends on the agent's account of what it changed, and an agent that misread a file will misread its own summary too. A save point does not: it lives in the folder, in a hidden subfolder, and does not care what the agent believes.

What a commit actually is

A commit is a recorded snapshot of your project's files, taken at one moment, with a short message attached. Pro Git describes the mechanism plainly: Git basically takes a picture of what all your files look like at that moment and stores a reference to that snapshot.[1] GitHub's own quickstart puts the same idea in one sentence: A commit is like a snapshot of all the files in your project at a particular point in time.[2]

Three things go into every commit:

  • The state of the files. Not only the lines you changed — the whole picture of every file the project is already keeping track of, at that instant. Git is efficient about it: if files have not changed, Git doesn’t store the file again, just a link to the previous identical file it has already stored.[1]
  • A message in your own words: "Add a contact page", "Fix the broken menu on phones". The message is for the person reading the history later, which is usually you.
  • A place in the chain. The new commit points back to the one before it, so the snapshots form an ordered line you can walk backwards.

The command that creates one is git commit, and its manual says it will Create a new commit containing the current contents of the index and the given log message describing the changes.[3] You will not type that by hand much: you will ask the agent. What matters now is that you know what you are asking for.

A chain you can walk back

Because each commit links to its parent, the project carries its own log. git log shows it in reverse chronological order; that is, the most recent commits show up first.[4] Here is a real two-commit history from a throwaway folder used to prepare this lesson:

$ git log --oneline
bfa5e7b Say when we are open
fef94e8 Add a first page

The seven characters on the left are the commit's short identifier; the rest is the message. In a project with sixty commits that list is your outline of what happened, and you can point at any line and ask the agent to show it, compare against it, or return the project to it. That last move is what makes a save point useful rather than decorative.

Recall before you read on

Without scrolling up: name the three things that go into a commit, and explain why "the agent says it undid the change" is weaker than a save point.

A commit holds the state of every file the project keeps, a message, and a place in a chain of earlier commits. The agent's account lives only in the session and depends on its own memory; a commit lives in the folder, is dated, and can be inspected or returned to without asking the agent anything.

The moment you choose matters

A commit records the folder exactly as it is, including work that has nothing to do with the task you had in mind. Timing is therefore part of the skill, and so is knowing what is in the snapshot.

A real pattern, anonymized

A user asked an agent for a large reorganization, then said "commit and push all pending changes" once the checks were green. The agent did exactly that: one commit of about thirty-five files. It included the reorganization, a test update, a dependency removal — and several files the user had been editing for a different reason, which had been sitting uncommitted the whole time. The save point existed, but it told two stories at once. Untangling them later meant reading the diff file by file, because there was no earlier point to fall back to.

A commit is only as useful as the state it captures: save before a risky change, save after something works, and glance at what is going in. 3.4 Commit messages and staging covers that choice; here you only need to notice it exists.

When to make a save point

Three moments cover most of what a beginner needs:

  • Before a risky change. "Reorganize the files", "replace the styling", "try a different layout" — anything where a bad result would be costly to unpick.
  • After something works. You ran it, you looked at the screen, and it does what you wanted. That state is the one you will want back in an hour.
  • At the end of a session. Work that exists only as unsaved changes is work you have not decided to keep.

Pro Git states the underlying habit: you commit a snapshot each time the project reaches a state you want to record.[5] In this course the habit is called checkpointing, and 3.13 Checkpoint often is the lesson devoted to it. For now, remember that a long agent run with no save point before it is a bet, not a plan.

Keep approvals on

When you ask the agent to commit, it proposes a command and waits. Read the command rather than the agent's summary of it: you are checking for the word commit and a message you recognise. Approvals are covered in 0.6 Approvals and permissions.

Check yourself

Question 1 of 3

Your agent has just finished a change you like. What does committing it add?

A commit records the current state inside the project's own history. It is not a cloud backup, and later commits can follow it; the old snapshot stays available either way.

Question 2 of 3

The agent says it undid a bad edit by editing the files again. Why is a commit stronger?

A snapshot is an independent record in the folder. A re-edit depends on the agent's memory of what the old text was, and on it getting every file right the second time.

Question 3 of 3

You are about to ask for a large, risky reorganization. What is the best save point?

The snapshot must cover everything the agent may touch, and it must be taken before the work begins. A partial copy or a warning in the chat does not give you a state to return to.
