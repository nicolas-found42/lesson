Show, don't tell: screenshots as bug reports

The agent reads files and command output. It does not look at your screen. When something is wrong in a way words keep missing, a picture is the shortest true description you can give.

Why this matters for shipping your app

Your app will be judged on a screen: a phone, a laptop, a friend's old browser. Most of what goes wrong there is visual and slightly absurd — a button half off the edge, white text on a white card, an image covering the heading. You can describe that in a paragraph and watch the agent fix a different paragraph. Or you can show it.

This lesson is about that gap. It is not about pretty design. It is about handing over the one piece of information the agent has no other way to get: what your screen actually looks like right now.

What the agent can see

A coding agent works through tool calls. Each call returns text: a file's contents, a command's output, an error message. That is the world it reasons about. Your browser window is not in that world.

ThingCan the agent see it?How it gets there
Files in your project folderYes, once it reads themIts read tool
Command output, errors, test resultsYes, once it runs themIts run tool
The page as it looks in your browserNo, unless you show itA screenshot you attach, or a browser tool it drives itself
Your screen, other windows, your cursorNoNothing in this course shares these

Read the third row twice. The agent can read the HTML that produces a page and still not know that the page looks broken. It has the recipe, not the cake.

Some setups close part of that gap. Claude Code can drive a Chrome window it opens, and can record what it sees there.[1] A separate computer-use feature lets it see and click on your screen after you approve each app.[2] Both are opt-in and both are narrow: with computer use, Claude never sees your terminal window, and screenshots are downscaled before the model sees them.[2] Do not assume either is on. The screenshots you attach are the reliable channel, on all three agents.

A screenshot is a bug report

Anthropic's guidance for images is blunt about the division of labour: Use images when text descriptions would be unclear or cumbersome.[3] Codex's image page says the same thing from the other side: Explain what ChatGPT should inspect and what outcome you want; don't rely on the image alone to communicate the task.[4] The image carries the evidence. Your words say what to do about it.

A real pattern, anonymized

A user had asked for a small training app with a statistics panel. The agent wrote tests for the panel, and the tests passed. Then the user sent one screenshot: black rectangles sitting on top of the labels, text half hidden behind them. The agent had never seen the app window; it had only checked numbers in a simulated display. Confronted with the picture, it reproduced the fault on a real screen, found that a drawing layer was being filled with an opaque colour, and fixed that. No paragraph the user could have written would have pointed at the right layer as quickly as one picture did.

Notice what the screenshot did and did not do. It did not explain the cause. It fixed the location of the search: this panel, this overlap, this moment. The agent still had to find the reason. That is the right split of work. You are the only one who can see the symptom; the agent is better at tracing the cause.

Recall before you read on

Without scrolling up: name two things the agent can see on its own, and one thing it cannot see unless you hand it over.

The agent can see files it reads and command output it runs. It cannot see the page as it appears in your browser — or your screen at all — unless you attach a screenshot or it is driving a browser or screen tool you approved.

Handing over a screenshot

All three agents accept an image in the prompt. The mechanics differ, so pick your tab.

In the terminal, Drag and drop an image into the Claude Code window, paste one with Ctrl+V (Alt+V on Windows and WSL), or type its path in the message.[3] A pasted image is part of that message, so describe it in the same message.

Paste the image into the interactive composer, or start a run with a file: codex -i screenshot.png "Explain this error and suggest the smallest fix". For several, codex --image before.png,after.png "Compare these states". PNG and JPEG are accepted.[4]

Paste with Ctrl+V, drag the file in, or mention it as @path/to/image.png. A chip in the composer confirms the attachment.[5] The docs add the sentence this whole lesson is about: Say what each attachment is for; a path by itself supplies context but not intent.[5]

What to type around the image

A picture with no words leaves the agent guessing which part of it matters, and which of the many things it can see is the mistake. Four short lines remove the guess.

Compare these two messages, both with the same screenshot attached.

Picture only

"This looks wrong, fix it."

Picture plus four lines

"This is my page at a narrow window width. The heading runs under the photo and the last word is cut off. I expected it to wrap above the photo. Fix only that, then take a new screenshot at the same width and show me."

The weak version asks the agent to find a problem in an image with no stated target. The strong version names the view, points at the exact symptom, states the expectation, and asks for a picture back. That last clause matters: it gives the agent a way to check its own work instead of declaring success.

This screenshot shows [the page and the window size or place].
The problem is [exactly what is wrong, and where to look].
I expected [what should happen instead].
Fix that and change nothing else. Then take a new screenshot at the same size and show it to me.

Keep the screenshot cropped to the part that matters. A full desktop with your mail client in the corner gives the agent more to interpret and gives you something to leak. Crop first, then attach.

Claude Code's best-practices page makes the same request from the agent's side: ask for the command it ran and its output, or the screenshot as evidence, because "all tests pass" on its own tells you very little.[6] A returned screenshot is not decoration; it is the proof that the thing you complained about is gone.

Careful with what is in the frame

A screenshot can carry your name, your email, a private message, a file path, or a key pasted into a form. Crop it, or cover those parts before attaching. The same caution applies to recordings: Claude Code's own page warns that a browser recording captures everything visible in the browser, including account details on logged-in pages.[1] Unit 8 covers secrets properly; here, the rule is plain: look at the picture before you send it.

Two habits that keep it honest

Show the state you mean. If the bug appears only after you click a button, click it, then screenshot the result. A picture of the page before the click describes a page that works.

Ask for the after picture. The fix is not proven by the agent saying it is fixed. Ask it to repeat the same view and attach the result, or reopen the page yourself. This is the same rule as lesson 0.1 — "done" is a claim — applied to something you can now see side by side.

If the agent has a browser tool, you can also tell it to keep its own screenshot as a file: Take a screenshot of the checkout page and save it to disk is the example in Claude Code's Chrome page.[1] That file is evidence you can compare later, not only a message that scrolls away.

Do it now, in your own project

You should see the specific overlap fixed, and nothing unrelated changed. If the agent's new screenshot is taken at a different window width, say so and ask for the same width — otherwise you are comparing two different pages. Keep approval prompts on; attaching an image does not change what the agent may do.

Check yourself

Question 1 of 4

You attach the right screenshot but write only "this looks wrong, fix it". What usually goes wrong?

With no stated target, the agent picks its own interpretation of "wrong" and may fix something you did not mean. The image locates the screen; your words must locate the fault.

Question 2 of 4

Which of these does a terminal agent have by default, before you attach anything?

Files and command output arrive through its tools. The screen, pointer and sound do not, unless a browser or screen feature you approved is supplying them.

Question 3 of 4

The agent says the layout bug is fixed. What is the strongest next step?

A new picture at the same window size is evidence you can check yourself. Summaries and promises are claims about the work, not observations of the result.

Question 4 of 4

Your screenshot shows a whole desktop with private messages in it. What do you do?

Cropping to the app area is the practical habit: it removes private material and also removes distraction, so the agent looks at the thing you meant. Recopying text by hand loses detail.

Stuck on a bad screenshot? Ask the agent giving you this course: "Here is my screenshot. What are the three most likely causes, and how would you check each one?" Then send the best answer back to your coding agent with the image attached.
