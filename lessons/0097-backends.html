Backends: hosting vs functions vs database

Your static site is served by a host that only hands over files. Once your app needs shared data or secrets, three different pieces appear — and they are not the same thing. Knowing which is which saves you from paying for the wrong one.

About 15 minutesBuilds on: 6.1 Static vs dynamicWin: you can name the three backend pieces and say which ones your idea needs

Why this matters for shipping your app

In lesson 6.1 you learned that a static host sends stored files exactly as they are. That works until one visitor's action must change what the next visitor sees. At that point your app stops being one thing and becomes three: a place for files, a place for code that runs on demand, and a place for data that must persist. These three are often sold together under one brand, which is exactly why beginners confuse them. This lesson separates them.

Recap: the host only hands over files

MDN describes the two kinds of server plainly: A dynamic web server consists of a static web server plus extra software, most commonly an application server and a database.[1] So "the server" is not one object. The static part is the host you already use. The extra software is what this lesson is about.

The three pieces

A backend is the part of your app that visitors never see but every visitor depends on. It comes in three distinct pieces:

PieceWhat it doesAnalogy
HostingSends stored files unchanged, any time, to anyone.A library shelf: it hands you the book it already has.
Serverless functionRuns your code once per request, then stops. You never keep a machine awake for it.A librarian who is only called when someone asks a question.
DatabaseStores, retrieves and edits data so it survives after the visitor closes the browser.The library's catalogue and archive, not only the shelf.

Hosting you already have. The other two are what "going dynamic" actually means.

Functions: code without a kept-alive machine

A traditional server is a program that runs all the time, waiting. A serverless function is the opposite: it exists as a file, and the platform starts it only when a request arrives at its address, then stops it again. You pay for the running moments, not for the waiting ones. Cloudflare describes its Workers platform as a serverless platform for building, deploying, and scaling apps across Cloudflare's global network with a single command — no infrastructure to manage[2]

That is why the name is "serverless": there is no server you manage. There is still a machine somewhere — the platform's — but starting, stopping and scaling it is not your job. Typical uses are checking a login, calling a third-party API with a secret key, or processing a form submission.

"Serverless" refers to who manages the machine, not to whether machines exist. The trade-off is that a function must be short and stateless: it cannot remember anything between two requests, which is what the database is for.

Database: the memory that outlives the visit

When a visitor closes the browser, everything in that browser is gone. A database is the place data lives on your side instead. AWS defines it as an electronically stored, systematic collection of data, managed by software called a database management system (DBMS) to store, retrieve, and edit data.[3] MDN shows the classic use: on a dynamic website, HTML pages are normally created by inserting data from a database into placeholders in HTML templates.[4]

Comments, accounts, orders, scores: anything one visitor creates and another must later see belongs in a database. A database also holds the access rules — who may read what — which is why it needs a secret credential, covered in lesson 8.1.

A real pattern, anonymized

A real pattern, anonymized

A user had a small team app: a web page served from a static host, a handful of small server-side functions that handled sign-in and calls to outside services, and a database holding the team's shared records. During deployment, the page went live first while the functions still returned "not found" — the functions were a separate deploy step that had not run yet. The user learned to treat "the site is up" and "the backend is up" as two different checks, and to probe each function's address directly after deploying.

The pattern: hosting, functions and database are deployed and billed separately, and each can be up while another is not. When something fails, ask which piece is actually missing before changing code.

Which pieces does your idea need?

Use the three questions from lesson 6.1. If no visitor's action changes another visitor's page and nothing needs a secret, you need hosting only. If you need to run code per request — a login check, a payment call, a webhook — add functions. If data must survive the visit — comments, accounts, orders — add a database, and the functions are what read and write it safely. Most small apps that go dynamic need all three, but they are chosen one at a time, and each addition is a new thing to secure and a new line on the bill.

Do not buy the bundle reflexively

Platforms sell "hosting + functions + database" as one product because that is the common case, not because every app needs all three. Start from what your idea actually does, and add pieces only when a real user need demands them. Lesson 8.10 covers the related trap of testing against a local copy instead of the real deployed pieces.

Recall before you read on

Without scrolling up: name the three backend pieces, and say in one sentence what each one is for.

Hosting sends stored files to visitors. A serverless function runs your code once per request without a machine you keep on. A database stores data so it survives after the visitor leaves, with access rules.

Do it: have your agent map your idea

Ask your agent to classify your app idea against the three pieces. This works the same in all three tools; keep approval prompts on (lesson 0.6).

Here is my app idea: (describe it in one or two sentences).
Answer in plain words:
1. Could it ship as static hosting alone? What fact would make it dynamic?
2. If it needs code to run per request, what would that code do? (login, payment, webhook, something else?)
3. Does any data need to survive after a visitor closes the browser? What data?
Then say which of the three pieces — hosting, functions, database — my idea actually needs, and which piece I should add first and why.
Do it in your own agent

You should get a verdict per piece — hosting only, plus functions, plus database — each with a reason tied to your idea. The follow-up should get an answer like: visitors could read data but nobody could safely add or change it, because only server-side code should hold the database credential.

Check yourself

Question 1 of 4

A visitor adds a comment that the next visitor reads. Where does the comment live between the two visits?

The comment must survive after the first visitor leaves and be readable by someone else, so it lives in the database on the server side — not in any visitor's browser or in a static file.

Question 2 of 4

What is the main difference between static hosting and a serverless function?

Hosting hands over stored files unchanged; a function is your code, started only when a request arrives. The other options get the division backwards or invent a price rule.

Question 3 of 4

Your app needs a shared leaderboard and user logins. Which pieces do you add beyond static hosting?

Shared scores must persist, so they need a database; logins must run code with a secret, so they need functions. The browser cannot share data between visitors, and disk space alone runs no code.

Question 4 of 4

When does a serverless function actually run?

The platform starts the function when a request arrives at its URL and stops it afterwards. Deploying only uploads the code; it does not run it.
