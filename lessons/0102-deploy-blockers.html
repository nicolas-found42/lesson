Deploy blockers: missing secrets and secret managers

Your app works on your own machine and breaks the moment it is deployed. The most common reason: the deploy host has none of your secrets. This lesson shows how to find and fix that.

About 15 minutesBuilds on: Lesson 8.1, SecretsWin: you can unblock a deploy by listing your app's secrets and storing them in the host's secret manager

Why this matters

So far you have shipped pages that need nothing from the outside world. The moment your app talks to a service, it needs secrets. A database, a login provider, a payment API: each one asks for a key or token that proves who your app is. Those secrets cannot live in your code (lesson 8.1). At deploy time they must live somewhere else. When they are missing there, the deploy fails or the live app fails. That is a deploy blocker, and missing secrets are its most frequent cause.

"It works on my machine"

On your own computer the app works because your machine has the secrets. They may sit in a .env file, in a signed-in command-line tool, or in your shell. A deploy host starts empty. It gets only what you explicitly give it. So the same code that ran fine locally fails on the host. You see sign-in errors, permission errors, or a deploy that refuses to finish.

A .env file is easy to forget, because nothing announces it. It sits in your project folder, often hidden from the file browser, and the app reads it at startup. The deploy host has no such file. It has only the secrets you typed into its settings page.

On GitHub Actions the failure is quiet. GitHub's own documentation states: If a secret has not been set, the return value of an expression referencing the secret (such as ${{ secrets.SuperSecret }} in the example) will be an empty string.[1] An empty string is not an error message — the step runs, the sign-in fails quietly. That is why "the deploy said nothing was wrong" and "the live app does not work" often happen together.

Reading the failure

Two symptoms look different, but they share one cause. In the first, the deploy stops before it ships anything. The host checked a list of required values, found one missing, and refused to go on. In the second, the deploy finishes and the live app breaks when a visitor tries the feature. The code ran with an empty value and failed later.

The first symptom is the easier one, because the host names the missing key. The second is quiet, because an empty string looks like a value.

Say your app has a form that saves notes to a database. On your laptop, DATABASE_URL comes from .env, so saving works. On the host, that name does not exist. The page still loads, because loading needs no database. The save button fails. Nothing in the log says "missing secret"; the log says the connection failed.

A real pattern, anonymized

A user's app had server-side functions that each needed their own key. The deploy tool checked every declared secret before shipping anything, so one missing key blocked the whole deploy — six of them, in fact. The agent restructured the code, so features that needed no secrets could ship first. The user then created the missing secrets one by one in the host's settings. Deploy went green only when the last secret existed.

Where deploy-time secrets live: the secret manager

Every host has an encrypted store for secrets — a secret manager. On GitHub it is reached via the repo's Settings → Secrets and variables → Actions. GitHub's docs describe creating secrets at three levels: repository, environment, and organization.[1] Repository secrets are visible to every workflow in the repo. Environment secrets belong to one named environment, such as production. That is useful when the live site and a test site use different keys. You can also manage them from the terminal with gh secret set SECRET_NAME (it prompts for the value, or reads it from a file) and gh secret list.[1]

Other hosts (your cloud provider, your registrar, your backend platform) each have an equivalent store. You do not need to memorize them. You need the pattern: the host keeps the value, your code asks for it by name. omp's own documentation puts the rule this way: prefer an environment-variable or secret-manager reference instead of a literal key. It also says to inject the value from the CI secret store or a password manager, and to confirm that project files, shell history, logs, and exported session transcripts do not contain it.[4]

The unblock checklist

When a deploy fails and you suspect secrets, run the same short checklist every time: list what the app needs, compare with what the host has, add the missing ones, redeploy. Ask your agent for the first step — it can read the code and name every secret:

My deploy fails with sign-in errors but works locally. List every secret this app reads: its name, what it is for, and where the value comes from. Then tell me exactly which ones are missing on the host and how to add each one to the host's secret store. Never print, log, or commit any secret value.
Do it now with your app

What you should see: gh secret list shows every name from the agent's list, the deploy finishes, and the live app signs in successfully. If a name is still missing, the host's list will not show it — that gap is the blocker.

Never do this

The three ways secrets leak at deploy time

Never put the value in the workflow file, the README, a log line, or a chat message, even temporarily. GitHub masks secrets it knows about, but if a value ever reaches your repository, history keeps it (lesson 8.3). GitHub's guidance is blunt: as a first step you need to revoke and/or rotate that secret, and its secret-scanning page adds that on an alert you should rotate the affected credential immediately, to prevent unauthorized access.[2][3] Push protection exists to stop hardcoded secrets from being pushed at all.[2] The safe habit: values travel only through the host's secret page or gh secret set reading from a file — never through your screen, your chat, or your logs. See the safety checklist and deploy checklist.

Recall before you read on

Without scrolling up: when a deployed app fails to sign in but works locally, what is the first thing to check, and where should the missing value be stored? Write it in your own words.

Check the host's secret store. The host starts empty, so a secret that exists only on your machine is missing on the host — in GitHub Actions the reference silently becomes an empty string. The value belongs in the host's secret manager (repository or environment secret), never in code, logs, or chat.

Check yourself

Question 1 of 3

Your app works on your own machine, but the deployed copy fails to sign in. What is the most likely cause?

The host starts empty and only has the secrets you added to it. Locally your machine already has them, which is why the same code behaves differently in the two places.

Question 2 of 3

In a GitHub Actions workflow, what does ${{ secrets.MY_KEY }} become when MY_KEY was never created?

GitHub's docs say an unset secret evaluates to an empty string, not an error. The step runs, the sign-in fails, and the log gives no obvious clue — so check the secret store, not just the log.

Question 3 of 3

Which is the safest home for a production secret that a deployed app needs?

The host's secret manager keeps the value encrypted and out of your repo, your logs, and your history. Any copy in code, chat, or README is a leak that git history will keep (lesson 8.3).
