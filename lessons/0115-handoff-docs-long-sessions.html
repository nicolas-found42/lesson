Handoff docs: carrying a long session forward

A session ends; the project does not. A short handoff doc in the project folder is how you make hours of work survive the session that produced them — and start the next one already oriented.

About 15 minutesBuilds on: 5.1 The context windowWin: you can end a long session with a handoff doc and start the next one from it

Why this matters for shipping your app

Your mission is to take an idea to a live app, and the real building happens in long sessions: hours of prompting, fixing, and checking. But every session is temporary. It ends when you close the window, when the context fills and compacts, or when you stop for the day. The project folder is permanent. A handoff doc is the bridge between the two: a few paragraphs the agent writes at the end of a long run, saved next to the code, read at the start of the next run.

When one session gets too long

Lesson 5.1 showed why long sessions degrade: the context window fills, older turns are replaced by a summary, and early instructions can be lost. Resuming the session brings the history back — and brings the crowd back with it. Anthropic is blunt that each new session starts clean: Sessions are independent. Each new session starts with a fresh context window.[1] Sometimes the strongest move is not to resume, but to hand off: write down the state, then start fresh from that note on a tidy desk.

A real pattern, anonymized

A user spent about twenty hours in one session on an existing web app used by their team, with a break overnight. Partway through, a deployment was blocked on setup steps only the user could do — signing in and creating keys. At that point the agent wrote a handoff note into the project folder: the phases already finished, the exact blocker, what only the user could do, and the next three steps. The next session began by reading that note and continued from the blocked step, instead of re-discovering the whole day.

What a handoff doc is — and where it lives

A handoff doc is a plain text file in the project folder, usually called HANDOFF.md. It is not the rules file (that holds standing instructions; lesson 1.12), and it is not the chat transcript (that is the whole crowded desk). It is a short, current account of the work. Because it lives in the project folder, git can commit it, you can read it without opening the agent, and a teammate can pick it up too. omp even records sessions locally by default so they can be shared: Sessions are saved locally by default. Resume earlier work … or share a session when someone else needs the context.[5]

What goes in it

Keep it short enough that a fresh session can hold it in mind. Seven sections earn their place:

SectionWhat goes in
GoalThe whole task in one line, so the next session knows what "done" means.
Done and verifiedWhat is finished and how you checked it — not merely what the agent believes.
In progressWhat was underway and exactly where it stopped.
Decisions and whyChoices made along the way, so they are not re-litigated or silently reversed.
Standing rulesA pointer to the rules file, not a copy — compaction-proof rules live there.
BlockersAnything only you can do: logins, one-time setup, approvals (lesson 5.10).
Next stepsThe next three steps at most, each with how to verify it.

Never put secrets in the doc — no keys, tokens, or passwords, ever (lesson 8.1).

Write HANDOFF.md in the project folder for a fresh session of this project.
Include: the goal in one line; what is done and how it was verified; what is
in progress and where it stopped; decisions made and why; a pointer to the
rules file for standing rules; anything only I can do (logins, one-time
setup); and the next three steps with how to verify each. No secrets.
Save the file, then stop and wait for me.

Start the next session from the doc

Open a new session in the same project folder and begin with the doc, not with memory:

Read HANDOFF.md in this project folder. Summarize the state of the work in
three lines, then continue from the next step. If anything in the note
conflicts with the files on disk, trust the files and tell me.

How each tool starts fresh versus resumes:

Start fresh by typing claude in the project folder; claude -c continues the most recent session, and /resume opens a picker inside a session. Anthropic documents that claude --continue or claude --resume reopens it under the same session ID.[1] There is no built-in handoff command — use the prompt above.

Start fresh by typing codex in the project folder; inside a session, /resume opens saved ones — the docs put it as Continue an interactive session by ID or resume the most recent chat.[4] No built-in handoff command — use the prompt above.

Start fresh with omp; -c continues this terminal's last session in the current directory and omp -r opens a picker.[3] omp also has a built-in: /handoff Generates a handoff document and commits it as a compaction entry in the same session.[2] omp is documented only by its own authors, so check surprises with your teacher.

Common trap

The handoff doc is the agent's account of the work, not the work. Files on disk and the git history are the source of truth — check the doc's claims against them (lesson 5.8). Update the doc at each checkpoint and commit it, so the note never drifts from reality.

Recall before you read on

Without scrolling up: name the sections a handoff doc should contain, and say why the doc lives in the project folder instead of only in the chat.

The sections are: goal, done and verified, in progress, decisions and why, a pointer to the rules file, blockers only you can do, and the next three steps. The doc lives in the project folder because the folder persists while sessions end — and because git can commit it and teammates can read it.

Try it in your own agent

Use a practice project folder — anything small you made earlier. Keep approval prompts on, as always.

Do it now
  1. Start your agent in the project folder and paste the first prompt above to write HANDOFF.md.

    A new file HANDOFF.md appears in the project folder, with the seven sections filled in.

  2. Open HANDOFF.md yourself. Check it answers: what is the goal, what is done, what is next.

    You can state the next step from the doc alone, without scrolling the chat.

  3. Commit the doc: git add HANDOFF.md && git commit -m "checkpoint: handoff note".

    git status afterwards shows a clean working tree — the note is now a save point in history.

  4. Start a new session in the same folder and paste the second prompt above.

    The agent summarizes the state from the doc in a few lines and names the next step, without you re-explaining anything.

Tick each step as you finish it.

Check yourself

Question 1 of 3

One session has run for hours and its context window is nearly full. Best move?

A handoff doc plus a fresh session gives the next run a small, accurate desk. Repeating rules inside a full window is exactly what compaction loses (lesson 5.1).

Question 2 of 3

Which line belongs in a handoff doc?

A handoff doc records concrete state — blockers, finished work, next steps. Vague reassurance wastes the little room a fresh session has.

Question 3 of 3

A new session reads HANDOFF.md. What should you still do?

The doc is the agent's account of the work, not the work itself. Files on disk and the git history are the source of truth (lesson 5.8).
