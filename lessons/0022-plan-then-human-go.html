Plan, then a human "go"

A plan is words. An edit is your files changed. Keeping those two apart, with you in between, is the cheapest safety net you will ever own.

About 15 minutesBuilds on: 1.4 The interviewWin: you can read a plan and decide when editing starts

Why this matters for shipping

By now you have answered the agent's questions and you hold a set of decisions. The next thing the agent wants to do is change your project. That is the moment where one cheap check saves an afternoon: ask what it is going to do, read the answer, and only then let it work. A plan you have read costs two minutes. Unpicking a build you did not expect costs far more, and it happens while you are not looking.

A plan is not an edit

A plan is a proposal written in words: the steps the agent intends to take, the files it expects to touch, and how it will know the result worked. It changes nothing on disk. An edit is a tool call that rewrites a file. The distinction is not philosophical. It is the difference between reading a menu and eating the meal.

All three agents can hold at that line. Claude Code's plan mode tells Claude to research and propose changes without making them, and edits stay blocked until you approve the plan.[1] Codex documents the same move as a command whose purpose is to propose an execution plan before implementation work starts.[2] In omp, once planning starts, the next turn explores and drafts rather than implements.[3] The names differ; the shape is identical.

You can also get the same effect without any special mode, by asking for a plan and saying "do not edit anything yet". That works in every version of every tool, including ones released after this course was written. The modes exist to make the pause harder to lose by accident, not because the pause needs machinery.

The two gates

Gate one was the interview: decisions in words. Gate two is the plan: actions in words. Both happen before your files change. Nothing in an interview answer authorises a build, and nothing in a plan authorises an edit until you say go.

What a plan is for

You are not approving the agent's competence; you are checking four things you can actually judge without reading code.

  • Scope. Does the list of steps match what you asked for, or has it quietly grown a second feature? Scope creep is easiest to catch here, in a sentence, before it exists.
  • Order. Which step comes first, and what must be true before the risky one? If step 4 deletes data, you want to see step 4 coming.
  • Proof. How will the agent show it worked? "Run the site and open the page" is a check. "It should look better" is not.
  • Blast radius. Which parts of the project does it expect to touch, and which does it promise to leave alone?

A plan that answers those four in half a page is good enough. A plan that is a page of confident prose with no file names and no check is a mood, not a plan.

Reads like progress, decides nothing

"I'll improve the gallery page, clean up the styling, and make sure everything works nicely. Then I'll verify and finish up."

No files, no order, no check, no boundary. You cannot disagree with any sentence in it, which means you cannot approve it either.

Same task, readable plan

"1. Read the gallery page and the stylesheet. 2. Change only the caption layout in the gallery template. 3. Leave the image sizing and the data files alone. 4. Start the site, open it, and take a screenshot at phone width. 5. Stop before publishing."

Every line can be checked against what you asked. You can strike line 2, add a line, or refuse the whole thing without a single file having moved.

The go is a decision, not a formality

When the plan arrives, you have three real options, and they are not "yes" or "no".

  1. Go. The plan matches your intent and names a check you believe in. Say so in one line.
  2. Amend, then go. Most of it is right; one line is wrong. Say which line and what it should say instead, inside the same message. A tiny correction inside an approval keeps your control without another round trip.
  3. Keep planning. The plan solved a different problem, or the order is dangerous. Say what is wrong with the thinking, not with the wording.

The second option is the one beginners miss. You do not have to choose between "accept everything" and "start over". A single sentence — "yes, but leave the header alone" — is a complete instruction, and the agent will fold it into the plan before it starts.

A real pattern, anonymized

A user asked an agent to make a small data-explorer app easier for newcomers. After a long interview the agent wrote a five-step plan and asked whether it captured the shared understanding. The user read it and answered with one word. Work began. Much later, mid-build, a second instruction arrived about how dragged items should settle; the agent took it as the next step rather than a restart, because the plan had made the current step visible enough to slot a change into.

In another session the agent finished planning and asked for confirmation before touching anything, even though the user had already said "implement all of it". That felt like friction for a moment. It was the gate doing its job: the plan was the last cheap place to notice a wrong assumption, and the agent was not allowed to skip it on its own.

Recall before you read on

Without scrolling up: name the four things you check in a plan, and explain the difference between a plan and an edit in one sentence.

Scope, order, proof, and blast radius. A plan is a written proposal that changes nothing; an edit is a tool call that actually rewrites your files. The gate sits between them, and only you can open it.

Asking for a plan

The request is a plain prompt and needs no special vocabulary. What makes it work is the stop line at the end: without it, many agents will produce a plan and then, in the same turn, start implementing it.

Before you change anything, write me a plan.

List, in order: the steps you will take, the files you expect to touch,
what you will leave alone, and how you will check that the result works.
Keep it under half a page. Do not edit, create or delete any file yet.

Stop after the plan and wait for my explicit go.

If something in my request is ambiguous, put it in a short "open
questions" line at the end of the plan instead of guessing.

Then read it. If a step is missing its check, ask for the check rather than approving and hoping. If two steps could run in either order, ask which one is riskier and why. These are questions about the plan, so they cost nothing but a sentence.

Plan mode is a permission mode: press Shift+Tab until the status bar reads ⏸ plan mode on, or start with claude --permission-mode plan.[1] When the plan is ready you choose how to proceed. Pick Yes, manually approve edits so you keep reviewing each change; the other option hands editing to a mode that no longer asks. Ctrl+G opens the plan in your text editor if you would rather rewrite it directly.[1]

Type /plan and press Enter to switch the active chat into plan mode; you may add the request after it on the same line.[2] The command is unavailable while Codex is already working, so use it before the turn that would start editing. Your approval settings from lesson 0.6 are untouched by planning.

Type /plan with the request, or on its own and then describe the task; the default chord is Alt+Shift+P.[3] The draft opens in a review screen where you can annotate sections or delete them, and /plan-review reopens the latest draft. Approval starts implementation immediately, and Save and quit writes the plan to a file and executes nothing.[3]

Planning costs one extra model turn and some context. For a one-line edit you can check by eye, skipping the plan is reasonable; the gate matters for anything you would not want to undo by hand.

What approval really starts

Saying go is not a promise that the plan will be followed exactly. It is permission to begin, and the agent may discover mid-way that step 2 is impossible. That is normal, and it is why a plan is a short document rather than a contract. What you gain is that the first discovery happens in front of you, with a sentence you can react to, instead of silently inside a large change.

Two habits keep the gate honest. First, ask for a checkpoint after the first step if the change touches anything you cannot easily redo. Second, when the work ends, compare what happened with the plan: which steps ran, which changed, what evidence exists. That comparison is the beginning of verification, which Unit 2 covers properly.

Do it now: get a plan and hold the gate

You should see a numbered plan naming real files, then a second version of it containing your amendment, and only after your go should a file change appear. If the agent starts editing before you answered, stop it, ask it to revert anything it touched, and repeat the last line of the prompt. If the plan has no check at all, that is the amendment to send.

Check yourself

Question 1 of 3

The agent is in a planning mode. What may it do to your project?

Planning is for gathering context and writing a proposal. Edits wait for your approval; that gap is the whole point of the mode.

Question 2 of 3

The plan is good except that it also restyles your header, which you did not ask for. Best reply?

An amendment inside the approval fixes one line without discarding the plan. Correcting scope before the edit is far cheaper than after.

Question 3 of 3

When can you reasonably skip the plan and let the agent edit straight away?

Planning costs a turn and some context. For a change you can fully check by eye, ordinary mode is faster; anything larger deserves the gate.
