Tokens, cost, and caching: why long sessions get expensive

Everything an agent reads or writes is counted in small units called tokens, and you pay for them. A cache keeps repeated reads cheap — until something invalidates it.

About 15 minutesBuilds on: 5.1 Context windowWin: you can explain why a one-line question in a long session still costs tokens, and what the cache does about it

Why this matters for shipping your app

Your app gets shipped through sessions, and sessions cost. Not always money out of your pocket — a subscription has a usage limit instead — but always attention to something that runs out. The expensive surprise for beginners is a session that ran for hours and ate a whole day's worth of usage, or a one-line question that was billed like a novel. This lesson gives you the mental model to spot both: what a token is, why every turn re-sends everything, and how caching softens the bill.

What a token is

The model does not read words; it reads tokens. A token is a small chunk of text — on the order of a word or a piece of one. Your messages, the files the agent reads, the tool results, and the agent's own answers are all chopped into tokens. Anthropic's cost page states the billing rule plainly: Claude Code charges by API token consumption.[1] Lesson 5.1 showed that all of this fits into the context window; tokens are the unit that window is measured in, and the unit the bill is measured in.

Every turn re-sends everything

Here is the fact that explains most surprise costs. The model remembers nothing between requests. So on every turn, the agent re-sends the whole conversation: the instructions, your project rules, every message, every tool result, and your new line. Anthropic's caching page describes it exactly: The model doesn't remember anything between requests, so Claude Code re-sends the full context.[2] A one-line question in a day-long session still carries the whole day with it. The best-practices page warns that this is discounted while the cache is warm and full price once it expires.[3]

The cache: paying once for the unchanged part

Prompt caching is the fix, and your agent handles it automatically. Because new content is appended at the end of each request, most of every request is identical to the one before. The API matches the start of the request — the prefix — against what it recently processed, re-reads that part cheaply, and fully processes only what changed: bills the re-read at the cached token rate, and fully processes only what changed.[2] The match is exact: a change anywhere in the prefix recomputes everything after it.[2]

Two things to know about how the cache behaves. First, it expires after a period of inactivity — the API offers a five-minute lifetime and a one-hour one; each request that hits the cache resets the timer.[2] After a long break, the first turn back reprocesses everything and feels slower. Second, some actions invalidate it mid-session: switching models is the big one, because each model has its own cache.[2] So pick your model at the start of a task and leave it there.

Why the start of a session matters most

The cache matches a prefix, so the oldest part of your context is the part most likely to be re-read cheaply. The order of a request works in your favour here. The system prompt and your project rules sit at the very start and rarely change, while your new question arrives at the end. A turn that only appends new text is a turn where almost everything can come from the cache.

This is also why a large file you read once stays on the bill. Its tokens join the prefix, and every later turn re-sends them: at the cached rate while warm, at full price once the cache expires. Reading a big file you did not need is a cost you keep paying for the rest of the session.

The same rule explains the cost of a break. Cached prefixes expire after a period of inactivity, and each hit resets the timer. Come back after lunch and the next turn has to process the whole history again. That is why the first turn back can feel slow, and why an idle session is not free to resume. If a task is nearly finished, one sitting is cheaper than leaving it and returning.

A real pattern, anonymized

A real pattern, anonymized

A user asked a one-line question: why did some models in a 3D viewer show no wheels? The agent found the cause in about 90 seconds. The follow-up — "now fix it exactly the way the original software does" — turned into a roughly 20-hour run that consumed about 423 million tokens, of which 99% were served from the cache, with over a thousand tool calls. The cache kept the run cheap per turn, but nothing stopped the run itself. The user's real need had been met in the first two minutes; the cost was in the hours nobody had bounded. Lesson 4.4 covers the budget habit that prevents this.

What you can do

You do not manage the cache by hand — you manage the things that break it and the habits that grow it:

  • Check usage before assuming. Ask your agent how much the session has used. In Claude Code, /usage shows token counts and a prompt-cache line reporting the share of input served from cache.[1]
  • Start fresh between unrelated tasks. Anthropic recommends Use /clear to start fresh when switching to unrelated work. Stale context wastes tokens on every subsequent message.[1]
  • Keep model and effort stable mid-task. Switching either invalidates the cache and makes the next turn slow and full-price.[2]
  • Set a budget in dollars or time. Lesson 4.4 shows how to cap a run so "keep going" cannot become 20 hours.
Do it in your own session

What you should see: a token count for the session and a cache share, for example "91% of input tokens from cache" — or an honest "my tool does not report this", which is itself useful to learn now.

Recall before you read on

Without scrolling up: why does a one-line question in a long session still use many tokens, and what does the cache change about that?

Every turn re-sends the full conversation because the model remembers nothing between requests, so the whole history is counted each time. The cache re-reads the unchanged prefix at a cheaper rate, so only the new part is processed in full — until the cache expires or something like a model switch invalidates it.

Check yourself

Question 1 of 3

What is a token, in plain words?

Tokens are small chunks of text — roughly a word or part of one. Files, messages, and commands are all chopped into tokens before the model reads them, and billing counts tokens.

Question 2 of 3

Why can a one-line question in a long session still cost a lot?

The model remembers nothing between requests, so each turn re-sends the full context. Prompt caching re-reads the unchanged prefix cheaply, but only while the cache is warm.

Question 3 of 3

What usually makes the first turn after a long break slower and pricier?

Cached prefixes expire after a period of inactivity. After the lifetime passes, the next request recomputes the full input, which is slower and billed at full price, then the cache rebuilds.
