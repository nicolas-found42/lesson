Merge or squash, and what "merged" means

The merge button has more than one setting, and they leave different history behind. Pick once, on purpose, and you will know what to do when a review comment arrives too late.

Why this matters for shipping your app

A pull request is a proposal. Merging is the moment the proposal becomes part of your app's real code. That moment is where beginners lose work: they merge, keep editing the old branch, and cannot understand why the live site does not change, or why Git refuses to delete a branch that looks finished.

Lesson 3.7 covered the proposal. This lesson covers the acceptance: the two usual ways to land it, what the word "merged" is actually a claim about, and the small rule that decides what you do when feedback arrives after the fact.

"Merged" is about reachability, not about a button

GitHub's own reference defines it precisely: a pull request can be marked as merged if its head branch commits become reachable from the base branch outside that pull request.[1] In plain words, "merged" means your base branch now contains your work, by whatever route.

That definition has a surprising consequence. A pull request can show as merged even if nobody clicked its merge button, because the same commits arrived another way. GitHub calls these indirect merges and warns they can affect automation and branch protection expectations.[1] You do not need to manage that case as a beginner. You do need the habit behind it: check what is in the base branch, not what a badge says.

For your course work the practical question is smaller. Once your work is merged, the pull request is a closed record of a decision. Comments still land on it, but it is no longer a place where new work happens.

Two ways to land the same work

On GitHub, the merge box offers up to three choices. The names you will see are Merge pull request, Squash and merge, and Rebase and merge.[2] The first two matter for this lesson.

Merge commit

Preserves every commit from the pull request branch and adds an explicit merge point.[1]

Your branch's history stays visible, including the "oops" commits. Main gets one extra commit that joins the two lines together.

Squash and merge

Combines all commits in the pull request into a single commit on the base branch.[1]

Main gets one tidy commit with all the changes and none of the intermediate steps.

Pro Git explains why a merge commit exists at all: when the two branches have both moved, Git creates a new snapshot that results from this three-way merge and automatically creates a new commit that points to it.[4] That commit has two parents, one from each branch.

Here is a real run in a throwaway repository. A small branch made three commits, the last of which fixes the wording of the first. Merged with a merge commit:

*   28baf1d (HEAD -> main) Merge pull request #1 from add-search
|\
| * 3f847ad Fix wording
| * 89fcb48 Oops, add empty message
| * 84b0d08 Add search box (first try)
|/
* 30d3dad Add home page

And the same three commits, squashed. Main has one line, and the branch's commits are not in it:

* be750f0 (HEAD -> main) Add search box (#1)
* 227c628 Add home page

Both results contain the same files. Only the history differs. If you want to inspect this yourself, git log --oneline --graph draws exactly those shapes.

Which one should you pick?

GitHub's reference gives a rule of thumb for each. Choose a merge commit when your team values complete history; choose squash when a pull request represents one logical change, especially if the branch includes many small fixup commits.[1]

Working with a coding agent produces fixup commits. The agent adds a feature, you ask for a spacing change, it commits again, then a review fixes a typo. On main, nobody needs that sequence. They need one commit that says what changed and why. That is the case squash was built for.

For a small app built with an agent, squash is usually the easier choice to live with: main stays scannable, and each line in the history maps to one pull request.

A merge commit is not "better history". It is more history. Whether that is an asset or clutter depends on who reads it.

If you are unsure, ask before merging. A sentence to your agent is enough: "This repo allows merge commits and squash. Which do the existing commits look like, and which should I use?" The agent can read the log; you make the call.

What squash changes about your branch

Squash is more than a cosmetic setting. Git documents what git merge --squash really does: it produces the working tree and index state as if a real merge happened (except for the merge information), but do not actually make a commit.[3] Something has to make that commit afterwards. On GitHub, the merge button does it for you. On your laptop, you commit yourself.

Two practical effects follow, and both surprise people.

First, Git does not think the branch is merged. In my demo, right after the squash landed, deleting the branch failed:

$ git branch -d add-search
error: the branch 'add-search' is not fully merged

The content is identical — git diff main add-search printed nothing — but the commits are not the same objects. Git compares commits, not file contents, so it cannot see that the work already arrived. GitHub lets you delete the branch after a squash merge anyway, because it tracks the pull request rather than the commit graph. On your laptop you would need -D, and that is a small red flag worth understanding before you type it.

Second, the old branch becomes a bad place to continue. GitHub's reference is direct: Squash merging works best for short-lived branches. Keep committing on the same head branch and later pull requests can include commits that were already squashed into the base branch.[1] The result is duplicated work and avoidable conflicts.

The habit

After any merge, treat the branch as spent. Start the next piece of work from an updated default branch, on a new branch.

Late review comments need a new pull request

Reviews do not stop when you merge. A reviewer opens the page the next morning, a bot re-runs a check, or a friend notices that the button is off-centre. The comment lands on a pull request that is already closed as merged.

A merged pull request is a finished record: its branch has already landed, and pushing more commits to it would not change main. GitHub's own instructions for changing merged work follow that shape — Reverting a merged pull request creates a new pull request.[5] Fixing forward follows the same rule.

So the sequence is: new branch from the current default branch, make the fix, push, open a new pull request, and in its description point at the old one ("follow-up to #12, which merged before this review arrived"). The reviewer's comment stays attached to the original for the record.

A real pattern, anonymized

A user was shipping a small browser game with an agent. The pull request looked fine and the local checks passed, so they said "merge" while the hosted check was still running. It landed as a merge commit. Minutes later a review bot commented on that merged pull request with a genuine bug: one score value was written where another was read, and the display showed a number that never changed.

The agent did not try to reopen anything. It opened a fresh branch from the updated default branch, made the one-line fix, wrote a test that failed before the fix, and opened a second pull request that referenced the first. The user merged that one once the hosted check had finished. A merge ends one conversation; a comment after it starts a new one.

Recall before you read on

Without looking back: after a squash merge, what does your default branch contain, and is the old branch "merged" as far as Git is concerned?

Main contains one new commit holding all of the pull request's changes, with the individual commits discarded. Git does not consider the old branch merged, because its commits were never recorded on main, so a plain git branch -d refuses. GitHub still marks the pull request merged and lets you delete the branch there.

Try it on your own pull request

You need a repository with an open pull request, and your permission prompts left on. Stop at any step you do not understand and ask your agent to explain it first.

Do it now: land one pull request deliberately

You should see one new commit on main whose message matches the pull request title, and no intermediate commits from the branch. If your agent is running, ask it: "Show me the last five commits on main and tell me whether the pull request looks squashed or merged." A squash shows one line per pull request; a merge commit shows a line with two parents.

If you prefer the terminal, the GitHub CLI exposes the same choice. In gh 2.102.0, gh pr merge --help lists -s, --squash as "Squash the commits into one commit and merge it into the base branch".[6] The decision is still yours; only the clicking moves.

Check yourself

Question 1 of 3

What lands on main when you choose Squash and merge?

The pull request's commits are combined into a single commit on the base branch. The individual commits stay only in the pull request's record, not on main.

Question 2 of 3

A merged pull request gets a valid review note the next day. What now?

A merged pull request is a closed record; its branch no longer represents what main should become. New work starts on a new branch and gets its own pull request, which can reference the old one.

Question 3 of 3

After a squash merge, why does git branch -d refuse?

Git compares commits, not file contents. A squash creates a different commit with the same effect, so the branch's original commits are not in main's history and the safety check fires.

Before we merge this pull request: tell me which merge method this repository is set up for. Then explain in two sentences what main will look like after a merge commit versus a squash, and which one fits this branch's commits. Do not merge anything yet.
