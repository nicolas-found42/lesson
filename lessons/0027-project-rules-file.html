Why this matters for shipping your app

Getting an app live takes many sessions across several days. Each new session, the agent starts with an empty memory of your project. So you explain again where the files live, which command starts the app, and that the pictures must stay under a certain size. Then a week later you forget one line, and the agent does the thing you already corrected.

A rules file fixes that. It is a small file you write for the agent, kept with the project so it travels with it. Every session begins by reading it.

The correction you typed twice

Claude Code's documentation gives a simple trigger for adding to the file: when Claude makes the same mistake a second time, or when you type the same correction or clarification into chat that you typed last session.[1] Both sentences describe the same moment. You are about to say something you have already said. That is the signal to stop typing and write it down.

The rule of thumb: a fact needed in every session goes in the file. A one-off task does not. "The app starts with npm run dev" is a fact. "Today, change the heading to blue" is a task.

An instruction file, not a lock

All three agents read a file like this before doing any work. Anthropic calls them markdown files that give Claude persistent instructions for a project, your personal workflow, or your entire organization.[1] OpenAI's page opens with: Codex reads AGENTS.md files before doing any work.[2] omp's page says: Put an AGENTS.md in your repository root. omp loads it automatically and applies it throughout the session.[3]

One honest caveat, because it changes how you write the file. Anthropic says plainly: Claude treats them as context, not enforced configuration.[1] A rule raises the chance the agent does what you want; it does not guarantee it. If something must never happen, that belongs in permissions and approval prompts (lesson 0.6), not only in a text file.

The file name depends on your agent

The file is CLAUDE.md, in the project root or in a .claude/ folder inside it. Run /init and Claude analyzes your codebase and creates a file with build commands, test instructions, and project conventions it discovers.[1] Check what loaded with /context, under "Memory files". If a project has an AGENTS.md and no CLAUDE.md, Claude reads that instead; if both exist, it reads the CLAUDE.md files only.[1]

The project file is AGENTS.md at the repository root. Codex also reads a personal one in ~/.codex/AGENTS.md, and files in subfolders, with the closer file overriding. /init in the CLI will generate an AGENTS.md scaffold in the current directory.[4] Files that add up past project_doc_max_bytes, 32 KiB by default, are cut off.[2]

The project file is AGENTS.md at the repository root. omp also reads a user-wide ~/.omp/agent/AGENTS.md and a stricter .omp/RULES.md for rules that should always apply. Changes are picked up after /new or a restart, and /extensions shows which files loaded.[3] omp's documentation comes only from its own authors, so check anything surprising with your teacher.

Claude Code reads AGENTS.md when no CLAUDE.md exists, so one file can serve all three tools if your project has no Claude-specific instructions. Keep the name your agent actually reads.

What belongs inside

OpenAI's best-practices guide suggests a useful picture: Think of AGENTS.md as an open-format README for agents.[5] Four kinds of content earn a place:

  • How to run it. The command that starts the app locally, and the command that runs the checks.
  • Where things live. "Pages are in site/; the pictures are in site/images/." The agent can find these, but telling it saves a hunt and prevents edits in the wrong copy.
  • Conventions and boundaries. "Plain HTML and CSS, no build step." "Never edit files in vendor/." "Do not add accounts or a database."
  • What done means. "Done means the page opens from a link and the text is readable on a phone."

Write each line so that someone could check it. Anthropic's examples make the difference clear: Use 2-space indentation instead of Format code properly; Run npm test before committing instead of Test your changes.[1] A rule you cannot check is a mood, and the agent will treat it as one.

What does not belong inside

Length is not free. omp's page puts it best: keep the file short and concrete, because every loaded instruction consumes context.[3] Anthropic asks for under 200 lines per CLAUDE.md file, because longer files are followed less reliably.[1] Three things usually push a beginner's file over that line:

  • A long procedure. If a rule needs ten steps, it is a job, not a standing fact. Claude's docs send multi-step procedures to a skill; lesson 1.11 covers those.
  • Personal taste. Your own scratch URLs and test names are not the project's rules. Keep them in a personal file, such as CLAUDE.local.md, which the docs say to add to .gitignore so it stays out of version control.[1]
  • Secrets. A key belongs in an environment variable, never in a file that gets committed. Unit 8 covers this; for now, the rules file holds no passwords.

One rule, written badly and well

Rules that cannot be followed

"Always write clean, modern code. Make sure everything works before you say you are done. Remember the important files. Be careful with the images."

Rules that can be checked

"Run npm run check before saying a task is done. Pages live in site/. Images must stay under 500 KB; ask before replacing one. Never edit vendor/."

The left column is advice. The right column is a set of facts and limits, each of which you could test. The agent can act on the right column on its first try, without a conversation about what "clean" means.

A real pattern, anonymized

A user asked an agent to put a small site online for friends, then edit the project's front page to show the link. That was the entire message. The project already had a rules file: it named the branch convention, the review step, the check command, and the fact that large media files are served from elsewhere. The agent read it, followed the same path the project always used, ran the checks, opened the real public address, and only then wrote the link in. The user sent nothing else. The speed came from the file, not from a clever sentence. On a project without those rules, the same request produces a longer conversation and more chances to drift.

Recall before you read on

Without scrolling up: what are the four kinds of content that belong in a rules file, and what happens to the agent's behaviour when the file is long?

How to run the project, where things live, conventions and boundaries, and what "done" means. A long file is followed less reliably and eats context, so keep it short and keep each line checkable.

Draft it with the agent, then cut it

The fastest way to get a first version is to ask the agent to write it from what it can see. Do not let it invent commands: tell it to check. This prompt works in any of the three agents.

Read this project first: the folder listing, the README if there is one,
and whatever file lists the commands. Then draft a project rules file.

Use the file name your tool reads at the start of a session
(CLAUDE.md for Claude Code, AGENTS.md for Codex and omp).
Put it in the project root.

Include only:
- the exact command that starts the app locally
- the exact command that runs the checks, if one exists
- where the main files live
- three rules a beginner would otherwise break
- one sentence for what "done" means

For every command, say where you found it. If you cannot find one,
write "unknown" instead of guessing. Keep the whole file under 40 lines.
Do not change any other file yet.

Then read the draft as its editor. Delete every line you do not understand, replace every guessed command with one you have seen work, and add the one correction you have already typed twice.

Do it in your own agent

You should see the file listed as a loaded instruction source, and the short task should follow it without a reminder. If the task ignores a rule, either the file did not load (check the list) or the rule was too vague to act on (rewrite it as something you could test). If it follows the rule, you have just removed one sentence from every future session.

Check yourself

Question 1 of 3

You type the same correction in three sessions in a row. Where does it belong?

A correction you repeat is a standing fact about the project. The rules file is read at the start of every session, so you write it once; a chat message is gone when the session ends.

Question 2 of 3

Your agent keeps editing files in a folder you said to leave alone. What is the durable fix?

A clear boundary in the file is read at the start of every session, so you stop repeating it. Renaming or deleting the folder breaks your own project, and repeating the warning lasts only one turn. For a limit that must hold, approvals still matter.

Question 3 of 3

A rules file says "write clean code". What is wrong with that line?

"Clean" has no test. The docs' pattern is the opposite: name the concrete habit, such as indentation width or the command to run. A line you cannot check gives the agent nothing to act on.

Ask your teacher

Unsure whether a line belongs? Ask the agent that gave you this course: "Here is my draft rules file. Which lines could you not check, and which are one-off tasks rather than standing rules?" or "Explain what happens to my rules file in a brand-new session."
