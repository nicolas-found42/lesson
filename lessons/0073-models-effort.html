Models and effort: picking the right brain

The agent is a shell; a model is the brain inside it. You can swap brains mid-session, and tell one how hard to think. Matching the brain to the job saves money and time without lowering quality where it matters.

About 15 minutesBuilds on: 0.1 What a coding agent isWin: you can pick a model and effort level on purpose, and pay less for routine work

Why this matters for shipping

Your mission is to ship an app by directing an agent, and every message you send runs a model that charges for its work. If you run the strongest, most expensive brain on every step — including the boring ones — you pay more and wait longer for no gain. If you run the cheapest brain on a genuinely hard design decision, you may get a wrong answer that costs an hour to undo. The skill is matching them. Lesson 5.2 covered what tokens cost; this lesson is about choosing which model spends them.

One shell, several brains

The agent program — Claude Code, Codex, or omp — is the part that reads files, edits them, and runs commands. The model is the AI that does the thinking inside that loop. Anthropic's documentation explains the trade-off plainly: Sonnet handles most coding tasks well. Opus provides stronger reasoning for complex architectural decisions.[1] Its best-practices page adds the money side: the default model handles most coding well, while a smaller one costs less on routine work.[2]

So the spectrum looks like this: big models reason better and cost more per token; small models are cheaper and faster, and are fine for mechanical work. Which names you see depends on your plan and account — open the model picker and look at what your account offers rather than trusting a fixed list.

Effort: how hard the brain thinks

Many models can also vary how long they reason before answering. That setting is usually called effort or reasoning effort. Higher effort means the model thinks longer before each reply: better on hard problems, slower and pricier on easy ones. Codex's overview lists it as a first-class choice: Choose the model, reasoning effort, permissions, and commands that fit the task.[3] In Claude Code the same idea exists as an effort level for the session (claude --help documents --effort <level>, "Effort level for the current session").

Recall before you read on

What are the two separate dials this lesson describes, and which direction saves money on a boring task?

Dial one: which model (brain) the session uses. Dial two: the effort level, how hard that model thinks before answering. A boring task gets cheaper by moving either dial down: pick a cheaper model, or a lower effort level — ideally without touching the ones a hard step needs.

Switching mid-session

You do not have to restart to change your mind. All three agents let you switch models inside a running session, and the command is the same word in each: /model. Claude Code's docs say to Switch with /model during a session, or start with claude --model <name>.[1] Codex's command guide shows /model choosing the active model, and notes that /model --reasoning=high keeps the current model and sets its reasoning effort to high if the model supports it.[4] And omp's quickstart tells API-key users to use /model to change the current session's model.[5]

Run /model to pick from the picker; press s there to switch for this session only, without saving it as your default.[6] Run /effort to change the effort level mid-session.[6]

Run /model and pick from the popup (the picker only shows models your account and workspace can use). You can also pass --reasoning=<level> to change effort for the current session.[4]

Run /model in the session, or start with omp --model <name> (it fuzzy-matches short names). Run omp models in a terminal to list what is available. omp also has role models — a fast "smol" model, a slow reasoning model, a planning model — that its features can pick per job.[7]

The pattern: expensive thinking, cheap building

The highest-value habit is splitting a job into a deciding part and a doing part, and paying for the brain accordingly. Deciding — "how should this app be organized?" — needs good judgement. Doing — "now implement the plan we agreed" — is often mechanical, and a cheaper model follows a clear plan equally well.

A real pattern, anonymized

A user with a cluttered web app asked the agent an open question: how should the project be organized? The agent spent about five minutes reading the code and official documentation, and wrote up a reorganization plan. The user read it, then switched the session to a cheaper model and typed a three-word instruction: implement the reorganization. The cheaper model moved a large block of markup into its own file, proved the moved file was byte-for-byte identical, added tests, and left every check green. The expensive thinking happened once, up front; the cheap model did the long tail of the work.

You can run this pattern by hand — ask, read the plan, switch with /model, then say "go" — which is lesson 1.7's plan-then-go gate with a cheaper brain behind it. omp also automates it: its help documents a mode that will Switch from the active model to a fast/cheap model at the first edit/write after the plan's todo list exists.[7] The plan happens on the model you chose; the edits happen on a cheap one.

Strong model everywhere

Best judgement on every step, including routine edits. Highest cost, slowest turns. Worth it when the task is genuinely hard or you are unsure what you want.

Matched to the job

Strong model for the open question and the plan; cheaper model and lower effort for executing it. Same plan, lower bill — as long as the plan was clear and somebody checks the result.

What switching costs

Two cautions. First, switching is not free: Claude Code's caching docs note that Each model has its own prompt cache, so the first request after a switch re-reads the whole conversation uncached,[8] so flip-flopping between models every message wastes money. Switch at phase boundaries, not every turn. Second, a cheap model on a hard problem can cost more than it saves: wrong turns, rework, and extra messages to repair them. If a cheaper model keeps failing at a step, that step belongs to the stronger one — that is information, not defeat.

Try it yourself

Do it now
  1. Open your project folder and start your agent (claude, codex, or omp).
  2. Type /model and look at the picker. Note which models your account actually offers.
  3. Close the picker without changing anything yet. If your tool has a status command, run it (/status in Claude Code and Codex) and find the line naming the current model.
  4. Decide one thing: which job in your next session deserves the strongest model, and which could run on a cheaper one.
What you should see: a list of model names offered to your account, and a status line showing the model this session is using. Nothing was changed, so nothing else moved.

Check yourself

Question 1 of 4

Your agent faces one genuinely tricky design decision. What is a good use of model choice?

Hard judgement is exactly what strong models and high effort are for. Spend there; save the cheap settings for routine work.

Question 2 of 4

You switch models in the middle of a session. What is a real cost of doing that?

Each model has its own prompt cache, so the first request after a switch re-reads the conversation uncached. Switch at phase boundaries, not constantly.

Question 3 of 4

Which order matches the cheaper-for-building pattern?

Judgement is needed once, at the plan; execution follows the plan and suits a cheaper model. The reverse order pays for judgement at the wrong moment.

Question 4 of 4

What does the effort (reasoning effort) setting change, exactly?

Effort is about the model's thinking depth, not files or permissions. Permissions are their own dial, covered in lesson 0.6.
