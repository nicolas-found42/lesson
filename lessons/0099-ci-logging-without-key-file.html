How CI logs in without a key file

Your workflow runs on a fresh machine that belongs to GitHub, so it cannot carry a key file. The modern trick is a short-lived digital ID that proves which repo and which run is asking — no stored secret at all.

About 15 minutesBuilds on: 6.5 An Actions workflow, 8.1 SecretsWin: you can explain why a CI job can log in with no key file, and spot the id-token: write line that enables it

Why this matters for shipping your app

In 6.5 you learned that every push runs your recipe on a brand-new virtual machine. That machine is a stranger: nothing you saved on your laptop travels with the code. So when a workflow needs to log in somewhere — to publish, to talk to a cloud service — it cannot open a key file, because there is no key file on that machine. In 8.1 you learned never to put keys in your code. CI has the same problem one level up: the credential has to live somewhere, and the wrong somewhere is a leak waiting to happen.

The old way: one long-lived key in settings

The traditional answer is a key stored as a GitHub secret, which the workflow presents on every run. GitHub's own documentation describes exactly that: These credentials are usually stored as a secret in GitHub, and the workflow presents this secret to the cloud provider every time it runs.[2] The trouble is the word long-lived. Such a key keeps working until someone remembers to rotate it, so if it ever leaks, it is a door that stays open.

The new idea: prove who you are, briefly

The newer approach is called workload identity. Instead of carrying a key, the running job asks GitHub for a signed, short-lived identity token — think of it as a temporary badge that says this is repository X, branch Y, run Z. GitHub's OIDC documentation puts the mechanism plainly: Every time your job runs, GitHub's OIDC provider auto-generates an OIDC token.[1] The job shows that badge to the cloud provider, the provider checks it against a trust rule you set up once, and hands back a token that is only valid for a single job, and then automatically expires.[1] If the badge leaks, it is worthless within minutes. The payoff, in GitHub's words: You won't need to duplicate your cloud credentials as long-lived GitHub secrets.[1]

OIDC (OpenID Connect) is the standard behind this. You do not need to implement it — official actions do that for you. You only need to recognize the id-token: write permission.
A real pattern, anonymized

A user's app deployed fine from their own laptop, but in CI the deploy stopped at the login step. The cause was not a wrong password: the cloud side had no trust rule for this repository's workflow, so the short-lived identity was refused. Running the project's one-time setup again fixed it, and every later push deployed with nobody ever typing a key into CI.

The trust rule is the other half

A short-lived badge only works because the cloud side agrees to read it. Before any of this runs, you set up a trust rule in the provider's console. That rule names which repository may ask, and often which branch or workflow file. When a job presents its token, the provider compares the two. If they match, the provider issues its own short-lived access token. If they do not, the login fails, and the error looks like a permission problem rather than a wrong password.

This is the part people forget. The workflow file can be perfect and the job can still be refused, because nobody wrote the cloud-side rule. That was exactly the failure in the vignette above.

Treat the token as disposable. Do not print it, copy it into a file, or hand it to another job. It exists so one run can prove who it is, once.

You already use this: the Pages deploy

The site you shipped in 6.3 is the everyday example. When GitHub Pages is deployed through a custom workflow, the deploy job needs no secret at all. GitHub's instructions state: The job must have a minimum of pages: write and id-token: write permissions.[3] The permission is the switch that lets the job request the badge:

jobs:
  deploy:
    permissions:
      contents: read
      pages: write
      id-token: write   # lets this job ask for a short-lived ID token
    steps:
      - uses: actions/deploy-pages@v4

The workflow syntax reference defines the permission in one line: id-token: Fetch an OpenID Connect (OIDC) token. This requires id-token: write.[4] Nothing in that file is a secret. The deploy works because GitHub itself vouches for the run.

When to use which

Secrets are still the right tool for things like third-party API keys, which you will meet in 8.4 — those services have no way to verify a GitHub badge. Workload identity is the right tool whenever the other side is a cloud provider that supports OIDC (AWS, Azure, Google Cloud and others). GitHub's secrets page says it directly: This will let you stop storing these credentials as long-lived secrets and provide other security benefits.[2] A third-party API key sits on the other side of that line. A weather service has no trust rule for GitHub, and it cannot check a badge. The key is the only proof it accepts, so it has to be stored and rotated. Matching the tool to the trust model is the whole skill. If you are unsure whether a service supports it, ask your agent: "does this provider support OIDC login from GitHub Actions?" — and check the provider's own docs for the answer.

The habit

Three things must line up for the badge to work: the cloud trust rule names your repository; the workflow declares id-token: write; and the provider grants a role with only the access the job needs. Miss any one and the login fails.

Before storing any new credential as a CI secret, ask whether the target accepts a short-lived identity instead. If it does, prefer the badge: nothing stored, nothing to rotate, nothing to leak for long.

Recall before you read on

Without scrolling up: what does a workflow present instead of a key file when it logs in to a cloud provider, and why does that thing become useless on its own?

A signed OIDC identity token naming the repo, branch and run. The cloud exchanges it for an access token valid for a single job only, which then expires by itself — so a leaked token is soon worthless, unlike a stored key.

Check yourself

Question 1 of 4

A workflow must deploy to a cloud service. Which credential does this lesson say to avoid storing in GitHub?

The stored long-lived key is the risky one: it stays valid until rotated, so a leak keeps working. The short-lived token and the signed note are the workload-identity side, which expires by itself.

Question 2 of 4

What does giving a job id-token: write permission allow?

The workflow syntax reference is explicit: id-token means "fetch an OpenID Connect (OIDC) token", and it requires id-token: write. The other options describe things a job should never do with that permission.

Question 3 of 4

Why is a workload-identity token safer than a stored key if it leaks?

GitHub's OIDC page says the cloud issues a token "only valid for a single job, and then automatically expires". Length, your laptop, and skipping trust setup are all wrong: the safety comes from the expiry, and the trust rule is exactly what you configure once.

Question 4 of 4

Which deploy in this course already logs in without any key file or stored secret?

The Pages deploy job uses pages: write and id-token: write with actions/deploy-pages, so GitHub vouches for the run and no secret is stored. Third-party APIs still need secrets (lesson 8.4), and a database password must never be committed.
