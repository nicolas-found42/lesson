Definition of done: deciding what "finished" means

A goal tells the agent which direction to walk. A definition of done tells it where to stop. Without one, the agent picks a finish line of its own, and it is rarely the one in your head.

Why a goal is not a finish line

In lesson 1.1 you learned to state the goal and the audience rather than the method: "a page where my friends can see my photos", not "make a grid with CSS". That gets the agent moving in the right direction. It does not tell anyone when the work is over.

The agent will not wait for you to supply that part. Claude Code's best-practices page describes the default: Claude stops when the work looks done.[1] "Looks done" is a judgement the agent makes alone, from whatever it happens to know.

So you need two small pieces of writing, and they work at different sizes:

  • The definition of done is the standing bar for the whole project: what must be true of anything you would call shippable. "It loads on a phone, every link goes somewhere real, and the live URL opens without an error."
  • Acceptance criteria are the checks for one change, written before the work starts. "The contact form shows my email address and the Send button opens a mail draft."

Same idea at two scales. The project bar keeps you from shipping something embarrassing. The per-task criteria keep a single request from turning into an expedition.

This is not a coding-course ritual. Anthropic's essay on building agent systems singles out the tasks where agents add most value as those that have clear success criteria, enable feedback loops, and integrate meaningful human oversight.[4] Clear criteria are one of the three, and it is the one you own.

Two sessions, one missing sentence

Here is what the gap looks like in practice. Both examples are patterns from real sessions, anonymised.

A real pattern, anonymised

A user asked a one-line question about a 3D model viewer: why were some parts of a model invisible? The agent found the cause in about ninety seconds. The user then said, roughly, "do it the way the original did it, not with a workaround." Nothing in that sentence said how close was close enough, so each answer defined the next question. The session ran for twenty-two hours, made about fifteen hundred tool calls, and ended only when the user typed "stop here, commit and open a pull request".

The second session began with a clearer goal and an unclear finish line: a dashboard that summarised public records. Partway in, the user added "run tests until no issues remain". That sounds strict. It is actually open-ended, because "issues" was never defined and the thing judging the output was itself an AI that kept finding new classes of problem. The loop ran about twelve hours and roughly fourteen hundred commands before the user interrupted it.

Neither user was careless. Each had a goal. Neither had written down what would make the work done.

What a usable criterion looks like

A criterion is usable when you can answer it by looking, without an argument. Four tests:

  1. Observable from outside. Someone who did not write the code can check it: open the page, click the button, read the file.
  2. Pass or fail. Not a matter of taste. "The menu opens when tapped" passes or fails; "the design feels modern" does not.
  3. Written before the work. A criterion invented afterwards describes whatever the agent built, which is the same as having none.
  4. Checkable in a minute. Three to five of them, each something you can verify in one look or one command.

The usual failure is a wish wearing the clothes of a criterion. Compare:

WishCriterion you can check
"The gallery looks good.""At phone width, all six photos appear in one column and none is cut off."
"The site is fast.""The page shows its first photo within two seconds on my connection."
"The form works.""Filling all fields and pressing Send shows a confirmation line and clears the fields."
"Clean up the code.""The project's check command exits with no errors."

The right-hand column is not more technical. It is more specific about the observation. That is the whole trick.

Add one line about what is not included

A definition of done is also a definition of enough. Write one exclusion next to your criteria: "No login, no comments, no image uploads this round." It costs a sentence and removes a whole category of "while we are here" work. The next lesson takes that idea further.

Say the finish line in the prompt

You do not need a special format, but a labelled block is easy to write and easy for the agent to follow. Codex's prompting guide recommends four parts, the last of which is Done when: What should be true before the task is complete, such as tests passing, behavior changing, or a bug no longer reproducing?[2]

Change: add a contact section to my one-page site, under the photos.

Done when all of these are true:
1. The section shows my email address as text a visitor can read.
2. Pressing the "Email me" button opens a new mail draft addressed to me.
3. At phone width the section does not overflow sideways.
4. The page still opens from the local server with no error in the browser console.

Not included this round: a contact form, a mailing list, or any server code.

Before you edit anything, restate these four checks in your own words and tell me if any is impossible to verify. If one is unclear, ask me one question and wait. Then do the work. When you report back, give one line per check: what you ran or looked at, and what you saw. If a check fails, say so plainly instead of calling the task done.

The last paragraph is the part people skip. It turns your list into something the agent has to answer, not something you have to remember to ask about. Claude Code's guide puts the same point as a question to ask before leaving an agent alone: Does it know what done looks like? A goal condition, a spec file, or a failing test it has to turn green.[1]

It also helps to give the agent something runnable, because then "done" stops being an opinion: If you give it something that comes back pass or fail, Claude can close that loop itself.[1] A test, a build that succeeds, or a screenshot you compare against a sketch all count. Unit 2 covers building those checks; here, the point is that each criterion should point at one.

Recall before you read on

Without scrolling up: what are the four tests of a usable acceptance criterion, and what is the difference between a definition of done and acceptance criteria? Write both in your own words.

Observable from outside, pass or fail, written before the work, and checkable in about a minute. The definition of done is the standing bar for the whole project; acceptance criteria are the checks for one specific change. The project bar stops you shipping something broken; the per-task list stops one request from expanding forever.

Where the tools differ

The idea is identical in all three agents. Only the wording in their own documentation changes.

Its best-practices page lists "Does it know what done looks like?" as the first question before an unattended run.[1] You can state the finish line in the prompt, and for longer runs you can also set it as a goal that a separate model checks after every turn; that feature is covered in lesson 5.5.

Its guide recommends the four-part prompt: Goal, Context, Constraints, and Done when.[2] Writing the fourth part is the whole of this lesson; the other three come from lesson 1.1 and 1.4.

Its "Using omp" page describes a reliable task as: State the outcome and boundaries. Name the bug or feature, important paths, anything that must not change, and the check that should pass.[3] It then asks you to Review evidence. Expand tool cards and diffs. Check the changed paths, command exit status, test result, and final explanation.[3] The criteria tell you which cards to open. omp's documentation comes only from its own authors.

No agent needs a magic phrase. What each one needs is a sentence it can compare reality against.

Write three checks for your own app

This is worth doing once on a real project, because the habit sticks only after you see the difference in one session.

Your turn — about 5 minutes

The agent replies first with a numbered restatement of your checks, not with a diff. It may ask one question about a check that cannot be verified — that is a good sign, not a delay. Its final message names each criterion and what it observed. One line may say "not verified" or "failed"; treat that as useful information rather than a failure of the exercise. You end with a small list you can paste into the next request, and later into a pull request description.

Check yourself

Question 1 of 3

Which line is an acceptance criterion rather than a wish?

It names something you can look at and answer yes or no. The others describe taste, code quality, or a vague range of devices, so two people could disagree without either being wrong.

Question 2 of 3

You tell the agent "keep fixing until no issues remain". What usually happens?

"No issues" has no boundary: every fix can reveal another class of problem, and a model judging the output can always find something. Name the cases, the number of runs, and the pass bar instead.

Question 3 of 3

Which of these is evidence that your criteria were actually met?

Evidence is something that comes back pass or fail and that you could repeat yourself. A summary, a promise, and a picture of the conversation all report what the agent believes.

Ask your teacher

Stuck on turning a wish into a check? Ask: "Here is what I want: 'the site feels friendly'. Give me three acceptance criteria I can verify by looking, and explain why each one qualifies." Then try the same rewrite yourself on the next one.
