Emulator vs production

Your app's backend can be imitated on your own machine so you can test without touching the real service. An imitation is fast and safe — and it is also the place where "all tests passed" most often stops being true.

About 15 minutesBuilds on: 8.9 BackendsWin: you can say which parts of a test run were real and which were imitated

Why this matters for shipping

In lesson 8.9 you met the three pieces of a dynamic app: hosting, functions, and a database. Those pieces run for real on someone else's computers, where real users' data lives. If every test goes straight to that real service, one careless run can delete a user's record. It can send a real email or burn your quota. So backend platforms give you an emulator: a private imitation of the backend that runs on your own machine. Knowing what that imitation can and cannot prove is the difference between "it works" and "it works there but not here."

What an emulator is

An emulator is a program that copies the behavior of the real backend and runs it locally. Your app talks to it as if it were the real service — same kind of calls, same kind of answers — but nothing leaves your machine. One popular backend platform lists the advantages of this: Safe testing: You can experiment with different configurations and features without affecting your production environment.[1]

That last phrase, production environment, names the other side of this lesson. Production is the real, hosted backend — the one your live site uses, with real accounts and real data. The emulator is the rehearsal room; production is the stage.

Recall before you read on

Without scrolling up: name the three pieces of a backend from lesson 8.9, and say which piece an emulator replaces on your machine.

Hosting, functions, and a database. An emulator usually imitates the functions and the database (and sometimes logins) on your own machine; the hosting of your static files is separate.

Why not always test in production?

Because production is shared and permanent. A test that writes to production writes where your users' data lives; a test that deletes, deletes for real. Anthropic's agent guidance draws the same line for automated workers: We recommend extensive testing in sandboxed environments, along with the appropriate guardrails.[2] An emulator is exactly that kind of contained space for a backend: free to run, quick to reset, safe to break.

It also protects other people. A local stack holds any sensitive data on your machine, and its own documentation warns: You should never expose your local development stack publicly.[1] Keep the rehearsal room closed and the stage separate.

The gap: what an emulator cannot imitate

An emulator imitates the backend's own behavior well. But a real app is more than a backend. Green emulator runs turn into real-world failures in places outside its walls:

  • Real logins. The emulator fakes a signed-in user. Real sign-in goes through a provider's popup and a redirect address that must match exactly. Your organization may impose token rules on top. None of that happens until you log in for real.
  • The browser's rules. Pages enforce rules about which sites may call which. A command-line test skips them; a real browser does not. Lesson 8.8 is the classic case.
  • Services nobody emulated. Sending emails, payments, analytics — many side services do not exist in the imitation. Code that touches them does nothing, or fails only in production.
  • Real limits and real money. Quotas, rate limits and billing exist only against the real service. An emulator cannot tell you that you are about to exceed a plan's cap.
  • Configuration drift. The imitation reads its settings from your machine. The deployed service may be configured differently, or several changes behind your branch. Then the emulator faithfully tests a world that no longer exists.

And one trap deserves its own paragraph. The emulator takes over only if your app is pointed at it. If that connection is not configured, the app keeps calling the real production service — your "safe local test" is now writing to the stage. When you ask for an emulator run, ask for evidence that the app was really connected to it.

A real pattern, anonymized

A real pattern, anonymized

A user's app had a button that connected each teammate to an outside service. Every automated check passed, and so did the whole run against the local emulator. Then a teammate opened the live app and clicked the button for the first time — and it failed. In the imitation there was no real browser and no real third party. So nobody had noticed that the server never told the browser the connection was allowed. Only a signed-in click in a real browser revealed it. Meanwhile, a setup script meant to configure a throwaway practice project granted permissions on the real project instead. That was caught only because the agent stopped and checked which project it had touched.

Two failures, one shape: the test environment was not the world the click lived in. Neither was a coding mistake in the usual sense — both were assumptions about where the code was running.

The habit: two questions before you trust a run

You do not need to memorize every difference. Make the agent draw the map for you:

Before we test: list which parts of this app would run against
the local emulator and which parts would touch production even
in a test run. Mark anything the emulator cannot imitate
(real logins, browser rules, third-party calls, quotas).
Then prove which backend the app is actually pointed at.
The emulator run passed. Now tell me exactly what this proves,
what it does not cover, and what the first real-browser,
real-login check should be. Do not say "done" until that
first real check passes or you tell me what only I can do.

This is the same claim-versus-evidence habit from Unit 2, pointed at a new border. Claude Code's own best-practices page names the underlying failure honestly: Claude said it was done and it wasn't quite, usually because it had no way to check its own work.[3] An emulator that was never connected to is precisely a way of checking work that checks the wrong world.

Try it yourself

In your project

If your app has a backend, ask your agent:

Make a two-column table: "runs in the emulator" and "touches
production no matter what". Include logins, database writes,
function calls, and any third-party service. Then point the
app at the emulator, start it, and show me a log line that
proves a test write landed in the emulator, not production.

What you should see: a short table, then a log or console line from the local emulator showing your test write. If the only evidence is the agent saying "it worked locally" with no local log, you do not yet know where the write went.

If your app is still static, you can rehearse the habit instead: ask the agent "which parts of my current project would need a backend, and what would I want to imitate locally before touching a real one?"
