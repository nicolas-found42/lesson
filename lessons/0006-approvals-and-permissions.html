Approvals and permissions: what your agent may do

The agent works with your account and your files. One setting decides whether it stops to ask you before it acts, and that setting is the difference between a helpful assistant and a mess you did not see coming.

About 15 minutesBuilds on: 0.1 What a coding agent isWin: you can put your agent in a mode that asks, and answer the prompt

Why this comes before your first real prompt

Your mission ends with a public app. On the way there, an agent will create files, delete files, install things and run commands in your project folder, using your permissions, on your computer. The tools are real, and so are their effects.

You will not read every line the agent writes. You will make one decision well: how often it stops for your yes. This lesson covers that decision, its switches, and why the safe setting also teaches you the most.

Two questions, not one

Permissions are two dials, and they answer different questions.

The first is what may the agent touch at all? That is the sandbox: an operating-system boundary around the files and network the agent's commands can reach. Claude Code calls its version a boundary that the operating system enforces around the shell commands Claude runs on your machine.[1]

The second is when must it stop and ask me? That is the permission mode. What you see is an approval prompt: the agent pauses, shows one action, and waits. Claude Code calls it the setting that decides which actions Claude can take in a session without asking you first.[2]

OpenAI draws the same line for Codex. A sandbox mode is what Codex can do technically, while an approval policy is when Codex must ask you before it executes an action.[3]

Keep the two apart

A fence and a gatekeeper. The sandbox is the fence: where the agent can go even when nobody is watching. The approval prompt is the gatekeeper: which actions wait for your yes. Either can exist without the other.

Recall before you read on

Without scrolling up: what is the difference between a sandbox and an approval prompt? Say it in one sentence each.

A sandbox is a boundary the computer enforces around what the agent's commands can reach, whether or not you are watching. An approval prompt is the agent stopping to show you one action and wait for your yes or no. The first limits damage; the second gives you a say.

The modes, in plain words

Each tool has its own modes, but most sort into four postures. Read these as a ladder: each step lets more happen without asking.

PostureRuns without asking youRight when
Read onlyLooking at files. No changes, no commands.You want an opinion or a plan first.
Ask before changesReads. Stops before edits and commands.Learning, or working on something you care about.
Ask before commandsReads and edits inside the folder. Stops before running programs.Routine building after the first week.
Ask nothingEverything, up to the sandbox boundary.Only in a disposable container or virtual machine.

Claude Code's Manual mode is the second row: Reads only run without a prompt.[2] Codex calls the same posture read-only: the agent can inspect files, but it can't edit files or run commands without approval.[4] omp calls its asking row write, which its docs call a safer starting point.[5]

What a sandbox is, and what it is not

A sandbox limits consequences; it does not decide whether an action is a good idea. Codex's default shows the split: in a version-controlled folder the agent edits and runs routine commands, but By default, the agent runs with network access turned off, and it asks for approval to edit files outside the workspace or to run commands that require network access.[3]

omp is the honest counterexample. Its approvals page says the modes do not make model output trustworthy or sandbox an allowed command.[5] There, an approved command runs with the access your account already has; the prompt is the only boundary. Claude Code is the same unless you enable its Bash sandbox, which is off by default and turns on with /sandbox.[1]

Do not read a mode name as a guarantee

"Ask before commands" means the agent asks. It does not mean the approved command was safe, or that it ran in a box. Approvals and sandboxing are separate protections; some tools offer only the first.

Set your agent to ask

Your agent is installed from lesson 0.5. Open it in your practice folder and check the mode before you type anything else. Pick your tab.

Start with claude --permission-mode manual. That is the mode the CLI shows as Manual, and it is the one that stops before edits and commands.[2] During a session, Shift+Tab cycles the modes, so you can see the name change in the status area. To make Manual the default for every session on this machine, put "defaultMode": "default" under permissions in ~/.claude/settings.json; the same page shows that exact snippet.[2]

A good first action to watch: "create a file called notes.txt with one line". In Manual mode the edit waits for you.

Leave the default alone for now. In a folder tracked by version control, Codex starts with the workspace-write sandbox and on-request approvals, and OpenAI's advice for newcomers is direct: If you're new to coding agents, start with the default permissions.[6] Inside a session, /permissions shows and changes the settings.[7]

A good first action to watch: ask it to fetch a page from the internet. With network off by default, that request has to come to you.[3]

omp needs a change, because its built-in default asks nothing. Either run omp --approval-mode write for one session, or set tools: approvalMode: write in ~/.omp/agent/config.yml to keep it. Both forms are on the approvals page, which recommends write for interactive work.[5] Check what is in force with omp config get tools.approvalMode.

A good first action to watch: "count the files in this folder and tell me the number". In write mode, reads go ahead but the shell command that does the counting stops for you.

Your tab choice is remembered, so later lessons open on the same agent.

Why you keep prompts on for now

Fast settings exist for a reason, and experienced people use them. Here is the honest version, from three anonymized long runs.

A real pattern, anonymized

Three pieces of work — a gallery put online, a catalogue updated, a site rebuilt over four hours — ran with prompts off. All three finished cleanly. That looks like an argument for prompts off. It is not: each folder already held a rules file describing the workflow, a check script that failed loudly, and a habit of reporting what was skipped. The project earned the autonomy before the person granted it.

Prompts off, day one

The agent decides what "done" means, edits files you have not seen, installs what it needs. You find out at the end, when the folder no longer matches what you pictured.

Prompts on, week one

Every unusual action pauses and shows its name. You learn the four or five commands your project uses, and you can say no before an edit lands.

Four concrete reasons to stay in an asking mode until you ship something.

You cannot yet judge a command. A prompt forces the question at the moment it matters. Reading "delete the build folder and rebuild" is easy; deciding later whether it was fine is guesswork.

The prompts are the curriculum. After a week you will recognise the handful of actions your project repeats. That knowledge makes a faster mode safe later.

There is no undo yet. Version control arrives in Unit 3. Until then an unwanted overwrite is gone for good.

A prompt costs seconds. A wrong blanket yes can cost an afternoon, and you will not know which file did it.

How to answer a prompt well

An approval prompt is not a quiz with a hidden right answer. If you can explain the action in one plain sentence, approve it. If you cannot, deny it and ask what the command does and why.

Three habits cover it:

Approve one action, not a category, while you are learning. A prompt offering "always allow this kind of command" is offering to stop teaching you. Decline it in week one.

Refuse anything that reaches outside your project folder. Editing your home folder, installing a global tool, changing your shell settings: none of that is needed to build a web page, and all of it is hard to reverse.

Treat a denial as information. If the agent immediately tries the same thing another way, notice it. A good agent reports what it could not do rather than quietly working around you.

Do it in your own agent

You should see a prompt that names the exact tool and, where there is one, the exact command. After your denial the agent should stop and report, not repeat the action or find a way around you. After your approval the file or listing should exist, and nothing else in the folder should have changed.

Check yourself

Question 1 of 4

What does a permission mode decide?

A permission mode is about the stopping, not the speed or the model. It sets which actions the agent may take before it asks you.

Question 2 of 4

The agent asks to run a command you do not understand. What is the best move?

If you cannot explain the action in one sentence, do not approve it. Denying is reversible; asking for an explanation costs one turn and teaches you the command.

Question 3 of 4

You switch every approval prompt off on your first day. What is the main risk?

With prompts off, edits happen without a moment where you could object, and Unit 3's undo does not exist yet. Speed and editors are not what changes.

Question 4 of 4

What is a sandbox?

A sandbox is enforced by the operating system and limits what commands can reach, including the network. An approval prompt is a separate protection, and some agents do not sandbox at all.
