Which questions the agent can't answer — and which you can

Every question a run asks belongs to one of two places: the project folder, or your head. Answering from the wrong place wastes hours.

Why this matters for shipping your app

A run pauses when the agent hits something it cannot resolve alone. What happens next depends on who can actually answer. If the answer lives in your project folder, the agent can find it itself, and a detour through you costs you minutes. If the answer lives only in your head — which account, which folder on your disk, what you actually want — then only you can answer, and a guess from the agent invents facts. Sorting the question correctly is the difference between a one-line reply and a twenty-minute detour.

The dividing line is the folder

An agent's whole view of your machine is the folder it runs in. Claude Code's documentation states the boundary plainly: By default, Claude has access to files in the directory where you launched it.[1] Codex describes the same boundary from the other side: in its default sandbox, the agent can read files, edit within the workspace, and run routine local commands inside that boundary, and it asks for approval to edit files outside the workspace.[2] omp behaves the same way: omp resolves context from the session's working directory.[3]

Everything inside that folder — every file, every line of code, every log — the agent can read, search, and run. Everything outside it — the rest of your disk, your accounts, your screen, your intentions — it can only ask about. That is the whole lesson in one sentence: if the answer is in the folder, the agent can find it; if it isn't, you have to supply it.

Three sorts of questions, three owners

QuestionWhere the answer livesWho answers
"Where is the function that renders the page?"In the project filesThe agent, by searching. If it asks you, say "it's in this folder" and let it look.
"Where is the photos folder on my disk?"Only you knowYou, in one line: a path. The agent cannot see your disk outside the folder.
"Should the gallery open full-screen?"Only you know — it is your product decisionYou. Product intent is never in any folder.
"Will the free host accept a 200 MB video?"Nowhere yet — it must be checkedNobody. Turn it into a cheap test, not a question.

The first row is the one beginners get backwards. When the agent asks where is X? and X is in the project, do not answer from memory and do not let it search your whole computer. Point it at the folder: "Search the project for it." If the file is outside the folder, the second row applies: give the exact path, because that is the one fact the agent cannot discover. The third row is a decision, and decisions are yours — the agent asking is actually doing the right thing by pausing, as the prompting guides put it, when the parts you haven't pinned down are yours to pin down.[4]

Worked example: the missing input file

A real pattern, anonymized

A user asked an agent to work on an app that needs a data file the user keeps on their own machine. The agent could not find it. It searched the project, then the version-control history, then ran a search across the entire disk — and only then asked the user. Seventeen minutes later the user typed one line: "It's in the folder called game-files, inside the project." The answer had been one folder away the whole time.

agentrun — find across the whole disk (still running)
youStop that. The file is in this folder: ./game-files/. Search there only.
agentread — found game-files/export.bin (1 file). Continuing.
The disk-wide search found nothing and cost 17 minutes; the folder search cost seconds. Same question, different owner.

In another session the pattern repeated inside the project: the agent asked twice where a needed file was, after spending about twenty-five minutes searching history and old archives. The user replied "In this repo, find it" — and the file was where it should have been. The lesson is not that asking is bad. The lesson is that "it's in this folder" is a complete answer, and it is faster than any search the agent can run on your behalf.

Make the answer permanent

If the agent had to ask where something lives, the next session will ask again. Write the answer down where the agent reads at startup. Project rules files exist for exactly this: CLAUDE.md files are markdown files that give Claude persistent instructions for a project, and Codex reads AGENTS.md files before doing any work.[5][6] One line — "Input files live in ./game-files/. If you can't find one there, ask me once and list what you searched." — removes the question forever, for every future run.

When nobody can answer: make it a check

The fourth row of the table is the subtle one. Will the free host accept this file? has no answer in the folder and no answer in your head, because the host's limits are not written in either place. The wrong move is guessing (and building on the guess). The right move is to convert the question into a check the agent can run: upload the file, read the response, report what happened. A question that nobody can answer becomes evidence in one run. Lesson 2.2 builds the full habit; here you only need the reflex: if there is no answer, make a test.

Don't answer what you don't know

The mirror-image mistake is answering a question you cannot answer — "I think it's in the old project?" — because the agent will treat your guess as fact and act on it. If you don't know, say so in one line and offer the way to find out: "I don't know; it's either in ./a or ./b — check both and tell me what you found." An honest "not sure" plus a pointer beats a confident wrong path.

Recall before you read on

Without scrolling up: what is the one-line test for whether the agent can answer its own question, and what are the two things you should supply when it can't?

The answer lives in the project folder, or it doesn't. If it's in the folder, the agent searches and finds it ("it's in this folder"). If it isn't, you supply the fact — a path, an account, a decision — in one line. And if nobody knows, you turn the question into a check instead of a guess.

Do it now: route one real question

You should see the agent resume immediately after a pointer answer, with no disk-wide search. When you add the line to the rules file, a fresh session should answer its own question without asking you at all — that is the win.

Check yourself

Question 1 of 3

The agent asks "where is the data file?" and the file is inside the project folder. What is the fastest correct reply?

The answer lives in the folder, so the agent can find it itself. A pointer is instant; a disk-wide search is slow and finds nothing extra; removing the feature throws away the task.

Question 2 of 3

Which of these questions can only you answer, not the agent?

The first, second, and fourth answers are in the project files, so the agent can search them out. What the app should do is your product decision; no folder contains it.

Question 3 of 3

The agent says it cannot find a file, and you know the path. What makes your answer stick for future sessions?

Rules files load automatically at the start of every session, so one line there removes the question forever — no repetition, no disk search, no reliance on memory.
