Tools: what your agent can see and do

Your agent has no eyes and no memory of its own beyond the conversation. Everything it knows arrives through tool calls: read, edit, run. Knowing that is what lets you predict it.

Why this matters for shipping your app

Lesson 0.1 showed the loop: gather, act, verify. This lesson opens the box and shows the only three kinds of hands the loop has. When something goes wrong in your app — a change that did not land, a command that "worked" but broke something — knowing the tools tells you where to look. The agent is not a person sitting at your keyboard. It is a model that can perceive the world only through what its tools hand back.

Three tool groups: read, edit, run

Across all three agents in this course, the tools fall into the same three groups. Anthropic's documentation sorts the built-in tools into five categories — file operations, search, execution, web, and code intelligence — but for your purposes they collapse into three: read (look at a file or search), edit (change a file), and run (execute a command).[2] OpenAI describes the same deal for Codex: it can inspect files, make edits, and run the tools already installed on your machine.[3]

A vendor-neutral definition says agents are typically just LLMs using tools based on environmental feedback in a loop.[6] The feedback is the point: each tool returns text, and only that text reaches the model. As Anthropic puts it, the surrounding layer provides the tools and manages the context the model sees.[2]

How each agent shows you the tool calls

You will watch these tools fire dozens of times per message, so it helps to know where your agent displays them.

Tool calls appear inline in the session as they happen, named Read, Edit, Bash and so on, each with its result. The tools reference lists them and their exact behavior.[1]

Codex shows commands and diffs as they appear in the terminal, so you can inspect each edit and each command's output while the turn runs.[3]

omp shows a tool card per call: A tool card shows what is pending, succeeded, failed, or was cancelled; edit cards include the affected path and a diff summary.[5] Truncated command output can be expanded. (omp's docs are single-vendor, from its own authors.)

Read: the agent sees only what it reads

The read tool takes one file and returns its contents. Two limits matter to you. First, Read only reads files, not directories — listing a folder is a run-tool job.[1] Second, big files come back in pages: one read returns at most 25,000 tokens and a whole file over 256 KB is refused outright, so the agent gets a PARTIAL view notice and must page through with offsets.[1] Binary files are refused too, and images come back downscaled. If the agent quotes a file at you, it read that text; it did not glance at the folder.

Edit: exact text, read first

The edit tool is deliberately dumb, and that is a safety feature: The Edit tool performs exact string replacement. It takes an old_string and a new_string and replaces the first with the second.[1] No fuzzy matching. The old text must appear exactly once, and the agent must have read the file in the current session first — that is the read-before-edit rule. So when an edit fails, the cause is almost always that the file on disk differs from what the agent last read, or the quoted text appears twice.

A real pattern, anonymized

During a long build, a user's agent hit a burst of edit errors saying the expected lines were not found. Each time, the agent re-read the file and tried again; the errors were trivial and self-corrected. The lesson: an edit failure is not a catastrophe, it is the read-before-edit rule doing its job.

Run: commands in a sandbox, output as text

The run tool executes a shell command. The Bash tool runs each command in a separate process, and environment variables don't persist between commands.[1] What comes back is text, capped: roughly the first 30,000 characters of output reach the agent inline before the rest is handed over as a file to page through.[1] And the run is fenced: Codex's default sandbox has network access turned off and writes limited to the active workspace, enforced by the operating system (Seatbelt on macOS).[4] Whether a given command needs your approval is the subject of lesson 0.6.

What the agent cannot see

A real pattern, anonymized

A user's screen locked mid-task, and every screenshot the agent captured came back black. The agent noticed the blank captures, added a guard against them, switched to a rendering mode that did not need the screen, and finally asked the human to unlock the machine. It never "saw" the screen at all — only the pixels a tool returned.

So the blind spots are concrete: your screen and other apps (unless a tool returns a screenshot), files it has not read this session, changes made outside the session since it last looked, anything behind a sandbox fence, and — because each new session starts with a fresh context window[2] — anything from a previous session it has not been shown. When the agent sounds confidently wrong about your project, one of these is usually why: its picture of the world is exactly as fresh as its last tool result.

The habit

When in doubt, give the agent fresh eyes: ask it to re-read the file, re-run the command, or take a screenshot — and check the tool result yourself.

Recall before you read on

Without scrolling up: name the three tool groups, and one thing the agent cannot perceive unless a tool returns it.

Read (files, search), edit (exact text changes), run (shell commands). It cannot perceive your screen, unread files, or out-of-session changes on its own — only what a tool call returns.

Try it: watch the tools work

Do this in your own agent

You should see a list of read/edit/run-style tools, then a tool call for the file read, then one for the command — each with its returned text visible in the session. That returned text is all the agent got.

Check yourself

Question 1 of 3

The agent wants to change one line in a file. What does its edit tool actually do?

Edits are exact string replacement of text the agent has read, matched once. Memory-based rewriting is not how the edit tool works.

Question 2 of 3

The agent wants to know what your screen looks like right now. Where can that come from?

The agent perceives the world only through tool results plus the conversation. Screens, webcams and windows are invisible unless a tool returns them.

Question 3 of 3

What happens when the agent runs a shell command for you?

Each command runs in a separate process, possibly inside a sandbox, and only its output text comes back to the agent.
