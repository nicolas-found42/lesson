Mocks vs live tests: what each one can catch

A test that talks to a pretend service is fast and free, but it can only catch problems in your own code. A test that goes live can catch the opposite. This lesson is about knowing which is which, and asking for the right mix.

Why this matters for shipping your app

In lesson 2.3 a test was a machine-repeatable check: input in, result compared. So far the examples only exercised your own code. But a real app also calls things outside itself: a payment service, a login provider, a database, an email API. For those, you now have two very different kinds of test, and a green run does not mean the same thing in each.

The stakes are concrete. A mocked test can pass while the real call would fail. A live test can fail while your code is fine. Knowing which kind you are reading is what turns "all tests passed" from a slogan into evidence.

Pretend objects: mocks, stubs, fakes

When a test replaces a real outside thing with a pretend one, the pretend object is called a test double. Martin Fowler, who popularised the vocabulary, defines it as the generic term for any kind of pretend object used in place of a real object for testing purposes.[1] The common kinds, in plain words:

  • A fake actually works, but takes a shortcut — Fowler's example is an in-memory database: Fake objects actually have working implementations, but usually take some shortcut.[1]
  • A stub only answers: Stubs provide canned answers to calls made during the test.[1]
  • A mock additionally checks how it was called — Fowler contrasts them directly: the stub uses state verification while the mock uses behavior verification.[1]

None of these touch the real service. That is what makes them fast, free, and repeatable — and what limits what they can prove.

Fixtures: the saved sample a test runs against

A fixture is the fixed sample a test uses: a saved request, a saved response, a saved file. Anthropic's own guidance lists a script that diffs output against a fixture as an example of a check an agent can run by itself.[4] Fixtures make runs comparable — same input every time — but they are still pretend data. A fixture copied from a real response last month can go stale without anyone noticing (see lesson 5.8 for that habit).

Wire tests: the real path, the fake destination

Between fully-mocked and fully-live sits the wire test. Your app really builds the request, really sends it over HTTP, and really reads the response — but the destination is a small fake server running on your own machine. Microsoft's integration-testing docs describe exactly this shape: Integration tests are conducted using the Microsoft.AspNetCore.TestHost, which includes the TestServer, and the page's summary is that integration tests ensure that an app's components function correctly at the infrastructure level.[2] A wire test catches the wiring bugs mocks cannot see: wrong URL, wrong header, wrong shape of the real request.

A real pattern, anonymized

A user asked their agent to push a project's checks further. The mocked tests all passed — the fake service accepted everything, because a stub answers whatever it is programmed to answer. When the agent finally ran the same flow against the real service, every request failed: the app was sending a setting the real service rejects. The pretend object had been too polite to say no, and only a live call exposed it.

In the same project, one "unit" test secretly called a real outside API. It passed on the laptop, then failed in the hosted checks and cost a rerun; the fix was to mock it. The lesson: tests that quietly go live are flaky by nature, and tests that quietly pretend prove less than they seem.

What pretending cannot catch

Google's testing blog puts the caution plainly: it can seem easy to ignore your code's dependencies by mocking them out, and over-mocked tests pass while the real integration is broken.[3] So use mocks for what they are good at — fast checks of your own logic — and do not let them be the only thing standing between you and a real outage. Lesson 2.7 makes the same point for screens: simulated checks passed while the real page was wrong.

Live tests cost real things

A live test is the only kind that proves the real service accepts your real request. But it is slow, it needs real credentials, it can hit rate limits, and — the dangerous one — it can touch real data. The same audit behind this lesson caught a test that started the app against the user's real saved data and added fake entries to it; the fix was to rerun against a throwaway copy. Say the rule up front when you ask for live tests: never touch my real data or real accounts, give a spend cap (lesson 4.4), and mark live tests so they can be skipped where no key exists — you know the word skipped from lesson 2.3. Lesson 8.12 shows one more way to keep live-ish tests isolated.

A mocked test says

"My code produced the right request."

It says nothing about whether the real service accepts it, is up, or changed its rules.

A wire or live test says

"The request went out over the real path and came back accepted."

Wire tests prove the path against a local fake; live tests prove it against the real service, at real cost.

The mix to ask for

You do not choose one kind for everything. Ask for a small pyramid: many mocked tests for your own logic, a wire test for each outside seam (the request your app really sends), and a few live tests, budgeted and isolated, marked so they skip when no key is present. When you read a run, count what each kind proved — and treat the live-test column as the one that can still surprise you (lesson 2.11).

Recall before you read on

Without scrolling up: name the three kinds of test this lesson contrasted, and say one thing a fully mocked test can never catch.

Mocked tests (pretend objects answering canned replies, with fixtures), wire tests (real requests over the real protocol to a local fake server), and live tests (real calls to the real service). A mocked test can never prove the real service will accept your real request.

Do it in your own agent 
Do not change any files yet. Look at this project folder and answer, quoting exact lines from the test files as evidence.
1. List each test file and label it: mocked (uses a pretend object or fixture), wire (sends real HTTP to a local fake server), or live (calls a real outside service).
2. For every live test, quote the line showing the real URL or key it uses.
3. Name the one outside call this app depends on most (API, login, database).
4. Propose one wire test for that call, using a local fake server. Show the exact commands you would run. Then wait for my go-ahead before writing anything.

You should see each test labelled with a quoted line, not a claim like "all tests are unit tests". At least one live test should be exposed by its quoted URL or key line — if the agent cannot tell which tests are live, that itself is the finding, and you should ask it to add labels. The proposed wire test must use a local fake server and must not contain a real key; if it does, say "no real keys in tests" and ask again. A project with no tests at all is a normal answer; the useful output is then the proposal in step 4.

Check yourself

Question 1 of 3

A test replaces the real payment service with a fake that always replies "ok", and the test passes. What does that prove?

A fake answers whatever it is programmed to answer. The green run proves your code built the expected call; it says nothing about the real service accepting it. That is what wire and live tests are for.

Question 2 of 3

Which of these is a wire test?

A wire test exercises the real path — the app really sends an HTTP request — but the destination is a fake server on your own machine. The browser-click check is a real-vs-simulated check (lesson 2.7); the other two are mocked-style checks with fixtures.

Question 3 of 3

A live test passed on your laptop but failed in the hosted checks. What is the most useful next step?

Live tests depend on the environment: credentials, the real service's state, real data. A disagreement between machines is a clue about that difference, not noise to vote away. Mocking the outside call usually removes the flakiness (see the vignette above).
