Local vs CI: skipped locally, failed in the cloud

Your checks passed on your laptop. Then the pull request went red. Nothing is broken in your code and nothing is lying to you: two different computers ran two different sets of checks.

Why this matters for shipping your app

You have a pull request open. On the pull request page, GitHub shows a list of checks, and those checks decide whether the merge button is available.[1] They do not run on your laptop. They run on a machine that GitHub builds for your change, and that machine has never seen your laptop.

Sooner or later you will meet the confusing case: everything passed at home, and the pull request is red. Beginners read that as "the tool is broken". It is usually the opposite. The cloud run caught something your local run could not, because it was never really running the same checks. This lesson teaches you to see the difference and to close it.

Two computers, one repository

Continuous integration (CI) is the practice of running the project's checks automatically every time code is pushed to a shared repository. GitHub's documentation describes it as a software practice that requires frequently committing code to a shared repository.[2] It also names the split you are about to feel: Building and testing your code requires a server. You can build and test updates locally before pushing code to a repository, or you can use a CI server that checks for new code commits in a repository.[2]

On GitHub, those servers are called runners, and the fresh start is deliberate: If you use a GitHub-hosted runner, each job runs in a fresh instance of a runner image specified by runs-on.[3] Read that sentence as a list of what the cloud run does not have. It does not have the tool you installed by hand last week. It does not have the file you forgot to commit. It does not have the test database left over from your third attempt yesterday.

On your laptop

Your whole folder, including untracked and ignored files. Every tool you ever installed. Whatever a previous run left behind: caches, a local database, downloaded packages.

Checks can silently skip when something is missing. The run still ends green.

On the CI machine

Only the files in the commit, on a fresh machine image, with the software that image happens to include. Nothing you added by hand travels with a push.

Every job starts clean, every time, for every push.[3]

Neither side is wrong. The cloud run is a second opinion, and it is stricter because it is emptier. When the two disagree, the disagreement itself is information: something exists on one side and not the other. Your job is to find which.

Skipped is not passed

This is the part that catches almost everyone. A skipped test did not run. Node's test runner says it plainly: individual tests can be skipped with the skip option, and in its example the skipped body is marked This code is never executed.[4] Yet the run still finishes successfully. Node's own rule: If any tests fail, the process exit code is set to 1.[4] A skip is not a failure, so the exit code stays 0 and the gate looks green.

GitHub reproduces the same courtesy one level up: A job that is skipped will report its status as "Success".[1] The documentation adds that a skipped job will not prevent a pull request from merging, even if it is a required check.[1] So a check that quietly declines to run counts as passed, in the summary, in the merge button, and in the sentence the agent reports back to you.

The one line to look for

A pass is not one word. A real pass has counts: how many checks ran, how many passed, how many failed, how many were skipped. If the summary says "skipped" anywhere, you have not yet learned whether that check works.

A worked example, run for this lesson

A small site with two tests. The second test runs an HTML checker if the checker is installed, and skips itself otherwise. That guard is a common, reasonable-looking habit. Here is the same code on both machines (output shortened; the real run was executed in a throwaway folder for this lesson).

youpython3 -m unittest -v  (your laptop)
tooltest_html_is_valid ... skipped 'htmlcheck is not installed'
test_title_present ... ok
Ran 2 tests   OK (skipped=1)
Exit code 0. Every check that ran, passed. One check never ran.
yousame command  (the CI machine, checker installed)
tooltest_html_is_valid ... FAIL
AssertionError: 1 != 0 : index.html: <img> is missing an alt attribute
FAILED (failures=1)
Exit code 1. The test that had never run locally failed immediately.

Nothing changed in the code between those two runs. The only difference was a small checker tool that happened to exist on the CI machine and not on the laptop. The skip guard turned "I cannot check this" into "nothing to report", and that is how a green laptop run hides a real defect.

Notice also whose fault the red check is: not the cloud's. The bug was always there. The local run had no opinion about it.

Reading the failure without guessing

Open the pull request and click the failing check. GitHub keeps a log for every job, and each step in it. The useful lines are near the first error, not at the end: the last lines are usually a summary that repeats the count.

You can also read it from the terminal, which is handy when your agent is the one looking. GitHub's own instructions for the command-line tool are: To view the full log for a job, use the --log flag.[5] The same page shows gh run view --job JOB_ID --log and the --exit-status flag, documented as exit with a non-zero status if the run failed.[5] The installed command-line tool also offers --log-failed, which shows only the failed steps, and gh pr checks for the checks on a pull request, with a separate exit code 8 while checks are still pending (checked on this Mac, version 2.102.0).

A real pattern, anonymized

A user's change touched only documentation. The pull request still turned red, because one browser test timed out on the cloud machine and passed on the laptop. The agent did the right things: it reran the job, then repeated the test locally many times without a single failure, then said plainly that it could not prove the cause. That honest sentence is worth more than a green tick. A check that fails on one machine and passes on another, on the same commit, is called flaky, and it is a different problem from the one in this lesson — 2.11 covers it.

The habit: find the difference, then re-run the same check

When local passed and CI failed, do not ask the agent to "fix CI". Ask it to explain the gap. Three questions, in this order, resolve almost every case:

  1. Did this check run on my machine at all? If the answer is "it was skipped", you have found the gap. Remove the skip guard, or install what it was waiting for, and run again.
  2. What does the CI machine have that mine does not, or the reverse? A tool, a version, a file that was never committed, an environment value. The fresh runner makes this list short and readable.
  3. What is the first error line? Not the summary. The first line that names a file, a test, or a missing thing is where the work starts.

Then run the same command locally, and compare the counts. A check that skips in both places is still unverified, even after the pull request is green.

Prompt to paste into your agent

Read the failing check on this pull request. Before changing any code, tell me four things: which job failed; the first error line in its log; whether that same check ran on my machine or was skipped; and what exists on the CI machine that I am missing locally. Quote the log lines you used. Then propose the smallest change that makes the check run the same way on both.

That wording matters because of a habit you already met in 2.2: "the tests pass" is a claim, and a claim with counts and a command attached is evidence. If the agent cannot produce the counts, it does not know.

Recall before you read on

Without scrolling up: why can a run that says OK (skipped=1) still be hiding a broken check? And why does GitHub treat a skipped required check as a pass?

Because a skip means the test body never executed, and neither the test runner nor GitHub counts "did not run" as a failure. The runner exits with code 0 when nothing failed; the skipped job reports its status as "Success". Both summaries describe the checks that ran, not the checks that did not.

Do this with your own project

You should end with a short table: check name, ran locally, ran in CI, skipped anywhere. At least one row will surprise you. That row is the lesson. A typical first result looks like "3 checks in CI, 2 on my laptop, 1 skipped in both", which is exactly the gap this lesson is about.

Check yourself

Question 1 of 3

Your checks pass locally, but the pull request shows a failing check. What is the most likely cause?

CI runs on a fresh machine image with only your committed files and whatever software that image includes. Your hand-installed tools and untracked files do not travel with the push, so the two runs are not the same run.

Question 2 of 3

A test summary reads OK (skipped=1). What does that tell you?

A skip means the test body was not executed, and a skip is not a failure, so the process exit code stays 0. The summary reports a green gate over a check you have not actually run.

Question 3 of 3

CI failed on a check your laptop passed. What is the best next request to your agent?

The disagreement is the information. Ask which check ran where, what differs between the machines, and what the first error line says; then make the check run identically in both places. Rerunning first hides a real defect.

Ask your teacher

Anything unclear? Ask the agent that gave you this course. Try: "Show me the exact difference between my last local run and the last CI run, check by check" or "Find every place in this project where a check can skip itself." The second question usually finds one nobody meant to leave in.
