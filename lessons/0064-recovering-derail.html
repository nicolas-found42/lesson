Recovering a derail

A run has gone sideways. The fix is not a third correction in the same conversation. It is four moves: stop, commit, open a pull request, restart with a fresh goal.

Why this matters for shipping your app

Every hour a derailed run keeps going, it costs you the same three things: money, attention, and a mess of uncommitted files you cannot safely undo. The whole point of Unit 3 was that a commit makes a moment safe. A recovery is that idea used under pressure: stop the run while it is still small, save what exists, and start again with a goal that names its own finish line. Learners who cannot recover will sit through very long bad runs; learners who can recover will take risks, because nothing bad is permanent.

What a derail looks like

You do not need to catch the exact moment it starts. Three signs are enough:

  • Repeat corrections. You have told the agent the same thing twice and the output is still wrong. Anthropic's best-practices page puts the rule in one line: after two failed corrections run /clear and write a better prompt instead of a third[1]. A third correction adds another failed attempt to a history the agent will keep rereading.
  • Scope you did not ask for. The agent is fixing things adjacent to your request, or you have answered several "should I also…?" questions with yes. Lesson 4.2 names the pattern; here it is only a signal to stop.
  • Nothing to check. You could not say what changed, or the last commit was hours ago. Lesson 3.13 explained why long unsaved runs are risky: until files are committed, stopping is expensive, so you keep letting it run.

Any one of these is a reason to begin the four moves. Two together are not a judgment call any more.

Move 1: stop the run

Interrupting does not throw work away; it ends the turn and leaves the files as they are. Anthropic documents that Esc stops Claude mid-action and keeps everything up to that point, so you can redirect without losing work[1]. In Claude Code's interactive-mode table, the same key is listed to stop the current response or tool call mid-turn so you can redirect. Claude keeps the work done so far[2]. omp says the same thing in plainer words: if the agent heads the wrong way mid-turn, press Esc to interrupt it, then clarify the request[3]. Codex documents a different control: press Enter while Codex is working to inject new instructions into the current turn[4], and Ctrl+C or /exit to close the session.

Press Esc once to stop the run. The edits already made stay on disk. If you later want to undo the edits themselves, Esc twice on an empty prompt opens the rewind menu, where you can roll back code, conversation, or both — and git works alongside that, not instead of it.

Codex does not document an interrupt key. You can press Enter to inject a correction into the running turn, or press Ctrl+C (or run /exit) to close the session; the files it already changed stay as they are either way. Check your installed version's help for anything newer.

Press Esc to stop the active turn, then clarify the request. The session stays open on disk; omp -c continues it later if you close the window.

Keep approval prompts on while you do this. A stopping move should not also be the moment you grant the agent more freedom.

Move 2: commit what is worth keeping

Now look at the files. Some changes are good, some are the derail itself, and you do not have to decide which is which yet. Git is built for this: Git thinks of its data more like a series of snapshots of a miniature filesystem[5], so a commit is a snapshot, not a verdict. Take the snapshot now, on a branch, with an honest message, and you can unpick it later at leisure (lesson 3.11 covers undoing). The cost of an untidy commit is minutes; the cost of losing hours of good work because you were embarrassed by the bad work around it is a day.

git status                     # see what changed
git switch -c parked-run       # a branch for what exists now
git add -A
git commit -m "Parked after stopping the run; not finished"

Do not commit straight to main. A parked branch keeps the live site and your clean history untouched, and it gives the next move something to point at.

Move 3: open a pull request as the parking space

A branch that exists only on your machine is easy to lose and hard to think about. Push it and open a draft pull request. GitHub is explicit about the safety property: Draft pull requests cannot be merged[6], so the derailed work cannot reach main by accident, while the checks still run and the description gives the mess a name. The gh command marks one with --draft, documented as Mark pull request as a draft[7] — or ask the agent to open a draft and not merge it. Lesson 3.7 covered the page itself.

Write one true sentence in the description: what you asked for, what went sideways, and that the request is parked, not proposed. That sentence is what you will paste into the restart.

Move 4: restart with a fresh goal

Start a new conversation. The failed attempts in the old one are not neutral history; the agent will reread them and partly repeat them. Anthropic's own guidance: /clear plus one new prompt that folds in what you learned works better almost every time[1]. A fresh session is the same move in any tool.

Type /clear to start the session's history over, or close it and run claude again in the project folder. Lesson 5.1 covers what a fresh session keeps and drops.

Close the session with Ctrl+C or /exit, then start a new one; /resume is there if you want the old transcript back later.

Run /new, documented as Start a fresh session while keeping the current one on disk[8]. The old session stays readable with /resume.

Then write the fresh goal. It should say what the last run got wrong on your side, name a finish line you can check, and give the agent permission to stop. This is lesson 4.3 applied to your own recovery:

New task, fresh start. Ignore the earlier attempts in this project's history.

Goal: <one sentence describing the outcome, small enough to check>.
Do not: <the one or two things that derailed the last run>.
Work on a new branch from main. Commit after each finished step.
Stop when: <the observable condition that means done>.
If that condition is not met after <N> attempts, stop and report
what you tried instead of trying something new.

The <N> matters. Budgets are lesson 4.4; the short version is that "until it works" has no end, and a derailed run restarted without one is the same run with a new coat of paint.

A real pattern, anonymized

A user asked an agent for one small fix in their app. At each pause the agent asked "should I also handle this?", and the user kept saying yes. Around a day later the change had grown far past the original request, nothing was committed, and the automated review skipped the finished pull request because it was too large to read. The user finally typed one sentence — stop here, commit, push, open a pull request — and the derailed work sat safely in a draft marked unfinished. A new session, given a much smaller goal and an explicit stop condition, then finished the actual request in under an hour. The parked branch was never merged; it did not need to be. Its job was to make stopping cheap.

Recall before you read on

Without scrolling up: what are the four moves of recovering a derail, in order, and what does each one protect you from? Write it in your own words.

Stop the run (ends the spend; files stay as they are), commit what exists on a branch (a snapshot, so nothing is lost and undo stays possible), open a draft pull request (a named, unmergeable parking space with checks), and restart with a fresh goal in a new conversation that names a finish line and a limit on attempts.

Do it: rehearse the recovery before you need it

Do it now: park a run on purpose

Your repository's page shows a pull request labelled Draft, its branch named parked-run, and main unchanged. You have now done all four moves in miniature — minus the restart — and nothing on the live site moved. Rehearsed once, the sequence takes five minutes when a real derail happens.

Check yourself

Question 1 of 3

You have corrected the agent twice on the same mistake and it still drifts. What works better than a third correction?

A third correction adds another failed attempt to a history the agent rereads. Stopping and starting a fresh conversation with a better prompt breaks the loop.

Question 2 of 3

You have stopped a derailed run. Why commit before starting over?

A commit is a snapshot, not a judgment: the good and bad parts are parked where nothing can lose them and you can unpick them later. Git does not delete anything here.

Question 3 of 3

You open a draft pull request for the parked branch. What does the draft status itself change?

A draft cannot be merged, which is exactly what you want from derailed work; checks still run and nothing reaches main until you mark it ready.
