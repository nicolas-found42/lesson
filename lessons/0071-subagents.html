Subagents: one agent can hire helpers

Sometimes one question is bigger than one conversation. Your agent can hand parts of the work to helper agents — called subagents — that look around in their own space and report back. You stay the boss who cross-checks.

Why one agent is not always enough

Your mission is to ship your app. Along the way, you will ask questions that are too big for one sitting: "how does every part of this project fit together?", "which files touch the login flow?", "do these two reports agree?" An agent can answer these. But the searching fills its context window with raw output you will never read again. Anthropic's documentation describes the fix plainly: use a subagent when a side task would flood your main conversation with search results, logs, or file contents you won't reference again.[1]

Codex puts the same idea from the cost side. Subagent workflows consume more tokens than comparable single-agent runs, because each helper does its own model work.[2] So subagents are not free. They are a trade: more tokens, in exchange for a main conversation that stays clean and readable.

Parent and child

The agent you talk to is the parent. When it delegates, it spawns one or more subagents (child agents). Each child works in its own context window, with its own instructions and tool permissions. When it finishes, the subagent does that work in its own context and returns only the summary.[1] omp's documentation adds an important detail: a child session does not inherit the main conversation. It gets the assignment and the shared context you pass explicitly.[3]

That is why the handoff matters. If something is easy to miss — which file is the source of truth, which files must not be edited — say so in the delegation prompt itself.

Claude Code has built-in subagents such as Explore, a fast, read-only agent optimized for searching and analyzing codebases. It can spawn them automatically when a task needs exploration. You can also define your own in .claude/agents/ files, with a name, a description, a tool list and a system prompt.[1]

Codex can run subagent workflows by spawning specialized agents in parallel and then collecting their results in one response. You ask for delegation directly, or your rules file can request it. In the CLI, /subagents lets you inspect the running agent threads.[2]

omp lets you delegate in ordinary language: state the outcome, what may run in parallel, and the boundaries. It ships bundled specialists such as scout (fast, read-only exploration) and reviewer (evidence-backed review). Completed results come back into the main conversation.[3] This is single-vendor documentation; check anything surprising with your teacher.

Read-only contracts

The most useful kind of subagent for a beginner is one that may look but not touch. Claude Code's built-in Explore agent has read-only tools; Write and Edit are denied.[1] You can give the same contract in plain words: "do not edit anything". A contract like that makes the helper safe to run on your real project. It can read every file and still change nothing.

Split this question into independent parts and research each part with a read-only helper. The helpers must not edit or create any file. Each helper returns a short report plus a list of what it did NOT check. Then cross-check the reports against each other and against the code, and tell me exactly where they disagree.
Watch out

Even a read-only helper can leave files behind if you ask it to save a report into your project folder. The next commit would sweep it in. Have helpers report back in the chat, or into a scratch folder you delete afterwards.

Cross-checking reports

Subagents are fallible. When you run several of them, they will sometimes disagree, both with each other and with the code. That disagreement is not a failure; it is a signal. In a real session, one helper reported a progress bar ending at 450. Another said 500. The parent did the arithmetic and found both were partly right: one number was the gate, the other the display. It sent the helpers targeted corrections before answering.[3] In the same session, another helper claimed a feature paid no rewards. The parent found the code did pay them, and the report was corrected.

Two habits make this work. First, ask every helper to state what it did not verify. The final answer in that session ended with no full UI playthrough was performed, which is exactly the kind of honesty you want. Second, when reports conflict, go to the source: the file on disk or a command's real output beats both reports.

Two of your helpers disagree about a number. Do not average them and do not pick the first answer. Open the relevant file yourself, quote the exact line, correct the wrong report, and only then give me the final answer with what you did not verify.

Worked example

A real pattern, anonymized

A user asked one short question: "explain exactly how this app's progression mode works". They added: "use a team of helpers." The parent agent split the question into four slices: flow, progression, economy and saving. It launched four read-only helpers with a clear done-condition. While they ran, it checked some numbers itself with a small throwaway program. Over the next half hour, the helpers' reports contradicted each other in several places. The parent cross-checked against the code and sent about ten correction messages. It finally answered with a structured explanation, a "problems found" list, and an honest note about what it had not exercised. The whole thing took one user message.

Notice what the user did not do: they did not write the four assignments, did not read the raw search output, and did not trust the first summary. They named the outcome and the method, then verified at the end.

When not to use subagents

More helpers is not always better. omp's guidance is blunt: keep work in the main session when it is a small sequential change, when several steps must continuously modify the same file, or when each decision depends on the previous result — and overlapping writers create merge risk.[3] A chain of dependent steps does not get faster by adding workers. Two helpers editing the same file will collide. Subagents shine for independent slices: research, review and checking, not interleaved edits.

The drift trap

In another real session, a user asked an agent to "keep researching" a question with a team of subagents. Hours later there was a whole new product, a published repository, and a long grading campaign. Nobody had decided to build anything. Each short follow-up message added "and also". When a research question starts turning into a build, stop and restate the goal in one sentence before sending the next message.

Try it yourself

Try it in your own project

You should see the agent report which helpers it started. It should return short summaries rather than raw search output, and name any disagreements it found. It should say how it resolved each one against the code, and end with a list of unverified claims. Your project files should be unchanged.

Recall before you read on

Without scrolling up: what does a subagent return to the parent, what is a read-only contract for, and what should you do when two reports disagree?

A subagent works in its own context window and returns only a summary. A read-only contract means the helper may read but never edit. So it cannot break the project. When reports disagree, go to the source: the file or real command output. Correct the wrong report, and state what was not verified.

Check yourself

Question 1 of 4

A subagent finishes its work. What comes back to the parent agent?

Subagents do their work in their own context window. They return only the summary, which keeps the main conversation clean.

Question 2 of 4

Why give a research helper a read-only contract?

Read-only means Write and Edit are denied. The helper can search everything and still break nothing in your project.

Question 3 of 4

Two helpers report different numbers for the same thing. What should you do?

The file on disk or a command's real output beats both reports. Averaging, speed, or voting do not find the truth.

Question 4 of 4

When is splitting work across subagents a bad idea?

Sequential edits to the same file collide between writers. They gain nothing from parallelism. Independent slices are exactly what subagents are for.
