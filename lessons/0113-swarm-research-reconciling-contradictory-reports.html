Unit 9 · Lesson 9.5

Fan out the research, reconcile the reports

Some questions are too big for one pass: which free host fits your app, what an API really returns on error, whether the docs match the code. You can send a swarm of helper agents at the question. The win is not the speed — it is ending with one answer you can defend, contradictions resolved against sources.

About 15 minutesBuilds on: 5.4 SubagentsWin: you can run a research swarm and turn contradictory reports into one defensible answer

Why one pass is not enough

Before you ship your app you will hit questions no single sitting answers well: "which hosting option actually fits a small free site?", "what does this service return when the request fails?", "do the official docs match what the code does?" One agent searching serially can answer these, but the raw output fills its context window. Anthropic's docs describe the fix: use a subagent when a side task would flood your main conversation with search results, logs, or file contents you won't reference again.[1] Each helper works in its own context and returns only a summary, so your main conversation stays readable.[1]

Codex puts the cost on the table: subagent workflows consume more tokens than comparable single-agent runs.[2] So a swarm is a trade — more tokens spent, in exchange for coverage and a clean main session. Spend it on questions that matter, not on trivia.

Fanning out: disjoint slices, read-only, with a done-condition

The trick is to make the helpers' jobs disjoint: each gets one slice of the question, not the whole question. "How does saving work" and "how do points work" can run in parallel; two helpers reading the same files cannot. Give every helper the same three rules: stay read-only, cite the evidence for every claim (file and line, or URL and date), and end with a list of what you did not check. Then give the swarm a stop condition — a time budget and a definition of done — so "keep looking" cannot become an open-ended run (lesson 4.4 Budgets covers why "until no questions remain" never ends).

Research this question with a swarm of read-only helpers: [YOUR QUESTION, e.g. "which free hosting option fits my small static app?"]
Split it into independent slices and give each helper one slice. Rules for every helper: do not edit or create any file; cite file+line or URL+date for every claim; end your report with "NOT verified:" and what you did not check. You have [TIME BUDGET, e.g. 10 minutes]. When all reports are back, do not average or vote — reconcile against the primary sources and give me one answer.

How each agent runs the swarm

Claude Code can spawn subagents on its own when a task needs exploring, and you can ask for it in plain words ("use subagents for this research"). Built-in helpers such as Explore are read-only. You can also define custom helpers in .claude/agents/ files.[1]

Codex can run subagent workflows by spawning specialized agents in parallel and then collecting their results in one response — ask for delegation directly in your prompt. In the CLI, /subagents shows the running agent threads.[2]

omp delegates in ordinary language — state the outcome, what may run in parallel, and the boundaries — and ships bundled read-only specialists such as scout. Completed results are delivered back into the main conversation.[3] Single-vendor documentation; check anything surprising with your teacher.

Worked example

A real pattern, anonymized

A user sent one short message: "explain exactly how this app's career mode works — use a team of helpers." The parent agent split the question into four slices (menu flow, progression, rewards, saving), launched four read-only helpers, and while they ran, checked a few numbers itself with a small throwaway program. Over the next half hour the reports contradicted each other in several places: two helpers disagreed on where a progress bar ends (450 versus 500), and one claimed a feature paid no rewards while the code clearly did. The parent did the arithmetic, found both numbers were partly right (one was the gate, the other the display), found the rewards code, and sent the helpers about ten targeted corrections. The final answer was a structured explanation plus a "problems found" list and an honest closing line: no full playthrough of the running app was performed. One user message in, one defensible answer out.

Notice the shape: the user named the outcome and the method, the parent reconciled, and the answer said plainly what was still unverified.

Reconciling contradictory reports

Contradictions between helpers are normal, not a failure — they are a signal. The protocol has four steps:

  1. Sort the claims. Group every claim in the reports: agreed by all helpers, contradicted by at least two, or single-source. Also separate what the code says, what the docs say, and what remains unknown — docs go stale, and code is usually the source of truth for behavior.
  2. Go to the source for each contradiction. Open the file on disk, run the command, or read the primary page. Quote the exact line. Never average two numbers, never take a vote, never trust the first answer because it was fastest.
  3. Correct the wrong reports. Send each helper a targeted message: "your claim X is wrong, here is the source, fix your report." This keeps the reports themselves honest for the final synthesis.
  4. Answer with the disagreement visible. State what is agreed, what was contradicted and how it was resolved, and what remains unverified. Claude Code's own best-practices page admits the underlying failure: an agent said it was done and it wasn't quite, usually because it had no way to check its own work.[4]
Your helpers' reports contradict each other on some claims. For EACH contradiction: open the primary source yourself (file+line, real command output, or the official doc page+date), quote the exact evidence, and say which report was wrong and why. Do NOT average numbers, do NOT vote, do NOT trust the fastest report. Then give me the final answer in three parts: AGREED by all helpers / RESOLVED by source (with the evidence) / STILL UNVERIFIED.
Even your reconciliation check can be wrong. If the stakes are high, run a deliberate negative control — break one claim on purpose and confirm your check catches it (lesson 2.11).

Guardrails

Three ways swarms go wrong

Time: the slowest helper sets the pace; give the swarm a budget and be ready to say "deliver now, no more searching." Files: if helpers save report files into your project folder, your next commit sweeps them in — have them report in chat, or into a scratch folder you delete. Drift: a research question can quietly turn into a build ("while you're in there…"). When it does, stop and restate the goal in one sentence before the next message (lesson 4.2). Keep approval prompts on throughout.

Try it yourself

Try it in your own project

You should see the agent fan out to several read-only helpers, then come back with one answer that cites sources, names any contradictions it found and how it resolved them against the primary source, and ends with a STILL UNVERIFIED list. Your project files should be unchanged.

Recall before you read on

Without scrolling up: what are the four steps of reconciling contradictory reports, and why is averaging two conflicting numbers never the answer?

Sort claims (agreed / contradicted / single-source, and code vs docs vs unknown), check each contradiction against the primary source with an exact quote, send targeted corrections to the wrong helpers, and answer with AGREED / RESOLVED / STILL UNVERIFIED. Averaging invents a number nobody observed; the source decides.

Check yourself

Question 1 of 4

Four helpers research the same question; three report X, one reports Y. What should you do?

Majority, speed, and debate do not find the truth. The file on disk, a command's real output, or the primary doc page does — then the wrong report gets corrected.

Question 2 of 4

Besides its findings, what must every helper's report include?

The "NOT verified" list is what makes the final answer honest — it tells you where the swarm did not actually look, instead of a promise that means nothing.

Question 3 of 4

When reports contradict, what should the final answer state?

A defensible answer shows its work: what all helpers agreed on, what was contradicted and how the source resolved it, and what is still unverified.

Question 4 of 4

When is a research swarm the wrong tool?

Sequential edits to one file gain nothing from parallel helpers and risk collisions; small questions cost more tokens than they save. Independent read-only slices are exactly what a swarm is for.
