OAuth in pieces: what a "Sign in with…" button sets up

When your app wants to read a user's data from another service, you never ask for their password. OAuth is the standard handshake that lets the user grant your app limited access instead — and it comes down to five pieces you can name.

Why this matters for your app

Your mission is to ship a small public app. Sooner or later it will want something from another service: read a user's files, post to their calendar, list their tasks. The wrong way to get that is to ask users for their password on that other service — you would then be responsible for protecting it, and users should never hand passwords to a second app. OAuth exists so the other service can give your app a limited, revocable key instead. OAuth 2.0 is the industry-standard protocol for authorization.[2]

Lesson 8.6 taught you that sign-in tokens expire. OAuth is the mechanism behind most of those sign-ins, so this lesson takes it apart piece by piece. The pieces are the same for every provider; only the web addresses differ.

The cast

Four roles appear in every OAuth exchange. You are the resource owner: the person whose data is at stake. Your app is the client: it wants the access but cannot be trusted with the password. The provider (the other service) runs the authorization server: it authenticates the user and issues keys. The provider's API is where your app later presents the key. RFC 6749, the OAuth 2.0 standard, names these pieces in its sections on the client identifier, client authentication, and the authorization endpoint.[3]

Piece 1: the client ID and client secret

Before anything else, you register your app with the provider, and the provider issues credentials. Google's OAuth documentation describes obtaining OAuth 2.0 credentials such as a client ID and client secret that are known to both Google and your application.[1]

The client ID is a public name for your app. It travels in every request so the provider knows who is asking. The client secret is a password for your app itself. It may exist only when your app has a backend server that can keep it away from users: a JavaScript application does not require a secret, but a web server application does.[1] A browser-only app has nowhere safe to put a secret — every visitor can read shipped code — so providers do not issue one to it. This is the same rule as lessons 8.1–8.3: a value embedded in front-end code is not a secret. Keep server-side secrets in environment variables, never in the repo.

Piece 2: scopes

When your app asks for access, it lists what it wants to do — read files, create events. Each item is a scope. Google's docs put it exactly: A variable parameter called scope controls the set of resources and operations that an access token permits.[1]

Scopes are how you keep access small. Ask for read-only when you only read; ask for one thing at a time. Google states the best practice plainly: It is generally a best practice to request scopes incrementally, at the time access is required, rather than up front.[1] That is the same "smallest thing that works" habit as the scope ladder in lesson 4.2.

Piece 3: the redirect URI

OAuth happens partly in the user's browser. Your app sends the user to the provider's page, and afterwards the provider must bring them back to your app. The redirect URI is the exact address in your app that the provider sends the browser back to, and it must be registered with the provider in advance so a stranger cannot redirect the result somewhere else. It is not a secret — it is a destination, visible in the URL — but it is part of your app's identity with the provider.

Piece 4: the consent screen

Between sign-in and the redirect sits the consent screen: the provider's own page listing the scopes your app requested, where the user approves or denies. Google calls this step user consent[1]: the user is asked whether they are willing to grant one or more permissions that your application is requesting.[1] Nothing is granted until the user clicks approve. This screen is why you never see the user's password: they type it only into the provider.

Piece 5: per-user tokens vs shared tokens

The result of the flow is an access token, a short-lived key your app presents to the provider's API. Access tokens have limited lifetimes[1] — that expiry is the token expiry of lesson 8.6, and the refresh flow there is how the app gets a new one.

There are two ways to hold such a key. A per-user token is obtained through the consent flow above and acts as one signed-in user: it carries that user's scopes and can be revoked for that user alone. A shared token belongs to the app itself, not to any person — for server-to-server work Google says: use service accounts. No OAuth Client ID is required.[1] A shared token is convenient (no sign-in popups) but dangerous: it usually has wide powers, and if it leaks, everyone is affected at once.

A real pattern, anonymized

A small team app read a project-management tool using one shared token, pasted into a config file. During a browser session, a page snapshot exposed that value in plain text, and the team had to rotate it immediately. They then moved to per-user OAuth: each teammate clicked "Connect", approved a narrow read-only scope in their own popup, and the app stored each person's token server-side only. When one teammate left, their access was revoked without touching anyone else's.

Without scrolling up: name the five pieces of an OAuth sign-in, and say which value must live only on your server.

The five pieces: client ID, client secret, scopes, redirect URI, consent screen — ending in an access token (per-user) or a shared service-account token. The client secret must live only on your server, never in shipped browser code.

Check yourself

Question 1 of 4

Your app gets a client ID and client secret from a provider. Where may the secret safely live?

Providers issue a secret only to apps with a backend, because anything shipped to the browser is readable by every visitor. The client ID is the public one.

Question 2 of 4

A provider asks "this app wants to read your contacts". What is being decided?

That list of requested permissions is the scope set. It is shown on the consent screen, and it controls what the resulting access token permits.

Question 3 of 4

Why does a per-user token beat one shared token for a team app?

A per-user token acts as that one person, so removing one teammate's access touches nobody else. A leaked shared token affects everyone at once and usually carries wider powers.

Question 4 of 4

Why must the redirect URI be registered with the provider in advance?

The redirect URI is the destination the provider sends the browser (and the result) back to. Registering it first means a stranger cannot point your sign-in somewhere else.
