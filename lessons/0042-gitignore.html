What not to track: .gitignore

A save point should contain the things you meant to keep, and nothing else. One small text file decides which files git refuses to save, and that same file can quietly erase work you thought was safe.

Why this matters for shipping your app

When you publish an app, your project folder becomes public in a way that is hard to reverse. Anything git has saved travels with it. A key you pasted into a settings file, a folder of downloaded packages, a fifty-megabyte video: all of it becomes part of what other people can download, and part of every copy that already exists on someone else's machine. The flip side matters as much. Files git was told to skip never travel at all, which is fine for a cache and disastrous for instructions your agent needs to do its job on another machine.

This lesson is about the single file that draws that line.

One file, one list of patterns

A .gitignore file is a plain text file at the top of your project, holding one pattern per line. Git reads it whenever it decides whether a path is worth mentioning. The git manual describes the goal plainly: the file specifies intentionally untracked files that Git should ignore.[1] GitHub's own instructions put the file in the repository root, and add that you should commit the .gitignore file into your repository so the rules travel with the project.[2]

A pattern is only a name-matching rule. node_modules/ means "the folder called node_modules, anywhere in this project". .env means "a file named .env, anywhere". A line beginning with # is a comment, and a blank line is ignored. The syntax is the same one your shell uses for wildcards, which Pro Git calls simplified regular expressions that shells use.[3]

Ignoring is not deleting. The file stays on your disk exactly where it was. Git stops offering to add it, and git status stops listing it.[4]

Three things you keep out

Almost everything people ignore falls into three groups.

Secrets. A key, a password, a login token. These belong in a file that stays on your machine, often named .env, and nowhere else. If that file is committed, the secret is in your history, and removing it later is a rewrite of history that GitHub documents as carrying a high risk of recontamination.[5] The cheap move is to list the file before the first commit ever happens.

Caches and generated files. The node_modules folder an installer creates, compiled output, log files, temporary editor files. Pro Git names exactly this class: automatically generated files such as log files or files produced by your build system.[3] They can be rebuilt from the files that matter, so saving them adds weight and noise with no value.

Big files. GitHub warns above 50 MiB and blocks files larger than 100 MiB.[6] A video, a database dump or a folder of images pushed once stays in history even after you delete the file, because history is a stack of snapshots, not a current-state mirror. A blocked push in the middle of shipping is a bad time to learn this.

The rule of thumb

Ask of each file: could someone rebuild this from the rest of the project, or must it stay private? If either answer is yes, it does not belong in a save point.

The trap: a rule does not touch files already tracked

This is the part beginners get wrong, and the git manual says it in one line: Files already tracked by Git are not affected.[1] Adding .env to .gitignore after you have committed it changes nothing. The secret is already in the snapshot, and every later commit carries it forward.

The fix is a two-step move, and both steps matter. First, remove the file from git's index while leaving it on disk, with git rm --cached. Second, add the ignore rule, so it cannot be added back. GitHub's page describes it the same way: If you want to ignore a file that is already checked in, you must untrack the file before you add a rule to ignore it.[2] The git manual adds the reason for the second step: The filename can then be added to the .gitignore file to stop the file from being reintroduced in later commits.[1]

Note what this does not do. The old snapshot still contains the secret. Untracking stops the leak from growing; it does not clean the past. That is a separate, harder job, covered in Unit 8.

Why an ignored skill disappears

Now the failure that catches experienced users, not only beginners. An agent that has worked out how to test your app can write those steps down as a skill: a small folder of instructions it loads in later sessions. Claude Code puts project skills under .claude/skills/, Codex under .agents/skills/, omp under .omp/skills/.[7][8][9] Those folders sit inside your project, next to your code.

Many projects ignore the whole agent folder. The habit comes from a sensible place: agent state, logs and session files are not source code. But .claude/ with a trailing slash excludes everything inside, skills included. The skill works perfectly on the machine that wrote it. It never reaches a commit, so it is not on your other computer, not in a fresh checkout, and not in the copy your teammate clones. The agent that wrote it will not warn you unless you ask.

A real pattern, anonymized

A user spent an afternoon having an agent build a project-local testing skill: launch a desktop app, drive its menus with scripted keys, save screenshots and logs as evidence. It worked. The agent used it to map six screens. Near the end, the agent mentioned, three separate times, that there would be no pull request. The reason was the same each time. The agent folder was listed in the ignore file, so the skill existed only in that one working copy. Nothing was committed, and the next person to open the project would have to rebuild it from scratch.

The transcript of how that looks in practice:

you      "Check whether the skill we wrote is saved."
agent    run   git status --short
agent    run   git check-ignore -v .claude/skills/testing/SKILL.md
output         .gitignore:7:.claude/   .claude/skills/testing/SKILL.md
agent    says  "It is ignored by line 7 of .gitignore, so it has
                never been committed."

git check-ignore is the tool for exactly this question. It prints the path if it is excluded, and with -v it prints the exclude pattern together with the path, so you learn which line did it.[10] The same demo on this machine, in a throwaway repository, produced this:

$ git check-ignore -v .env node_modules/pkg.js .claude/skills/check/SKILL.md
.gitignore:2:.env             .env
.gitignore:1:node_modules/    node_modules/pkg.js
.gitignore:3:.claude/         .claude/skills/check/SKILL.md
Recall before you read on

Without scrolling up: what are the three groups of files you keep out of a save point, and what happens if you add an ignore rule for a file you already committed?

Secrets (keys, passwords, tokens), caches and generated files (packages, build output, logs), and big files (videos, dumps, image folders). A rule does not touch files already tracked: the old snapshot still holds the file, and you must untrack it with git rm --cached before the rule can take effect.

Where a project skill lives

If you want a skill to travel with the project, it has to live in a folder that your ignore file does not exclude, and it has to be committed. This is what each agent expects.

Project skills live at .claude/skills/<name>/SKILL.md. The documentation is explicit about sharing: Commit it so your team gets it too.[7] If your ignore file contains .claude/, narrow it, or add an exception for the skills folder.

Team skills can be checked into .agents/skills inside a repository, while personal skills sit in $HOME/.agents/skills.[8] Ignoring .agents/ wholesale removes the shared ones along with the private state.

Skills live at ~/.omp/agent/skills/<name>/SKILL.md for your machine, or .omp/skills/<name>/SKILL.md inside the project.[9] omp's docs come only from its own authors, so check anything surprising with your teacher.

Do not ignore the rules file

Your project's rules file is the other thing an agent reads to know how your project works. It is a normal file in the project and belongs in a commit. The same goes for the .gitignore file itself: it is only useful to others if they receive it.

Try it in your own project

Step 4 prints one line for .env, naming the pattern and line number that excludes it, and prints nothing for index.html because tracked files are not subject to ignore rules. Step 5 should name each excluded folder in plain words and tell you whether a skill folder is inside one of them. If a skill you rely on turns out to be ignored, that is the finding worth acting on: narrow the rule, commit the skill, and check with git status that it now appears.

Check yourself

Question 1 of 3

You add .env to .gitignore, but you committed that file last week. What does the new rule do?

The git manual says files already tracked are not affected. The old commit still holds the secret, and the file keeps appearing in status until you untrack it with git rm --cached and commit that removal.

Question 2 of 3

Which pair most clearly belongs in an ignore file rather than a save point?

Both are rebuildable or private: a package cache can be recreated from its lockfile, and a key must never travel. The other options mix in files that are the actual source of your app, which you do want in history.

Question 3 of 3

Your ignore file excludes .claude/. The agent writes a useful project skill there. What is the sound move?

The skill belongs in the project. The narrow fix is to keep the folder excluded but re-include the skills path, or to replace the folder rule with a list of the specific state files you meant to exclude. Moving it elsewhere hides the problem rather than fixing it.

Read this next (primary source)

gitignore(5) — the reference page, and shorter than it looks. Read the description and the pattern-format bullets, then stop before the examples. It answers the two questions beginners ask most: why a rule did not apply, and why an exception inside an excluded folder did not work.

Ask your teacher

Anything unclear? Ask the agent that gave you this course. Try: "Read my .gitignore and tell me, for each line, what it protects against" or "Is any skill or rules file in this project currently ignored by git?" Questions are the point.
