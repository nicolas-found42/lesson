Logins and token expiry

Signing in is not a one-time event. Logins turn into tokens, tokens expire, and sometimes your organization forces a re-login on its own schedule. Here is how to recognize each case and what to do.

About 15 minutesBuilds on: 8.1 SecretsWin: you can tell an expired token from an organization policy, and you know the exact command that renews a login in your agent

Why this matters for your app

Once your app goes beyond a static page, it will touch services that require a login: a hosting provider, a database, a third-party API. Your agent also logs in to its own model provider. It logs in to those same services when it deploys for you. Any of those logins can expire at the worst moment, usually in the middle of a long agent run. Knowing why it happens turns a confusing failure into a two-minute fix.

A login becomes two tokens

When you sign in through a modern login flow (OAuth), the provider does not hand your agent your password. It hands it an access token instead. The OAuth standard says what such a token carries: Tokens represent specific scopes and durations of access, granted by the resource owner.[6] Access tokens are short-lived on purpose. The lifetime field expires_in is measured in seconds, so a value of 3600 denotes that the access token will expire in one hour.[6]

Alongside it you usually get a refresh token. The standard defines it as the credential used to obtain a new access token when the current access token becomes invalid or expires.[6] Your agent stores both, plus the expiry time, in its local credential store. omp's documentation describes exactly that row: an OAuth access token, refresh token, expiry, and available account metadata.[3]

Refresh usually hides the expiry — until it can't

In the background, the agent quietly swaps an expiring access token for a new one. It uses the refresh token: omp sends the refresh token to the provider's token endpoint when the access token needs renewal.[3] Claude Code behaves the same way. It refreshes the profile's login automatically, and when refresh fails, requests fail … until you sign in again.[1] You normally never notice any of this.

You notice when the refresh itself is refused. Claude Code's docs list the symptom plainly: Expired sign-in: your earlier sign-in expired and Claude Code can't refresh it. Log in again at the prompt.[1] From then on each model request fails with 'Login expired · Please run /login' until you sign in again.[1]

Warning signs, and the command that fixes it

Good tools warn you before the hard failure. When a Claude Code login is within three days of expiring, startup shows Your login expires in 3 days · run /login to renew. You can also check any time: /status shows a Login row reading Expired — log in again.[1] The docs add why early renewal matters. A session that outlives the login stops making progress once the credential expires and can't recover until you sign in again.[1] That is exactly how a long unsupervised run dies silently.

The fix is a re-login command in every agent. Each one below was verified in that tool's own help output on this machine.

Inside a session, type /login to re-authenticate or switch accounts.[2] From the shell, claude auth login signs in, claude auth logout signs out, and claude auth status shows the current state (claude auth --help: login — Sign in to your Anthropic account).

From the shell, codex login manages the login (codex login --help: Manage login, with a status subcommand) and codex logout will Remove stored authentication credentials. An API-key sign-in is an alternative to the subscription sign-in.[5]

Inside a session, /login reopens sign-in for OAuth users.[4] From the shell, omp login [PROVIDER] is the terminal counterpart of /login (omp login --help); /logout removes a stored account.[3]

When your organization forces the re-login

Sometimes the expiry is not the provider's choice but your employer's. Google Workspace, for example, lets an administrator control how long different users can access … the Cloud SDK without having to re-authenticate. The admin sets a Reauthentication policy of Require reauthentication at a chosen frequency. The range is narrow: the minimum frequency allowed is 1 hour, and the maximum is 24 hours.[7] When that session length expires, the application will require the user to re-authenticate to continue operating. Command-line tools then report a reauth-related error until the user signs in again.[7] Similar admin settings exist for other providers. Claude Code, for instance, lets admins require claude.ai logins to belong to a specific organization.[1]

So if a teammate's deploy login keeps dying on the same schedule, the cause may be a policy. It is not a bug. Test the failing call once and read the actual error, instead of guessing. Then ask your company's admin whether a non-personal credential is allowed for automation; lesson 8.11 covers that kind.

A real pattern, anonymized

A user on a small team kept getting "credentials no longer valid". It came from a hosting tool's command-line login, roughly every fifteen hours. The agent first proposed three causes and a cleanup of credential files. One thirty-second test of the failing command showed the real cause. The company's login policy forced a fresh sign-in on a fixed schedule. The fix was not deleting files. It was signing in again, or using the service credential the policy permitted.

Recall before you read on

Without scrolling up: what are the two tokens a login produces, which one expires first, and what happens when even the refresh is refused?

The login produces a short-lived access token and a longer-lived refresh token. The access token expires first; the agent silently uses the refresh token to get a new one. When the refresh is refused too, every request fails with a login error until a human signs in again.

Keep the stored credential safe

These tokens are secrets (lesson 8.1). Where they are stored matters. Claude Code keeps credentials in the encrypted macOS Keychain on a Mac. Elsewhere it falls back to a permission-locked file (0600).[1] omp is more candid: The local database is not encrypted at rest. It relies on directory permissions instead: protect the entire directory and any backups or sync copies, not only agent.db.[3] And never paste a credential into the chat itself. Paste credentials only into that login prompt, the docs say — not into a chat message or a shell argument.[3] A token that was already issued may remain valid until the provider expires or revokes them. Signing out also means revoking it in the provider's console.[3] See the safety checklist.

Check yourself

Question 1 of 4

Every request from your agent now fails with a login error, though it worked this morning. What most likely happened?

Logins expire by design. When the refresh token is also refused, requests keep failing with a login error until someone signs in again — no code change is involved.

Question 2 of 4

Why does signing in again fix an expired login without changing any code?

A re-login stores a new token pair. The project files were never the problem, so nothing in the app needs to change.

Question 3 of 4

Your workplace admin sets a re-login policy on your account. What can it force?

Organization policies such as Google Workspace's reauthentication setting make users sign in again after a fixed session length — here between 1 and 24 hours. It has nothing to do with approvals, hosts, or memory.

Question 4 of 4

What does a refresh token actually do?

Per the OAuth standard, a refresh token is used to obtain a new access token when the current one expires. It is not a password copy and it does not delete anything.
