Permission errors: when the server says no

A refused push does not mean your app is broken. Find out which account, repository and permission the request actually used before changing anything.

About 15 minutesBuilds on: 3.6 Remote, origin, pushWin: you can turn a permission refusal into a specific access request

Why this matters for shipping your app

Your app may work perfectly on your computer and still fail at the last step: sending its commits to GitHub. When a push is refused, asking the agent to rewrite the app will not help. You need to distinguish a code problem from an access problem, preserve the work, and ask the right person for the smallest necessary permission.

Keep the refusal message. It tells you more than “push failed.” The useful questions are: where did the request go, whose account did it use, and was that account allowed to do that particular thing?

Two numbers, not a complete diagnosis

403 Forbidden is a response from a web server. MDN describes it as the server understood the request but refused to process it.[1] Treat it as a refusal to investigate, not an invitation to keep retrying. The same documentation says an unchanged request should be expected to fail again.

404 Not Found needs more care. A wrong address or a missing repository is possible, but lack of access is possible too. GitHub says its “Repository not found” error can mean the repository does not exist or you do not have permission to access it.[2] You cannot conclude that someone deleted the repository from that message alone.

Why hide access behind “not found”? MDN explains that a server may return 404 instead of 403 when it does not want to admit that a resource exists.[1] The number is a clue. The full message and the account used are the evidence.

Read the code and the message together. The code says which kind of refusal it is. The message often names the account, the repo or the rule. Neither one tells the whole story alone.

Guessing

“It says not found. Create a replacement repository and push everything there.” This changes the destination before establishing whether the original exists.

Diagnosing

“Check the owner and repository spelling, then establish which account the failed command used. Stop before changing the destination.”

Permission has more than one gate

An account role is the set of jobs a person is allowed to do on a repository. Reading code, pushing commits, and changing settings are different jobs. For organization repositories, GitHub recommends the Write role for people who push. Admin adds risky settings work.[3] Being able to read a repository is not proof that you can push to it.

Put the three gates in order. First the destination: which repo, which branch. Second the account: which login makes the request. Third the credential: what that login handed to the tool. A refusal comes from the first gate that closed. Widening a later gate cannot open an earlier one.

A personal access token is a secret credential used to authenticate requests. GitHub says A token cannot grant additional access capabilities to a user.[4] If your account cannot push to a repository, a more powerful token will not turn you into its owner.

The token can also be narrower than your account. A scope limits the access carried by an OAuth token or a classic personal access token. GitHub's fine-grained personal access tokens instead select a resource owner, repositories and specific permissions. Both approaches limit the credential; neither adds rights the account lacks.[4][5]

Do not request every permission to make an error disappear. GitHub recommends choosing the smallest repository access and permissions needed.[4] A code push is not a reason to grant repository deletion.

A useful access request names four things. The repo, the action, the account, and what you already tried. For example: “I cannot push the gallery commits as this account. Here is the redacted message.” That gets a faster answer than “GitHub is broken”.

Recall before you read on

Your account can read a repository but cannot push. Could adding scopes to its token create write access? What else might “Repository not found” mean besides deletion?

No. A token can narrow the account's rights, not expand them. “Repository not found” can also mean a wrong address or insufficient permission to access that repository.

A fork is another repository

A fork starts as a copy of another repository, called the upstream repository. GitHub explains: A fork has its own settings and permissions but stays connected to the upstream repository.[6] A branch is a line of work within one repository; a fork is a separate repository.

This explains a common surprise: pushing to your fork works, but pushing to the original does not. Success at one destination is not permission at the other. Read the owner in the remote address, not only its nickname. As you learned in lesson 3.6, origin is a name saved in your project, not a promise of ownership.

The remote address ends in owner/name.git. Git also stores a short name for it. Print the address, not the short name. The address is the fact; the short name is a label you chose.

If you intend to contribute without direct write access, a fork can hold your changes and a pull request can propose them to the original. Creating a fork is a collaboration choice, not something the agent should silently do to bypass a refusal. Private-repository policies can restrict whether and where forks may be created.[6]

A real pattern, anonymized

A user had a personal copy and a shared copy of an app. The agent pushed to the personal copy, then received a 403 at the shared copy. The user arranged access and told the agent it had changed; the same push then succeeded. Later, a repository-management operation needed stronger access, and deleting an unwanted fork needed a token capability the stored credential did not carry. Those were separate permissions, not one broken login.

The boundary matters even when credentials already exist. In another run, an agent used a stored credential to publish a public repository before asking which account the user intended. The credential worked; the decision was wrong. Before publication, name the account, destination and intended visibility. A working credential is not your consent.

Diagnose without exposing the credential

When GitHub CLI is already part of your setup, gh auth status reports its active account and authentication state. Its help also offers --show-token; do not use that option for this exercise. A local run showed a “Token scopes” line for an OAuth credential. That is useful metadata, not a reason to print the token itself.[7]

That check describes GitHub CLI's credentials. Do not assume a separate Git command used the same credential. GitHub's troubleshooting guide warns that incorrect or outdated cached credentials can cause authentication failures.[2] If the evidence does not identify the credential used by Git, mark that part unknown rather than guessing.

Credentials go stale. A token can expire, be revoked, or stay cached after you switch accounts. A login that worked last month is not evidence about today. That is why the first check is what the tool says it is using right now.

Keep secrets out of the diagnosis

GitHub says Treat your access tokens like passwords.[4] Never paste a token into your prompt, screenshot or error report. Share the status code, operation and redacted message instead.

Do it in your own project 
Help me diagnose repository access without changing it.
Inspect the configured remote addresses without exposing credentials. If GitHub CLI is installed, run gh auth status without --show-token.
If I have supplied a refusal message, separate what it proves from what remains unknown: destination, account role, and token limits.
Do not push, create a fork, change remotes, create credentials, widen scopes, or alter approvals. Do not read or print token values.
Finish with the smallest specific access request I could send to the repository owner, or the missing evidence needed first.

You should see an identified destination, available account metadata, and a short list of known facts and unknowns. No new permission or repository is required. If you have no current failure, a destination-and-credential inventory is a valid result; do not manufacture a refusal.

After the owner or account holder changes the relevant access, ask for one approved retry of the planned action. If the message instead names a branch rule, follow that rule rather than widening a token; lesson 3.15 covers that case.

A refusal is not a verdict on your app. It is a statement about one action, for one account, at one moment. Fix that access, retry once, and read the next message on its own terms. A refusal that names a rule, a missing review or a failed check is a different problem; treat it as one.

Check yourself

Question 1 of 3

A repository request says “not found.” What conclusion is justified?

Check the address and account access. GitHub documents “Repository not found” for both missing repositories and insufficient access.

Question 2 of 3

Your account lacks write access. What can a wider token do?

A token is further limited by scopes or permissions. It cannot grant rights its owner does not have.

Question 3 of 3

You pushed to your fork. What does that establish?

A fork is a separate repository. A successful push there does not demonstrate write access to, or update, the upstream repository.
