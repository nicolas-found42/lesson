The three agents: same ideas, different shells

Claude Code, Codex and omp all run the loop you met in lesson 0.1. What changes is the shell around it: the start command, the rules file, the mode names, the key that stops a run.

About 15 minutesBuilds on: 0.1 What a coding agent isWin: you can find the same four controls in any of the three

Why this lesson exists

This course is written for three agents because they are the ones you are likely to have, and because the habits you learn work in all of them. You do not need all three. You need one, plus a clear picture of which parts are the agent and which parts are its packaging.

That distinction matters for shipping your app. Tutorials, videos and advice are usually written for one tool. If you follow them in another tool, the idea may still be right while the words are wrong. Knowing where the difference sits saves you from blaming yourself for a command that was never meant for your program.

What a "shell" means here

Think of the model as the part that reads and reasons, and the shell as everything you actually touch: how you start it, what it calls its settings, which file it reads for project rules, which keys steer it. Anthropic calls its shell a harness. The loop is the same; the buttons are not.

All three are programs you launch from a project folder in a terminal, and all three keep a session you can resume later. You will install one in lesson 0.5 and learn the terminal in 0.4. Nothing here depends on having them yet.

The same three things, in each shell

Each agent below starts from a folder, reads a plain-text file of standing instructions, has a setting that decides when it asks before risky actions, and lets you stop a run in progress. Those are the four things to learn. The next section shows what each one calls them.

Made by Anthropic, and described by its own docs as an AI-powered coding assistant that helps you build features, fix bugs, and automate development tasks.[1] Type claude inside your project folder to start. It reads a rules file called CLAUDE.md, and from version 2.1.283 it opens in auto mode, where a second model reviews actions instead of you.[2] Press Esc to stop a turn; the work done so far stays.[4]

Made by OpenAI. Its CLI page says it can inspect code, make changes, run commands, and automate repeatable work without leaving your terminal.[5] Start it by running codex in a project folder.[5] It reads AGENTS.md: Codex reads AGENTS.md files before doing any work.[6] Its default posture pairs a workspace-write sandbox with on-request approvals, where the agent asks when it needs to go beyond that boundary.[7] While it works, Enter adds instructions to the current turn and Tab queues a follow-up.[8]

An independent open-source agent from Stencil Labs, describing itself as a coding agent with the IDE wired in.[9] Start it with omp in your project folder. Its rules file is AGENTS.md at the repository root: omp loads it automatically and applies it throughout the session.[10] Its built-in default is the least cautious of the three: The built-in default is yolo.[11] Press Esc to stop the active turn.[12] All omp documentation comes from its own authors, so treat surprising claims with care.

Your tab choice is remembered; later lessons put your agent first.

Here is the whole map. Read down the column for the agent you picked; you do not need the other two columns.

Two cells deserve a warning. The permission names are not a ranking, and the same word can mean different things in different shells. More importantly, none of these defaults is a promise of safety: Claude's auto mode uses a classifier, Codex's default keeps writes inside the project folder, and omp's default asks nothing at all. Lesson 0.6 covers how to put any of them into a mode that asks before it acts, and why a beginner should.

A real pattern, anonymized

A user installed two agents in the same week and switched between them depending on which window was open. Each session started in the same project folder, so the work was always in the right place. What broke was quieter: the standing instructions had been written into the rules file of the first tool only. The second tool never read that file, so it ignored the project's build command and test procedure for several days. Nothing errored. The user re-explained the same things, and the agent sometimes guessed differently.

The fix took one prompt: write the same instructions into the file the other tool reads, or keep a single AGENTS.md and let both tools read that. The user then picked one agent for the rest of the project.

That is the ordinary cost of mixing shells. It is not a bug in either tool. The lesson is not "never try another agent"; it is "know which file your current agent reads, and do not assume the last tool's words still apply".

Recall before you read on

Cover the table. Name the four things every one of these agents has, and say which of them changes from tool to tool. Write it before revealing.

Every shell has a way to start in a project folder, a project rules file, permission or approval modes, and a way to stop a running turn. The ideas are constant; their names, defaults and keys differ. Resuming a session and the exact mode labels also differ.

Choosing, once

For this course, choose one agent and stay with it through the first shipped page. The choice is mostly practical: whatever you can install and sign into, on the machine you have. All three can read and edit the files in a folder and run commands there, which is all the first-ship path needs.

Two honest differences, from the vendors' own pages. Codex also runs inside the ChatGPT desktop app, not only the terminal; Claude Code also exists as a desktop and IDE surface.[13][1] omp is a terminal program, and its docs are its only documentation.[9] Neither fact changes the loop.

The rule for this course

One project, one agent, one rules file, until the page is live. Switching is allowed later, and lesson 1.12 shows how to write the rules file so a switch is cheap.

Do it now — name your shell in four lines

You should have four short lines that mention one tool only, for example: omp · AGENTS.md · always-ask · Esc. If a line mixes two tools, fix it now. That mixture is exactly what confused the user in the example above.

Check yourself

Question 1 of 3

You move to a different agent halfway through a project. What carries over unchanged?

The folder and its files are yours, not the tool's. The keys, mode labels and rules filename belong to the shell, and they do change.

Question 2 of 3

Two agents show different approval prompts for the same file edit. What follows?

Prompts are labels on the same underlying decision: may this action run without asking? The labels differ; the edit does not.

Question 3 of 3

A guide written for one agent gives you a command that fails in yours. Best response?

The idea usually transfers; the spelling of the command does not. Your tool's own docs are the source for its command names and flags.
