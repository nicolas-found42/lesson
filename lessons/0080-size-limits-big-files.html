Size limits and big files: host them elsewhere

Free hosting has hard size limits. Learn to measure your project, read the limits, and keep big files somewhere else — so your link still loads for your friends.

About 15 minutesBuilds on: 6.3 GitHub PagesWin: you can measure your project and keep a too-big app shippable

Why size decides whether your link works

Your mission is a public link you send to someone. That link only works if the host accepts your files and serves them fast enough. Lesson 6.3 put your app on GitHub Pages; this lesson is about the ceiling that host imposes. A page full of huge files is not merely slow — above a certain size the host refuses it outright, and your "live" site shows nothing at all.

Measure first, guess never

Before you change anything, find out how big your project folder actually is. In a terminal inside your project folder, the command du -sh . prints one line: the total size and the folder. On this Mac it prints, for example, 3.0M  . To see which subfolders are heavy, du -d 1 -h . | sort -hr lists them biggest first. You can also ask your agent directly: "Measure my project folder and list the ten biggest files in it."

A real pattern, anonymized

A user asked an agent to put a 3D model gallery online for friends who are not technical. Measuring the folder showed about 3.6 GB, while the free host caps a published site at 1 GB. The agent did not shrink or delete the models. It published only the app and its small catalog — about 45 MB — and made the page fetch the huge model files from the repository's raw file addresses at a pinned commit. The public link worked the same afternoon.

The limits, in one table

GitHub publishes these numbers in its own documentation. A size limit is a hard or soft ceiling: hard limits refuse, soft limits warn or throttle.

Read the table as three separate walls. A single file over 100 MiB cannot even be pushed to the repository — GitHub blocks it. A published site over 1 GB is refused at deploy time. And even a site that fits can misbehave if it moves more than 100 GB of traffic a month, which is a soft limit: GitHub says it may stop serving the site or write to you suggesting you put a content network in front of it or move hosts.[1]

Recall before you read on

Without scrolling up: name the two hard size walls a GitHub Pages project can hit, with their numbers. Then say in one sentence what "soft limit" means.

A single file over 100 MiB is blocked from the repository, and a published Pages site over 1 GB is not served. A soft limit (100 GB bandwidth per month, 10 builds per hour) does not refuse immediately — it warns, throttles, or may stop serving later.

Host the big files somewhere else

The fix is not to shrink your ambition; it is to split the project. The site — HTML, CSS, JavaScript, small images — stays in the repository and is published by Pages. The big files — videos, model files, large downloads — live elsewhere, and your pages link to them with an absolute URL (the full address including https://, the kind lesson 6.3 reserved for other people's sites, because these files are no longer inside your site's folder tree).

GitHub itself offers two verified places for the big files:

  • A release. You attach files to a release on your repository's page. GitHub's large-files page says: If you need to distribute large files within your repository, you can create releases on GitHub.com instead of tracking the files, and we don't limit the total size of the binary files in the release or the bandwidth used to deliver them (each file still has a per-file cap).[2]
  • A raw file address at a pinned commit. Open any file in your repository on GitHub and click the Raw button — GitHub's docs describe this as viewing the raw content of a file without any styling.[3] The address looks like https://raw.githubusercontent.com/YOUR_USERNAME/my-app/main/assets/big-file.bin. Replace main with a commit ID to get a pinned raw file URL: https://raw.githubusercontent.com/YOUR_USERNAME/my-app/<commit-id>/assets/big-file.bin. A branch name can move; a commit ID cannot.

Any other file host or storage service works too — the only requirement is a public absolute URL. What matters is that the file is served by that host, not by Pages, so it never counts against your 1 GB.

Do not "fix" size by deleting blindly

Deleting files to fit under a limit can break the app: the page may reference a file you removed, and the link then 404s. Decide per file — ship it, host it elsewhere, or truly drop it — and after publishing, open the live page and click through to the big file to prove it loads.

Ask the agent for a size plan

You do not need to compute anything by hand. This prompt works in any of the three agents:

Measure my project folder and list the ten biggest files with their
sizes. My site is published on GitHub Pages, which serves published
sites of at most 1 GB and blocks single files over 100 MiB. Propose a
plan: which files the site itself must ship, and which big files should
be hosted elsewhere (a release, a raw file URL at a pinned commit, or
another host) with the absolute URL each page should use. Change
nothing yet — show me the plan first, and stop there.

Notice the stop condition: "show me the plan first, and stop there." A size plan is a decision you should read before anything changes.

Do it now

du -sh . prints one line like 3.0M  . The agent's plan separates "site must ship" from "host elsewhere", and after publishing, the live page loads a big file from its absolute URL (for example a pinned raw address) without the file being inside the published site.

Start it with claude inside your project folder, then paste the size-plan prompt as a normal message.[4] Keep approval prompts on; lesson 0.6 shows how to check which mode your session is in.

Start it with codex inside your project folder. It can inspect code, make changes, run commands, and automate repeatable work without leaving your terminal, which covers measuring and editing.[5] Keep the approval prompts as they are.

Start it with omp inside your project folder; the same prompt works unchanged.[6] Its documentation comes only from its own authors, so double-check anything surprising.

Check yourself

Question 1 of 3

Your whole project folder measures 3.6 GB. GitHub Pages says published sites may be no larger than 1 GB. What should you do?

The site itself must fit under 1 GB; the big files can live outside it and be linked by absolute URL. Deleting at random can break the app, and the published-size limit is not negotiable per account.

Question 2 of 3

One video file in your repo is 250 MB. What happens when you try to push it?

GitHub blocks files larger than 100 MiB (a warning starts above 50 MiB). A 250 MB file never enters the repository, so Pages never sees it either.

Question 3 of 3

You move a big file out of your site and link to it by its full URL. Why must that link be absolute?

A relative link is completed from your page's own address, so it can only point inside your site. A file hosted elsewhere needs the full URL with its own domain.
