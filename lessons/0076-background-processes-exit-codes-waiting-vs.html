Background processes: started is not finished

A command can keep working after the agent speaks. Learn what to wait for, what an exit code tells you, and when checking again helps.

Why this matters for your app

Shipping your app involves commands that take time: preparing files, checking them, or starting a preview. If you mistake “started” for “finished,” you can publish before the check ends. If you restart every quiet command, you can create duplicate work. Your job is not to demand constant chatter. It is to ask for the right evidence at the right point.

A process is a running instance of a program. A background process keeps running while control returns to the place that launched it. In Bash, a shell that interprets terminal commands, ending a command with & starts it in the background: the shell does not wait for the command to finish.[1] You do not need to add that symbol yourself for this lesson. An agent may manage background work through its own tools.

Keep three questions separate

First: did it start? Second: has it ended? Third: did it achieve your goal? Those are different questions. A job identifier, a label used to refer to one run, answers which job you mean. It is not a passing result.

EvidenceWhat you can conclude
Job started; identifier returnedThere is a run to track, not yet a result.
Still running; progress outputWork continues; completion remains unknown.
Finished; exit code recordedThe program ended and reported a status.
Expected page or report checkedYou have evidence about the requested outcome.

The distinction matters even when you see a zero immediately after launching work. Bash documents that starting an asynchronous command returns status zero without waiting for it.[1] That zero belongs to launching the background command, not proof of its eventual success. Ask which command and which stage a reported status describes.

Read the exit code, then read the result

An exit code, also called an exit status, is a number a program reports when it ends. For the shell, zero means success and a nonzero number means failure. The Bash manual states the rule plainly: a non-zero exit status indicates failure.[2] A running job does not yet have its final exit code. “No error yet” is not the same as “finished successfully.”

Do not treat every nonzero code as the same diagnosis. Ask for the number and the relevant output: the text the program produced. Conversely, a zero only tells you the program reported success according to its own rules. It cannot tell you whether the page looks right or whether the requested report actually exists.

Worked example · anonymized

A user asked an agent to run a long visual check of an app. The run ended with code zero, but the expected images were missing. The cause was not established. The user required progress and images to be saved during the run, rather than discovering an empty result at the end.

The better report was not “passed.” It was “the process ended with zero; the expected images are missing; the requested check is not proven.” That wording preserves both facts without inventing a cause.

For your app, specify the expected result before starting. A finite check should finish and provide its summary. A preview server, a program that serves your page while you use it, has a different goal: be ready and remain running. Ask the agent to name a readiness check rather than waiting for that server to exit. A process that stays alive is not automatically stuck.

Recall before revealing

A command has a job identifier and has printed no errors. What two facts are still missing before you call its check successful?

Whether that run has finished, including its final exit code, and whether the expected result was actually produced. An identifier and silence prove neither.

Waiting is not repeated checking

Polling means repeatedly asking whether work has finished. Waiting, here, means leaving that work alone until a completion signal arrives. A completion notification is a message that a run has ended. Progress output describes what has happened so far; it need not mean the job is over.

Prefer a completion notification or a tool's wait facility when available. That is a workflow recommendation, not a claim that every agent has the same button. If notifications are unavailable, agree on spaced status checks and a limit in advance. Asking every few seconds cannot make a slow job finish sooner.

There is a separate reason to inspect an ongoing run: catching a bad result early. For a ten-minute visual check, an early sample image can show that the wrong page opened. That is an evidence checkpoint, not a loop that asks “done yet?” without learning anything new.

Keep a timeout, a limit on how long an operation may wait, separate from a diagnosis. If a tool reports a timeout, ask whether the underlying process ended, was stopped, or remains running. Do not launch another copy while that state is unknown. If work must stop, request confirmation that the specific job stopped before restarting it.

Ask for state, not reassurance

Keep approval prompts on. Before starting a long command, tell me whether it should finish or stay running, what evidence will show success, and how we will learn its state. Track the same job; do not restart it because it is quiet. Prefer completion notifications or a wait facility over repeated polling. If neither exists, propose a bounded checking interval. Report the final exit code and expected result separately. If interrupted or timed out, establish whether the process still runs.

Use the same request in all three agents. Where you inspect the work depends on your interface:

In Claude Code's desktop app, open Background tasks from the title bar's menu once background work exists. The documentation says: Click any entry to see its output in the subagent pane or stop it.[3] In another interface, ask for the current job and its output rather than assuming the desktop controls exist.

Ask Codex to identify the current run, its available completion signal, and how to inspect its output in your interface. This lesson does not assume a particular background-task button. Keep “running,” “ended,” and “verified” separate in its report.

Ask omp (oh-my-pi) to identify the current run and explain its available wait or notification mechanism before starting. Do not copy another agent's interface instructions. Require the final status and expected evidence for that same run.

Before doing the practice, keep approval prompts on; lesson 0.6 explains the settings. Approval to start a command is not approval to launch unlimited copies or leave unwanted work running.

Practice: observe one harmless run

You should see one completed run, its short message, and a final exit code. If it ran in the foreground, there may be no background identifier or notification. That is not a failure: you have still separated starting, ending, and checking the output.

Check yourself

A background check returns a job identifier. What should happen next?

Track the same run and obtain its completion result. Starting is not passing, and a duplicate can make the evidence harder to interpret.

A run ends with zero, but the expected report is absent. Which conclusion fits?

Zero reports program success, not fulfillment of your whole request. The missing report must remain visible as a gap in the evidence.

Completion notifications are available for a slow check. Which approach is better?

A completion signal answers the state question without repeated polling. An early evidence checkpoint may still be useful, but repeated reassurance adds no proof.

Ask your teacher

Ask: “Should this command finish, or stay running?” or “What would distinguish a quiet healthy run from a stuck one in my app?” Bring the job's output and current state, not only the agent's summary.
