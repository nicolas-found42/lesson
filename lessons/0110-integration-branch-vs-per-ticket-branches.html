Integration branch vs per-ticket branches

When you have several tickets in flight at once, you have to decide where finished work collects: straight onto main, or onto a holding branch first. This lesson shows both layouts and when each one saves you pain.

About 15 minutesBuilds on: 3.5 BranchWin: you can choose a branch layout for a multi-ticket job and say why

Why this matters for shipping

So far your app has had one line of work: make a branch, build a thing, merge it back. That works until you run several pieces of work side by side — a search page, a style pass, a settings screen. Git calls a branch a lightweight movable pointer to one of these commits[1], which means branches are cheap: you can have many at once. The question is not whether you can — it is which arrangement keeps main safe and keeps the pieces from colliding.

Two words, one decision

A per-ticket branch is one branch made for a single ticket, created from main, and merged back when that ticket is done. GitHub's documentation names the pattern: A branch you create to build a feature is commonly called a feature branch or topic branch.[2] One ticket, one branch, one pull request.

An integration branch is one extra branch (often named integration or develop) that collects several finished tickets before any of it goes to main. Ticket branches merge into it; later, the whole batch merges to main in one step.

The git command underneath both layouts is the same. To merge is to join two or more development histories together[3] — the layouts differ only in which histories join when.

Recall before you read on

Before reading further: with three tickets and one integration branch, which branch do you create each ticket branch from, and which branch does each ticket merge into? Write both answers.

Each ticket branch is created from main (or from integration, if your convention says so — pick one and stick to it), and each finished ticket merges into the integration branch, not into main. Main receives everything only once, at the end.

Layout A: every ticket goes straight to main

Ticket branch off main, finish, merge to main, delete the branch, next ticket. This is the layout you already know from lesson 3.5. Its virtue is that main is always current: each merged ticket is visible, reviewable, and shippable on its own, in small pieces.

Its cost appears when several agents work at once, or when the tickets only make sense together. If ticket 3 is broken but tickets 1 and 2 are fine, main now contains the broken piece, and rolling back means unpicking a merge.

Layout B: a holding branch between the tickets and main

Ticket branches still come off main, but their pull requests target the integration branch. Main does not move until you are satisfied with the whole batch. If one ticket turns out badly, you drop that one merge from integration; main never saw it.

The cost: main gets one big merge at the end, so review happens in bulk, and problems between tickets surface late rather than one at a time. GitHub's conflict guidance applies to both layouts — Merge conflicts often happen when people make different changes to the same line of the same file[4] — but with an integration branch, several tickets' worth of overlap arrives at once instead of dribbling in.

Per-ticket → main

Best when: tickets are independent; each should ship as soon as it is done.

You get: small reviews; main always current; a bad ticket must be reverted from main.

Tickets → integration → main

Best when: tickets belong to one feature; you want to test the whole batch before main moves.

You get: a safe staging area; main moves once; review happens in one big batch.

What this looks like with an agent

A coding agent does not care which layout you choose, but it must be told. Left alone, it will pick something sensible or something surprising, and you will find out by reading git branch afterwards. In one real session, a user handed an agent a long roadmap of tickets and named exactly three to build. The agent gave each ticket its own branch, worked on them in parallel, and merged each finished ticket into a shared integration branch. At the end it opened a single pull request covering all three. That one decision — three small branches, one holding branch, one PR — is Layout B, and it worked because the tickets were parts of one feature. Later in the same run the user said, in effect: stop work when these three tickets have merged and closed. Naming the done-state kept a many-ticket job from sprawling.

Spot the layout. A user asks an agent to build three related screens for a gallery app. The agent creates ticket-search, ticket-style, and ticket-settings, finishes them in turn, and after each one runs git switch integration then git merge ticket-search. When all three are in, it proposes one pull request from integration to main. The user reviews once, merges once. If the settings screen had gone wrong, main would still be untouched.

Try it yourself

You can feel both layouts in five minutes with a throwaway folder. This is real git, the same commands your agent would run — check the result at each step.

Do it: build the integration layout
  1. Make a scratch repo and give it a starting file: 
    mkdir branch-practice && cd branch-practice
git init -b main
echo "<h1>my app</h1>" > index.html
git add . && git commit -m "first page"
  2. Create the holding branch, then go back to main for ticket work: 
    git switch -c integration
git switch main
  3. Build "ticket A" on its own branch and merge it into integration: 
    git switch -c ticket-search
echo "<p>search</p>" > search.html
git add . && git commit -m "add search page"
git switch integration
git merge ticket-search
  4. Build "ticket B" the same way, from main, into integration: 
    git switch main
git switch -c ticket-dark
echo "body { background: #222; }" > dark.css
git add . && git commit -m "add dark styles"
git switch integration
git merge ticket-dark
  5. Compare the two lines of history: 
    ls
git switch main
ls
On integration you should see dark.css  index.html  search.html. After switching to main, only index.html — main has not moved. (Real output, git 2.56.0.) Note the pattern in steps 3–4: each ticket branched from main and merged into integration. If two tickets edit the same lines, a merge will stop and ask you to resolve it — lesson 3.9 covers that.

Choosing, in one sentence each

Choose per-ticket-to-main when each ticket could ship alone and you want small, steady steps. Choose an integration branch when the tickets are one feature and you want to prove the whole batch before main changes. Mixing them without saying so is the real hazard: if your agent merges to main while you expected a holding branch, you learn it from the diff, not from a warning. So put the layout in the prompt — "one branch per ticket; merge each into integration; PR to main only when all three are in" — and confirm with git branch and git log afterwards.

Check yourself

Question 1 of 3

In the integration layout, where does a finished ticket merge first?

The integration branch is the holding area between ticket branches and main. Main receives the whole batch in one merge at the end; individual tickets do not touch it.

Question 2 of 3

Which situation most favors an integration branch over per-ticket merges to main?

A holding branch pays off when tickets belong together and you want main to move once, after the batch is proven. Independent or urgent single changes are simpler merged straight to main.

Question 3 of 3

You told the agent to use a holding branch, but suspect it merged to main. What is the fastest check?

Claims are not evidence (lesson 2.2): the branch pointers are facts you can read with git branch and git log in seconds. Asking the agent may help, but the repo is the source of truth.
