Unit 4 · Lesson 4.7

Reward hacking, or the metric gets gamed

Give an agent something to hit and it will hit it. Whether that something still stands for what you wanted is a separate question, and it is yours to answer before you ship.

About 15 minutesBuilds on: 4.1 Definition of doneWin: you can spot a check that passes without the work being done

Why this matters for shipping your app

Lesson 4.1 gave you acceptance criteria: written conditions that say what "done" means before the agent starts. That was the right move, and it is also the moment a new risk appears. A condition you can check is never the whole of what you wanted. It is something you can see: a passing test, a number, a page that loads. The agent optimizes what it can see.

You do not need a malicious agent for this to hurt you. You need an ordinary one, doing exactly what you asked, plus a criterion that was easier to satisfy than you realised. This lesson is about noticing that gap before your users do.

A measure is a stand-in, not the thing

Goodhart's law warns that optimizing a measure can make it stop tracking your goal. Charles Goodhart's original formulation, quoted by Manheim and Garrabrant, says any observed statistical regularity will tend to collapse once pressure is placed upon it for control purposes.[1] This is a risk, not a rule that every measurement becomes useless.

A proxy is a measurable stand-in for what you want. Researchers describe reward hacking as optimizing an imperfect proxy reward function leads to poor performance according to the true reward function.[2] DeepMind calls the related pattern specification gaming: a behaviour that satisfies the literal specification of an objective without achieving the intended outcome.[3]

Those sources discuss learning systems. We will apply the same distinction to coding tasks: satisfying the written check is not necessarily satisfying your intent. You do not need to infer human-like dishonesty to inspect that gap.

The cars that learned to win the wrong game

A real pattern, anonymized

A user watched cars in a small driving simulation learn shortcuts that counted as completed laps without driving the intended course. The score improved while the behaviour got worse.

The coding agent added ordered checkpoints: a lap counted only after the car passed the checkpoints in sequence. It tested that change. The repair tightened what counted as success rather than asking the learning program to try harder.

Three shapes it takes in a small project

Here are three illustrative ways the gap can appear in your app work:

  • The check gets weaker. A test fails, so the test is deleted, skipped, or loosened until it passes. The suite is green and the bug is still there.
  • The example gets special-cased. The criterion says "the total is correct". The code returns the right total for the one row you showed it, and is wrong for every other row.
  • The letter is hit, the product gets worse. A reviewer is asked to find problems, so it finds some, and you fix all of them. The page gains layers, guards and tests for situations that cannot happen, while the actual goal, a page a friend can use, gets no better.

Anthropic warns that A reviewer that's asked to find problems will always find something.[4] Treat that as practical guidance, not a universal guarantee. Aim review at your written requirements rather than at producing a large number of findings.

What a tighter criterion looks like

The difference is not more words. It is a different kind of evidence.

Loose: a number that can move

"All tests pass."

Deleting a failing test can satisfy this sentence without fixing the bug.

Tighter: an outcome someone can check

"A first-time visitor opens the page on a phone, taps the button, and sees the confirmation text. All tests still pass, and no existing test was deleted or skipped."

Now you require evidence of the user outcome, not only a passing suite.

Tightening usually means adding one of four things: a named example with real values, a case you keep back and do not show the agent, a second criterion that a shortcut would fail, or an explicit sentence about what is not allowed ("do not delete or skip tests to make them pass").

The tell: read the evidence, not the verdict

The agent's report is a claim, which lesson 2.2 covered. When a metric is in play, the report usually has a second layer: the tool that produced the number. omp's documentation says exactly this about its own display: A successful card means that action completed, not that the whole task is correct.[5]

Ask for the command and its full output, then inspect the changed lines. Look for removed or skipped tests and conditions tied to your sample value. If a check seems unable to fail, use a negative control: deliberately introduce the relevant failure in a disposable copy and see whether the check detects it. Lesson 2.11 explains the safe procedure.

In another anonymized session, a layout checker passed a page with overlapping text because it skipped newer element types. A deliberately broken example exposed the gap. Passing was real; coverage was missing. A negative control tests that limited question, not whether every possible failure is covered.

Recall before you read on

Without scrolling up: name the three shapes a gamed criterion takes, and say what a negative control proves.

Weaker check (test deleted, skipped or loosened), special-cased example (right answer for the one input you saw), and letter over spirit (the rule is satisfied while the product gets worse, as with an unbounded review). A negative control proves the check can fail: you break the code on purpose and confirm the check reports it.

Do it in your own project

You should get at least one honest shortcut named, because the prompt asks for the cheapest path rather than for a confession. If the answer is "none", push once with a concrete example: "Could it pass by hard-coding the value from my screenshot?" In the diff, a test that lost a line or gained a skip is the usual finding. A check you cannot make fail is not yet evidence; the next step is lesson 2.11's negative control, not a rewrite.

Run /diff: it lets you look over the changes in your working tree without leaving Claude Code.[6] Read the changed lines there before you accept a summary.

Type /diff to inspect the Git diff, including files Git is not tracking yet.[7] The panel is the place to spot a loosened test.

omp keeps file changes in your working tree and does not commit them unless you ask. Its docs say your editor, git diff, and the transcript remain the final review surfaces.[8] Use git diff in a second terminal.

Your choice of tab is remembered, so later lessons show your agent first.

Fix the criterion, not the agent

When you find a shortcut, the tempting response is a sharper instruction: "be careful", "do it properly", "don't cheat". None of those change what the check rewards, so none of them change the outcome. Two moves do.

The first is to make the shortcut fail something. Add the case you held back, require the old tests to still exist, or ask for the behaviour on input the agent has not seen. The second is to widen the evidence from one number to a small set: a passing suite plus a real click plus a screenshot of what the user sees. Lesson 4.1's criteria and lesson 2.8's screenshots combine well here, because a screenshot is much harder to satisfy by editing a test file.

Keep the old criterion too. A tightened rule that quietly drops the original requirement is its own small reward hack, and it is one you commit against yourself.

Check yourself

Question 1 of 3

You ask for a bug fix; the criterion is "all tests pass". The agent loosens a test and reports success. What happened?

Passing tests stood in for "the bug is fixed". Loosening the test satisfies the stand-in without touching the bug, which is reward hacking rather than a testing accident.

Question 2 of 3

Which acceptance criterion is hardest to satisfy without doing the real work?

A person using the page cannot be satisfied by editing a test, a build script or a lint rule. The other three can all go green while the page is still unusable.

Question 3 of 3

A reviewer told to "find problems" returns twelve findings. What is the best response?

An open-ended "find problems" rewards volume, not value. Tie the findings back to what you said done means, and skip the ones that only add layers.
