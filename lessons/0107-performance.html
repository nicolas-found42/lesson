Performance: measuring what is slow

"It feels slow" is not something an agent can fix. A number can be. This lesson teaches four words — frames per second, benchmark, bottleneck, parallel worker — and how to make the agent measure before it changes.

Why this matters for shipping

An app that works but is painful to use is not done. Friends will close a page that stutters or freezes, the same way they close a page with a broken link. The good news: speed problems are the kind of problem agents handle best, if you steer them with numbers instead of feelings. Everything in this lesson is one habit: turn "slow" into a measurement, then ask for the measurement to change.

Frames per second: the speed of "smooth"

Screens update by drawing many still images per second — each one is a frame. Frames per second (fps) is how many the app manages each second. Browsers redraw a page many times a second, and MDN notes that The most common refresh rate is 60hz, (60 cycles/frames per second), though 75hz, 120hz, and 144hz are also widely used.[1] At 60 fps each frame gets about 16.67 milliseconds; if your app's work for one frame takes longer than that, frames are dropped and the motion looks like stutter.

That budget gets smaller as the screen gets faster. At 120 fps a frame has about 8 milliseconds. At 144 fps it has about 7. So a page that feels smooth on one laptop can still stutter on a phone with a fast screen. Ask for frame time and for the screen rate it is held to, and you have a target you can check.

For web apps, the browser calls your animation code once per frame through requestAnimationFrame, which requests the browser to call a user-supplied callback function before the next repaint — and those calls are paused in most browsers when running in background tabs.[1] You do not need to remember the function name. You need the idea: how fast your app runs is a countable thing, and your agent can print the count on screen.

Benchmarks: a number instead of a feeling

A benchmark is a small, repeatable measurement of how long something takes, run the same way each time so you can compare. When you say "make it faster", the agent may guess at what is slow. When you say "write a benchmark, run it before and after, show me both numbers", the agent has to prove the change helped.

Here is a tiny Python benchmark — two ways of building the same list, timed. This is the actual output of running it on the course author's machine; your numbers will differ, and that is fine. The point is the ratio, not the absolute time.

way A: 0.080 s   way B: 0.114 s   B is 1.4x slower
The script used Python's built-in timeit module, which runs the same code many times and reports total time, so tiny one-off delays don't distort the result.

One run can fool you. The first run often pays a setup cost, and other programs on your machine take turns on the same core. So run the same benchmark three times and look at the spread. If the three numbers sit close together, the measurement is stable enough to trust.

Web pages can measure too: the browser provides performance.now(), which returns a high resolution timestamp in milliseconds and uses a monotonic clock: its current time never decreases and isn't subject to adjustments.[2]

A benchmark belongs in your repo next to your tests, so it runs the same way every time — the same idea as the checks you met in the test lesson.

Bottlenecks: fix the slowest step, not a random step

A bottleneck is the single slowest step in a piece of work — named after the narrow part of a bottle that limits how fast liquid pours. Speeding up anything else changes almost nothing until the bottleneck moves. This is why "make everything faster" is a bad prompt: the agent will rewrite code at random, risk breaking what worked, and possibly not touch the real problem.

Ask the agent to profile — to measure each part and rank them — before it edits. A prompt that works in any agent:

My app is slow when I do [describe the action]. Before changing any code:
1. Write a small benchmark that measures the current speed and prints a number.
2. Run it and show me the number.
3. Identify the bottleneck: the slowest single step, with evidence.
4. Propose a fix for that step only. Do not rewrite anything else.
Stop after step 3 and wait for my approval.

Notice the stop condition in the last line: measure first, get your approval, then change. That is the plan-then-go habit from earlier lessons applied to speed.

Recall before you read on

In your own words: what is a bottleneck, and why should the agent measure before it edits? Write it down, then check.

The bottleneck is the slowest single step, and it caps the whole speed. Measuring first (a benchmark and a profile) shows where the time actually goes, so the agent fixes that step instead of guessing and rewriting code that wasn't the problem.

Parallel workers: using the whole machine

Your computer has a brain with several cores — separate units that can each run work at the same time. A parallel worker is a piece of your app set up to run alongside the others, one per core, so a big job is split instead of done in one line. Web pages can do this with Web Workers: MDN explains that Web Workers makes it possible to run a script operation in a background thread separate from the main execution thread, allowing the main (usually the UI) thread to run without being blocked/slowed down.[3]

That last part matters even when you don't care about raw speed: heavy work on the main thread freezes the buttons and scrolling. Moving it to a worker keeps the page responsive and can be faster.

A real pattern, anonymized

A user had a learning simulation and asked for "1000 times speed, showing every step, at 120 fps". The agent did not blindly rewrite the app. It built the speed control, measured, and reported that the requirements contradicted each other: showing every step at that speed needed more drawing than any screen refreshes. It undid the experiments that had not helped, showed the numbers, and asked which requirement to relax. The user chose, and the app shipped with a slider instead of a broken promise.

That is the goal: when the agent measures, it can tell you honestly that a target is impossible, and you decide the trade-off. When it only guesses, it may claim success.

Do it: make your agent measure something

The agent writes and runs a small script, prints a time in seconds or milliseconds, and the three runs land near each other (within roughly a few percent). If the numbers vary wildly, ask it why — run-to-run noise is itself a lesson about benchmarks.

Check yourself

Question 1 of 4

Your animation stutters. Why does "make it faster" underperform as a prompt?

With no number to aim at, the agent guesses what is slow and may rewrite working code. A benchmark gives it a target and a way to prove the fix helped.

Question 2 of 4

What is a bottleneck in your app's work?

Like the neck of a bottle, the slowest step limits the flow of everything else. Fixing other steps barely helps until that one is fixed.

Question 3 of 4

What does moving heavy work to a parallel worker mainly protect?

Work that blocks the main thread freezes buttons and scrolling; a background worker keeps the interface moving while the heavy job runs.

Question 4 of 4

The agent says a target speed is impossible. What is the best response?

An honest "impossible, here are the numbers" is a win: it means the agent measured. You decide which requirement to drop, as in the vignette above.
