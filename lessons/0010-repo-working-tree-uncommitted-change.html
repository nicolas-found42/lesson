Repository, working tree, uncommitted change

Your project sits in two places at once: the files you can open, and the history git keeps. Two commands show you where those two disagree. Reading them is how you know what your agent actually changed.

Why this matters for shipping your app

An agent edits files. It does not automatically save those edits into your project's history. So after a long run, two different questions have two different answers: "what is on my disk right now?" and "what is recorded as a save point?" Beginners answer the first and assume it is the second. That assumption is how a working app and a broken one get mixed into one commit, and how a change you wanted to keep disappears when you ask for a clean slate.

This lesson gives you the two commands that answer both questions, and teaches you to read their output before you decide anything.

Two places, one folder

A repository (usually shortened to repo) is your project folder together with a hidden folder named .git, where git stores every commit you have made. The working tree is everything you see when you open the project folder: the files as they are on disk at this moment.

Git's own glossary defines the working tree as The tree of actual checked out files.[3] The same entry adds that it normally holds the last commit's contents plus any local changes that you have made but not yet committed.[3]

That gap is the whole subject of this lesson. A commit records a copy of the working tree at one moment. Editing a file afterwards does not change the commit. The file on disk moves forward; the history stays where it was.

Uncommitted change: the plain definition

An uncommitted change is any difference between your working tree and your most recent commit. There are three shapes you will meet constantly:

  • Modified. A file that is already in the history has been edited since the last commit.
  • Untracked. A file exists on disk that has never been committed. Git does not know about it yet.
  • Deleted. A file that was in the last commit is no longer on disk.

A fourth word, staged, names changes you have picked for the next commit. It belongs to lesson 3.4, but you will see the heading in the output below, so know that it exists and ignore it for now.

Command one: git status

Pro Git says it directly: The main tool you use to determine which files are in which state is the git status command.[1] The command lists file names, grouped by what kind of uncommitted change each one is. Git's reference page describes it as showing paths in the working tree that are not tracked by Git, alongside paths that differ from the last commit.[2]

Here is real output from a small project. One committed file was edited by hand, and one new file was added:

$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   index.html

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	ideas.txt

no changes added to commit (use "git add" and/or "git commit -a")

Read it in three passes. First, the branch line: which line of work you are on. Second, Changes not staged for commit: files that exist in history and now differ. Third, Untracked files: files that have never been committed. Everything after a file name that starts with use is advice, not a report. You can skip it.

When there is nothing to report, the output is one short sentence:

$ git status
On branch main
nothing to commit, working tree clean

Pro Git explains it: This means you have a clean working directory; in other words, none of your tracked files are modified.[1] Note the careful wording. Clean means the files git knows about match the last commit, and no untracked files are present either. It does not mean your app works, and it does not mean the last commit is good.

For a shorter list, add --short. Two columns of letters appear before each path:

$ git status --short
 M index.html
 M style.css
?? ideas.txt

The left column describes what is picked for the next commit, the right column describes the working tree. An empty left column and M on the right means "edited, not yet picked". ?? means untracked.[2] This form is handy when the agent shows you a status summary, because it fits on one screen.

Command two: git diff

Status gives you names. Diff gives you lines. Pro Git describes the pair this way: status answers "very generally by listing the file names", while diff shows you the exact lines added and removed — the patch, as it were.[1]

With no arguments, diff compares the working tree to what is picked for the next commit, which usually means your last commit:[4]

$ git diff
diff --git a/index.html b/index.html
index 00b1dc1..9c5cfd9 100644
--- a/index.html
+++ b/index.html
@@ -1,4 +1,5 @@
 <!doctype html>
 <html><head><title>My app</title></head>
-<body><h1>Hello</h1>
+<body><h1>Hello, friends</h1>
+<p>Coming soon.</p>
 </body></html>

You only need four things from this. Lines beginning with - were removed. Lines beginning with + were added. Lines with a leading space are there for context and did not change. The @@ line is a position marker inside the file; you can ignore it.

For a summary instead of every line, add --stat:

$ git diff --stat
 index.html | 3 ++-
 style.css  | 1 +
 2 files changed, 3 insertions(+), 1 deletion(-)

This is the form to ask for when a change touched many files and you want to see the shape before the detail.

The trap that catches everyone

git diff says nothing about untracked files. In the example above, ideas.txt is on disk and git diff does not mention it. A new file that has never been committed is invisible to diff until it is added. If you check only the diff, you will miss every new file the agent created. Check status first, then diff.

What your agent does to these two places

Every agent in this course edits the working tree, not the history. omp's documentation states it plainly: File changes are applied to your working tree as omp works. It adds: They are not committed unless you ask for a commit.[5] Claude Code's documentation lists what it can see when it starts in a folder, and one item is Your git state. Current branch, uncommitted changes, and recent commit history.[6] Codex's security guidance recommends you keep git status clean before delegating.[7]

Two consequences follow. First, an uncommitted change is normal and expected in the middle of a task; it is not an error. Second, an uncommitted change is fragile: it can be overwritten, undone, or swept into an unrelated commit, and no history entry will help you recover it. Lesson 3.13 covers checkpointing for that reason.

A real pattern, anonymized

A user finished a long session on a small dashboard and typed "commit all". Earlier that afternoon they had hand-edited two files while trying an unrelated idea, and left a scratch note in the folder. They had forgotten both. The agent did exactly what was asked and produced one commit containing about thirty-five files: the dashboard work, the abandoned idea, and the scratch note. Nothing was lost. But the history now claims that one piece of work happened, when three did, and unwinding the abandoned part later needed more care than it should have.

The agent was not careless. "Commit all" means all. The information that could have prevented it was already on the user's screen: two lines of git status. Reading them takes ten seconds and belongs to you, not the agent.

Recall before you read on

Without scrolling up: what is the difference between the working tree and the repository? Which of the two does the agent edit? And which command shows you file names but not lines?

The repository is the project folder plus .git, where commits live. The working tree is the files as they sit on disk now. Agents edit the working tree, so their work is uncommitted until someone commits it. git status lists file names by state; git diff shows the added and removed lines.

Try it in your own project

After the edit, status shows a modified: line for the file the agent touched, and diff shows the old heading with - and the new one with +. The short form shows something like  M index.html, with a blank left column. Your wording and colours may differ slightly by git version and settings; the groups and the +/- markers will not. If your project is still clean after the edit, the agent may have edited a file in a different folder. Ask which path it changed.

Check yourself

Question 1 of 3

You edit a committed page by hand. Status lists it as modified. What is now true?

Editing touches the working tree only. The commit is a fixed snapshot; a modified file is a difference from it, not a change inside it.

Question 2 of 3

An agent creates a brand-new file. git diff shows nothing. Why?

Diff compares tracked content. A file that has never been committed has no earlier version to compare against, so git status lists it instead.

Question 3 of 3

Before you say "commit all", what is the useful check?

"Commit all" means all. Status shows which files are uncommitted, including forgotten scratch notes and someone else's work in progress. Naming them first is the cheap guard.
