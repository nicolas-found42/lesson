Branch: a parallel line of work

A branch lets you try something unfinished without putting it in the version of your app you would hand to a friend. It also costs one line of typing, not a second copy of your folder.

About 15 minutesBuilds on: 3.1 Why save points existWin: you can start a change on its own branch and get back to main safely

Why this matters for shipping your app

In lesson 3.1 a commit became a save point: a snapshot you can return to. Snapshots solve "go back". They do not solve "work on something else for a while without disturbing what already works".

That second problem shows up the moment your app is public. The version the world sees is built from one line of commits, and every half-finished experiment you commit on that line rides along with it. A branch is the cheap way to keep the experiment somewhere else until you are ready. The pull request in lesson 3.7 is built on top of one, and so is every "let me try a redesign" you will ever ask an agent to attempt.

Your history is a line of commits

Each commit records the snapshot before it, so a project is a chain with the oldest work at the bottom. Pro Git describes the data as a series of snapshots of a miniature filesystem.[1] Your history has been one chain so far: commit, then commit, then commit.

A branch is how git grows a second chain from the same history. The name of a branch is not a folder and not a copy of your files. It is a label on one commit, and git moves that label forward each time you commit while you are standing on it. Pro Git states it in one sentence: A branch in Git is simply a lightweight movable pointer to one of these commits.[2]

Creating a branch creates a label

That single sentence explains the surprise that follows. Creating a branch does not duplicate anything on disk. Pro Git says the command creates a new pointer to the same commit you’re currently on, and warns that The git branch command only created a new branch — it didn’t switch to that branch.[2]

Git's own reference for git switch separates the two moves. Switching updates your files: The working tree and the index are updated to match the branch. The -c option does both at once: it creates the new branch before switching to the branch.[3]

I ran this in a throwaway project with one page and one commit:

$ git branch
* main

$ git switch -c add-search
Switched to a new branch 'add-search'

$ git branch
* add-search
  main

The asterisk marks where you are standing. Git's documentation for git branch says the current branch will be highlighted in green and marked with an asterisk, so you can always read your position rather than remember it.[4] Nothing was copied: the same one file, the same one commit, a second label.

Recall before you read on

Without scrolling up: when you create a branch, what is added to the project, and where do your files live?

A branch adds a label pointing at a commit. Your files stay in the same project folder. A branch is not a second folder and not a copy of the work.

Switching moves the files

This is the part that catches beginners, including beginners directing an agent. Because there is one folder, switching branches changes what is inside it. Pro Git puts the consequence plainly: It moved the HEAD pointer back to point to the master branch, and it reverted the files in your working directory back to the snapshot that master points to.[2]

Continuing the same project, I committed a search box on add-search, then switched back:

$ git switch main
Switched to branch 'main'

$ cat index.html
<!doctype html>
<h1>My Reading List</h1>
<ul>
  <li>One book</li>
  <li>Another book</li>
</ul>

The search box is gone from the file, and it is not lost. It lives in the commit that add-search points at. Switch back and it returns. Think of the folder as a desk that git rearranges when you tell it which line of work you want in front of you.

One habit before switching

Commit or stash your edits first. Git's reference says a switch is aborted if the operation leads to loss of local changes, so git protects you, but the refusal arrives as an error message that is easier to avoid than to read.[3] Lesson 3.2 shows how to see uncommitted work with status.

main versus a feature branch

Most projects keep one line that is meant to stay usable. On GitHub that line is called the default branch, and GitHub's docs say it is the branch that GitHub displays when anyone visits your repository and the base branch for new pull requests and code commits.[5] In a new repository GitHub names the default branch main.[5]

A second line, started from that one, is where an unfinished idea goes. GitHub: Branches let you develop features, fix bugs, or safely experiment with new ideas in a contained area of your repository. And the common name for it: A branch you create to build a feature is commonly called a feature branch or topic branch.[5]

Name branches for the change, not for yourself: add-search says more than test. Nothing enforces the name, and the person who reads it later is you.

A real pattern, anonymized

A user asked an agent to put a gallery online for friends. Before touching anything, the agent made a branch for the publishing work, did the editing and checking there, and opened a pull request instead of writing straight to main. Later, the same user asked for a tidy-up: the agent renamed the default branch, then checked each leftover branch against the server before deleting it, because a second reviewer had claimed one branch still existed. The server showed that all of them were already merged. The branch had done its job twice: it kept the experiment away from main, and it gave everyone a place to look before the change became the shipped version.

Directing an agent on a branch

An agent will happily commit to whatever branch it is standing on, and it may create one without narrating it. Three habits keep you oriented without learning much git.

  1. Say the branch in the prompt. "Do this on a new branch called add-search" removes the guess.
  2. Ask where you are. "Which branch am I on, and is anything uncommitted?" is one cheap command and one honest answer.
  3. Ask for the switch, not a summary. After a change, ask it to show git branch and the file on main. The listing is evidence; "I created a branch" is a claim.
A branch is not a backup

Branches live in the same repository on the same disk. If the folder is lost, every branch goes with it. Copies leave your machine only when you push, which is lesson 3.6. Two branches are two versions of your work, not two safes.

Do it in your own project 
First, show me which branch I am on and whether anything is uncommitted. Do not change any file yet.

Then create a branch called add-search and switch to it. Do not commit on main.

On that branch, add a search box above the list on my main page (index.html unless I tell you otherwise) and commit it with a one-line message.

Then switch back to main and show me `git branch` and the top of that same page, so I can see the search box is not there.

Do not merge, do not push, and stop after showing me the file on main.

A git branch listing with the asterisk moving from main to add-search and back; one new commit visible only while you are on the branch; and index.html on main without the search box. If the file still shows the search box after the switch, you are not on main, whatever the summary said.

Branch switching and your agent's approvals

Switching branches rewrites many files at once, so it is a moment to read the prompt rather than approve from memory. The three tools ship with different defaults; lesson 0.6 owns the settings.

Recent versions start permissive: With Claude Code v2.1.283 or later, auto mode is the built-in starting permission mode for interactive terminal and VS Code sessions.[6] While you are learning, switch to a mode that asks before commands.

Codex separates the sandbox from approvals, and its guidance for newcomers is to keep both tight: If you’re new to coding agents, start with the default permissions.[7] Its permission page says the CLI opens the same settings with /permissions.[8]

omp's docs state the opposite default: The built-in default is yolo. They recommend tools.approvalMode: write for interactive use.[9] With that default, expect a branch switch to run without asking.

Check yourself

Question 1 of 4

What does creating a branch actually create?

A branch is a movable pointer to a commit. No files are copied and nothing leaves your machine; push is what copies commits to a server.

Question 2 of 4

You switch from a feature branch back to main. What happens to your files?

Switching branches updates the working tree to the target branch's snapshot. Work committed on the other branch is still there, one switch away.

Question 3 of 4

Why keep unfinished work on a feature branch instead of main?

The default branch is what visitors see and what new work starts from. A feature branch keeps a half-built idea out of that line until you propose it as a pull request.

Question 4 of 4

Your agent says it created a branch. What should you check?

The branch listing shows the labels that exist and marks where you stand. A sentence in the chat is a claim; the listing is evidence.
