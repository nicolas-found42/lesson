Your first prompt, and a page on your screen

One short message, one small page, one address you can open. This is the moment the agent stops being an idea and starts being a thing you can look at.

About 15 minutes Builds on: 0.5 Install and sign in, 0.6 Approvals and permissions Win: you can ask for a page, open it yourself, and say what the address means

Why this is the moment

Your mission is a public app that other people can open. Before anything can be published, a page has to exist and you have to be able to see it. Today you make that happen once, slowly, and notice every step. Later lessons repeat the same move at larger sizes.

You already know the agent reads files, changes them and runs commands, and that it asks your permission before it acts. This lesson spends that knowledge on a single, visible outcome.

Ask for an outcome you can check

A first prompt works when it names three things: what should exist, where it should live, and how you will judge it. That is not a magic formula. It is the smallest amount of information that lets the agent stop at the right place instead of guessing.

Here is the prompt this lesson uses. It asks for one page, in the folder you are standing in, that you will look at yourself.

Build a single web page in this folder. It should show a big heading that says "Hello from my first page" and one sentence under it saying today's date. Keep it to one HTML file with no frameworks and no build step.

Then start it on a local server and open it in my browser so I can see it. Tell me the exact address you opened.

Two sentences carry the weight. "One HTML file with no frameworks" keeps the result small enough to inspect. "Start it and open it" asks for a result you can see, not a description of a result.

That last habit is worth naming, because it does not come from a menu. In real sessions, people fall into a two-word ritual after every change: start and open. It means the agent should run the thing and put it in front of you, rather than telling you it would work. A short, boring phrase like that is easy to reuse for the rest of the course.

What happens after you press Enter

From the outside it looks like a long pause. Inside, the loop you met in lesson 0.1 runs several times.

youBuild a single web page in this folder … start it and open it.
toollist the folder — is anything already here?
toolwrite index.html (asks your approval first)
toolrun a local server on port 8000
toolopen http://localhost:8000 in your browser
agentServing at http://localhost:8000 — it is open in your browser.
The middle four lines are tool calls. You only wrote the first line and read the last.

Your agent may choose a different port, or open the page a different way. What matters is that the last line contains an address you can type, and a window on your screen that you can look at.

Keep the session open

A page served this way exists only while the server process is running. If you close the terminal, or the agent stops the process, the address stops answering. That is normal, not breakage. Ask the agent to start it again.

What "localhost" and "port" mean

localhost is the name a computer uses for itself. A page at a localhost address is being handed to your browser by a small program running on your own machine, out of a folder on your own disk. Nobody else can reach that address. The numeric form 127.0.0.1 means the same thing.[1]

A port is a numbered doorway on a computer, so that several services can listen at the same address without colliding. Mozilla's glossary puts it as: a port is a communication endpoint. Ports are designated by numbers.[2] When you read http://localhost:8000, the part after the colon is the doorway. Change the number and you knock on a different door.

The plain-language definition of localhost above is mine, not a quotation. The linked Mozilla page documents the port part and the localhost address used to reach a local server.

Mozilla's beginner guide shows the same shape with a one-line Python server: it runs the folder you are standing in, and By default, this will run the contents of the directory on a local web server, on port 8000.[3] You then open localhost:8000 and click the page. If that port is busy, the guide's advice is to pick another number and use it in the address.[3]

That is why the number in the agent's message may not be 8000, or 3000, or whatever you saw in a tutorial. The message is the truth about this run. Read the address it printed; do not retype one from memory.

Recall before you read on

In your own words: if a page is at http://localhost:5173, who is serving it, and who can open it besides you?

A small server program on your own computer is serving files from a folder on your disk, and it is listening on port 5173. Only you can open it, because localhost means "this machine". To let other people in, the files have to be published somewhere public, which is a later unit.

Two ways a page can reach your screen

There is an older, simpler way to see an HTML file, and it is worth knowing so you can tell the two apart when something behaves oddly.

Double-click the file

The browser opens the file directly from your disk. The address starts with file://. One page with text on it works fine. Anthropic's terminal guide for beginners uses exactly this: once the files exist, double-click the HTML file to open it in your browser.[4]

The limit appears as soon as the page loads other files, or a script asks the network for something. Browsers treat those requests as crossing a boundary and may refuse them.[3]

Serve it, then open the address

A local server reads the same folder and answers at http://localhost:PORT. The page behaves the way it will behave on the real web: links, images, styles and scripts load through the same kind of request.

This is why "start it and open it" is the habit worth keeping. It matches the thing you will eventually publish, instead of a special case that only works on your desktop.

Do it: one page, in front of you

Use an empty folder, not an existing project. Lesson 0.3 covers making one and moving into it; lesson 0.4 covers the commands. Keep approvals on, as lesson 0.6 argued.

Your turn — about 5 minutes

A browser window shows your heading and a date. The address bar reads something like http://localhost:8000 with a number that may not be 8000. After the second request, the heading changes and the agent prints the address again. If the port changed, the old address may no longer work — use the new one.

Where the tools differ

All three agents can create the file. They differ in who opens the browser and what they can see once it is open.

In the terminal you can ask it to run the server and open the address; in the desktop app a preview pane does the opening, and By default, the preview opens http://localhost:<port>.[1] After a change you can run /verify, which the docs describe as having Claude build and run the app and look at the result.[5]

The CLI can run the server, but it cannot show you the page: Browser isn't available in Codex CLI or the Codex IDE extension.[6] Your browser, opened by you or by the server's own open flag, is the window. For a shared preview inside the chat, the same page says to use the ChatGPT desktop app.

omp can drive a browser of its own. Its docs call it the right choice for rendered pages, local development servers, screenshots, and it runs headless by default, so you may not see a window until you ask for one.[7] Ask in plain words: "open http://localhost:8000 and show me a screenshot".

When no page appears

Most first attempts work; the failures are boring and easy to name. Check these before you ask the agent to rewrite anything.

  • The address does not load. The server probably stopped, or it is on a different port than the one you typed. Ask: "Is the server still running, and what exact address is it on?"
  • The page looks empty or stale. Reload the tab. Dev servers normally read the file from disk when the browser asks, so an edit made while the server runs usually shows up on reload; if it does not, ask the agent whether it restarted the server.
  • The browser opened one address and the agent reported another. Trust the one that renders the page, and ask the agent to reconcile them.
  • Nothing at all happened. The agent may be waiting on an approval you did not notice. Look at the last lines of its output before typing anything.

When you are done looking, stop the server rather than leaving it running for days. Pressing Ctrl+C in the terminal that runs it ends the process; the address then stops answering, which is the expected result.

Check yourself

Question 1 of 3

The agent says it opened http://localhost:5173. What are you looking at?

localhost means your own computer, and 5173 is the port its server is listening on. Nobody else can reach that address.

Question 2 of 3

The browser shows "can't connect" at the address the agent gave you. What is the most likely cause?

A local page exists only while its server runs. Ask whether the server is still up and which port it is on before changing any code.

Question 3 of 3

In plain words, what is a port?

A port is a numbered endpoint that a program listens on, which is why two servers on one machine need two numbers. It is not storage and not security.
