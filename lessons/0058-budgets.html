Budgets: time, attempts, dollars

A stop condition tells the agent what success looks like. A budget tells it how much effort you authorize before it must return control to you.

About 15 minutesBuilds on: 4.3 Stop conditionsWin: you can set limits on a run and define what happens when they are reached

Why this matters for shipping your app

Your mission is a public app, not a perfect app. In lesson 4.3 you learned to end a run with a condition like stop when the page is deployed and I can open the link. That answers what does finished look like. It does not answer what happens if the agent never gets there. Agents are patient; they will keep trying, and every try costs something you own: your time, your attempts at a fix, and your money if the run uses a paid API. Before you press Enter on any big request, you should be able to say the three numbers.

Three budgets, three currencies

A budget is a limit you set before work starts. Make it measurable, and agree how you will track it. There are three useful kinds:

  • Time: how long the run may take. Give up after 20 minutes of work and report.
  • Attempts: how many tries at the same problem. Try at most three fixes; if it still fails, stop and tell me what you learned.
  • Dollars: how much paid API spend the run may cause. Spend no more than two dollars on external calls.

Each budget needs a handoff rule: what the agent should do when it reaches the limit. Ask it to stop starting new work, preserve the current files, and report what is unfinished. Do not require a new commit at the deadline: unfinished changes need review, and a blanket commit could include unrelated work. Define an attempt too: here it means one proposed fix followed by its check, whether or not that check passes.

Why until no issues remain never ends

The problem is not that tests can never pass. A fixed list of checks can pass and end a run. The problem is leaving issues undefined: does it include every possible bug, every design preference, or every suggestion a reviewer makes? Each fix can expose another problem. If another model judges the output, its findings can vary too. Without a fixed set of cases or a budget, the agent may keep looking instead of returning control.

A real pattern, anonymized

A user asked for a feature, then added an instruction to keep testing and repairing everything discovered. The implementation took around ten minutes, but the session stretched across roughly half a day and hundreds of checks and repairs. Some complaints came from the model judging the output, not the app. Paid-service credits ran out along the way. When the user eventually interrupted, the changes were still in a draft pull request rather than shipped.

A budget would not have made the feature pass. It would have limited how long the agent could keep trying before asking you to decide. That distinction matters: reaching the budget means paused with work remaining, not done. Success can end the run early; otherwise the first limit reached ends the authorized work.

Anthropic advises: Give it a cap on turns or spend, and have a person approve the result at the end.[1] Treat a number in a prompt as an instruction, not an automatic enforcement mechanism.

Recall before you read on

Without scrolling up: name the three budgets, and say why until no issues remain cannot end a run on its own.

The three budgets are time (how long), attempts (how many tries), and dollars (how much paid spend). An undefined search for every possible issue has no clear endpoint. State the cases to check, and return control when success or the first budget limit is reached.

An instruction is not a hard cap

A hard cap is enforced by software, rather than relying on the agent to remember a sentence. Even software caps have scope: an agent's estimate may not include another paid service it calls. Keep approval prompts on and check which account and services a dollar limit covers.

Claude Code documents --max-turns and --max-budget-usd for print mode: runs started with claude -p rather than an interactive session. The dollar flag uses an estimate that can differ from your bill, and spend can pass the cap.[2] These are not a universal spending switch for every paid service. Anthropic also documents monthly API spend limits at the organization level; those are a different scope from one task.[3]

Codex's guide recommends stating what must be true before a task is complete.[4] Add the budget and handoff alongside that success condition. OpenAI's API documentation distinguishes a spend alert, which lets traffic continue, from a hard spend limit, which rejects affected requests.[5] Those are API organization/project controls, not a claim that your Codex subscription has a per-task dollar switch. No per-run CLI cap is assumed in this exercise.

omp documents count- or duration-bounded repetition with /loop: A positive integer limits iterations. It also warns: Plain prose is an unbounded inline prompt.[6] An iteration is one repetition of the task, not one bug fix or a dollar amount. You do not need loop mode for this exercise; use an ordinary prompt. This is a single-vendor source, from omp's own authors.

Two other anonymized sessions show why the number alone is not enough. One user agreed to a small dollar ceiling before paid experiments began; the available record did not establish whether it was enforced. Another user set a one-dollar limit, and the agent later reported spending about half of it. That report is useful evidence, but it does not prove the limit was monitored throughout. Ask which meter is used, what it covers, and whether the amount is measured, estimated, or unavailable. If spend cannot be checked, do not authorize paid calls for a strict-budget exercise.

Do it in your own project

Do it in your own project 
Fix this small issue: NAME_THE_ISSUE.
Success check: DESCRIBE_THE_VISIBLE_RESULT.

Stop when the check passes, or when the first limit is reached: 3 fix-and-check attempts or 15 minutes elapsed. Do not use paid external services. Do not change my approval settings.

Before starting another attempt, check the limits. At the limit, start no new work. Preserve the current files; do not commit, publish, or widen the task. Report what changed, which checks passed or failed, attempts used, and what remains. Do not call unfinished work done.

You should receive either evidence that the named check passed, or a clearly unfinished handoff when a limit was reached. Compare the attempt count with what you watched. If the first attempt succeeds, stopping early is correct; there is no need to use the whole allowance.

The trap to avoid

Do not automatically answer a stalled run by raising its budget. Read the handoff first. If you choose to continue, authorize a new bounded attempt with a reason: a new clue, a narrower task, or a different check. The agent must not grant itself more time or money.

Check yourself

Question 1 of 3

You ask for repairs to continue until every possible issue is gone. Why is that risky?

Without a fixed set of cases, findings can keep widening the task. Passing agreed checks is meaningful; proving the absence of every possible issue is not a useful run boundary.

Question 2 of 3

Which sentence gives the agent a budget instead of just a goal?

Only the second sentence sets a number (three attempts) and a handoff (then stop). The others are goals or stop conditions with no limit on effort.

Question 3 of 3

The third allowed attempt fails. Your prompt says to stop and report at three. What should happen?

The attempt allowance is exhausted. Return control with an honest handoff. The user, not the agent, decides whether new evidence warrants another bounded attempt.

The habit

Every big request gets three numbers — time, attempts, dollars — and one handoff rule: stop, preserve the work, report. A success condition defines the desired result; a budget limits authorized effort if that result is not reached. Use both.
