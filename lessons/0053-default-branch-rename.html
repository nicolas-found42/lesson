Renaming the default branch and retiring branches

The name of your main line is a setting, not a law. Changing it in one place leaves three copies of that name out of step, and deleting a branch is safe only after you have checked what would be lost.

Why this matters for shipping your app

To ship your app reliably, you need to know which branch the publishing setup uses. A branch name is not proof that its contents are live. Renaming master to main is housekeeping, not a deployment. The other half of housekeeping is retiring finished branches without losing unfinished work.

"master" is a habit, not a rule

Both names are ordinary names. Pro Git is explicit: “master” does not have any special meaning in Git, and it explains where the habit came from: “master” is the default name for a starting branch when you run git init.[1] A repository made in 2015 is not broken; it carries the name that tool used then.

GitHub's branch reference says: By default, GitHub names the default branch main in any new repository.[2] An older repository named master does not need a rename to work. Rename when it helps your project follow one naming convention, not because the old name means the app is broken.

One branch, three copies of its name

The name exists in three places, and a rename touches them one at a time:

  1. Your local branch. A label on a commit, in your project folder (lesson 3.5).
  2. The branch on the server. What GitHub shows to anyone who opens the repository.
  3. Everyone else's clone. Including a second copy on your own laptop, or a folder your agent opened earlier.

A clone is a local copy of a repository. Its upstream is the branch a local branch tracks, such as origin/main. Here origin means the remote named in git remote -v; confirm that it is your intended server before changing anything.

The server also records which branch is the default branch: the base branch for pull requests and code commits.[4] Renaming that branch needs administrator permissions.[5]

Choose one route

The recommended route is GitHub's Rename branch operation on the default branch, followed by updating each clone. A different route creates a new server branch, switches the default setting to it, then deletes the old branch after comparing their commits. Do not mix the routes or delete the old name before the new default exists.

Renaming without breaking your own copy

A local rename does not rename anything on the server. In this throwaway demonstration, the local master contained two commits not yet pushed. After renaming and pushing, the server held both names:

$ git branch -m master main
$ git branch -vv
* main 1111750 [origin/master: ahead 2] Merge feature
$ git push -u origin main
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
$ git ls-remote --heads origin
111175082ff0b0cbf5fa9dc3518467c777a0f39d  refs/heads/main
653613040078d07b265a4202d4201543c4aed963  refs/heads/master

The tracking link still named origin/master after the local rename. The push with -u changed it to origin/main. Notice that the two server names point to different commits here. Neither the name nor the existence of both branches proves they contain the same work.

For your project, prefer the host-side route: on GitHub open the branch dropdown, choose View all branches, open the menu beside master, and choose Rename branch. Enter main and review the warning. Then update each existing clone using GitHub's documented sequence, replacing the placeholders with master and main:[5]

git branch -m OLD-BRANCH-NAME NEW-BRANCH-NAME
git fetch origin
git branch -u origin/NEW-BRANCH-NAME NEW-BRANCH-NAME
git remote set-head origin -a

git branch -m renames the local branch; fetch retrieves the server's state; branch -u sets the tracking relationship; and remote set-head updates the local record of the remote's default. GitHub also suggests git remote prune origin to remove old tracking references.[5] If main already exists locally, stop and compare rather than overwriting it.

A rename is not a redirect for everything

GitHub redirects ordinary file URLs, but raw file URLs are not redirected. Its documentation also says GitHub Actions workflows do not follow renames.[5] Ask your agent to find settings and scripts that mention the old branch, and review them before declaring the migration complete.

Recall before you read on

Without scrolling up: where does the branch name live, and which of those places does git branch -m change?

Your local branch, the server branch, and every other clone each have their own name. git branch -m changes only the local branch. A GitHub-side rename requires each clone to update its local name and tracking relationship.

Retiring a branch: check, then delete

For a finished feature branch, check its commits against the branch you intend to keep. After fetching, git branch --merged origin/main lists local branches whose tips are contained in the server's main line. git branch -r --merged origin/main checks remote-tracking names.[6] Exclude main itself from your deletion candidates.

These selected outputs from separate stages of the local demonstration show the difference between merged and unmerged work:

$ git branch -d feature
Deleted branch feature (was c1ec207).
$ git branch -d unmerged
error: the branch 'unmerged' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D unmerged'

The lowercase -d checks whether the branch is merged into its upstream, or your current branch if it has no upstream.[6] That upstream might be the feature branch's own server copy, not main, so a successful deletion alone does not prove the work reached main. Keep the explicit comparison above. If Git refuses, stop; do not replace -d with the force option -D.

If the ancestry check disagrees with a pull request marked merged, preserve the branch and inspect the difference. See 3.8 Merge versus squash before deciding; a disagreement is not permission to force-delete.

Local deletion does not delete a server branch. The separate command git push origin --delete feature removes that server name.[1] In the throwaway demonstration it also accepted an unmerged branch, so do not treat remote deletion as a merge check. Require the candidate to appear in the refreshed remote merged listing and obtain approval for its exact name.

A remote-tracking branch, such as origin/feature, is your local record of a server branch, not a live view. After someone else deletes it, git fetch --prune origin removes obsolete tracking references.[7] Pruning does not delete server branches or your local feature branches.

A real pattern, anonymized

A user asked an agent to rename the default branch and tidy leftover branches. The user handled the default setting when the agent lacked permission. During cleanup, an AI report claimed a branch still existed, but that claim came from a stale local reference. The agent checked the server instead. A separate claim about unmerged work also proved wrong after comparison. Only after establishing that four branches were already merged did it delete them. The useful habit was not trusting either report without evidence.

Do it in your own project

Use a repository you own. Keep approval prompts on (lesson 0.6). The commands are ordinary Git commands, identical whichever of the three agents runs them. A repository already named main needs no rename.

Your turn 
Inspect only first. Show the project folder, git status, git branch -vv, and git remote -v. Confirm this is my intended repository and identify the server's default branch. Stop if there are uncommitted changes.

If the default is master, explain GitHub's Rename branch route. Wait for me to perform it, then propose the documented clone-update commands. Do not push a second main branch, overwrite an existing local main, or delete master as part of this route.

For cleanup, fetch and prune origin. Show git branch --merged origin/main and git branch -r --merged origin/main. Propose at most one feature branch, excluding main, the current branch, and branches in use elsewhere. Compare its local and server tips separately; do not infer one from the other.

Show the evidence and exact deletion commands, then wait for my approval. Use git branch -d locally. Treat any refusal or missing merge evidence as a stop condition, including possible squash merges. Get separate approval before git push origin --delete for the exact server name.

Do not force-delete, force-push, or merge anything. Finish by showing the local tracking names and the real server branch list.

What you should see: after a rename, GitHub and your local branch both say main, and the local tracking relationship says origin/main. For cleanup, you see the chosen name in the refreshed merged listing before approving its deletion. No deletion occurs for a branch missing that evidence. Local and server lists change only as separately approved.

Check yourself

Question 1 of 3

You rename the default branch on GitHub from master to main. What happens to the clone on your laptop?

A GitHub-side rename does not rename your local branch. Update the clone's local name and tracking relationship using GitHub's documented sequence; pushing a second branch is a different route.

Question 2 of 3

An unused local branch has no upstream. You are on main; git branch -d old-idea reports that it is not fully merged. What does that mean?

The lowercase -d deletes only a fully merged branch. The refusal is the safety check working; -D removes the check, so find out what the branch holds before reaching for it.

Question 3 of 3

A teammate deleted a branch on the server, but your listing still shows origin/old-topic. What is the honest reading?

Remote-tracking names are your last-known picture of the server. git fetch --prune removes those whose branch no longer exists; nothing is wrong with the clone, and the server is not hiding anything.

Ask your teacher

Not sure whether a branch is safe to delete? Ask: "Here is the output of git branch --merged and git log --oneline main..the-branch. Is any work on this branch missing from main?" Paste the real lines. A branch that is not merged is not rubbish; it is work you have not decided about yet.
