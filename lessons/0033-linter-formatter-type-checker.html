Linters, formatters and type checkers

A test runs your app and watches what happens. Three cheaper readers never run it at all: they read the code and complain. Knowing which one to ask for turns a vague "looks fine" into a pass or a fail.

Why this matters for shipping your app

An agent can write more code in ten minutes than you can read in an evening. You will not catch its mistakes by staring at files you did not write. What you can do is ask for checks that read the code for you, quickly, in the same way every time.

These checks also give the agent something to check itself against, which is the habit from lesson 2.2. Anthropic's guidance for Claude Code lists the three commands first among what a project's rules file should record: the exact test, typecheck, and lint commands[1]. This lesson explains what those words mean, because you cannot ask for a check you cannot name.

Three readers, three complaints

All three are static checks: they read the files, not the running app. They differ in what they look at and what they say.

CheckWhat it readsWhat it tells youFixes itself?
FormatterSpacing, quotes, line breaks"This file is not formatted"Yes, it rewrites the file
LinterSuspicious patterns and unused namesRule name, line, and a hintSometimes, for simple rules
Type checkerWhat kind of value each name holds"This value does not fit here"No; the fix is a decision

Each one ends by reporting a result, and the result is what you act on. When there is a problem these tools finish with a non-zero exit status, which is how your agent and your terminal know the check failed.

The formatter: one style, no arguments

A formatter chooses how code looks and applies that choice everywhere. Prettier, a common one, describes itself as an opinionated code formatter and says that It removes all original styling and ensures that all outputted code conforms to a consistent style.[2] Deno's built-in formatter works the same way: it auto-formats your code to a consistent style.[3]

Two consequences matter. Formatting is about appearance, not correctness: the same program, printed differently. And there is nothing to debate; if your project has a formatter, run it and accept the result.

Formatters also have a checking mode. With Deno, deno fmt --check will verify files are formatted without modifying them, and it exits with a non-zero status code if any files are unformatted.[3] That mode is what you want in an automated check, because it cannot quietly change your files while reporting success.

The linter: a second reader looking for trouble

A linter does not reformat anything. It scans for patterns that tend to go with bugs. Deno's documentation states the job plainly: the linter analyzes your code for potential errors, bugs, and stylistic issues.[4]

Notice the word potential. A linter is a set of lint rules written by people, and a rule can be wrong for your situation. An unused variable is usually a leftover; sometimes it is deliberate. That is why linters let a project switch rules on and off, and why a silenced rule should carry a written reason. Lesson 2.11 takes up what to do when a check is mistaken; for now, remember that "the linter is happy" is evidence about the rules, not a proof of quality.

The report names a rule, a line, and often a hint. Like the other two, it fails the run with a non-zero status: Deno's linter exits with a non-zero status code when it finds violations.[4]

Recall before you read on

Without scrolling up: what does a formatter change, and what does a linter report that a formatter never would? Write it in your own words.

A formatter changes only appearance: indentation, quotes, line breaks, all toward one consistent style. It never judges whether the code is right. A linter reports suspicious patterns and rule violations, such as an unused variable, with a rule name and a line number, and it leaves the text alone.

The type checker: catching a whole class of mistakes

A type is the kind of value something holds: a number, a piece of text, a list. A type checker follows values through your functions and asks whether each one fits where it lands.

Deno's checker type-checks your TypeScript (or JavaScript) code without running it, and it exits with a non-zero status code if there are type errors[5]. Here is a real run, in a scratch folder, on a small file where one call passes a number to a function that expects text:

$ deno check greet.ts
Check greet.ts
TS2345 [ERROR]: Argument of type 'number' is not assignable to parameter of type 'string'.
const message = greet(7);
                      ^
error: Type checking failed.

Nothing was executed. The tool followed the value 7 into greet, compared it with the declared kind of the parameter, and refused. That is why type errors are worth taking seriously: in a project without a type checker, the same mistake can survive until a visitor clicks the wrong button on the live site.

The same scratch file also shows the split between the checks. Its linter reported one problem, an unused variable, at line 2. Its formatter reported that the file needed indentation and semicolons, then fixed exactly that. And the type error stayed, because no formatter or linter rule can decide what you meant to pass. Three tools, three different sentences about one small file.

A real pattern: the strictness loop

A real pattern, anonymized

A user asked an agent to apply two patches, get the project's tests passing, and then tighten the lint rules until nothing was left. The tests passed. The formatter passed. Then the agent went through the relaxed rules one at a time, counted how many complaints each one produced, fixed what it could, and kept a written reason only where a rule truly did not fit the code. The final report listed one remaining exception instead of the nineteen the project had started with.

The useful part was not the clean result. It was the method: one rule at a time, a count before and after, and a reason attached to every silence. Pushing it further, with a later request for maximum strictness, mostly produced more exceptions with reasons, which is what diminishing returns look like when a check is pushed past usefulness.

Copy that method when you talk to your agent: name the check, ask for the count, and ask which rules were switched off and why. A report that is clean because forty rules were disabled is a different fact from a clean report on the rules you chose.

What the three checks cannot tell you

None of these tools opened your app. They never loaded the page, clicked the button, or logged in. So a project can pass all three and still be broken in the way a visitor notices first.

What green checks mean

The code is consistently printed, no chosen rule objects, and every value fits the kinds you declared.

They say nothing about whether the page loads, the layout holds, or the form submits.

What you still have to do

Start the app, open it, and use it as a visitor would. That is the loop from 2.1 and the real-browser check in 2.7.

Tests and these checks narrow the search. They do not replace looking.

This is the same boundary as in lesson 2.3, one step earlier. A test executes code and asserts a result. A static check only reasons about text. Both produce evidence; neither produces a working app.

Read the exit status, not the adjectives

When you ask an agent to run checks, ask for the command and its output. Anthropic's page lists A linter among the checks an agent can run, and describes the requirement it should meet: Give Claude something it can run that comes back pass or fail.[1] The printed output is what tells you which it came back as.

The request that works

"Run the formatter check, the linter, and the type checker. Paste the exact command and its full output for each, and tell me the exit status. If anything is silenced with a rule exception, list it and say why."

Two details make that request strong. It asks for the command, so you can run the same thing yourself later. And it asks about exceptions, because the cheapest way to make a check pass is to switch it off.

Where the three commands live

A check only helps if you and the agent run the same one. Each agent reads a project rules file, and that file is where the three commands belong. The file name differs, which is the only part of this lesson that changes by tool.

CLAUDE.md in the project root. Anthropic describes these as files that give Claude persistent instructions for a project.[6] Put one line per check, each with its exact command.

AGENTS.md in the project root. OpenAI's page is direct: Codex reads AGENTS.md files before doing any work.[7]

AGENTS.md in the project root. The omp docs say to Put an AGENTS.md in your repository root. omp loads it automatically and applies it throughout the session..[8]

Lesson 1.12 covers writing that file well. For now, three lines are enough: the formatter check, the linter, and the type checker, each exactly as the project runs it.

Do it in your own project

You should see three commands, or an honest "this project has no linter or type checker yet". A check that reports nothing still prints something, and its exit status is zero; a failing check prints the rule or error and returns a non-zero status. If the agent reports "clean" with no command and no output, ask again: you have a claim, not evidence. If a check does not exist, that is a normal starting point, and lesson 2.6 shows how to put the ones you want into one command.

Check yourself

Question 1 of 3

Your page loads, but a name is passed where a number belongs. Which check is built to catch that before you open the browser?

Types describe the kind of value each name holds, so a mismatch between a call and a function's declared parameter is exactly what a type checker reports. Formatters change appearance; linters flag patterns; tests only catch what they execute.

Question 2 of 3

The formatter reports nothing, the linter is clean, and the page's main button still does nothing. What is the best explanation?

All three are static: they reason about source text without starting the app. A dead button is a behaviour problem, so it needs a test or a real click to show up.

Question 3 of 3

Your agent writes: "Lint is clean." What should you ask for next?

A clean report is a claim until you can see the command that produced it, what it printed, and what it returned. That is the evidence habit from lesson 2.2, applied to checks.
