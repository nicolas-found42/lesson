Unit 2 · Lesson 2.7 · First-ship path ★

Tests passed, but the screen was wrong

A passing test can be honest and still say nothing about what a person sees. Before you ship, someone has to open the page in a real browser and look at it.

About 15 minutesBuilds on: 2.1 Run it yourselfWin: you can tell a simulated check from a real one, and ask for the real one

Why this matters for shipping your app

You are going to send a link to people who cannot fix what they find. If the page renders wrongly on their screen, nothing in your project's test output will save you. The tests were green; the visitor leaves. This lesson is about a gap that catches careful beginners: a check can be performed in a place where the failure you care about cannot happen, so it always passes.

That place has a name. A simulated environment imitates enough of a browser for a program to read and change the page, but it does not put pixels on a screen. A real browser does. Keep those two apart and most "but it passed" surprises stop happening.

The test that passed while the screen was broken

A real pattern, anonymized

A user was building a small animated app and asked the agent to make its text easier to read. The agent changed the code, ran the app's automated checks, and reported success. The checks were honest: the text was correct in the page's structure, and the drawing code ran without an error. Then the user looked at the running app and sent a screenshot. Black rectangles sat on top of words in the middle of the picture. The checks could not have seen it, because they never draw anything; the rectangles appeared only when the real window painted its canvas and the text was drawn over the wrong layer.

The agent fixed it in one turn once it could reproduce the problem on a real display. Cost of the detour: one round trip that a single look would have avoided.

What a simulated check really does

Most of your project's automated checks fall into this category. A test that loads your page into a JavaScript-only imitation of a browser can read elements, click buttons, and compare text. The most common library for this work describes its own limits plainly: jsdom does not have the capability to render visual content, and even with its "pretend to be visual" option on, jsdom still does not do any layout or rendering.[1]

Layout is where things overlap, overflow, hide behind a fixed header, or shrink to nothing on a phone. None of that is an error in the code. All of it is visible to a person. So a check that never lays anything out cannot report it.

A browser can also run with no window at all. Chrome's documentation describes headless mode as a way to run the browser in an unattended environment, without any visible UI.[2] That is useful for automation, and it is still not the same as the browser a person uses: nothing is displayed, so nobody sees the result until a screenshot is taken and looked at.

Kind of checkWhat it can tell youWhat it cannot

No single row is enough on its own. The lower rows are not "better tests"; they are a different kind of evidence, and the last row is the one your visitor will experience.

Who opens the browser

The good news: you usually do not have to describe the bug in words first. All three agents can be pointed at a running page, and one of them runs it in a browser window you can watch.

With its Chrome integration, Claude Code connects to your own browser. The documentation says it is there to test web apps, debug with console logs, automate form filling, and extract data, and that Browser actions run in a visible Chrome window in real time.[3] It needs the browser extension and a signed-in session, so the first attempt may show an install prompt; approve it and read what it asks for. The same page notes that Claude pauses and asks you to handle a login page or CAPTCHA by hand.[3]

The built-in browser is part of the ChatGPT desktop app, not of the Codex command-line tool. OpenAI's page states: Browser isn't available in Codex CLI or the Codex IDE extension.[4] In the desktop app it can review a page you're building.[4] If you work in the terminal, the simple fallback is to open the page yourself and paste a screenshot into the prompt.

omp has a browser tool, and it is treated as an executable action: in the write approval mode it prompts for Executable actions such as bash, eval, browser control, and task.[5] Leave approvals on, read the prompt, and let it open the page. Because omp publishes only its own documentation, check anything surprising against what you see on screen.

Claude Code's own best-practices page makes the case for this step in one sentence. Its /verify command has Claude build and run the app and look at the result, and that catches the kind of problem that tests and typechecks miss.[6]

A run where the gap shows up

The exchange below is a typical pattern, not a transcript of one particular session. It shows the same code surviving two different questions.

youMake the heading larger and centre the price. Tell me when it is done.
agentEdited styles.css. Ran the checks: 12 passing. Done.
youOpen it in my browser and look at it before you say that.
toolstarted the local server on port 3000; opened the page in Chrome
agentThe price is under the heading, but the heading now wraps onto two lines at this width and pushes the button off screen. Fixing.
note">Same code. Different question. The checks asked "is the markup right?" The browser asked "what does a person see?"

Notice what changed in the second message. It did not add a new requirement. It named the place where the check had to happen. That is the whole move, and it works as a standing instruction.

Make it part of the definition of done

For anything with a visible surface, "tests pass" is an incomplete finish line. Write the real check into the task before the work starts, so the agent cannot stop at the simulated one:

When you think the change is finished:
1. Start the app and open the page in a real browser window, not a simulated one.
2. Look at it at a wide window and at a narrow phone-sized window.
3. Tell me what you actually saw, including anything that overlaps, overflows, or is cut off.
4. If something looks wrong, fix it and look again. Stop when both widths look clean, or when you have tried three times.
Do not say "done" on the strength of tests alone.
Simulated only

"All 12 tests pass. The heading element has the correct class and the price sits after it in the markup."

True, and silent about the one thing the user will notice.

Real browser

"Opened at 1280px and 390px wide. At 390px the heading wraps and the button leaves the screen; I reduced the heading size and it now fits. Here is a screenshot of each width."

Describes a screen someone can check, and names the evidence.

Two details make this instruction reliable. First, name the widths, because "looks fine" usually means "looks fine at whatever size the window happened to be". Second, require a report of what was seen, not a verdict. A verdict invites the same optimism that produced the false "done"; a description is something you can compare with your own eyes.

Recall before you read on

Without scrolling up: name one thing a simulated page check can prove, and one thing only a real browser can show you.

A simulated check can prove things about the page's structure and logic: the right elements exist, the text matches, a click runs the handler. It cannot show layout or painting, because it does not render. Only a real browser shows what a person sees: overlap, overflow, cut-off text, wrong colours, and whether the page is usable at a given window size.

Do it now: catch the gap yourself

You should see the agent's description and your own view agree, or you should have found a real difference and had it fixed. Either result is a win: you now know which kind of check your project actually runs, and you can tell the difference next time.

Check yourself

Question 1 of 3

The agent reports that all page tests pass. What have you learned?

Tests of page logic check structure and behaviour. They say nothing about what a person sees, because no layout or painting happens, so they cannot show overlap, cut-off text, or a broken width.

Question 2 of 3

A screenshot from a headless browser shows your page. What is the next step?

A headless browser does render, but nobody has seen the result yet and it is one size only. Look at the image, then open the page yourself; tests still check things a screenshot cannot.

Question 3 of 3

Which instruction best closes the simulated-versus-real gap?

It names the place where the check must happen and asks for an observation instead of a verdict. Adding tests of the same kind cannot reveal a layout problem that only appears when something is drawn.

Ask your teacher

Not sure whether your project's checks render anything? Ask: "Which of my checks run in a simulated page, and which open a real browser?" A useful follow-up is "Show me the last real browser check you ran, and what you saw."
