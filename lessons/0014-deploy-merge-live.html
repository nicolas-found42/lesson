Merged is not live

Your pull request says Merged and the checks are green. The page your friend opens is still yesterday's. Three different states are all called "done", and only one of them is the address you will share.

Your friend opens a URL, not a repository

The end of your mission is a link that works on someone else's phone. A GitHub Pages project site has a fixed shape: https://<owner>.github.io/<repositoryname>/.[1] Nothing about your commits, your branch or your careful pull request is visible at that address. What is visible is whatever the host is serving at that moment, which is a separate thing you have to go and look at.

Beginners collapse several moments into the single word "done". They are separate events, and each one can succeed while the next has not happened yet.

StateWhat it meansWhat it provesWhat it does not prove
MergedYour change is now part of the main branch.The project's history contains your edit.That the host has built anything at all.
DeployedA deployment run finished and handed the host a package of files.A build was accepted for publishing.That the URL is already serving that package.
LiveThe public URL returns your new content.That a visitor, right now, receives it.Anything beyond what you actually looked at.

Merge puts your change on main. It publishes nothing.

Merge is a version-control action. GitHub's instructions describe it plainly: Merge all commits into the base branch by clicking Merge pull request.[2] After that click, main contains your work. That is all it says.

Publishing is a second, later event. GitHub's Pages documentation is explicit: Your GitHub Pages site will always be deployed with a GitHub Actions workflow run.[3] So a merge can land at 10:00 while the workflow that packages your files is still queued at 10:01, still running at 10:05, or failing quietly while the pull request stays green from yesterday. The pull request reports on the branch; the site reports on whatever was last published.

This is why "the PR is merged" is a terrible thing to tell a friend. It describes a change to a filing cabinet, not a page on the internet.

A green deployment is still only a claim

Deploy means handing the host a finished package and asking it to serve it. On Pages, that is usually the workflow from lesson 6.5: one job builds and uploads the files, another publishes them in a job tied to a deployment environment called github-pages.[4] The deploy step reports a result, and that result includes The URL of the deployed Pages site as an output.[5]

Useful — but read it for what it is. It is the deployment job saying where it put things, not a visitor's view. The same action's own default timeout is Time in milliseconds after which to timeout and cancel the deployment (default: 10 minutes).[5] Deployments take minutes, can be queued behind other runs, and can be re-run. A green tick means the package was accepted. It does not tell you what an address returns when a stranger types it.

Live means the URL serves your change

There is a third gap, and it is the one that catches almost everyone. GitHub's Pages quickstart warns that it can take up to 10 minutes for changes to your site to publish after you push the changes to GitHub.[6] So the boring explanation for "my change is missing" is usually time. Check again before you start changing files.

Two more causes are worth knowing, because they look identical from the outside.

Your browser reused an old copy. The HTTP cache stores a response associated with a request and reuses the stored response for subsequent requests.[7] That is normal and useful, and it means a plain reload can show you a page from before your deploy. A private window, or a reload that bypasses the cache, asks the host again.

The address is not the one you think. A project site lives under the repository name, so leaving out /my-app/ lands somewhere else entirely.[1] Pages looks for index.html as the entry file, and The name of the index.html file is case sensitive.[8] A 404 can be a typo, a file at the wrong level, or a capital letter. And a 404 only indicates that the resource is missing without indicating if this is temporary or permanent[9] — so one 404 right after a deploy is a hint, not a verdict.

The habit

Do not ask "did it work?" Ask "what does the exact URL return, right now, in a window that has never seen this site before?" That question has an answer you can see.

A pattern from real sessions

A real pattern, anonymized

A user asked an agent to put a small gallery online for friends who do not use code hosting, and to put the link where those friends would look. In about a quarter of an hour the agent had opened a pull request, watched the automated checks finish, and merged it. Then it kept going: it waited for the deployment run, opened the public address, searched the page for one item that only existed in the new version, and repeated that until the new version actually appeared. Only then did it write the link into the project's front page.

In a longer session with the same shape, every merge was followed by three separate looks: the checks, the Pages deployment, and the real address. One merge went green while the site still served the previous build for a couple of minutes. A report written at the green tick would have been wrong, and nobody would have noticed until a visitor did.

What a checkable report sounds like

Weak

"The pull request is merged and the build passed, so the site is updated."

Three states, one word. Nothing here tells you what an address returns.

Strong

"I fetched https://YOUR_USERNAME.github.io/my-app/. It returned 200 and shows "Version 2" in the heading. I loaded it in a private window after the deployment run finished."

An address, a status, and a line that only exists in the new version.

Check it yourself in about a minute

Do it now — on your own site, or on any URL

200, and your new text visible in the private window. A 404 means nothing is being served at that path — check the repository name and the file name's capitalisation. The old text means the deployment has not taken effect yet, or the host is answering from an older build; wait, then re-check. For comparison, here is the same check run against a throwaway page on a local machine, not GitHub Pages:

$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8766/
200
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8766/versoin-2/
404
$ curl -sI http://localhost:8766/ | head -n 1
HTTP/1.0 200 OK

The shape is the same for any web address: 200 for found, 404 for absent. The first URL was real, the second had a typo, and no amount of staring at the files would have told you which was which.

Your agent can check the address too — with one more approval

Fetching a URL is a tool call like any other, so it goes through the same permission rules you set in lesson 0.6. The three agents differ here, and the differences matter exactly when you are waiting on a deploy.

Claude Code has a web fetch tool, and the permissions table says approval is required for it — Yes, except a built-in set of preapproved documentation domains.[10] So expect a prompt naming the address before it can look at your site. Approve that one, and keep the rest of your prompts on.

Codex runs its commands in a sandbox, and By default, the agent runs with network access turned off.[11] A check of your public URL may therefore need an approval or a network setting. Let it ask; do not turn the sandbox off to save one click.

In omp's write approval mode, the things that prompt include Executable actions such as bash, eval, browser control, and task.[12] Its built-in default is yolo, which prompts for nothing by tier, so check which mode you are in before asking it to browse. Lesson 0.6 covers changing that safely.

If approvals are getting in the way of a simple check, open the URL yourself. Your browser needs no permission and shows you the same page.

Ask for proof, not a status word

This prompt works in any of the three agents. It turns "is it live?" into an answer you can check in one glance.

After you merge, do not tell me the site is live until you have fetched the public URL yourself.

Then reply with:
1. the exact URL you fetched;
2. the HTTP status you got;
3. one line of text from the page that only exists in the new version;
4. if the old version is still served, wait and check again up to three times, then tell me what is still missing and stop.

Do not make unrelated edits while waiting. Keep approval prompts on.

The fourth line matters as much as the first. Without a stopping rule, "check until it is live" becomes an open-ended loop that can run for an hour and drift into other work. Lesson 4.3 covers stop conditions; this is the deploy-shaped version of one.

Recall before you read on

Without scrolling up: name the three states a change passes through after you merge it, and say what single piece of evidence proves the third one. Write it in your own words.

Merged (the change is on main), deployed (a deployment run finished), live (the public URL serves the new content). The evidence for the third is that you loaded the exact address — ideally in a private window — and saw text that only exists in the new version, with a 200 status to match. A merged pull request and a green deployment run prove the first two, and nothing more.

Check yourself

Question 1 of 3

Your pull request says Merged and its checks are green. The public URL still shows the old page. What is the best description?

Merging changes main. Publishing is a workflow run, and the site is served separately; none of that follows from a green pull request.

Question 2 of 3

Which one of these is evidence that your friends can see the new version?

Only what the address returns counts. Checks, runs and commits describe the pipeline; the URL describes what a visitor gets.

Question 3 of 3

You open your public URL and see last week's page. What should you try first?

A cached copy or a deployment that has not finished are the common causes. Publishing can take minutes; a private window and a short wait separate both from a real fault.

Ask your teacher

Not sure what your address should be? Ask the agent that gave you this course. Try: "My repository is called my-app and my username is YOUR_USERNAME. What is the exact URL, and what should I see there when my change is live?" or "Here is what my URL shows. Is this the old version, a cache problem, or a wrong address?"
