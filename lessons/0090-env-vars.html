Environment variables: settings that stay out of your code

Your app will need values it must not carry inside its files — a key, a password, an address. Environment variables are the place those values live, and a .env file is how you keep them on your own machine without committing them.

About 15 minutesBuilds on: 8.1 Secrets: what they are and why not in codeWin: you can give your app a secret safely and explain the difference between .env and .env.example

Why this matters for shipping your app

Your mission is to take an idea to a public app. The moment your app talks to any outside service — a map, a payment provider, an email sender, even a login — it needs a credential. Lesson 8.1 covered why that credential must never sit inside your code. This lesson covers the practical half of that rule: where the value lives instead, and how you keep it out of git while still telling teammates what to set up.

What an environment variable is

Every program you run gets a small list of named values from the shell around it, called its environment. An environment variable is one entry in that list: a name, an equals sign, and a value, like MY_APP_KEY=abc123. The running program can read these values without them being written anywhere in its files. The Twelve-Factor App methodology — a widely used standard for building apps — puts the rule plainly: Store config in the environment and keep strict separation of config from code, because config varies substantially across deploys, code does not.[1] Agents themselves work this way: Claude Code's quickstart notes that if the ANTHROPIC_API_KEY environment variable is set and approved, login is skipped.[2]

You can see the idea in your own terminal. Typing printenv lists every variable your shell currently holds — on an ordinary machine, well over a hundred.

Scope matters here. A value loaded in one terminal is not visible in another one. So if your agent reports that a variable is unset, check which shell started it. omp's docs give a short rule for what belongs in the environment at all: use one when a value belongs to the machine or process rather than the project — a secret, a cloud key, a proxy address, or a setting for one machine only.[3]

A real pattern: keys from the shell, not from files

A real pattern, anonymized

A user told their agent to use the API keys already present in their shell environment rather than pasting them into any file. During live testing the agent discovered that one test had sent a made-up contact address to a real external service — the kind of value that must come from configuration. The fix was to read the value from an environment variable and skip that test cleanly when the variable was unset. No key ever appeared in a file, a log, or a commit.

The lesson of that pattern: the app asks the environment for the value at runtime. The value itself never becomes part of the project.

The .env file, and its companion .env.example

Typing export MY_KEY=... by hand every time you open a terminal is tedious and error-prone. The common convention is a file named .env in your project folder, holding one NAME=value per line. The agent tool itself loads it: omp's documentation lists $PWD/.env in the launch directory among the places it reads environment values from, and describes the .env syntax as lines of names and values with Blank lines and # comments are allowed.[3] (Single-vendor source: this is omp's own documentation.)

The syntax is plain text. A name may hold letters, digits, and underscores. It may not start with a digit. A comment line starts with #, and a blank line is fine. The word export is optional. So a working file can be short and easy to read:

# real values — never commit this file
MY_APP_KEY=PASTE_YOUR_KEY_HERE
MAP_TOKEN=PASTE_YOUR_KEY_HERE

But .env holds real secrets, so it must never be committed — lesson 3.3 .gitignore covers how to exclude it, and the next lesson covers what happens when that fails. Instead, you commit a second file, .env.example, with the same names and empty or placeholder values. It is a template: it tells anyone cloning your project which variables to create, without containing a single real value.

Two habits that save you

First, omp's docs are explicit: Keep credential-bearing .env files out of version control.[3] Second, environment changes are not picked up by a running session — omp says Restart omp after changing a .env file. Environment changes are not hot-reloaded.[3] After editing .env, start a fresh agent session (and restart your app) so the new values are read. omp also asks you to restrict their permissions, for example with chmod 600 ~/.omp/.env, so nobody else on the machine can read the file.[3] A value that reaches a log is as exposed as one in a commit. That is why the prompts below ask the agent to say whether a key is set, and never to print it.

Recall before you read on

Without scrolling up: which of the two files — .env or .env.example — do you commit to the repository, and what goes inside it? Write your answer in your own words.

You commit .env.example, containing the variable names with empty or placeholder values and no real secrets. .env holds the real values, is listed in .gitignore, and is never committed.

Set it up in your own project

This is a doing lesson, so do it in the project folder of your app — or in any throwaway folder if you are not mid-project. Keep your agent's approval prompts on; creating two small text files is exactly the kind of change you should see and approve.

You should see: git status lists .env.example as a new file to commit but never mentions .env; and the agent replies that MY_APP_KEY is set, without echoing the placeholder value. (A fresh agent session may be needed if you edited .env while one was already running.)

One prompt that does the whole setup

You do not need a special skill for this. One plain message works in any agent:

My app needs a secret called MY_APP_KEY. Create a .env file in the project
folder with MY_APP_KEY=PASTE_YOUR_KEY_HERE, create a .env.example with the
same key and an empty value, and add .env to .gitignore. From now on, read
MY_APP_KEY from the environment variable — never hardcode it in a file, and
never print its value back to me.

Check yourself

Question 1 of 3

What is an environment variable?

It is a name-and-value pair in the program's environment, readable at runtime and stored nowhere in the code. Files and commits are separate things.

Question 2 of 3

A teammate clones your project and needs the same settings. Which file do you commit, and what does it contain?

.env.example is the committed template: same variable names, empty or placeholder values, no real secrets. .env stays local and ignored.

Question 3 of 3

You edited .env, but the running agent still sees the old value. What is the best move?

Environment changes are not hot-reloaded: a fresh session re-reads the environment (omp's docs say to restart after changing a .env file). Committing would also leak the value.
