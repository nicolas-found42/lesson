Branch protection: making "PRs only" a rule

A convention lives in your head and in a rules file. A branch protection rule lives in GitHub, where a tired agent at midnight cannot talk its way past it.

About 15 minutesBuilds on: 3.7 The pull requestWin: you can turn "changes go through a pull request" into a setting that enforces itself

Why this matters for shipping your app

Your app is published from the default branch of your repository, usually main. Every commit that lands there can reach your live site. You have already learned the safe path: work on a branch, open a pull request, let the checks run, merge when it is ready. Lesson 3.7 covered that path.

The safe path has one weakness. It depends on somebody choosing it every time. That somebody includes an agent working at speed while you are making coffee. Branch protection moves the choice out of the moment and into the repository's settings. After this lesson you can set it up in a few clicks, and you will know exactly what it does and does not stop.

A habit is not a gate

GitHub draws the distinction itself. Its branch reference describes protected branches as a way for maintainers to enforce rules on important branches, and says such a branch can block force pushes or deletion, require status checks, require reviews, require code owner approval, or require signed commits before changes can merge.[1] Every one of those is a thing GitHub checks before it accepts the change. None of them is a suggestion.

This matters more with an agent in the loop than without one. An agent follows your project rules file because it read the file and decided to comply. That is ordinary, fallible behaviour. Protection is different: the server receives a push, compares it against a stored rule, and answers yes or no. The agent can be confused, over-eager, or working from a stale plan and the answer is still no.

The one-sentence version

Branch protection is how you write "pull requests only" somewhere other than your own memory.

What a rule actually does

GitHub's documentation lists the settings a rule can carry. Four of them cover almost everything a beginner needs.[2]

SettingWhat it stops
Require a pull request before mergingA commit pushed straight to the branch, bypassing review and checks
Require status checks to pass before mergingA merge while tests, a build or a linter is failing or still running
Do not allow bypassing the above settingsYou, or anyone with admin rights, quietly ignoring the rule
Allow force pushes / Allow deletions (off)Rewriting history or deleting the branch by accident

Two of those are on by default the moment you create a rule. GitHub states that by default, each branch protection rule disables force pushes to the matching branches and prevents the matching branches from being deleted.[2] Requiring a pull request is a checkbox you add. For a beginner's repository that checkbox is the whole point.

A rule applies to a branch name or a pattern, so one rule on main covers every future change to your app. The pattern does not need to match a branch that exists yet. GitHub notes that when you create a branch rule, the branch you specify doesn't have to exist yet in the repository.[3]

What it feels like when it fires

Protection is not silent. A direct push is rejected at the remote, and the message names the rule it broke. GitHub's own page shows the shape of that refusal:

remote: error: GH006: Protected branch update failed for refs/heads/main.

That line is useful, not mysterious. It means the commits are fine and the route was wrong. The fix is the workflow you already know: put the commits on a branch, push the branch, open a pull request.

A real pattern, anonymized

A user asked an agent to merge a finished redesign. The agent first read the repository's rules file, which said to wait for the automated checks and then confirm the deployed site. It found one of its own check jobs failing, fixed it, waited for a green run, and only then merged. An hour later a second change merged first, and the next pull request was reported as behind the main branch. The agent brought the branch up to date and ran the checks again rather than reaching for an administrator override. Two merges, two extra waits, no broken live page.

Notice what the setting did there. It did not make the agent careful; the agent was already trying to be careful. It removed the option of being careless at the moment when that costs most: right before a merge.

The administrator hole

Here is the part almost everyone misses on the first pass. A protection rule does not bind administrators unless you tell it to. GitHub's wording is precise: by default, the restrictions of a branch protection rule don't apply to people with admin permissions to the repository, and you can optionally apply the restrictions to administrators.[2]

On a repository you created, you are the administrator. So a rule without that checkbox protects you from your agent, and from a collaborator, but not from yourself. The checkbox is labelled Do not allow bypassing the above settings.[3] Tick it if you want the rule to mean what it says.

The same idea appears inside the tools. Claude Code's permission documentation lists Merging a pull request no human has approved among the actions its safety classifier blocks by default.[4] A repository setting and a tool guardrail are separate layers; neither replaces the other.

There is a cost, and you should accept it knowingly. With bypass disabled, a genuinely urgent fix still goes through a branch and a pull request. That is a few extra minutes. In exchange, the answer to "how did this reach the live site?" is always the same. It came through a reviewed, checked pull request.

Recall before you read on

Without scrolling up: name two things a protection rule stops by default, and the one checkbox that decides whether it applies to you as the repository's administrator.

By default a rule blocks force pushes and prevents deletion of the matching branch. Requiring a pull request and requiring status checks are separate checkboxes. The administrator exception is closed by Do not allow bypassing the above settings; without it, admins keep their override.

Set it up on your own repository

This is a web-interface task, identical in all three agents, so there are no tool tabs here. Do it once on the repository that publishes your app.

Settings → Branches now lists a rule for main. Ask your agent to commit a one-line change on main and push it: the push is refused with a message containing GH006 and Protected branch update failed. Then have it move that same commit to a branch and open a pull request — that route still works, and the pull request's merge box names the requirement it is waiting on.

Rulesets are the same idea, newer

GitHub now also offers rulesets. GitHub describes them as an alternative to branch protection rules with better discoverability without requiring admin access.[5] You can apply several at once. The concept from this lesson carries over unchanged: a stored rule, evaluated by GitHub, that a push must satisfy. This course uses the classic page because it is the one most tutorials and most repositories still show. If your repository has rulesets instead, look for the same checkboxes and the same bypass setting.

Whatever the mechanism, the test is the same. Try to push to main and see what GitHub says. If it accepts the push, nothing is protected, no matter what the settings page appears to claim.

Check yourself

Question 1 of 3

What does a branch protection rule on main actually add?

GitHub evaluates the rule when it receives the push. Your agent's goodwill, your rules file and your memory are not part of the decision.

Question 2 of 3

A push to main comes back with GH006: Protected branch update failed. What is the right response?

The refusal is about the route, not the code. A branch plus a pull request is the supported path; the other options are the bypass habits protection exists to stop.

Question 3 of 3

Why tick Do not allow bypassing the above settings?

Without that setting, people with admin permissions — on your own repository, that is you — can still merge without meeting the requirements. The rule binds everyone else and leaves you an override.

Ask your teacher

Unsure whether protection is on? Ask your agent: "Check whether main is protected in this repository, and show me the evidence rather than telling me it is fine." Then confirm in Settings yourself — the setting page is the source of truth.
