Unit 0 — Orientation & setup

9 lessons · 8 ★ What an agent is, how to install it, and a page on your own screen.

★What a coding agent actually is

0.1 · Lesson

A chat can only talk. An agent can look at your files, run things, and check what happened. Everything else in this course builds on that difference.

★The three agents: same ideas, different shells

0.2 · Lesson

Claude Code, Codex and omp all run the loop you met in lesson 0.1. What changes is the shell around it: the start command, the rules file, the mode names, the key that stops a run.

★Your project is a folder

0.3 · Lesson

An app is not a cloud, a database or a website. Before any of that, it is a folder of text files on your computer, and the agent only works on the folder it was pointed at.

★The terminal in five commands

0.4 · Lesson

The terminal is the room your agent works in. Five commands are enough to walk into the right folder, see what is there, open it, and start something — and to fix things when the agent says a file exists that you cannot find.

★Install and sign in

0.5 · Lesson

Two one-time jobs stand between you and your first prompt: put the program where your terminal can find it, then prove which account pays for the work. After that, launching is one word.

★Approvals and permissions: what your agent may do

0.6 · Lesson

The agent works with your account and your files. One setting decides whether it stops to ask you before it acts, and that setting is the difference between a helpful assistant and a mess you did not see coming.

★Your first prompt, and a page on your screen

0.7 · Lesson

One short message, one small page, one address you can open. This is the moment the agent stops being an idea and starts being a thing you can look at.

Anatomy of a web page

0.8 · Lesson

Every page you ship is a small set of text files. One holds the words, one holds the look, one holds the behaviour. Learn to tell them apart and you can point your agent at the right one.

★Ship a hello world page

M.1 · Lesson

A file in a folder and a page a stranger can open are separated by five named states. This milestone walks all five once, with a page too small to distract you.

Unit 1 — Telling the agent what you want

13 lessons · 9 ★ Say what should exist and who it is for, and get a plan before the work starts.

★Goal and audience, not method

1.1 · Lesson

Tell the agent what should exist and who it is for. Let it choose the steps. Your two sentences about the person at the other end do more work than twenty about tools.

★Orient first

1.2 · Lesson

Before you ask for a change, ask for a map. One question that only reads costs almost nothing. One change built on a wrong guess has to be found and undone.

★Ask what a word means

1.3 · Lesson

Half of a beginner's trouble with an agent is vocabulary. One question, asked at the moment the word appears, turns a paragraph you skim into a decision you can check.

★The interview: numbered questions with a recommended answer

1.4 · Lesson

You have said what the app is for. Now the agent needs the hundred small decisions that turn a goal into something buildable. A good interview asks them as numbered questions, and answers every one of them with a recommendation you can accept in a single word.

★"Yes to all" — and amending inside the yes

1.5 · Lesson

An interview can return twenty questions. You do not have to answer twenty times. One message can accept the whole list, name the two answers you want changed, and still leave you in control of what gets built.

When to override a recommendation

1.6 · Lesson

Every question in an interview comes with an answer the agent would pick for you. Some of those answers are technical guesses you should accept. A few are decisions about your product, and those are yours.

★Plan, then a human "go"

1.7 · Lesson

A plan is words. An edit is your files changed. Keeping those two apart, with you in between, is the cheapest safety net you will ever own.

A reference is a spec

1.8 · Lesson

"Make it feel like this" is a target. "Make it nice" is a guess. Point at something that already exists, say which parts you mean, and your own last working version becomes the bar for everything after it.

★Show, don't tell: screenshots as bug reports

1.9 · Lesson

The agent reads files and command output. It does not look at your screen. When something is wrong in a way words keep missing, a picture is the shortest true description you can give.

★Steering an agent that is already running

1.10 · Lesson

A run that takes twenty minutes is not a black box. You can add a condition, stop a wrong turn, ask where things stand, and send it on again, all without losing the work it already did.

Skills, slash commands and @-mentions

1.11 · Lesson

You will type the same instructions again and again: how to check a page, how to review a change, how to write a release note. A skill saves that procedure once, under a name. This lesson shows what those packs are, how to start one, and how to point the agent at a file.

★Write the procedure once

1.12 · Lesson

You have typed the same correction twice this week. There is a place for it: a short text file inside the project, which the agent reads at the start of every session. Write it once and stop repeating yourself.

Outcome-sized prompts, not micro-managing

1.13 · Lesson

One prompt should buy one result you can look at. Smaller than that and you are doing the agent's job of choosing steps. Larger than that and nobody can tell when it is finished.

Unit 2 — Knowing what it actually did (verification)

14 lessons · 4 ★ Evidence over claims: run it, test it, screenshot it, have it reviewed.

★Run it yourself

2.1 · Lesson

The agent can change the files. Only you can see whether the change is any good. Start the app, open the address, look at the screen — then decide what happens next.

★Claims versus evidence

2.2 · Lesson

"Done" is a sentence about what the agent believes. Evidence is something that would have come out differently if the work were wrong. Only the second one lets you ship.

What a test is

2.3 · Lesson

A test is a check a machine can repeat: set up an input, ask the app for a result, compare it with the result you expected. Three words come back with it — pass, fail, skipped — and only two of them tell you anything.

Prove the bug before you fix it

2.4 · Lesson

A test written after a fix can only agree with the fix. A test that fails first is evidence that the bug was real, that the test exercises it, and that the repair changed something.

Linters, formatters and type checkers

2.5 · Lesson

A test runs your app and watches what happens. Three cheaper readers never run it at all: they read the code and complain. Knowing which one to ask for turns a vague "looks fine" into a pass or a fail.

One command gate: put the checks in the repo

2.6 · Lesson

When all your checks live behind one short command, the agent can grade its own work before it tells you it is finished. You type the same command, and you get the same verdict.

★Tests passed, but the screen was wrong

2.7 · Lesson

A passing test can be honest and still say nothing about what a person sees. Before you ship, someone has to open the page in a real browser and look at it.

Screenshots as evidence

2.8 · Lesson

A picture is the closest you get to "I looked at it". But a file that ends in .png proves only that some program wrote a file. Here is how to tell a useful capture from a useless one, and why so many of them come back black.

Logs and telemetry: enough to diagnose?

2.9 · Lesson

When something goes wrong, a screenshot shows you the symptom. A log shows you what the app was doing at that moment. Without one, every fix is a guess.

The independent reviewer

2.10 · Lesson

The agent that wrote the change believes the change is right. A second agent that never saw the reasoning can disagree for a useful reason — as long as you treat its report as advice, not as an order.

The checker can be wrong

2.11 · Lesson

A green check is a claim too. Tests can pass without testing anything, the same test can give two answers for one unchanged file, and an AI asked to judge your work has good days and bad days. The skill is telling a real pass from a quiet one.

★Be a first-time user

2.13 · Lesson

You know where everything is, so you cannot feel what a stranger feels. Send two people through the live app with no map: your agent, then a friend. What they stumble on is your real to-do list.

Reading a real user's screenshot

2.14 · Lesson

A screenshot is a photograph of a symptom. It is not a description of the cause, and it never contains what happened one second earlier. Reading one well is what turns "it's broken" into something you can fix.

Local vs CI: skipped locally, failed in the cloud

2.12 · Lesson

Your checks passed on your laptop. Then the pull request went red. Nothing is broken in your code and nothing is lying to you: two different computers ran two different sets of checks.

Unit 3 — Version control as the safety net

15 lessons · 7 ★ Commits, branches and pull requests: the undo button for agent work.

★Why save points exist

3.1 · Lesson

An agent can rewrite twenty files while you watch one paragraph of text scroll by. A commit is how you decide that this state of the folder is worth keeping, and give it a name you can come back to.

★Repository, working tree, uncommitted change

3.2 · Lesson

Your project sits in two places at once: the files you can open, and the history git keeps. Two commands show you where those two disagree. Reading them is how you know what your agent actually changed.

★Remote, origin and push

3.6 · Lesson

A commit saves your work on your own machine. A push copies those commits to a server, where a lost laptop cannot take them and where Unit 6 can publish them.

★What not to track: .gitignore

3.3 · Lesson

A save point should contain the things you meant to keep, and nothing else. One small text file decides which files git refuses to save, and that same file can quietly erase work you thought was safe.

Commit messages, and what a commit includes

3.4 · Lesson

A commit is a labelled save point. The label is the only part you will read six weeks from now, and the label can lie about what the commit holds. This lesson fixes both halves.

★Branch: a parallel line of work

3.5 · Lesson

A branch lets you try something unfinished without putting it in the version of your app you would hand to a friend. It also costs one line of typing, not a second copy of your folder.

★The pull request: a proposal, not a merge

3.7 · Lesson

A branch keeps your work separate. A pull request is how that work gets looked at, checked, and only then allowed into main .

Merge or squash, and what "merged" means

3.8 · Lesson

The merge button has more than one setting, and they leave different history behind. Pick once, on purpose, and you will know what to do when a review comment arrives too late.

When two changes collide

3.9 · Lesson

Sooner or later two branches change the same line, and Git stops and asks you to choose. That stop is not a failure. It is the moment the tool refuses to guess about your app.

Worktrees: two checkouts, one repository

3.10 · Lesson

A worktree gives you a second folder showing a different branch of the same project at the same time. It removes the need to keep switching, and it creates a new way to lose track of where the agent is typing.

Undo: revert, reset, and the copy of the remote you cannot see

3.11 · Lesson

There are two ways to take a change back, and they make opposite promises. Choosing the wrong one is the fastest way for a beginner to lose work that other people can no longer recover.

Permission errors: when the server says no

3.12 · Lesson

A refused push does not mean your app is broken. Find out which account, repository and permission the request actually used before changing anything.

★Checkpoint often

3.13 · Lesson

A coding agent can work for an hour and change a hundred lines across a dozen files. If none of that is committed, the folder holds one undivided lump of work. A checkpoint cuts the lump into pieces you can keep, compare and drop.

Renaming the default branch and retiring branches

3.14 · Lesson

The name of your main line is a setting, not a law. Changing it in one place leaves three copies of that name out of step, and deleting a branch is safe only after you have checked what would be lost.

Branch protection: making "PRs only" a rule

3.15 · Lesson

A convention lives in your head and in a rules file. A branch protection rule lives in GitHub, where a tired agent at midnight cannot talk its way past it.

Unit 4 — Scope & stopping (field guide to derailments)

13 lessons · 4 ★ Define done, cap the run, and recover when it drifts off course.

★Definition of done: deciding what "finished" means

4.1 · Lesson

A goal tells the agent which direction to walk. A definition of done tells it where to stop. Without one, the agent picks a finish line of its own, and it is rarely the one in your head.

★Scope creep and the scope ladder

4.2 · Lesson

A session rarely derails in one leap. It climbs a ladder one reasonable step at a time: a question becomes a fix, the fix becomes a product, the product becomes something you publish. This lesson teaches you to see the ladder, and to climb only the rungs you actually choose.

★Stop conditions: decide where the run ends

4.3 · Lesson

A definition of done says what finished looks like. A stop condition says where the work ends — and what the agent must not start next.

★Budgets: time, attempts, dollars

4.4 · Lesson

A stop condition tells the agent what success looks like. A budget tells it how much effort you authorize before it must return control to you.

Root cause versus workaround

4.5 · Lesson

A red message can be silenced in a second or understood in an hour. Only one of those leaves your app working, and you get to choose which you asked for.

Conflicting requirements: spot them, surface them, choose

4.6 · Lesson

Two things you ask for can pull in opposite directions. Make the conflict visible before the agent builds around an assumption you never approved.

Reward hacking, or the metric gets gamed

4.7 · Lesson

Give an agent something to hit and it will hit it. Whether that something still stands for what you wanted is a separate question, and it is yours to answer before you ship.

Vague prompts are safe only when the repo defines "works"

4.8 · Lesson

A short request like "does the project work?" can be the cheapest message you ever send — or the start of a twelve-hour run with no finish line. The difference is not in the wording. It is in what your repository already says about the word "works".

Long runs you don't watch: checkpoints and progress logs

4.9 · Lesson

Some tasks take twenty minutes or two hours, and you cannot stare at the chat the whole time. Two habits make a long run safe: demand the first piece of evidence early, and make the run write down what it is doing as it goes.

Recovering a derail

4.10 · Lesson

A run has gone sideways. The fix is not a third correction in the same conversation. It is four moves: stop, commit, open a pull request, restart with a fresh goal.

Over-asking: cap the interview before it runs too long

4.11 · Lesson

An interview exists to catch wrong guesses before they become code. Past a certain length it stops catching them — and starts costing you the attention it was supposed to save.

Which questions the agent can't answer — and which you can

4.12 · Lesson

Every question a run asks belongs to one of two places: the project folder, or your head. Answering from the wrong place wastes hours.

Cutting scope on purpose: ship the smaller thing

4.13 · Lesson

Every app has more ideas than time. The skill is choosing what to leave out, saying so out loud, and writing it down — so "not finished" becomes "finished for now".

Unit 5 — How agents work (mental model)

11 lessons Context, tools, cost and subagents: why a run succeeds or fails.

The context window: what your agent remembers

5.1 · Lesson

An agent does not remember your project the way you remember a room you are standing in. It holds a working memory that fills up, gets summarized, and can lose early instructions. Knowing that explains a lot of strange behaviour on long builds.

Tokens, cost, and caching: why long sessions get expensive

5.2 · Lesson

Everything an agent reads or writes is counted in small units called tokens, and you pay for them. A cache keeps repeated reads cheap — until something invalidates it.

Tools: what your agent can see and do

5.3 · Lesson

Your agent has no eyes and no memory of its own beyond the conversation. Everything it knows arrives through tool calls: read, edit, run. Knowing that is what lets you predict it.

Subagents: one agent can hire helpers

5.4 · Lesson

Sometimes one question is bigger than one conversation. Your agent can hand parts of the work to helper agents — called subagents — that look around in their own space and report back. You stay the boss who cross-checks.

Goal mode and persistent objectives

5.5 · Lesson

Keeping a target active can help an agent finish a long task. It can also keep a bad task running long after you expected it to stop.

Models and effort: picking the right brain

5.6 · Lesson

The agent is a shell; a model is the brain inside it. You can swap brains mid-session, and tell one how hard to think. Matching the brain to the job saves money and time without lowering quality where it matters.

Instructions hiding in your files

5.7 · Lesson

Your agent reads whatever you point it at. Sometimes that text contains lines written to trick it — and the agent cannot reliably tell your instructions from theirs. This lesson shows you where those lines hide and how to stay safe without becoming paranoid.

Stale or invented claims: check the source of truth

5.8 · Lesson

An earlier answer is not proof of the current state. Learn to trace a claim to the right source, check its freshness, and mark what remains unverified.

Background processes: started is not finished

5.9 · Lesson

A command can keep working after the agent speaks. Learn what to wait for, what an exit code tells you, and when checking again helps.

Human-only steps: logins, attestations, and runbooks

5.10 · Lesson

Some steps of shipping your app are yours alone: typing a password, agreeing to terms, confirming which plan you are on. Your agent cannot do them — and a good agent will write you a numbered list, called a runbook, telling you exactly what to do and when.

Desktop apps vs the terminal: buttons, cards, and checklists

5.11 · Lesson

The same agent can live in a window full of clickable controls or in a terminal where you type everything. The loop underneath is identical; only the surface changes. Knowing both lets you pick the right one for the moment.

Unit 6 — Shipping a static app

10 lessons · 7 ★ From a local file to your own public URL, with the deploy checklist.

★Static or dynamic, and what hosting means

6.1 · Lesson

Some apps are a pile of files that a host hands over untouched. Others need a program running all the time. Which one you are building decides whether free hosting is enough.

★GitHub Pages: what your URL will be

6.3 · Lesson

Pages turns your repository into a website at a predictable address. Learn the address shape now, and your links will keep working after you send them to someone.

★Merged is not live

6.6 · Lesson

Your pull request says Merged and the checks are green. The page your friend opens is still yesterday's. Three different states are all called "done", and only one of them is the address you will share.

★The build step: source becomes deployable files

6.2 · Lesson

Many projects are not published as-is. A program first turns your source files into a separate folder of finished files, and it is that folder — not your source — that goes online. Knowing which is which stops the classic "works on my machine, blank on the web" surprise.

★Size limits and big files: host them elsewhere

6.4 · Lesson

Free hosting has hard size limits. Learn to measure your project, read the limits, and keep big files somewhere else — so your link still loads for your friends.

★An Actions workflow: a recipe GitHub runs on every push

6.5 · Lesson

The checks on your pull request and the publishing of your site are not done by your laptop. They are done by a small recipe file in your repo that GitHub runs for you, on a fresh machine, every time you push.

★Put the link where people look

6.7 · Lesson

Your app is live, but most people will not arrive through the link you send them. They will find your repository on GitHub first — so the link has to live on the repository page itself, in the two places eyes go first.

Other free hosts, and the guardrails on every free plan

6.8 · Lesson

GitHub Pages is not the only free place to put a static site. Cloudflare, Netlify, and Vercel all do the same job with different extras — and every free plan comes with limits that can pause your site. Learn to read them before you depend on them.

Rollback: main is not the live site

6.9 · Lesson

A friend reports your app is broken. The fastest way back is not "undo everything" — it is knowing which of two separate records you need to fix: the branch called main, or the copy your host is serving.

Your own address for the site (optional)

6.10 · Lesson

Your app already has a working address like YOUR_USERNAME.github.io/my-app. A custom domain — yourname.com — is a nice extra, not a requirement. This lesson shows what it involves so you can decide whether it is worth it.

Unit 7 — Capstone

3 lessons · 2 ★ One idea, one app, shipped end to end, then a retrospective.

★Choose your capstone idea

7.1 · Lesson

Everything you have learned so far was practice. Now you pick the app you will actually take from a blank folder to a public link. The skill in this lesson is choosing an idea small enough to ship — and knowing the fallback if you cannot choose.

★The capstone path: interview, plan, build, verify, ship, share

7.2 · Lesson

You already shipped a hello world page. Now you ship the app you actually chose. Six steps, in order, each one already practised on its own — this lesson is about running them as one continuous run.

Retrospective: which failure modes did you hit?

7.3 · Lesson

You built and shipped an app. Before the memory fades, name the ways the run went wrong — because the failure modes you hit once are the ones you will hit again, unless you write them down.

Unit 8 — Beyond static (advanced tracks; nothing dropped)

20 lessons Optional advanced tracks: secrets, logins, backends, CI, real APIs.

Secrets: what they are and why they never live in your code

8.1 · Lesson

The moment your app talks to a paid service, you hold a password-like value that must never end up in a file that git tracks. Knowing what counts as a secret — and why code is the wrong home for one — is the foundation for everything else in this unit.

Environment variables: settings that stay out of your code

8.2 · Lesson

Your app will need values it must not carry inside its files — a key, a password, an address. Environment variables are the place those values live, and a .env file is how you keep them on your own machine without committing them.

Never print, never commit

8.3 · Lesson

A secret key that appears on your screen or in your project's history is a key a stranger can use. This lesson gives you two habits — never print a secret, never commit one — and one repair move: rotate a leaked key immediately.

Third-party API keys, rate limits, and spend caps

8.4 · Lesson

Your app will call services you don't run — maps, weather, AI. Their keys work like yours: they identify you, meter you, and can run out or hit a ceiling. Learn the two error numbers that mean "slow down" and "pay up".

What you send to third parties

8.5 · Lesson

Every prompt you type and every request your app makes can leave your machine. Before you ship an app that leans on outside services, you should know exactly what leaves, where it goes, and who is allowed to keep it.

Logins and token expiry

8.6 · Lesson

Signing in is not a one-time event. Logins turn into tokens, tokens expire, and sometimes your organization forces a re-login on its own schedule. Here is how to recognize each case and what to do.

OAuth in pieces: what a "Sign in with…" button sets up

8.7 · Lesson

When your app wants to read a user's data from another service, you never ask for their password. OAuth is the standard handshake that lets the user grant your app limited access instead — and it comes down to five pieces you can name.

CORS: why tests pass and the real click fails

8.8 · Lesson

Your app's page and the service it calls live at different addresses. Browsers only allow that when the service explicitly says so — and only a real browser enforces the rule, which is why every test can be green while the first real click fails.

Backends: hosting vs functions vs database

8.9 · Lesson

Your static site is served by a host that only hands over files. Once your app needs shared data or secrets, three different pieces appear — and they are not the same thing. Knowing which is which saves you from paying for the wrong one.

Emulator vs production

8.10 · Lesson

Your app's backend can be imitated on your own machine so you can test without touching the real service. An imitation is fast and safe — and it is also the place where "all tests passed" most often stops being true.

How CI logs in without a key file

8.11 · Lesson

Your workflow runs on a fresh machine that belongs to GitHub, so it cannot carry a key file. The modern trick is a short-lived digital ID that proves which repo and which run is asking — no stored secret at all.

Docker: run tests in a throwaway box, not on your real data

8.12 · Lesson

Once your app has a backend, every test can write to a database. Docker lets you start a private, disposable copy of that backend so tests never touch what is real. Four words cover it: image, container, volume, port.

Mocks vs live tests: what each one can catch

8.13 · Lesson

A test that talks to a pretend service is fast and free, but it can only catch problems in your own code. A test that goes live can catch the opposite. This lesson is about knowing which is which, and asking for the right mix.

Deploy blockers: missing secrets and secret managers

8.14 · Lesson

Your app works on your own machine and breaks the moment it is deployed. The most common reason: the deploy host has none of your secrets. This lesson shows how to find and fix that.

Third-party churn: deprecations and dead documentation

8.15 · Lesson

The services your app calls are run by other people, and they change without asking. Features get deprecated, doc pages move or die, and a confident agent can quote a dead page as if it were fact. Learn to spot churn early and to verify every link before you build on it.

LLM calls as a dependency: limits, timeouts, retries, JSON

8.16 · Lesson

When your app calls an AI model at runtime, that model is a dependency like any other service — it can be slow, capped, overloaded, and it does not guarantee well-formed output. Learn the four ways those calls fail and the rules that make them safe.

Data you don't own: provenance, units, evidence status

8.17 · Lesson

Your app will show numbers that came from somewhere else — a website, a list, a sensor, another service. Before you ship, each of those numbers needs three labels: where it came from, what unit it is in, and how well it is actually supported.

Assets &amp; licensing — and the reverse-engineering caution

8.18 · Lesson

Images, sounds, fonts, icons, and other people's files make your app look finished — and each one has an owner. An agent will happily fetch, copy, or rebuild whatever you point at, without checking who owns it. Learn to check the license before an asset enters your repo, to license your own work, and to pause before asking an agent to take apart something you don't own.

Performance: measuring what is slow

8.19 · Lesson

"It feels slow" is not something an agent can fix. A number can be. This lesson teaches four words — frames per second, benchmark, bottleneck, parallel worker — and how to make the agent measure before it changes .

Accessibility basics: targets, keyboard, reduced motion

8.20 · Lesson

Your app will be used by people with shaky hands, sore eyes, and a dislike of spinning screens. The agent will not fix any of this on its own — but it can, in one prompt, if you know the three things to ask for.

Unit 9 — Working at scale

8 lessons Many tickets, parallel agents, review bots and handoff docs.

From one big spec to a frontier of tickets

9.1 · Lesson

When your app grows past what fits in one prompt, you stop asking for "the app" and start asking for one ticket at a time. The pipeline is: spec, then tickets, then the dependency graph — and the frontier tells you what is safe to build next.

Integration branch vs per-ticket branches

9.2 · Lesson

When you have several tickets in flight at once, you have to decide where finished work collects: straight onto main, or onto a holding branch first. This lesson shows both layouts and when each one saves you pain.

Parallel agents and the shared build folder

9.3 · Lesson

Two agents working at once can finish in half the time — or quietly overwrite each other's work. The difference is usually one folder: where the build writes its output.

Babysitting a pull request: bots review, you merge

9.4 · Lesson

Once you run many changes through pull requests, you cannot watch every page yourself. Automated reviewers and CI can do the watching — but the decision to merge, and the patience to wait for green checks, stays with you.

Fan out the research, reconcile the reports

9.5 · Lesson

Some questions are too big for one pass: which free host fits your app, what an API really returns on error, whether the docs match the code. You can send a swarm of helper agents at the question. The win is not the speed — it is ending with one answer you can defend, contradictions resolved against sources.

Let the agent schedule the work

9.6 · Lesson

For big tasks you stop typing the steps and start handing over goals with a finish line. The agent becomes the scheduler. And when your prompting feels off, you can ask the agent to critique it — that is a meta-prompt.

Handoff docs: carrying a long session forward

9.7 · Lesson

A session ends; the project does not. A short handoff doc in the project folder is how you make hours of work survive the session that produced them — and start the next one already oriented.

Triage first: diagnose before you act

9.8 · Lesson

When a project has grown several branches and open questions, the expensive mistake is acting on a guess. A read-only triage pass turns "something is off" into a ranked list you approve before anything changes.
