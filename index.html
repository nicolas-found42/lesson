Zero to Shipped · Static Web Applications

Building Apps with a Coding Agent

A complete beginner's curriculum for directing Claude Code, Codex, and omp to take an idea and ship a working, public web app—without writing code and without losing control.

Target: General Users & Non-Programmers ~15 Minutes Per Lesson One Tangible Win Per Module

How to use this course: Each lesson tackles one tightly focused concept with interactive recalls, real anonymized vignettes, tool-specific command tabs, and self-checks.

Start with Unit 0 and follow the ★ First-Ship Path to deploy your first static page to GitHub Pages as early as possible. Lessons are currently being authored and published in this repository.

Unit 0 — Orientation & setup

★What a coding agent actually is

0.1 · Lesson

A chat can only talk. An agent can look at your files, run things, and check what happened. Everything else in this course builds on that difference.

★The three agents: same ideas, different shells

0.2 · Lesson

Claude Code, Codex and omp all run the loop you met in lesson 0.1. What changes is the shell around it: the start command, the rules file, the mode names, the key that stops a run.

★Your project is a folder

0.3 · Lesson

An app is not a cloud, a database or a website. Before any of that, it is a folder of text files on your computer, and the agent only works on the folder it was pointed at.

★The terminal in five commands

0.4 · Lesson

The terminal is the room your agent works in. Five commands are enough to walk into the right folder, see what is there, open it, and start something — and to fix things when the agent says a file exists that you cannot find.

★Install and sign in

0.5 · Lesson

Two one-time jobs stand between you and your first prompt: put the program where your terminal can find it, then prove which account pays for the work. After that, launching is one word.

★Approvals and permissions: what your agent may do

0.6 · Lesson

The agent works with your account and your files. One setting decides whether it stops to ask you before it acts, and that setting is the difference between a helpful assistant and a mess you did not see coming.

Anatomy of a web page

0.8 · Lesson

Every page you ship is a small set of text files. One holds the words, one holds the look, one holds the behaviour. Learn to tell them apart and you can point your agent at the right one.

★Ship a hello world page

M.1 · Lesson

A file in a folder and a page a stranger can open are separated by five named states. This milestone walks all five once, with a page too small to distract you.

Unit 1 — Telling the agent what you want

★Goal and audience, not method

1.1 · Lesson

Tell the agent what should exist and who it is for. Let it choose the steps. Your two sentences about the person at the other end do more work than twenty about tools.

★Orient first: ask before you change anything

1.2 · Lesson

Before you ask for a change, ask for a map. One question that only reads costs almost nothing. One change built on a wrong guess has to be found and undone.

★Ask what a word means

1.3 · Lesson

Half of a beginner's trouble with an agent is vocabulary. One question, asked at the moment the word appears, turns a paragraph you skim into a decision you can check.

★The interview: numbered questions with a recommended answer

1.4 · Lesson

You have said what the app is for. Now the agent needs the hundred small decisions that turn a goal into something buildable. A good interview asks them as numbered questions, and answers every one of them with a recommendation you can accept in a single word.

★"Yes to all": accepting an interview in one line

1.5 · Lesson

An interview can return twenty questions. You do not have to answer twenty times. One message can accept the whole list, name the two answers you want changed, and still leave you in control of what gets built.

When to override a recommendation

1.6 · Lesson

Every question in an interview comes with an answer the agent would pick for you. Some of those answers are technical guesses you should accept. A few are decisions about your product, and those are yours.

★Plan, then a human "go"

1.7 · Lesson

A plan is words. An edit is your files changed. Keeping those two apart, with you in between, is the cheapest safety net you will ever own.

A reference is a spec

1.8 · Lesson

"Make it feel like this" is a target. "Make it nice" is a guess. Point at something that already exists, say which parts you mean, and your own last working version becomes the bar for everything after it.

★Show, don't tell: screenshots as bug reports

1.9 · Lesson

The agent reads files and command output. It does not look at your screen. When something is wrong in a way words keep missing, a picture is the shortest true description you can give.

★Steering an agent that is already running

1.10 · Lesson

A run that takes twenty minutes is not a black box. You can add a condition, stop a wrong turn, ask where things stand, and send it on again, all without losing the work it already did.

★Write the procedure once: a project rules file

1.12 · Lesson

You have typed the same correction twice this week. There is a place for it: a short text file inside the project, which the agent reads at the start of every session. Write it once and stop repeating yourself.

Outcome-sized prompts, not micro-managing

1.13 · Lesson

One prompt should buy one result you can look at. Smaller than that and you are doing the agent's job of choosing steps. Larger than that and nobody can tell when it is finished.

Unit 2 — Knowing what it actually did (verification)

★Claims versus evidence

2.2 · Lesson

"Done" is a sentence about what the agent believes. Evidence is something that would have come out differently if the work were wrong. Only the second one lets you ship.

Linters, formatters and type checkers

2.5 · Lesson

A test runs your app and watches what happens. Three cheaper readers never run it at all: they read the code and complain. Knowing which one to ask for turns a vague "looks fine" into a pass or a fail.

One command gate: put the checks in the repo

2.6 · Lesson

When all your checks live behind one short command, the agent can grade its own work before it tells you it is finished. You type the same command, and you get the same verdict.

Unit 3 — Version control as the safety net

★Why save points exist

3.1 · Lesson

An agent can rewrite twenty files while you watch one paragraph of text scroll by. A commit is how you decide that this state of the folder is worth keeping, and give it a name you can come back to.

★Repository, working tree, uncommitted change

3.2 · Lesson

Your project sits in two places at once: the files you can open, and the history git keeps. Two commands show you where those two disagree. Reading them is how you know what your agent actually changed.

★Remote, origin and push: getting commits off your laptop

3.6 · Lesson

A commit saves your work on your own machine. A push copies those commits to a server, where they can survive a lost laptop and where the rest of this course can publish them.

Unit 6 — Shipping a static app

★Static or dynamic, and what hosting means

6.1 · Lesson

Some apps are a pile of files that a host hands over untouched. Others need a program running all the time. Which one you are building decides whether free hosting is enough.

★GitHub Pages: what your URL will be

6.3 · Lesson

Pages turns your repository into a website at a predictable address. Learn the address shape now, and your links will keep working after you send them to someone.
