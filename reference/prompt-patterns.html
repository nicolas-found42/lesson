Reference card

Prompt patterns

Copy the shape, replace the brackets, delete what you do not need.

Grouped by the job they do. Each pattern ends with the lesson that explains it.

Ask well

1. Goal, audience, one check

When: you know the result but not the steps. Lesson 1.1.

I want [one result] for [who], who [what they cannot do].
Done when I can [one check]. Do not [one boundary].
Pick the simplest option and say why.

2. Orient first

When: before changing an unfamiliar part. Lesson 1.2.

Before changing anything, read the project and answer:
1. Which files would I touch to change [thing]?
2. How does it work today, in three sentences?
Do not edit. Report only.

3. Ask what a word means

When: a term is doing work you cannot check. Lesson 1.3.

I don't know "[term]" from your last message.
Explain it in two sentences, in plain words, with one example from my project.

4. Interview, then a batch yes

When: several decisions are open. Lesson 1.4, 1.5, 1.6; cap in 4.11.

Before coding, interview me: numbered questions, one decision each,
your recommendation and a one-line reason. Max 6 per round, 2 rounds.
Stop when you could write a spec; show it and wait.
Then: "Yes to all, except 7: [change], 12: [change]. Change no files."
Override 9 with [choice] because [reason].

5. Outcome-sized prompt

When: one sitting's work, not a whole project. Lesson 1.13.

Outcome: [one result I can look at], for [who].
Done means: [one check I can run]. Do not [boundary] or start [next thing].
Work out the steps; ask once if a choice changes what I see.

Stay in control

6. Plan, then a human go

When: a wrong first step would be expensive. Lesson 1.7.

Before changing anything, write a plan: steps, files, what you will leave alone,
and how you will check it. Half a page. Do not edit. Stop and wait for my go.

7. Reference as spec; v1 as the bar

When: "like this" is the real request. Lesson 1.8.

Use [screen] as the reference. Copy [parts]; skip [parts]; keep my words.
Treat the current page as v1: keep it, and say where the new one is worse.

8. Show, don't tell

When: a bug is easier to point at than describe. Lesson 1.9.

This screenshot shows [page, size]. The problem is [exact thing, where].
I expected [result]. Fix only that, then screenshot again at the same size.

9. Steer a running agent

When: a run drifts: queue a note, Esc to interrupt, ask for state. Lesson 1.10.

What is the task, and what is its state? Four parts: task in one sentence;
done; in progress; blocked. Do not start new work until I reply.

10. Project rules file

When: you have corrected the same thing twice. Lesson 1.12; a repeated procedure can become a skill (1.11).

Read the project, then draft [CLAUDE.md or AGENTS.md] in the root.
Include only the start command, the check command, and rules I corrected twice.
Show it before writing.

11. Definition of done

When: agree what "finished" means before work starts. Lesson 4.1.

Change: [one change]. Done when all are true:
1. [visible result] 2. [action works] 3. [phone width fits] 4. [check passes].
Not included: [cuts].

12. Bounded run: stop, budget, objective

When: a run could continue past the point that helps. Lesson 4.3, 4.4; goal mode is 5.5.

Objective: [bounded result]. Keep [what must not change].
Done when: [observable state]. Stop there: no next task, no refactor.
Limit: 3 attempts or 15 minutes, whichever comes first. Then report.

13. Cut scope on purpose

When: ship the smaller thing now, not the ladder. Lesson 4.13.

Task: [one thing]. Out of scope: [items]. Do not build or fix them.
If you find a problem there, add a line to LATER.md and move on.
Done when: [observable state].

14. Human-only runbook

When: the task will hit a login or consent only you can give. Lesson 5.10.

Before you start, list every human-only step: logins, terms, ownership checks,
anything needing my consent. Number them, say when each is needed.
Never ask me for a password or key.

Check the work

15. Independent reviewer

When: the author's own report is not enough. Lesson 2.10.

Review my change as an independent reviewer. Do not edit; report only.
Check [behaviour and edge cases], skip style. Per finding: file and line,
what goes wrong, how to see it, severity.

16. Evidence checkpoint

When: the agent says "done" and you need proof. Lesson 2.2; long runs, 4.9.

Before you say done: exact commands and full output, files changed,
what you did not verify, and the smallest check for each gap.
Long run: one checkpoint in 5 minutes, plus progress.log.

17. Root cause before fix

When: a symptom is easy to hide but the cause is unknown. Lesson 4.5.

Something is wrong: [symptom and steps]. Before changing anything:
reproduce it with output; name the cause in one sentence; if you cannot, stop.
Fix the cause, not the symptom. No skipped or weakened checks.

For speed, ask for a benchmark and the bottleneck before any fix.

18. Surface conflicting requirements

When: two "musts" may contradict. Lesson 4.6.

Do not edit. Check my requirements for conflicts: name both, why they clash,
evidence versus assumption. Offer two choices and recommend one.
Wait for my answer, then restate the criteria.

19. Triage first

When: the project is messy and you do not know where to start. Lesson 9.8.

Triage this project. Read only: no edit, commit, push or merge.
Report state, each problem with evidence, recommendations safest first,
and the one next step you would take.

Recover

20. Park, then restart fresh

When: a run has derailed and steering will not save it. Lesson 4.10.

New task, fresh start; ignore earlier attempts. Goal: [one sentence].
Do not: [what derailed it]. New branch from main; commit per step.
Stop when [condition]; after [N] attempts, stop and report.

21. Spec, tickets, frontier

When: one spec is too large for a single run. Lesson 9.1.

Read SPEC.md; split it into one-run tickets. For each: title, goal,
depends on, done when. Draw the graph and list the frontier.
Do not start yet. Then work only the frontier ticket "[title]".

22. Meta-prompt: critique my prompting

When: a session felt clumsy and you want one habit to change. Lesson 9.6.

Look at this session. Critique how I have been prompting: which messages
were step-by-step instructions for one bigger outcome, and which were too vague?
Give three concrete changes and quote my own words. Do not change files.
Use them together

A goal-sized prompt with a finish line, a stop condition and an evidence request covers most of the page.
